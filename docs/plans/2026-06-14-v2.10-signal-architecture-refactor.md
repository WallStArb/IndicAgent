**Goal:** Restore the Extrinsic Confidence Layer (ECL) boundary, clean the signal universe of state-detection over-firing, restructure the data layer to separate signal detection from trade framing from trade execution, and produce a signal corpus that is valid training data for the ML/genetic optimization stack — with no survivorship bias at either the emission layer or the outcome layer.

**Architecture:** Two workstreams, reordered. Phases 123-126 fix data integrity (ECL boundary, APR migration, signal universe hardening). **Tech Stack:** Python/asyncpg, PostgreSQL/TimescaleDB, pytest, APR (config_schema/config_state tables), structlog/OTel.

## ECL Primer

**Extrinsic Confidence Layer (ECL):** The system of extrinsic confidence vectors — signals about external market context that annotate an emitted signal as metadata. Current vectors: CTF score (I6 cross-timeframe alignment), HMM regime weight, zone friction, exhaustion state.

**Intrinsic confidence composite:** A plugin's own weighted factor sum (price/volume/microstructure derived). Weights sum to 1.0. ECL vectors must never appear here.

**The ECL boundary invariant:** No extrinsic vector suppresses signal emission. If a setup meets its intrinsic detection criteria, it fires — always. Extrinsic vectors travel on the emitted signal as observable fields (`ctf_score`, `ctf_confirmed`, `zone_friction_score`) or in `context_features`. They are the inputs the ML model uses to learn which market contexts produce better outcomes. Hard-coding an extrinsic gate is a prior masquerading as a model — it removes training data from the ledger permanently and makes the model unauditable.

**Regime gate exception:** HMM regime weight suppresses signal *activation* (pending → regime_suppressed), not *emission*. The signal is written to the ledger before the regime gate is applied. This is structurally sound: the ML model sees regime-suppressed signals and, once counterfactual_pnl_r is populated (Phase 130), can learn whether the gate adds value.

---

## Two Survivorship Bias Layers

**Bias Layer 1 (fixed in Phase 123):** Extrinsic gates calling `no_signal()` before ledger write. CTF gate, zone friction gate, exhaustion guard gate. These prevent the training corpus from ever seeing suppressed cases. The model fits on a biased sample.

**Bias Layer 2 (addressed by 3-table architecture in Phase 128-130):** Regime-suppressed and unfilled signals have `pnl_r = NULL` because no trade was executed. The ML model trains on `WHERE pnl_r IS NOT NULL` — excluding all suppressed signals. The model has never measured what a high-quality pattern firing in a poor regime actually produces. This is survivorship bias at the outcome layer.

The 3-table architecture fixes this by making `counterfactual_pnl_r` a first-class column on `trade_frames` — always populated, regardless of whether the trade was executed. Every signal hypothesis gets its outcome measured against subsequent price action. The ML model trains on counterfactual outcomes, not execution outcomes.

### Phase 123: ECL Boundary Restoration

**Goal:** Remove all extrinsic emission suppressors across all plugins. Add `ctf_score: float | None`, `ctf_confirmed: bool | None`, `zone_friction_score: float | None`, `factor_scores: dict | None`, and `context_features: dict | None` as top-level signal schema fields. Promote `capture_signal_features()` output from the _shadow dict to a persisted column. Bump schema version.

**Why None semantics matter:** `None` = the extrinsic system had no data at emit time. `0.0` = genuine neutral reading. ML filters `IS NOT NULL` to exclude cold-start signals from extrinsic attribution analysis. These are different populations. The `or 0.0` fallback conflates them.

**Why context_features must be persisted now:** Phase 127 runs the last full historical replay for the foreseeable future. If `context_features` is not in the schema before the replay, the entire historical training corpus for SignalRanker is lost. The migration cost is one column; the replay cost is weeks.

## Workstream B: 3-Table Signal Architecture (Phases 128-130)

**Architecture decision (made):** The current `signal_ledger` monolith mixes three distinct concerns with incompatible cardinalities and incompatible update patterns. It will be decomposed into three tables. This is not an open question.

**Why 3-table is the only defensible design:**

1. **Cardinality.** One signal fire event can produce multiple trade frame hypotheses (one per entry_type: at_close, at_pullback, at_limit, at_reclaim, zone_proximal). One frame can have zero or one live execution plus always one counterfactual measurement. Forcing these into one table requires NULL-heavy rows and prevents independent querying of each layer.

2. **Bias Layer 2 elimination.** `counterfactual_pnl_r` on `trade_frames` is the key structural requirement — every frame gets an outcome measured against subsequent price action, regardless of execution. This eliminates survivorship bias at the target variable: the ML model trains on counterfactual outcomes for all signals, not execution outcomes for the executed subset.

3. **Attribution clarity.** `raw_confidence`, `factor_scores`, and `context_features` live on `signal_events` — they belong to the detection event, not the execution. `actual_pnl_r` lives on `trade_executions` — it belongs to execution quality. `counterfactual_pnl_r` lives on `trade_frames` — it belongs to the hypothesis. These are three separate claims and must be separately auditable.

4. **ML training corpus.** `SignalRanker` trains on `signal_events JOIN trade_frames` using `counterfactual_pnl_r` as the target and `context_features` as the feature matrix. This join produces a clean training set with no null targets (every frame has a counterfactual) and no survivorship bias.

#### G0: Writer Grouping Strategy — How signal_id maps to 3 tables

This is the critical write-path design for Phase 130. The current `signal_writer.py` inserts one `signal_ledger` row per signal dict. In the 3-table world, signals with the same `signal_id` (same plugin fire, different `entry_type`) must map to **one** `signal_events` row and **N** `trade_frames` rows. Without this explicit grouping logic in the writer, either (a) `signal_events` gets duplicate rows per entry_type, or (b) only one trade_frame is written per signal fire.

**Current cardinality in payload:** `make_signal_id()` hashes `(symbol, bar_ts, tf, OHLCV, setup_plugin)` — entry_type is NOT part of the hash. If a plugin calls `make_signal_from_frame()` twice (once for `at_close`, once for `at_pullback`), both signals carry the same `signal_id`. The `signals: [...]` list in the Kafka payload already carries all of them.

**Phase 130 writer contract:**

```python

signals_by_id = {}
for sig in signals:
    sid = sig["signal_id"]

# Step 2: for each unique signal_id, insert ONE signal_events row
# using the first signal in the group (detection fields are identical across entry_types)
for signal_id, group in signals_by_id.items():
    first = group[0]
    await conn.execute(
        "INSERT INTO signal_events (...) VALUES (...) ON CONFLICT (signal_id) DO NOTHING",
        # detection fields from first: symbol, ts, setup_plugin, direction,
        # raw_confidence, factor_scores, context_features, ctf_score, ctf_confirmed,
        # zone_friction_score, status, signal_schema_version

    # Step 3: for each signal in the group, insert ONE trade_frames row

        await conn.execute(
            "INSERT INTO trade_frames (...) VALUES (...)",
            # framing fields: signal_id, entry_type, entry_price, stop_price,
            # target_price, r_per_unit, was_selected
        )
```

**CounterfactualTracker design sketch (Phase 130):**
- Subscribes to `signal_events` Kafka topic
- Maintains a per-symbol sliding window of price bars
- For each new signal event: registers the frame's entry/stop/target
- On each new bar: checks all open counterfactual positions for that symbol
- Closes counterfactual when stop hit, target hit, or TTL expired
- Writes `counterfactual_pnl_r`, `counterfactual_mfe`, `counterfactual_mae`, `counterfactual_bars`, `counterfactual_exit_reason`, `counterfactual_measured_at` to `trade_frames`
- Fully in-memory state; checkpointed to file on shutdown (same pattern as intelligence_pipeline)
