### Phase 1.5 (Signal Aggregation & Management)

#### 1. Signal Ledger Database (`production/schemas/signal_ledger_migration.sql`)
- TimescaleDB hypertable with 7-day chunks
- Composite PK `(signal_id, timestamp)` for partitioning
- 30+ columns covering:
  - Signal identity (UUID, timestamp, symbol, timeframe, setup_plugin)
  - Signal details (from signal.v1 schema: entry, stop, targets, confidence, etc.)
  - Aggregation context (was_selected, num_signals_bar, resolution_method, composite_rank)
  - Market context snapshot (JSONB feature vector for future ML)
  - Lifecycle tracking (status, activated_at, exit_at, exit_reason)
  - P&L metrics (pnl_ticks, pnl_r, pnl_dollars)
- Compression enabled: segment by symbol+setup_plugin, compress after 30 days
- 4 indexes for common query patterns

#### 2. Signal Ledger Repository (`src/intelligence/trading/signal_ledger.py`)
- `LedgerEntry` dataclass matching database schema
- `insert_signals(db, entries)` — batch insert via execute_batch
- `update_signal_status(db, signal_id, ...)` — lifecycle updates
- `get_active_signals(db, symbol=None)` — query pending/active signals
- All async, all accept DatabaseManager instance

#### 3. Rules-Based Signal Aggregator (`src/intelligence/trading/aggregator.py`)
- `SETUP_PRIORITY` dict (LiquiditySweepReclaim=5 > MTFAlignment=4 > TrendFollowing=3 > SqueezeExpansion=2 > MeanReversion=1)
- `aggregate(signals, trend_regime)` → `AggregatedResult`
- Conflict resolution rules:
  - **Case A (one direction):** Pick by priority. Boost confidence by +0.05 per agreeing signal. Merge supporting_factors.
  - **Case B (mixed directions):** Majority wins. If tied, use trend_regime as tiebreaker (>0.4→longs, <-0.4→shorts, else→no signal).
- Resolution methods tracked: "sole", "priority", "majority", "regime_tiebreak", "no_signal"
- All signals ranked with composite_rank (1=winner)

#### 4. Lifecycle Tracker (`src/intelligence/trading/lifecycle_tracker.py`)
- Pure-function state machine (does NOT touch database)
- `evaluate_signal(signal, high, low, close)` → `Transition | None`
- State flow: pending → active → stopped_out | target_N_hit | expired
- Entry checks: long activates when high >= entry, short when low <= entry
- Exit checks: stop before targets (conservative), highest target first (maximize credit)
- TTL expiry: bars_elapsed > ttl_bars → expired
- P&L calculation: pnl_ticks = (exit - entry) * direction, pnl_r = pnl_ticks / risk, pnl_dollars = pnl_ticks * point_value

#### 5. Position Sizing Calculator (`src/intelligence/trading/position_sizer.py`)
- `calculate_position_size(entry, stop, direction, point_value, risk_amount, max_contracts)` → `PositionSize`
- Risk-based: contracts = floor(risk_amount / (stop_distance * point_value))
- Caps at max_contracts (default 100)
- Returns contracts, risk_per_contract, total_risk, capped flag

## Key Design Decisions (Context for Future Work)

### Why Rules-Based First?
No data exists yet to calibrate a scoring model. The priority order (LiquiditySweepReclaim > MTFAlignment > TrendFollowing > SqueezeExpansion > MeanReversion) is a **hypothesis** that will be validated from outcome data. The rules-based aggregator is temporary scaffolding — the signal_ledger is the real deliverable.

### Why Log ALL Signals (Not Just Winners)?
Enables "what if" analysis:
- Did runner-up signals outperform winners?
- Do certain setups perform better when they agree vs when they win solo?
- Is the priority order correct or backwards?

Loser signals with `was_selected=false` and `pnl_r=null` still provide value as negative examples for ML training.

### Why Composite PK (signal_id, timestamp)?
TimescaleDB requires the partitioning column (`timestamp`) to be part of any unique constraint. A UUID-only PK would fail hypertable creation. The composite key maintains uniqueness while allowing time-based partitioning.

### Why Lifecycle Tracker is Pure Functions?
Separation of concerns:
- Tracker evaluates state transitions (testable logic)
- Repository persists transitions (database I/O)
- Caller orchestrates the flow

This makes lifecycle logic testable without mocking the database and keeps P&L calculations isolated.
