## Finding D-1: `_DAG_ORDER` Missing 11 Deployed Services

**Severity:** HIGH
**Category:** Feedback Loop Gap
**Files:** `services/service_auditor_agent.py:55-96`

**Description:**
The following services have systemd units installed in `/etc/systemd/system/` and `production/systemd/` but are absent from `_DAG_ORDER`. The service-auditor only monitors units it discovers via `systemctl list-units`; since these appear dynamically but have no restart priority, graduated restarts issue `systemctl start` for them at priority 99 (the fallback) after all known-good services are up. More critically, `_AGENT_ID_TO_UNIT` cannot be populated for these services so Prometheus lag monitoring is completely dark for them.

Missing from `_DAG_ORDER`:
- `indicagent-shadow-auditor` - timer-triggered oneshot (shadow governance)
- `indicagent-weight-updater` - timer-triggered oneshot (CIS weight learning)
- `indicagent-ml-orchestrator` - timer-triggered oneshot (ML coordination)
- `indicagent-ml-data-quality` - timer-triggered oneshot (ML DQ auditor)
- `indicagent-ml-discovery` - timer-triggered oneshot (ML feature discovery)
- `indicagent-hmm-training` - timer-triggered oneshot (HMM model retraining)
- `indicagent-feature-validation` - timer-triggered oneshot (IC/p-value decisions)
- `indicagent-api` - always-on API server
- `indicagent-dashboard` - always-on dashboard server
- `indicagent-redpanda-ready` - infrastructure readiness gate
- `indicagent-redpanda-watchdog` - infrastructure watchdog

The five ML batch services are oneshot timers and do not need lag thresholds, but they should appear in `_DAG_ORDER` at layer 8 with a comment indicating `Type=oneshot` so the auditor can distinguish failed runs from normal `inactive (dead)` state. Without an entry, if `ml-orchestrator` hits a `StartLimitHit`, the auditor never sees it and never resets it.

**Fix:** Add all 11 services to `_DAG_ORDER` with appropriate priority levels (api/dashboard at 10 alongside service-auditor; oneshot batch services at 8; infrastructure units at 0 or as non-restartable sentinels).

## Finding D-3: `intelligence-pipeline` `After=` References a Non-Existent Unit

**Severity:** CRITICAL
**Category:** Feedback Loop Gap
**Files:** `production/systemd/indicagent-intelligence-pipeline.service:3`

**Description:**
```
After=network-online.target indicagent-bar-aggregator-compute.service indicagent-provider-merger.service
Wants=indicagent-bar-aggregator-compute.service
```

The unit `indicagent-bar-aggregator-compute.service` does not exist anywhere in systemd. The real unit is `indicagent-bar-aggregator.service`. systemd silently ignores `After=` and `Wants=` references to unknown units - systemd treats them as already-satisfied. This means on a clean boot, `intelligence-pipeline` starts immediately without waiting for bar-aggregator to be ready. If bar-aggregator starts after intelligence-pipeline, the pipeline will consume an empty `market.bars` stream and may emit spurious intelligence events with incomplete bar history before the aggregator has seeded HTF bars.

This is not a data corruption risk per se (Kafka consumer groups will catch up), but on cold start the pipeline seeds bar history from DB and could begin processing live bars before HTF bars from the aggregator arrive, producing signals against partially-seeded feature windows.

**Fix:** Change the `After=` line to `After=network-online.target indicagent-bar-aggregator.service indicagent-provider-merger.service` and update the `Wants=` line.

## Finding D-7: `feature_writer` Agent ID Mismatch in `_AGENT_ID_TO_UNIT`

**Severity:** MEDIUM
**Category:** Feedback Loop Gap
**Files:** `services/service_auditor_agent.py:131`, `services/feature_writer_agent.py:239-240`

**Description:**
`_AGENT_ID_TO_UNIT` maps `"feature_writer"` to `"indicagent-feature-writer"`. However, the feature writer registers itself with the name `"feature_writer_agent"` (line 240: `super().__init__(name="feature_writer_agent",...)`). The `PERSISTENCE_CONSUMER_LAG` Prometheus metric uses the `agent_id` label set from `self.name`, which means the metric will be labeled `agent_id="feature_writer_agent"` while the auditor queries for `agent_id="feature_writer"`. As a result, Prometheus lag monitoring for the feature-writer never returns a valid reading - the service can accumulate unbounded consumer lag without triggering degraded state. Feature-writer is the persistence layer for `intelligence_features` (the primary hypertable), making this a meaningful blind spot.

**Fix:** Change the key in `_AGENT_ID_TO_UNIT` from `"feature_writer"` to `"feature_writer_agent"` at `service_auditor_agent.py:131`.

## Finding D-8: Cross-Asset and Intelligence-Pipeline Bidirectional Dependency at Same DAG Layer

**Severity:** HIGH
**Category:** Feedback Loop Gap
**Files:** `services/cross_asset_service.py:173`, `services/intelligence_pipeline_agent.py:219`, `services/service_auditor_agent.py:64-66`

**Description:**
Both `indicagent-cross-asset` and `indicagent-intelligence-pipeline` are assigned the same DAG priority (5). Their topic dependency is bidirectional:

- `cross_asset_service` subscribes to `topic_intelligence` (published by `intelligence_pipeline`)
- `intelligence_pipeline_agent` subscribes to `topic_cross_asset` (published by `cross_asset`)

This is a **cyclic dependency** within the same priority layer. The DAG model (lower priority = restart first) means that if both services fail simultaneously, the auditor restarts them in undefined order since they share priority 5. If `intelligence-pipeline` starts before `cross_asset`, the pipeline will process bars with a stale/empty cross-asset cache. The cache is never automatically invalidated - it simply waits for the next `cross_asset` message.

Separately, neither service's systemd unit declares a dependency on the other. `cross_asset` starts after `network-online.target` only. The design intent (1-bar lag: bar N's intelligence feeds bar N+1's cross-asset features) means the cycle is tolerable architecturally, but the same-priority placement in `_DAG_ORDER` misrepresents the intended startup order.

`cross_asset` should be at a higher restart priority (e.g., 5) and `intelligence_pipeline` at a lower restart priority (e.g., 6), so that cross-asset is guaranteed warm before the pipeline processes its first bar after a dual-failure recovery.

**Fix:** Set `indicagent-cross-asset` and `indicagent-macro-compute` to priority 5 and `indicagent-intelligence-pipeline` to priority 6 in `_DAG_ORDER`, and add `After=indicagent-cross-asset.service indicagent-macro-compute.service` to the intelligence-pipeline systemd unit.

## Finding D-9: `macro-compute` Not a Startup Dependency of `intelligence-pipeline`

**Severity:** MEDIUM
**Category:** Alpha Leakage
**Files:** `production/systemd/indicagent-intelligence-pipeline.service:3`, `services/macro_compute_agent.py:106`, `services/intelligence_pipeline_agent.py:220`

**Description:**
`intelligence_pipeline` subscribes to `topic_macro_signals` (published by `macro_compute_agent`). On cold start, `macro_compute_agent` (which subscribes to `market.bars`) must receive enough bars before it can compute and publish yield curve slope, yield curve regime, `ftq_score`, and `ftq_regime`. The `intelligence_pipeline` reads these macro fields into its CacheManager on receipt (`_cache_mgr.update_macro(tf, macro_fields)`). If the pipeline starts processing bars before macro-compute has delivered any signals, all I7 calculations that gate on or blend macro regime context will run with zero/null macro fields for the first N bars of the session. This constitutes alpha leakage: signals emitted against a stale macro context could have incorrect regime classifications.

There is no systemd `After=` or `Requires=` ordering between intelligence-pipeline and macro-compute. Both are in `_DAG_ORDER` at priority 5, so graduated restarts of both in the same failure window provides no ordering guarantee.

**Fix:** Add `After=indicagent-macro-compute.service` to the intelligence-pipeline systemd unit; also noted in D-8 above for split priorities in `_DAG_ORDER`.

## Finding D-10: `roll_compute` Misclassified at DAG Layer 8 (Priority 8) - Depends on Layer 2

**Severity:** MEDIUM
**Category:** Feedback Loop Gap
**Files:** `services/service_auditor_agent.py:84`, `services/roll_compute_agent.py:377-382`

**Description:**
`roll_compute_agent` subscribes to `topic_market_bars` which is published by `provider_merger` (DAG priority 2). Yet `roll_compute` is placed at DAG layer 8 (priority 8), the analytics tier, alongside signal-metrics and graduation.

In the graduated restart logic, DAG priority determines restart order: lower numbers restart first. If the entire pipeline fails (e.g., after a reboot), `roll_compute` will not be restarted until all priority 1-7 services are healthy. Since `roll_compute` is the futures roll detection service that triggers `ibkr-provider` restarts for front-month promotions, a delayed `roll_compute` restart means that if a futures roll event occurred during the outage window and the roll event is on the Kafka topic, the roll will not be processed until `roll_compute` is healthy at priority 8 - which could be minutes after priority 2 services are producing bars again. During that window the pipeline processes bars for a stale contract.

**Fix:** Move `indicagent-roll-compute` to priority 3 in `_DAG_ORDER` (same tier as bar-aggregator, since it only needs market.bars from priority 2).

## Finding D-11: Multiple L6 Services Have No Systemd Ordering Dependencies on Their Upstream

**Severity:** MEDIUM
**Category:** Feedback Loop Gap
**Files:** `production/systemd/indicagent-lifecycle-writer.service:3`, `production/systemd/indicagent-lineage-writer.service:3`, `production/systemd/indicagent-graduation-compute.service:3`, `production/systemd/indicagent-graduation-writer.service:3`, `production/systemd/indicagent-signal-tracker-compute.service:3`, `production/systemd/indicagent-ctx-writer.service:3`, `production/systemd/indicagent-signal-metrics-writer.service:3`

**Description:**
All of the above services have only `After=network-online.target` in their `[Unit]` section, with no reference to their upstream Kafka producers. On a clean boot or after a full-stack restart, these services start consuming from Kafka immediately - before their upstream services are healthy. Kafka consumer groups with `auto_offset_reset="earliest"` will simply wait for messages, which is benign. However, services that use `auto_offset_reset="latest"` will skip messages that were published between their cold start and when the upstream comes up. Specifically, `lifecycle_writer_agent` uses `enable_auto_commit=False` and an explicit consumer, so it will catch up. However, the absence of ordering declarations means `service-auditor`'s `_discover_services()` restart loop sees all L6 services as equal priority peers, even though they are logically downstream. If a partial failure causes service-auditor to restart a subset of L6 services, the restart order is not guaranteed to be upstream-first.

**Fix:** Add `After=indicagent-intelligence-pipeline.service` and `After=indicagent-signal-tracker-compute.service` (for lifecycle-writer, graduation-compute, graduation-writer) to the relevant unit files so systemd respects ordering on a clean boot.

## Finding D-16: `bar_replay` Dual-Publishes to `market.bars` and `market.bars.htf` Simultaneously - No Conflict Guard

**Severity:** MEDIUM
**Category:** Alpha Leakage
**Files:** `services/bar_replay_provider_agent.py:43,122`, `production/systemd/indicagent-bar-replay.service`

**Description:**
`bar_replay_provider_agent` publishes 1m bars to `topic_market_bars` AND HTF bars directly to `topic_market_bars_htf`, bypassing `bar_aggregator`. This is the design intent for replay mode. However, `indicagent-bar-replay.service` has no `Conflicts=indicagent-ibkr-provider.service` declaration. If both services are started simultaneously (e.g., during a failed replay that did not cleanly stop, or if service-auditor restarts ibkr-provider while replay is running), both will publish to `market.bars` simultaneously. The intelligence pipeline has a single consumer group across both - bars from two sources in the same Kafka partition sequence will appear as legitimate data.

Additionally, `bar_replay`'s `ExecStopPost=/bin/systemctl start indicagent-bar-aggregator.service` fires when the replay process exits cleanly. But during replay, `bar_aggregator` is presumably stopped (per design intent). If `bar_aggregator` was already running, this start command is idempotent. If replay exits early (exception, not clean exit), `ExecStopPost` still fires because systemd runs it on all stop reasons for `Type=simple`, potentially starting bar-aggregator while replay produced incomplete bar data.

**Fix:** Add `Conflicts=indicagent-ibkr-provider.service` to the bar-replay unit to enforce mutual exclusivity. Consider using `ExecStopPost` conditional only on exit code 0 (`SuccessExitStatus=0`) or restructure as a pre/post oneshot sequence.

## Finding D-17: `graduation_compute` Has No Lag Threshold Despite Consuming `lifecycle_transitions`

**Severity:** LOW
**Category:** Feedback Loop Gap
**Files:** `services/service_auditor_agent.py:99-121`, `services/graduation_compute_agent.py:123`

**Description:**
`graduation_compute_agent` subscribes to `topic_lifecycle_transitions` and is in `_DAG_ORDER` (priority 8) and `_AGENT_ID_TO_UNIT`, but it is absent from `_LAG_THRESHOLDS`. The Prometheus lag check loop (`_fetch_prometheus_lag`) returns 0 lag for `indicagent-graduation-compute` even if the consumer group accumulates thousands of unprocessed transitions. A stuck graduation-compute would silently fail to evaluate transform graduation while appearing healthy to the auditor.

Similarly, `roll_compute_agent` (subscribes to `market.bars`) has no lag threshold.

**Fix:** Add `"indicagent-graduation-compute": 500` and `"indicagent-roll-compute": 500` to `_LAG_THRESHOLDS`.
