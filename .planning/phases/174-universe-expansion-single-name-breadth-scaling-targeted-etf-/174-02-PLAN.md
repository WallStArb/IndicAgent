<objective>
Replace the single conflated `instruments.is_active` boolean with a 3-way
backfill-eligible / compute-eligible / live-tradeable split, additively, so none of the 37
existing `get_active_contracts()` call sites change behavior (D-07). Plan 06 exposes the split
through `get_active_contracts(dimension=)`; this plan lands the schema and proves the default
mapping is correct rather than assumed.

Purpose: `is_active=true` today means "backfill it AND compute on it AND (implicitly) it would
be eligible for any future live-trading code path that reads the same flag." Marking a
Russell-3000-scale sample `is_active=true` under that model silently makes hundreds-to-thousands
of names live-eligible. IBKR's 80-simultaneous-subscription cap binds live streaming only — it
is not a backfill constraint — but a future `indicagent-ibkr-provider` restart against an
unsplit universe would nondeterministically fail to honor it. This gap already survived the
111→231 expansion untouched (todo 274); it does not survive a second, much larger one.

Output: migration 337 (applied live + committed), plus a reusable audit script whose measured
output justifies the `compute_eligible=true` default for all existing rows and whose exported
promotion predicate is the one Plans 10 and 12 reuse.
</objective>

Create `scripts/analysis/instrument_compute_eligibility_audit.py` — a read-only one-off that
answers RESEARCH.md Open Question 3: does every `is_active=true` row genuinely have enough
history to be compute-ready, or are some mid-onboarding?

For every row in `instruments` where `is_active = true`, report per symbol: row count and
earliest/latest `timestamp` in `market_data_ohlcv_tradeable` per timeframe in ('5m','15m','1h','1d'),
and whether a `backfill_status` row exists per timeframe. Emit a summary table to stdout plus
a single structlog line with aggregate counts (`n_active`, `n_with_all_four_tfs`,
`n_missing_any_tf`, `n_zero_rows`). Never log per symbol inside the loop — accumulate and log
once, matching `ic_engine.py`'s `n_skipped` pattern.

**Query shape is load-bearing, not incidental (review finding).** Do NOT issue one unconstrained
`SELECT symbol, timeframe, count(*), min(timestamp), max(timestamp) FROM market_data_ohlcv_tradeable
GROUP BY 1,2` — that is a sequential scan over every chunk of a hundreds-of-millions-of-rows
hypertable and will both take tens of minutes and contend for I/O with anything else running.
Instead:
- Drive the aggregation from `idx_ohlcv_symbol_tf_time` by constraining
  `symbol = ANY(%(symbols)s) AND timeframe = ANY(%(timeframes)s)` in every query, so the planner
  has index-usable equality predicates on the leading index columns rather than a bare scan.
- Get `min(timestamp)` / `max(timestamp)` per `(symbol, timeframe)` from separate
  `ORDER BY timestamp ASC LIMIT 1` / `ORDER BY timestamp DESC LIMIT 1` reads against the same
  index rather than from an aggregate over the full partition — those are index-only endpoint
  lookups, not scans.
- Batch symbols rather than issuing one query per symbol (231 round trips is its own problem);
  a batch size around 25 symbols per query keeps each statement's working set bounded.
- Before committing to the shape, run `EXPLAIN (ANALYZE, BUFFERS)` on the count query for one
  batch and record the plan node type and buffer counts in the SUMMARY. If it shows a
  `Seq Scan` on a chunk rather than an index scan, fix the query — a measured plan, not an
  assumption, per `docs/foundation/performance-investigation-sop.md`.

Also export a module-level constant `COMPUTE_READY_PREDICATE_SQL` — the canonical, reusable
SQL fragment expressing "this symbol is compute-ready", defined as: it has a `backfill_status`
row with `fetch_complete = true` for **all four** timeframes (not at least one), AND it has
non-zero `market_data_ohlcv_tradeable` rows in **all four** timeframes. Express the
all-four condition as a counted aggregate, e.g.
`(SELECT count(*) FROM backfill_status b WHERE b.symbol = i.symbol AND b.tf = ANY(%(timeframes)s) AND b.fetch_complete) = 4`,
never as a bare `EXISTS (... fetch_complete ...)`, which is an "any one completed" test wearing
an all-four label. Plans 10 and 12 import this constant rather than re-deriving the predicate,
so the gate cannot drift between the three places it is enforced.

Use parameterized queries (`%(...)s` placeholders) throughout; never f-string-interpolate a
symbol into SQL. Use `except X as error:`. Exit non-zero if the query fails; exit 0 regardless
of what the audit finds — this is a measurement tool, not a gate.

Run it and capture the output. The finding decides the migration's default in Task 2:
- If every `is_active=true` symbol has non-zero tradeable rows in at least one timeframe,
  `compute_eligible=true` for all existing rows is the correct, behavior-preserving default.
- If any symbol has zero rows in every timeframe, list those symbols explicitly in the
  migration header comment and still set `compute_eligible=true` for them (preserving today's
  exact behavior — narrowing them would be a silent behavior change), with the header noting
  them as candidates for a follow-up demotion decision outside this phase. File that follow-up
  as a `.planning/todos/pending/` item with a `PRIORITIES.md` row so it is tracked rather than
  buried in a migration comment.
