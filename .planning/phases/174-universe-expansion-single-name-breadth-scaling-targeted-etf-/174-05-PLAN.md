<objective>
Wire D-04's two structural mechanisms into `_compute_cross_sectional_tf`: a pre-flight cell-size
estimate that makes `_check_cell_size` reachable before any memory is allocated, and the
disk-backed `Float32ChunkAccumulator` from Plan 01 so peak anonymous RSS during accumulation is
bounded by chunk size rather than cell size.

Purpose: `_check_cell_size` exists precisely to fail loud on an oversized cell, but its only
cross-sectional call site (line 3614) runs *after* the whole cell has already been materialized
— so it can never fire before the allocation that kills the process. Todo 371 OOM-killed
ic_engine at 182 symbols (23% of a Russell-3000-scale sample) with that guard technically
present and structurally unreachable. Migrations 259 and 332 both responded by raising
`alpha.ic.max_cell_rows` instead; todo 371 records that as the anti-pattern. This plan makes
the guard reachable and removes the allocation it was guarding against.

Output: three edits to `_compute_cross_sectional_tf` (pre-flight check, disk-backed accumulator
construction, `finally`-block scratch cleanup) plus a new unit test file.
</objective>

**Memmap ownership contract (documented by Plan 01 in the class and `finalize()` docstrings — this
plan is the first consumer bound by it):**
- `finalize()` returns a VIEW over the memmap, not a copy.
- That view stays readable until, and only until, the caller calls `close()`.
- The caller owns `close()` and must not call it while any consumer still holds or reads the
  view. Reading a view whose mmap has been closed raises `ValueError: mmap closed or invalid`
  on Linux and is a platform-dependent invalid read elsewhere — there is no safe "close early"
  variant.
- Plan 01's migration-336 description for `infra.ic_engine.memmap_scratch_dir` already records
  that the scratch filesystem must hold TWO coexisting cell-sized files (`X_raw` from this plan
  and `X_nd` from Plan 09), which is the headroom figure Task 2's disk check must enforce.

Make three changes inside `_compute_cross_sectional_tf`.

**(a) Pre-flight estimate.** Immediately after the `regime_timestamps` fetch and its
`if not regime_timestamps: return` early-exit (around lines 4398-4407), compute
`n_estimated = len(regime_timestamps) * len(symbol_list)` and call

than being size-checked at zero.

Add a code comment stating that this estimate is deliberately a conservative UPPER bound — it
assumes full density (every symbol has a row at every regime timestamp), which overestimates
for symbols with shorter backfill history. That is the safe direction per D-04's crash-loud-over-
silent-degrade preference. Explicitly instruct future readers not to "tighten" it into an exact
count, since an underestimate reintroduces exactly the OOM this fix removes. Note that a
false-positive `CellTooLargeError` at Russell-3000 scale is itself useful information: it argues
for holding sparse-history symbols at `compute_eligible = false` (Phase 174 D-07) rather than
loosening the guard.

**(b) Disk-backed accumulator.** Replace the bare `X_acc = Float32ChunkAccumulator()` (line
4455) with a mode selection driven by the pre-flight estimate:
`use_disk = config.disk_backed_min_rows == 0 or n_estimated >= config.disk_backed_min_rows`.
When `use_disk`, construct
`Float32ChunkAccumulator(disk_backed=True, estimated_rows=n_estimated, n_cols=n_features, scratch_dir=config.memmap_scratch_dir)`;
otherwise construct it exactly as today. Because `n_estimated` is an upper bound and Plan 01's
`finalize()` trims to rows actually written, the memmap is correctly sized by construction and
short cells are trimmed, not padded.

Before allocating a disk-backed accumulator, check free space on `config.memmap_scratch_dir`'s
filesystem via `shutil.disk_usage` and raise a `RuntimeError` naming the required and available
byte counts if the requirement exceeds the free space. Filling the disk mid-run is the
2026-08-13 incident's failure shape; fail before allocating, not during.

The requirement is **`2.2 * n_estimated * n_cols * 4` bytes, not `n_estimated * n_cols * 4`.**
Two cell-sized scratch files coexist inside one cell's compute: `X_raw` allocated here, and the
`X_nd` memmap Plan 09 allocates from `X_raw` inside `_compute_one_cross_sectional_cell` while
`X_raw` is still open and being read. `X_nd` is narrower than `X_raw` (only the
non-degenerate, non-broadcast columns survive the mask), so 2.0x is the worst case and 2.2x adds
a 10% margin for filesystem overhead and rounding. Define the multiplier as a named module
constant with a comment naming Plan 09 as the second allocation, so a future reader who deletes
the `X_nd` memmap knows what the factor was for. Do NOT compute it as `1.0x` "because Plan 09
hasn't landed yet" — Plan 09 lands in the next wave against this same code, and a check that is
correct only until then is a check that silently stops being correct.

Log one structlog line (`ic_engine.cross_sectional_accumulator_mode`) carrying `tf`,
`regime`, `n_estimated`, `disk_backed`, and `scratch_dir` — once per cell, not per chunk.

**(c) Cleanup — scope the `try`/`finally` to the WHOLE cell, not the fetch loop.**

This is the single most breakable part of this plan. `finalize()` hands back a *view* over the
memmap (Plan 01's ownership contract, quoted in `<interfaces>`), and `X_acc.close()` closes the
mmap and unlinks the file. Any read of that view after `close()` raises
`ValueError: mmap closed or invalid` on Linux, or is a platform-dependent invalid memory read.
So the `finally` must not fire until every consumer of `X_raw` has returned.

Concretely, structure it as:

- `try:` opens BEFORE the accumulator is constructed.
- Inside the `try`: the chunk fetch loop, `X_raw = X_acc.finalize()`, the `bar_ts`/`X_raw`
  row-count alignment guard, the call to `_compute_one_cross_sectional_cell(...)` and its whole
  return-value handling, and — once Plan 09 lands — the `X_nd` construction, the streaming
  correlation, `_cluster_features`, and the per-scale rank/bootstrap loop, all of which read
  through `X_raw` or through views derived from it (`X_sub_nd = X_nd[0:n_raw:scale_stride]` is a
  view, not a copy). Everything that can touch the mapping lives inside this `try`.
- `finally:` contains `X_acc.close()` and nothing that reads `X_raw`.

Two things must be true after this task and must be stated in a comment above the `try:`:
1. `_compute_one_cross_sectional_cell` is called synchronously inside the `try` — it is not
   scheduled, deferred, wrapped in a task, or handed to an executor. If a future change makes it
   concurrent, the `finally` stops being a correct boundary.
2. Nothing returned by `_compute_one_cross_sectional_cell` holds a reference into the mapping.
   The cell returns per-feature IC rows (scalars aggregated over the cell), not array slices;
   assert this explicitly rather than assuming it, and if any returned structure does carry an
   array view, `np.asarray(...).copy()` it before the `finally` runs.

Across a multi-day, thousands-of-cells corpus run, a leaked scratch file per cell fills the disk
— so the `finally` must also run on every exit path, including the `CellTooLargeError` re-raise
and the row-count mismatch `RuntimeError`.

Constraints that must hold after this task:
- Do NOT add any `except CellTooLargeError` handler that subsamples, retries at reduced size,
  or otherwise degrades. D-04 forbids an automatic degrade path outright; the correct response
  to a still-too-large cell is a human-reviewed, pre-registered, visibly logged config override.
- Do NOT raise `alpha.ic.max_cell_rows`.
- Use `except X as error:`.
- `_compute_one_cross_sectional_cell`'s signature does not change; it now may receive a memmap
  view as `X_raw`. Its own `np.std(X_raw, axis=0, dtype=np.float64)` is a read-through reduction
  and stays correct on a memmap. Its `X_nd = X_raw[:, cluster_input_mask]` boolean-index copy is
  a known remaining defeat point and is Plan 09's scope — do not attempt it here, and do not
  claim D-04 complete in this plan's SUMMARY.
