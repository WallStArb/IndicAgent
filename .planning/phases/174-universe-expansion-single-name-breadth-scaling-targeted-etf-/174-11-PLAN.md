governs the method — measure before theorizing, never trust a read-only test for a write-path
question, treat chunk count and compression status as first-class suspects.

APR key holding a number derived from a measurement.

Answer D-01 empirically: what is the largest instrument count this infrastructure actually
supports?

The quantity that actually drives memory, scratch size and correlation wall-clock is the cell's
**row count** (`n_rows x n_features`), not its symbol count — the pre-flight guard's own formula
is `len(regime_timestamps) * len(symbol_list)`. Symbol count is the unit D-01 must be stated in,
but it enters only through that product. So measure a rows-to-cost curve at three or more real
points and invert it to symbols, rather than trying to conjure 400 real symbols out of a
231-symbol corpus.

**Arm A — real runs, no synthesis (source of both fetch and compute numbers).** Run the real
`ic_engine` cross-sectional path at two genuinely different real cell sizes:
(i) the 182-symbol `5m/high_bear` baseline from Task 1, and
(ii) the largest real cell available today — the full compute-eligible symbol set (231 symbols
at the time of writing; query it, do not hardcode) against whichever `(tf, regime_label)` pair
has the largest `regime_timestamps` count, determined by querying the regime timestamp counts
per label BEFORE choosing. Record the achieved `n_rows` for each, not just the symbol count.

**Arm B — write-free harness to reach ~400-symbol-equivalent rows.** Create
`scripts/analysis/ic_engine_cell_scale_harness.py`. It imports `_compute_cross_sectional_tf`'s
inner machinery from `services/ic_engine.py` and drives the accumulate → `X_nd` build →
streaming correlation → cluster → per-scale rank pipeline directly, feeding it a chunk stream
that is the **real** `5m/high_bear` fetch replayed K times with the symbol column rewritten to a
distinct alias per replay (`AAPL`, `AAPL#R2`, ...). Row multiplication happens in the chunk
stream, where duplicate source rows are appended rather than deduplicated — which is precisely
why this works and a duplicated `IN (...)` list does not. Set K so the achieved row count reaches
at least 2x Arm A(i)'s measured `n_rows` (K=2 against the 182-symbol baseline gives a
364-symbol-equivalent cell; K=3 gives 546, useful as a third curve point). Record the ACHIEVED
row count from `X_acc`'s write offset, never the intended one.

State the harness's limitation plainly in the document: it measures the compute phase's memory,
scratch size and wall-clock, not the database fetch phase. Fetch-phase wall-clock is extrapolated
from Arm A's real runs, where it is measured directly. An honest instrument with a stated blind
spot is evidence; a silent substitution is not.

**Write isolation — mandatory, and verified rather than intended.** No run in this task may write
a result row:
- The harness calls only the compute functions and discards their return values. It contains
  zero `INSERT` statements and never calls `ic_engine`'s persistence path — grep-assert both.
- Arm A's real runs use `ic_engine`'s existing no-write/dry-run path if one exists; if none does,
  run them against a connection whose role cannot write those three tables, or add a
  `--no-persist` flag to the harness invocation path rather than letting a throughput run reach
  `feature_ic_scores`.
- Snapshot `SELECT count(*)` for `feature_ic_scores`, `feature_ic_scores_history` and
  `ic_cell_fingerprints` immediately before and immediately after every run in this task, and

  those rows immediately by their run identifier, record the deletion and the verifying count in
  the document, and state what allowed the write — a throughput measurement blending into the
  results corpus is the measurement-integrity failure T-174-31 names.
- Nothing from any run in this task goes into `docs/research/construction-verdict-ledger.md`, and
  the document states in its own words that the scale-up runs produce no citable IC finding.

Measure at every size and record:
- Peak RSS vs. achieved cell ROW count (with the equivalent symbol count alongside it). If the
  fix works, this should be roughly flat, bounded by chunk and block sizes rather than by cell
  size. A peak that scales with row count means a defeat point remains; name it.
- Wall-clock vs. achieved row count, split into fetch phase (Arm A only) and compute phase (both
  arms), and the implied full-corpus recompute time by extrapolation from STATE.md's 66-77 hour
  figure at 231 symbols.
- Scratch-directory peak size vs. achieved row count — and note it should now peak at roughly 2x
  a single array, since `X_raw` and `X_nd` coexist (Plan 05's 2.2x headroom check). Record what
  row count, and therefore what symbol count, would exhaust the 568GB of free disk.
- Whether `alpha.ic.max_cell_rows = 15000000` becomes the binding constraint before memory,
  wall-clock or disk does — the pre-flight guard fires at `len(regime_timestamps) * len(symbol_list)`,
  so this is directly computable from the observed `regime_timestamps` count for the largest cell.

State the supported count as a decision with the binding constraint named: "N symbols, bound by
X." Choose the number so that the largest expected cross-sectional cell stays under
`alpha.ic.max_cell_rows` without any ceiling change, and so that the implied full-corpus
recompute time stays within what a research corpus can absorb. Do not pad the number with an
unstated safety margin — state the margin if you apply one.

Update `.planning/todos/pending/371-*.md` with the verification outcome: the measured
