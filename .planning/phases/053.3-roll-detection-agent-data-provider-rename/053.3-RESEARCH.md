# Phase 53.3: RollComputeAgent + DataProviderAgent Rename — Research

**Researched:** 2026-03-28
**Domain:** Agentic DAG extraction — class split, topic migration, rename
**Confidence:** HIGH

## Summary

This phase has two orthogonal deliverables: (1) extract `RollMonitor` from `tws_daemon.py` into a new `RollComputeAgent(BaseAgent)` with a typed `RollEvent` schema and dedicated `topic_roll_events()` topic; and (2) rename `tws_daemon.py` → `data_provider_agent.py` / `TwsDaemon` → `DataProviderAgent` with a new systemd unit. All decisions are locked in CONTEXT.md. No new detection logic is written.

The extraction is mechanically straightforward: `RollMonitor` is a self-contained class (lines 73–365 in `tws_daemon.py`) with minimal coupling to `TwsDaemon` — coupling is one-directional (daemon instantiates monitor, calls `update_volume()` and `check_roll()`, then calls `_on_roll_confirmed()`). The `signal_generator_agent` currently consumes roll events from `topic_system_events` and passes them to `parse_roll_event()` which extracts `old_symbol`/`new_symbol` from a raw dict — this must migrate to consuming `topic_roll_events` and using the typed `RollEvent`.

The main execution risk is the test file update surface: two test files import `from services.tws_daemon import RollMonitor` and `TwsDaemon` by path, and these must be redirected after the rename.

**Primary recommendation:** Keep `RollMonitor` private inside `services/roll_compute_agent.py` (not `src/intelligence/`) — no existing test imports it from `src/`, and moving it there would require adjusting all existing test patches (e.g., `patch("services.tws_daemon.get_roll_window")`). The signals test pattern already uses relative service imports.

## 2. BaseAgent Pattern (Confirmed)

**Confidence: HIGH — directly read from source**

File: `src/core/agent/base.py`

Key invariants:
- `__init__(self, name: str, metrics_port: int | None = None)` — sets `self.name`, `self._metrics_port`, `self._stop_event`, `self.logger` (structlog bound), `self.tracer`
- **config-before-super pattern**: extract `metrics_port` from kwargs before calling `super().__init__()` (documented in STATE.md Phase 52.6 decisions)
- `start()` calls: `_register_signal_handlers()` → metrics server → `_setup()` → lag reporter task → `_run()` → finally: cancel lag task → `_teardown()` → `stop()`
- `_run()` is `@abc.abstractmethod` — must be implemented
- `topics_consumed` / `topics_produced` are properties returning `list[str]`, default `[]`
- `_report_consumer_lag()` loops every 15s until `_stop_event` is set — override for real lag metrics
- `_stop_event: asyncio.Event` drives the `running` property and all loop terminations
- Signal handlers: `_register_signal_handlers()` uses `asyncio.get_running_loop()` — must be called from within running event loop (i.e., from `start()`)

**`__main__` block pattern** (all agents follow this):
```python
if __name__ == "__main__":
    from src.observability.otel import init_tracing
    init_tracing(service_name="roll_compute_agent")
    asyncio.run(main())
```

**Note on SignalTrackerAgent's super() call:** `SignalTrackerAgent.__init__` calls `super().__init__(name="signal_tracker_agent")` with no `metrics_port` — it calls `start_metrics_server` manually elsewhere. `RollComputeAgent` should pass `metrics_port=9122` directly to `super().__init__()` since BaseAgent auto-starts the metrics server in `start()` when `metrics_port` is set.

## 4. parse_roll_event in service_utils (Confirmed)

**Confidence: HIGH — directly read from source**

File: `src/core/service_utils.py`, lines 129–141:

```python
def parse_roll_event(event: dict, logger: Any) -> tuple[str, str] | None:
    if event.get("event_type") != "roll":
        return None
    try:
        return event["old_symbol"], event["new_symbol"]
    except KeyError as exc:
        logger.warning("roll_event_missing_fields", error=str(exc))
        return None
```

Currently parses raw dict keys: `event_type`, `old_symbol`, `new_symbol`.

**After D-02 migration**, this must parse `RollEvent` schema fields. Two options per Claude's Discretion:

**Option A — classmethod on RollEvent** (cleaner, co-located with schema):
```python
# in market_events.py
@classmethod
def from_kafka_payload(cls, payload: dict) -> "RollEvent | None":
    try:
        return cls.model_validate(payload)
    except ValidationError:
        return None
```
Then `parse_roll_event` becomes a one-liner shim or is removed entirely.

**Option B — update the module-level function** (fewer callsite changes):
```python
def parse_roll_event(event: dict, logger: Any) -> tuple[str, str] | None:
    try:
        roll = RollEvent.model_validate(event)
        return roll.old_contract, roll.new_contract
    except Exception as exc:
        logger.warning("roll_event_missing_fields", error=str(exc))
        return None
```

The return signature `tuple[str, str]` is unchanged — `_handle_roll_event()` in `signal_generator_agent` destructures it as `old_symbol, new_symbol = result` and that code doesn't need to change.

**Research recommendation:** Option B — fewer callsite changes, preserves the existing function signature, and `signal_generator_agent._handle_roll_event()` requires zero changes beyond the topic subscription switch.

**Note on field name change:** `old_symbol`/`new_symbol` (old dict) → `old_contract`/`new_contract` (RollEvent). The `parse_roll_event` wrapper abstracts this — callers still receive `(old_str, new_str)`.

```python
# Source pattern: signal_tracker_agent.py __init__ + BaseAgent lifecycle
class RollComputeAgent(BaseAgent):
    def __init__(self) -> None:
        settings = Settings()
        metrics_port = 9122  # config-before-super pattern
        super().__init__(name="roll_compute_agent", metrics_port=metrics_port)
        self.env_name = settings.env_name or ""
        self._kafka_bootstrap = settings.kafka_bootstrap_servers
        self._roll_monitor = RollMonitor(settings)
        self._symbol_to_base: dict[str, str] = {
            c.symbol: getattr(c, "base", c.symbol)
            for c in get_active_contracts(settings)
        }
        self._kafka_consumer: KafkaConsumerClient | None = None
        self._kafka_producer: KafkaProducerClient | None = None
        # Golden Signal counters (D-17)
        self._events_consumed = counter("events_consumed_total", "Bars consumed")
        self._rolls_detected = counter("rolls_detected_total", "Roll events published")
        self._detection_errors = counter("detection_errors_total", "Detection errors")

    @property
    def topics_consumed(self) -> list[str]:
        return [topic_market_bars(self.env_name)]

    @property
    def topics_produced(self) -> list[str]:
        return [topic_roll_events(self.env_name)]

    async def _setup(self) -> None:
        self._kafka_consumer = KafkaConsumerClient(
            topic_market_bars(self.env_name),
            bootstrap_servers=self._kafka_bootstrap,
            group_id="roll_compute_consumer",
            auto_offset_reset="earliest",
        )
        await self._kafka_consumer.start()
        self._kafka_producer = KafkaProducerClient(self._kafka_bootstrap)
        await self._kafka_producer.start()

    async def _run(self) -> None:
        async for topic, key, payload in self._kafka_consumer.messages():
            if not self.running:
                break
            # process bar, check roll, publish RollEvent

    async def _teardown(self) -> None:
        if self._kafka_consumer:
            await self._kafka_consumer.stop()
        if self._kafka_producer:
            await self._kafka_producer.stop()
        await super().stop()
```

### `volume_zscore` extraction for RollEvent

`RollMonitor.check_roll()` computes `z_score` locally but does not return it. Two options:

1. **Modify `check_roll` return signature** → `tuple[bool, float]` where the float is z_score on confirmed roll else 0.0
2. **Add a `last_z_score` state field** to `RollMonitor` that's set when `check_roll` returns True

Option 2 is lower-risk (no signature change). Set `self._last_z_score: dict[str, float] = {}` in `__init__`, update it inside `check_roll` when `z_score < -2.0`. `_on_roll_confirmed` caller reads it for the `RollEvent` payload.

For `confirmation_count`: `_confirmation_counts[base_symbol]` is accessible from outside (it's a public dict, not private). When `check_roll` returns True it resets to 0, so capture the count *before* the reset, or add a `_last_confirmation_count` field similarly.

## Common Pitfalls

### Pitfall 1: DB writes orphaned in `_on_roll_confirmed`
**What goes wrong:** `_on_roll_confirmed` currently does DB writes (contract_metadata toggle, system_events INSERT) in addition to Kafka publish. If this method moves verbatim to `RollComputeAgent`, the agent is no longer DB-ignorant.
**Why it happens:** The method was designed when all logic lived in one place.
**How to avoid:** Strip the DB writes when moving to `RollComputeAgent`. The agent publishes `RollEvent` to Kafka only. The contract_metadata toggle is a Phase 50 concern (when the agent is actually enabled and validated).
**Warning signs:** If the extracted agent imports `DatabaseManager` or `asyncpg`.

### Pitfall 2: `check_roll` resets confirmation_count before caller can capture it
**What goes wrong:** `RollMonitor.check_roll()` resets `_confirmation_counts[base_symbol] = 0` before returning True. Caller trying to populate `RollEvent.confirmation_count` reads 0.
**How to avoid:** Capture the count before the reset. Add `_last_confirmation_count: dict[str, int]` field, set it just before the reset line.

### Pitfall 3: `tws_daemon.py` ExecStart in systemd points to production wrapper
**What goes wrong:** The installed `indicagent-tws.service` runs `production/daemons/high_frequency_tws_daemon.py`, NOT `services/tws_daemon.py` directly. Renaming only `services/tws_daemon.py` leaves the running service pointing at stale code.
**How to avoid:** Check `production/daemons/high_frequency_tws_daemon.py` for `import TwsDaemon from services.tws_daemon` and update it, or update the systemd ExecStart to point directly to `services/data_provider_agent.py`.

### Pitfall 4: Test patch paths break silently
**What goes wrong:** `patch("services.tws_daemon.get_roll_window")` becomes a no-op after the module is renamed — patch still succeeds (creates a MagicMock on the old module path that nobody uses) but the actual code now imports from `services.roll_compute_agent`.
**How to avoid:** Search for all `patch("services.tws_daemon.*")` patterns and update to `services.roll_compute_agent.*` for roll-related patches.

### Pitfall 5: `topic_system_events` still in signal_generator_agent consumer group
**What goes wrong:** If `topic_system_events` is removed from `_setup_kafka_clients` topics list but the Kafka consumer group still has uncommitted offsets for that topic, the next consumer start on a different group config may produce warnings or replay old messages.
**How to avoid:** This is low risk since `ROLL_MONITOR_ENABLED=false` means no roll events have ever been published to `topic_system_events`. The consumer group offset for that topic is effectively at 0.

### Pitfall 6: `_is_paper_account` needs `settings.ib_host` at RollMonitor init
**What goes wrong:** `RollMonitor.__init__` calls `self._is_paper_account()` which reads `self._settings.ib_host`. If the `Settings` instance passed to `RollMonitor` doesn't have `ib_host`, initialization fails.
**How to avoid:** Pass the full `Settings()` instance from `RollComputeAgent.__init__`. Don't extract individual fields before passing.
