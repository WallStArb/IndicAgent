## Summary

Phase 49.2 fixes three operational bugs in `HMMRegimePlugin` (`src/intelligence/smart_money/hmm_regime.py`). The bugs are well-specified in `030-hmm-operational-fixes.md`. All research is source-code analysis — no external library research is needed.

**Bug 1 — Silent 2D fallback:** `_resolve_dims()` silently returns 2 when any of `rsi_14`, `adx_14`, `atr_14`, `macd_histogram_12_26_9` is absent from the features dict. The 2D mode slices columns from a 5D-calibrated parameter matrix (not independently calibrated for 2D). No log, no metric. Cannot audit how often this degraded mode ran.

**Bug 2 — No n_dims observability:** Neither `intelligence_features` JSONB nor service logs record which emission mode ran per bar. Gating decisions made in 2D mode are indistinguishable from 5D in the audit trail.

**Bug 3 — Warm-up noise passes regime gate:** After `_reset_state()` (called every `compute_full()` invocation), the forward algorithm starts from a uniform prior (`alpha = [0.333, 0.333, 0.333]`). The first ~20 bars converge toward the actual regime. During this warm-up window, `hmm_regime_prob ≈ 0.333`, which passes the `prob_min = 0.30` floor in `regime_gate.py`. This allows warm-up noise to gate real I7 signals as if regime confidence is valid.

**Primary recommendation:** Implement all four solution items from the todo spec as a single atomic change to `hmm_regime.py` plus schema additions to `SMCContext`. No changes needed in `regime_gate.py` — setting `hmm_regime_prob = 0.0` during warm-up exploits the existing `prob_min` check cleanly. No DB migration needed — `intelligence_features.smc` is a JSONB column that stores the full SMCContext dump; new fields appear automatically when added to the schema.

### _reset_state() is called on EVERY compute_full()

From `hmm_regime.py` line 129:
```python
self._reset_state()  # Called inside compute_full() every bar
```

This means the warm-up problem recurs on every full recompute. `compute_next()` (incremental) does NOT call `_reset_state()` — it preserves state. The warm-up window matters most at:
1. Service restart (first `compute_full()` call per symbol+TF)
2. Any bar where `compute_next()` falls back to `compute_full()` (df too short, prev_close unavailable)

### Warm-up Bar Count

`min_lookback = 20` is the guard for entering `compute_full()` at all (line 110-111). The forward algorithm runs over all bars from index 0. `regime_duration` in `_reset_state()` is initialized to `1`. After 20 bars of convergence the prior typically stabilizes.

The spec says: `hmm_warmed_up = True` once `regime_duration >= min_lookback`. This is correct — `regime_duration` tracks consecutive bars in the current regime. Once the dominant regime has persisted for `min_lookback` bars, convergence is sufficient.

**Alternative interpretation:** Use a separate `bars_processed` counter (not regime_duration) to track warm-up. This is more deterministic — `regime_duration` resets on every regime change, which could delay `warmed_up=True` indefinitely in choppy regimes. The spec uses `regime_duration >= min_lookback` — the planner should validate this choice. A `bars_processed` counter is strictly more reliable for warm-up detection. However, the spec's intent is defensible: if the regime is changing every bar, the signal is genuinely unreliable regardless.

**Recommendation:** Use a dedicated `_bars_processed` counter in `_reset_state()` (incremented each `_forward_step()` call) for warm-up tracking. This is independent of regime stability and gives a clean `bars_processed >= min_lookback` check. The spec's `regime_duration >= min_lookback` is acceptable but has the choppy-regime edge case above.

Using `bool | None` is correct since the plugin returns `{}` before min_lookback, so `None` is the absent case.

### Warm-up State Tracking Options

**Option A — use `regime_duration` (spec's recommendation):**
```python
hmm_warmed_up = self._state.get("regime_duration", 0) >= self.min_lookback
```
Caveat: choppy markets where regime flips every bar can delay `warmed_up=True` indefinitely.

**Option B — dedicated `bars_processed` counter (recommended):**
Add `"bars_processed": 0` to `_reset_state()`. Increment in `_forward_step()`. Check `bars_processed >= min_lookback`.

Option B is strictly safer and has no edge cases. The planner should pick Option B.

### compute_next() warm-up edge case

`compute_next()` calls `compute_full()` when state is uninitialized (line 148). After a successful `compute_full()`, `compute_next()` processes incremental bars. The warm-up tracking in `compute_next()` relies on the same `_state` dict — since `compute_next()` calls `_forward_step()` which increments `bars_processed` (under Option B), the counter continues growing across incremental calls. This is correct behavior: once warmed up via `compute_full()`, the plugin stays warmed up through incremental steps unless `compute_full()` is called again (which would reset).

### Renaissance Calibration Risk Assessment

The todo spec asks: "Does the 2D fallback expose a hidden calibration risk?"

**Answer (HIGH confidence):** Yes, but it is a pre-existing structural risk, not something Phase 49.2 can fix.

The 5D parameter matrix (`_DEFAULT_MEANS` shape `(3, 5)`) was not fitted via EM on real data — it uses hardcoded heuristic defaults. The 2D mode slices columns 0-1 from this matrix. The `_diag_gaussian_log_prob` function correctly handles the slice. The calibration risk is that the heuristic parameters may not accurately separate regimes in real market data regardless of dimensionality.

Phase 49.2's scope: add logging + observability so the extent of 2D fallback is measurable. The calibration training problem is tracked in `docs/ideas/hmm-multi-tf-and-training.md` and is out of scope here. The fix is correct and sufficient for the operational bugs.

### Adding a New Plugin Output Field (Schema-First Pattern)

1. Add field to `SMCContext` in `schemas.py` with `Optional` type and `None` default
2. Add field name to `HMMRegimePlugin.outputs` frozenset
3. Emit field value in `_build_output()` return dict
4. Tests: assert field present in result dict, assert correct values

This is the canonical pattern for every SMC plugin output. The `extra="forbid"` on `SMCContext` acts as a compile-time guard — if you add the field to the plugin but forget to add it to the schema, the feature pipeline will raise a validation error at runtime.

Add at the top of `hmm_regime.py` (currently has no logger). The `__name__` gives `src.intelligence.smart_money.hmm_regime` as the logger name — readable in log output.

### Warm-up Suppression Pattern

When `hmm_warmed_up=False`, override the probability outputs:
```python
if not warmed_up:
    output["hmm_regime_prob"] = 0.0
    # Optionally zero out all three prob fields too
    output["hmm_prob_ranging"] = 0.0
    output["hmm_prob_trending_up"] = 0.0
    output["hmm_prob_trending_down"] = 0.0
```

Setting only `hmm_regime_prob = 0.0` is sufficient for the gate. Zeroing all three prob fields is cleaner for the audit trail. The planner should zero all four probability fields during warm-up to prevent downstream consumers from acting on misleading individual-state probabilities.

## Common Pitfalls

### Pitfall 1: SMCContext extra="forbid" will reject new fields without schema declaration
**What goes wrong:** Adding `hmm_n_dims` to `_build_output()` without adding it to `SMCContext` causes a `ValidationError` in the feature pipeline at runtime.
**How to avoid:** Always update `schemas.py` first (schema-first pattern), then update plugin.

### Pitfall 2: outputs frozenset missing new field names
**What goes wrong:** `HMMRegimePlugin.outputs` is a frozenset declared at class level. If `hmm_n_dims` and `hmm_warmed_up` are not added, the plugin contract is technically inaccurate. While `validate_tier()` doesn't enforce outputs, tooling that inspects plugin metadata will show stale information.
**How to avoid:** Update `outputs` frozenset alongside `_build_output()`.

### Pitfall 3: Warm-up tracking resets when compute_next() falls back to compute_full()
**What goes wrong:** `compute_next()` calls `compute_full()` when state is uninitialized (line 148). Each `compute_full()` call resets `_state`, including the warm-up counter. This is correct behavior — but the test must validate that after a full-reset-then-incremental sequence, the warm-up flag correctly starts False and becomes True after enough bars.
**How to avoid:** Test `compute_next()` immediately after `compute_full()` to verify warm-up=False on the first incremental bar (since `compute_full()` just reset state).

Wait — actually `compute_full()` processes ALL bars in the df and returns the final state. After processing 200 bars, `bars_processed=200 >= min_lookback=20`, so `warmed_up=True`. The warm-up=False case only appears in the first ~20 bars of `compute_full()` processing. The `_build_output()` result reflects the FINAL state after all bars are processed — so `warmed_up` in the output will be True if the df has >= min_lookback bars. The per-bar suppression only matters live in `compute_next()`.

**Correction:** The warm-up suppression should affect the output only when the returned state has `bars_processed < min_lookback`. Since `compute_full()` processes all bars in sequence, the returned output always reflects the final bar's state. If the df has 200 bars, `bars_processed=200`, `warmed_up=True`. The warm-up problem applies to the incremental path (`compute_next()`), specifically on the first incremental bars after service restart where the seed dataset may have fewer bars than `min_lookback * 2`.

**Revised understanding:** `compute_full()` is called once at startup with the full history (200 bars). It resets state, then processes all 200 bars. After 200 bars, `bars_processed=200`, `warmed_up=True`. The output returned is for the LAST bar — so `compute_full()` output will have `warmed_up=True` as long as the history has > min_lookback bars.

The warm-up problem is real in two narrower cases:
1. `compute_full()` called with fewer than `min_lookback` bars of history (returns `{}` — already guarded at line 110)
2. A sequence of `compute_full()` calls where each call resets state and the loop in `compute_full()` processes bars 0..N. If `N >= min_lookback`, final output has `warmed_up=True`. If `N < min_lookback` (and >= vol_window), the final output has `warmed_up=False` — but this case is guarded by the `len(df) < self.min_lookback` check at line 110-111 which returns `{}`.

**Conclusion:** The warm-up guard at line 110-111 (`len(df) < min_lookback → return {}`) already prevents returning output when history is too short. The residual warm-up problem is in `compute_next()` when called immediately after a fresh `compute_full()` with exactly min_lookback bars. The `bars_processed` counter will be `min_lookback` after `compute_full()`, so `warmed_up=True` immediately — which means the first `compute_next()` call returns `warmed_up=True` even though it just saw one new bar.

**The real case the spec targets:** Service restart after a period of no data, where `compute_full()` is called but the return buffer and alpha are fresh from `_reset_state()`. The last bar of `compute_full()` correctly shows the converged state. The problem is subtler: early bars within a single `compute_full()` call influence the final state. This is the statistical convergence concern, not a per-output-event issue.

The spec's solution (emit `hmm_regime_prob=0.0` when `warmed_up=False`) is most cleanly applicable to `compute_next()` after state resets. For `compute_full()`, the output represents the converged final state and should be trustworthy if the df has sufficient history.

**Planner note:** Track `bars_processed` in `_state`. In `_build_output()`, set `hmm_warmed_up = bars_processed >= min_lookback`. In `compute_full()`, after the loop, `bars_processed` will equal `len(returns)`. If `len(returns) >= min_lookback` (which is guaranteed by the guard), `warmed_up=True` for `compute_full()` output. For `compute_next()`, each call increments `bars_processed` by 1. The first few `compute_next()` calls after a fresh `compute_full()` that processed exactly min_lookback bars will have `warmed_up=True` (since `bars_processed=min_lookback`). The warm-up=False case only arises on `compute_next()` if it falls back to `compute_full()` with a short df — which is already guarded. **This means the spec's warm-up suppression may be a no-op in normal operation.** The value is in edge cases: fresh service start with exactly min_lookback bars seeded, or a symbol with sparse history.

The feature is still correct to implement for defense-in-depth and observability — but the planner should not expect it to suppress many real signals in steady-state operation.

### Pitfall 4: Test for 2D fallback warning must mock structlog

### New _build_output() with hmm_n_dims and hmm_warmed_up
```python
def _build_output(self) -> dict[str, Any]:
    alpha = self._state["alpha"]
    regime = int(np.argmax(alpha))
    bars_processed = self._state.get("bars_processed", 0)
    warmed_up = bars_processed >= self.min_lookback
    regime_prob = round(float(alpha[regime]), 6)

    output = {
        "hmm_regime": float(regime),
        "hmm_regime_prob": regime_prob if warmed_up else 0.0,
        "hmm_prob_ranging": round(float(alpha[0]), 6) if warmed_up else 0.0,
        "hmm_prob_trending_up": round(float(alpha[1]), 6) if warmed_up else 0.0,
        "hmm_prob_trending_down": round(float(alpha[2]), 6) if warmed_up else 0.0,
        "hmm_regime_duration": float(self._state["regime_duration"]),
        "hmm_n_dims": self._state.get("n_dims", 2),
        "hmm_warmed_up": warmed_up,
    }
    return output
```

Note: `n_dims` must be stored in `_state` during `compute_full()`/`compute_next()` so `_build_output()` can access it.

## Open Questions

1. **bars_processed vs regime_duration for warm-up detection**
   - Spec says `regime_duration >= min_lookback` — implies warm-up ends when current regime has been stable for 20 bars
   - Counter-proposal: use dedicated `bars_processed` counter — warm-up ends after 20 bars regardless of regime stability
   - Recommendation: use `bars_processed` (more deterministic, no edge case with choppy regimes)
   - The planner should pick one and be explicit in PLAN.md

2. **Should hmm_regime_prob=0.0 zero ALL three individual prob fields too?**
   - The gate only checks `hmm_regime_prob`, not the individual `hmm_prob_*` fields
