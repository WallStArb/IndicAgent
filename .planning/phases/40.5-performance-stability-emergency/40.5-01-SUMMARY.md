## Decisions Made

- Used `DROP INDEX IF EXISTS` before re-creating indexes after the rename. PostgreSQL index names are schema-scoped: when `ALTER TABLE ... RENAME` is run, the indexes follow the table but retain their names, blocking the subsequent `CREATE INDEX`. Discovered on first migration attempt (ROLLBACK), fixed in migration revision.
- Used `DROP TABLE market_data_ohlcv_old CASCADE` instead of plain DROP. TimescaleDB creates internal `_partial_view` and `_direct_view` objects that depend on each hypertable, requiring CASCADE to clean up fully.
- 7-day chunk interval produces 21 chunks for ~2 years of data (vs 365 as estimated in RESEARCH.md — actual data spans less than a full year per the ~48 chunk estimate in the plan).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] DROP INDEX before re-CREATE after table rename**
- **Found during:** Task 1 (applying migration)
- **Issue:** After `ALTER TABLE market_data_ohlcv RENAME TO market_data_ohlcv_old`, PostgreSQL preserved the index names (idx_ohlcv_symbol_tf_time, idx_ohlcv_symbol_trgm, uq_market_data_ohlcv_ts_symbol_tf) on the renamed table. The subsequent `CREATE INDEX idx_ohlcv_symbol_tf_time ON market_data_ohlcv` failed with "relation already exists", rolling back the entire transaction.
- **Fix:** Added `DROP INDEX IF EXISTS` for all three index names before the `CREATE INDEX` statements in the migration. The plan SQL block did not include this step.
- **Files modified:** production/migrations/045_ohlcv_time_only_rebuild.sql
- **Verification:** Migration re-applied successfully with COMMIT; 334,805 rows inserted
- **Committed in:** 78d5109 (Task 1 commit)
