# Phase 40.5: Performance & Stability Emergency - Research

**Researched:** 2026-03-20
**Domain:** Python asyncio performance, TimescaleDB hypertable partitioning, signal lifecycle indexing
**Confidence:** HIGH

## Summary

Phase 40.5 targets six concrete production bottlenecks. Two are causing active pain (OHLCV 4-5s
query timeouts, 328K stale pending signals creating O(N) per-bar scans). The other four are
structural hazards that will compound when Phase 41 adds more computation load. All six
have clear, verified fix patterns with no exploratory work required.

The most urgent issue found in research — beyond what the roadmap describes — is that
`signal_ledger` has 328,079 pending/regime_suppressed signals without `exit_at` (up to 15K per
symbol). These have no exit because `signal_lifecycle_service._SELECT_ACTIVE_BY_SYMBOL_SQL`
queries them all on every bar, and they can never expire since the service only calls
`evaluate_signal()` for signals whose `timeframe` matches the incoming bar. This is the actual
O(N) problem: 15K signals per symbol, queried from DB per bar, then looped in Python.

**Important REQUIREMENTS.md vs ROADMAP discrepancy**: `REQUIREMENTS.md` has PERF-01 through
PERF-06 mapped differently from the ROADMAP description. The ROADMAP success criteria are the
authoritative spec. The planner should map tasks to ROADMAP success criteria, not REQUIREMENTS.md
IDs directly.

**Primary recommendation:** Fix the O(N) active-signal problem (PERF-04 by ROADMAP) first —
it is the worst live bottleneck. The OHLCV rebuild (PERF-01 by ROADMAP) requires a maintenance
window and should run second. Everything else is a single-service change with no downtime.

### PERF-01: OHLCV Hypertable Rebuild

**Current state (verified):**
- `market_data_ohlcv` has 2 dimensions: `Space` on `symbol`, `Time` on `timestamp` (1-day interval)
- 831 chunks (space partitioning multiplies time chunks by number of distinct symbols)
- 334,805 rows, 137MB total
- The table is backfill-only — live data never touches it (confirmed in CLAUDE.md)
- Unique constraint: `(timestamp, symbol, timeframe)`
- Existing indexes: `idx_ohlcv_symbol_tf_time` btree (symbol, timeframe, timestamp DESC), `uq_market_data_ohlcv_ts_symbol_tf` UNIQUE, `idx_ohlcv_symbol_trgm` gin

**Target state:**
- Time-only hypertable, 7-day chunk interval → ~365 chunks for 7 years of data
- Same schema, same indexes, same constraints

**Rebuild procedure (no live data at risk):**

```sql
-- Step 1: Rename old table
ALTER TABLE market_data_ohlcv RENAME TO market_data_ohlcv_old;

-- Step 2: Create new time-only hypertable
CREATE TABLE market_data_ohlcv (
  timestamp timestamptz NOT NULL,
  symbol text NOT NULL,
  timeframe text NOT NULL,
  open double precision NOT NULL,
  high double precision NOT NULL,
  low double precision NOT NULL,
  close double precision NOT NULL,
  volume bigint NOT NULL,
  source text,
  UNIQUE (timestamp, symbol, timeframe)
);

SELECT create_hypertable('market_data_ohlcv', 'timestamp',
  chunk_time_interval => INTERVAL '7 days',
  if_not_exists => TRUE);

-- Step 3: Recreate indexes
CREATE INDEX idx_ohlcv_symbol_tf_time ON market_data_ohlcv(symbol, timeframe, timestamp DESC);
CREATE INDEX idx_ohlcv_symbol_trgm ON market_data_ohlcv USING gin(symbol gin_trgm_ops);

-- Step 4: Backfill from old table
INSERT INTO market_data_ohlcv SELECT * FROM market_data_ohlcv_old;

-- Step 5: Verify row count matches, then drop old table
-- SELECT count(*) FROM market_data_ohlcv_old;
-- SELECT count(*) FROM market_data_ohlcv;
-- DROP TABLE market_data_ohlcv_old;
```

**TimescaleDB gotchas:**
- Apply with `docker cp file.sql timescaledb:/tmp/file.sql && docker exec timescaledb psql -U postgres -d indicagent -f /tmp/file.sql` (heredoc via stdin does NOT work)
- Compression policy must be re-added after recreate: `ALTER TABLE market_data_ohlcv SET (timescaledb.compress=true, timescaledb.compress_segmentby='symbol,timeframe', timescaledb.compress_orderby='timestamp ASC')`
- `pg_trgm` extension must be present for gin_trgm_ops index (already enabled in production)
- INSERT of 334,805 rows into time-only hypertable will be fast (all within hot SSD)

### PERF-02: Feature Writer Lag Investigation

**Current state (verified from code):**
`feature_writer_service` uses a single `KafkaConsumerClient` subscribed to 3-5 topics:
- `development.intelligence` (I1-I6 IntelligenceEvents)
- `development.intelligence.i7`
- `development.intelligence.i8`
- optionally `development.system.events` (roll monitor)
- optionally `development.cross_asset`

The consumer uses `async for kafka_topic, key, payload in self._kafka_consumer.messages()` — a single unified async generator. There are no sequential `xreadgroup` calls. The 920ms lag metric from the roadmap likely came from an older Redis-stream-based implementation.

**Actual bottleneck candidates:**
1. Per-message DB writes for i7 and i8 UPSERTs (not buffered like I1-I6)
2. The I1-I6 buffer only flushes on `BATCH_SIZE=50` or `FLUSH_INTERVAL_SECS=5.0` — 5-second hold

**Fix:** Buffer i7 and i8 UPSERT messages and flush them with the main batch (or separately at flush time), instead of writing per-message. If the lag is real, instrument the actual path first.

### PERF-03: Plugin Pipeline Thread Pool

**Current state (verified):**
`market_analysis_service._run_analysis_pipeline()` runs all I2-I6 plugins sequentially in an `async def` function using `async with self._get_state_lock(state_key)` per plugin. The actual plugin computation (`p.compute_full(frames)`) is synchronous CPU/pandas work running in the event loop.

**Problem:** On 1m bar close, multiple (symbol, tf) bars arrive within milliseconds. Each triggers `_run_analysis_pipeline()` which blocks the event loop for the duration of CPU work.

**Fix pattern — asyncio.to_thread():**

```python
import threading

# One lock per plugin instance to guard _state access
_plugin_locks: dict[str, threading.Lock] = {}

def _get_plugin_lock(plugin_name: str) -> threading.Lock:
    if plugin_name not in _plugin_locks:
        _plugin_locks[plugin_name] = threading.Lock()
    return _plugin_locks[plugin_name]

# In _run_tier():
async def _run_plugin_threaded(pname: str, frames: dict, state_key: tuple) -> dict:
    lock = _get_plugin_lock(pname)
    def _sync_run():
        with lock:
            p = self._plugin_cache[pname]
            p._state = self._plugin_states.setdefault(state_key, {})
            out = p.compute_full(frames)
            self._plugin_states[state_key] = p._state
            return out
    return await asyncio.to_thread(_sync_run)
```

**Critical constraints:**
- Plugins share `_state` keyed by `(plugin_name, symbol, timeframe)` — the existing `asyncio.Lock` per state_key is an async lock, safe for the current pattern but not for threads
- Replace per-state-key `asyncio.Lock` with `threading.Lock` in the to_thread path
- `frames` dict is passed by reference — if multiple symbol/tf combos run concurrently, each must get its own `frames` copy to prevent cross-contamination
- Plugin state is already per `(pname, symbol, timeframe)` — parallelism is safe at that granularity

**Simpler first step:** Just `asyncio.to_thread(p.compute_full, frames)` without parallelism within a bar. This unblocks the event loop for Kafka consumer to receive the next message while computation runs.

### PERF-04: Lifecycle O(1) Active Signal Index

**Current state (verified — most critical):**
`signal_lifecycle_service._process_single_bar()` calls `get_active_signals(self.db_manager, symbol=symbol)` on every bar message. The DB query returns ALL pending/active/regime_suppressed signals for a symbol.

**Verified scale:** 328,079 total pending signals without exit_at. Per-symbol counts:
- RTYH6: 15,134 — YMH6: 14,928 — ESH6: 14,140 — NQH6: 13,999 — CLJ6: 13,959

These signals exist because old signals were never expired (likely TTL-expired signals that `signal_lifecycle_service` never processed because it only runs evaluate_signal for signals matching the current bar's timeframe, but the pending signal count grows unboundedly).

**Root cause:** `_evaluate_signals_against_bar()` filters `relevant = [s for s in (all_active or []) if s.get("timeframe") == timeframe]` but `get_active_signals()` fetches ALL timeframes. With 14K pending signals per symbol, each bar triggers: 1 DB query returning 14K rows + Python O(14K) list scan.

**Fix:** Build an in-memory index at service startup and maintain it incrementally:

```python
# Service init
self._active_index: dict[tuple[str, str], list[dict]] = defaultdict(list)
# key: (symbol, timeframe) -> list of active signal dicts

# At startup: seed from DB
async def _seed_active_index(self):
    all_active = await get_active_signals(self.db_manager)
    for sig in all_active:
        key = (sig["symbol"], sig["timeframe"])
        self._active_index[key].append(sig)

# Per-bar: O(1) lookup
def _get_active_for_bar(self, symbol: str, timeframe: str) -> list[dict]:
    return self._active_index.get((symbol, timeframe), [])

# On signal exit: remove from index
def _remove_from_index(self, signal_id: str, symbol: str, timeframe: str):
    key = (symbol, timeframe)
    self._active_index[key] = [
        s for s in self._active_index.get(key, [])
        if str(s["signal_id"]) != signal_id
    ]
```

**Chandelier write guard (per ROADMAP):**
Currently `_UPDATE_CHANDELIER_SQL` is called on every active bar. Add a guard:

```python
# In _chandelier_state dict, add 'last_written_stop' key
# Only write to DB if abs(new_stop - last_written_stop) / last_written_stop >= 0.0001
# (0.01% threshold)
```

**Also needed:** A cleanup migration to expire the 328K stale pending signals that can never be processed (no bar data arrives for their original symbols after contract rolls). This is not blocking the O(1) optimization but should run as part of the migration.

### PERF-05: Calibration Ndarray Pre-Alloc

**Current state (verified):**

In `signal_generator_service._load_calibration_curves_from_db()`:
```python
new_cache[key] = (list(row["breakpoints"]), list(row["values"]))
```

These are stored as Python lists. In `_build_all_ranked()`:
```python
breakpoints, values = curve  # Python lists
sig["calibrated_confidence"] = round(float(np.interp(raw_conf, breakpoints, values)), 4)
```

`np.interp` called with Python lists converts them to ndarray on every call. With 36 I7 plugins × N symbols × 4 timeframes, this is thousands of allocations per bar burst.

**Fix:** Pre-convert at load time:

```python
# In _load_calibration_curves_from_db():
import numpy as np
new_cache[key] = (
    np.array(row["breakpoints"], dtype=np.float64),
    np.array(row["values"], dtype=np.float64),
)
```

Type annotation change: `dict[tuple[str, str], tuple[np.ndarray, np.ndarray]]`.
No change needed in `_build_all_ranked()` — `np.interp` accepts ndarray transparently.

### PERF-06: Refresh Loop Helper Coroutine

**Current state (verified — 5 loops in signal_generator_service):**

All 5 refresh loops share identical boilerplate:
```python
async def _xxx_refresh_loop(self) -> None:
    _REFRESH_INTERVAL = N
    while self.running and not self.shutdown_requested:
        try:
            try:
                await asyncio.wait_for(self.shutdown_event.wait(), timeout=_REFRESH_INTERVAL)
                break
            except TimeoutError:
                pass
            if self.shutdown_requested:
                break
            await self._load_xxx_from_db()
        except asyncio.CancelledError:
            break
        except Exception as e:
            self.logger.error("xxx refresh loop error", error=str(e))
```

The 5 loops are: `_drift_penalties_refresh_loop` (4h), `_perf_weights_refresh_loop` (1h),
`_cis_weights_refresh_loop` (30m), `_calibration_curves_refresh_loop` (30m),
`_tod_multipliers_refresh_loop` (4h).

**Fix — shared helper:**

```python
async def _run_refresh_loop(
    self,
    name: str,
    interval_s: int,
    fn: Callable[[], Awaitable[None]],
    backoff_s: int = 30,
) -> None:
    """Standardised refresh loop: wait interval_s, call fn, repeat until shutdown."""
    while self.running and not self.shutdown_requested:
        try:
            try:
                await asyncio.wait_for(self.shutdown_event.wait(), timeout=interval_s)
                break  # shutdown_event set
            except TimeoutError:
                pass
            if self.shutdown_requested:
                break
            await fn()
        except asyncio.CancelledError:
            break
        except Exception as exc:
            self.logger.error(f"{name} refresh loop error", error=str(exc))
            await asyncio.sleep(backoff_s)
```

Usage:
```python
asyncio.create_task(self._run_refresh_loop("drift_penalties", 14400, self._refresh_drift_penalties_from_db))
asyncio.create_task(self._run_refresh_loop("perf_weights", 3600, self._load_perf_weights))
asyncio.create_task(self._run_refresh_loop("cis_weights", 1800, self._load_cis_weights_from_db))
asyncio.create_task(self._run_refresh_loop("calibration_curves", 1800, self._load_calibration_curves_from_db))
asyncio.create_task(self._run_refresh_loop("tod_multipliers", 14400, self._load_tod_multipliers_from_db))
```

## Common Pitfalls

### Pitfall 1: TimescaleDB Migration via stdin
**What goes wrong:** `docker exec timescaledb psql ... -f /dev/stdin <<'EOF'` does not work.
**How to avoid:** Always `docker cp file.sql timescaledb:/tmp/file.sql` then `docker exec timescaledb psql -U postgres -d indicagent -f /tmp/file.sql`.

### Pitfall 2: Plugin State and asyncio.to_thread()
**What goes wrong:** `asyncio.Lock` is not thread-safe — it only prevents concurrent awaits in the event loop, not concurrent thread execution. If `to_thread` runs plugin A while the event loop also processes plugin A for a different (symbol, tf), `_state` will be corrupted.
**How to avoid:** Replace asyncio.Lock with threading.Lock for any state accessed from `to_thread` callables. Per-(plugin, symbol, tf) granularity avoids contention between different symbols.

### Pitfall 3: signal_ledger Stale Pending Signals
**What goes wrong:** The 328K pending signals without exit_at are not just a legacy artifact — new signals accumulate at the same rate unless explicitly expired. The O(1) index fix reduces query cost but the service still iterates the in-memory list.
**How to avoid:** Add a migration to expire stale signals (those created before the current front-month contract, or older than max(TF_TTL_BARS) × TF interval). Add this as part of PERF-04 plan.

### Pitfall 4: OHLCV Table Used by Backfill Script
**What goes wrong:** `historical_backfill.py` writes to `market_data_ohlcv` via `ON CONFLICT DO NOTHING`. If the table is renamed mid-backfill, the script fails silently.
**How to avoid:** Confirm no services are running backfill during the maintenance window. The table is backfill-only (confirmed), so production services do not write to it live.

### Pitfall 5: Calibration Curve Type Annotation
**What goes wrong:** The type annotation for `_calibration_curves` in `signal_generator_service` and the `calibration_curves` parameter in `aggregator._build_all_ranked()` currently declares `tuple[list[float], list[float]]`. Changing to `np.ndarray` without updating the annotation causes mypy/IDE confusion.
**How to avoid:** Update both the service attribute annotation and the function signature annotation to `tuple[np.ndarray, np.ndarray]`.

```sql
-- Expire pending signals older than max TTL per timeframe.

UPDATE signal_ledger

    exit_at = NOW(),

  AND exit_at IS NULL
  AND timestamp < NOW() - INTERVAL '48 hours';
```

## Open Questions

1. **Is feature_writer lag still 920ms?**
   - What we know: The ROADMAP says 920ms. Code shows single Kafka consumer. Redis era code may have had 3 separate polls.
   - What's unclear: Whether the lag was measured after the Kafka migration or before.
   - Recommendation: Instrument with `time.monotonic()` at consumer receipt and DB flush. If lag < 50ms already, PERF-02 may be a no-op. If lag is real, the per-message i7/i8 UPSERTs (unbuffered) are the likely culprit.

2. **Signal ledger stale pending signals — should they be cleaned up?**
   - What we know: 328K pending signals, ~14K per active symbol, with no exit_at. Per-symbol query returns all 14K. These accumulate from contract rolls (old symbol pending signals never expire).
   - What's unclear: Whether `signal_lifecycle_service` ever receives bars for these old symbols after a roll, which would allow natural expiry.
   - Recommendation: Add a stale signal cleanup step to PERF-04 plan. Expire signals where `timestamp < NOW() - 48 hours` and `status = 'pending'` and `exit_at IS NULL`. This is a prerequisite for the O(1) index to be effective.

3. **threading.Lock granularity for plugin state**
   - What we know: Per-(pname, symbol, tf) granularity is the current async lock scope. Threading.Lock at same granularity avoids all contention.
   - What's unclear: Whether the current production workload creates enough concurrent (symbol, tf) bars to benefit from parallel plugin execution, vs. just unblocking the event loop.
   - Recommendation: Start with simple `asyncio.to_thread()` without parallelism (one bar at a time). Measure first.
