### Why `registry_dual_write_verified` and NOT `decay_cells_flagged`

An earlier draft of this gate used `decay_cells_flagged` as the "a lifecycle-hook run actually
happened" signal. That was wrong, and the cross-AI review that flagged it was right: verified
against the code this session, `decay_cells_flagged` cannot carry that meaning.

  (i) It is emitted at the tail of `_apply_feature_transitions` (`services/ic_engine.py:3988-3997`),
      and `_run_lifecycle_hook` calls that function ONLY under `if not any_hold`
      (`services/ic_engine.py:4268`). A regime-shift hold run completes the entire hook — flushes
      the per-stratum guard facts, reaches the single commit point at ~4300, emits the staleness
      gauge — while emitting ZERO `decay_cells_flagged` rows. "The hook ran" and "a
      `decay_cells_flagged` row exists" are therefore not the same proposition, and gating on the
      second while meaning the first is exactly how a one-way door gets opened on no evidence.
  (ii) It predates Plan 06 and is emitted identically whether or not any dual write exists, so
      its presence says nothing about whether the dual-write comparison ran.

`registry_dual_write_verified` is emitted by code Plan 06 adds INSIDE `_apply_feature_transitions`,
after the per-feature dual-write loop and before the conditional divergence raise, unconditionally
on BOTH the divergence and the clean path, with `commit=True`. The metric name exists nowhere in
the codebase or the database before Plan 06, so a row bearing it is positive proof that the
dual-write comparison block executed to completion. Nothing else can produce one.

It inherits the same hold-path conditionality — a hold-only shadow period emits none — and that is
CORRECT rather than a residual gap: on a hold run the dual write genuinely does nothing, so there
is genuinely no evidence, and the gate must refuse.
