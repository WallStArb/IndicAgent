<threat_model>
ASVS L1 considerations:
- **V1.4 Trust boundary**: Migration runs as DB superuser (postgres). No user input — pure DDL. FK constraint on signal_id provides referential integrity.
- **V5 Input validation**: No user input in this plan; all fields are server-generated UUIDs/timestamps. JSONB columns accept arbitrary structure — but the producer (signal_writer_agent.py) is server-side trusted code, not external input.
- **V8 Data protection**: New tables inherit existing DB encryption-at-rest. No PII added.
- **V13 API/Web service**: No API surface added; tables are internal.
- **Threat: Orphaned enrichment rows** — if signal_ledger row is deleted, signal_ai_enrichment row must cascade or block. Mitigation: standard FK behavior (RESTRICT by default — explicit decision: do NOT add ON DELETE CASCADE; preserve audit trail).
- **Threat: NULL features_snapshot on legacy rows** — migration 083 truncated signal_ledger 2026-05-08; new rows from signal_writer_agent.py forward will populate it. Migration does NOT backfill; reads must handle NULL.
</threat_model>
