Implement AI-SEP-01 (TODO-018): migrate two AI writer services off the quant tables and onto the new AI-owned enrichment tables created in Plan 01. SwarmLedgerWriterAgent moves from UPDATE signal_ledger to UPSERT signal_ai_enrichment. LlmWriterService moves from UPDATE intelligence_features to UPSERT intelligence_ai_enrichment.

Purpose: Quant tables become immutable after the quant writer's INSERT — Jim Simons principle: clean data provenance. AI annotations live in separate tables joined at read time.

Output: Both writer services updated; no behavioral change visible at the swarm/LLM event boundary; downstream readers will gain LEFT JOINs in a future phase (not in scope here).
</objective>

<threat_model>
ASVS L1 considerations:
- **V1.4 Trust boundary**: Writers consume Kafka topics produced by trusted internal services (AlphaSwarmComputeAgent, LlmWriterService upstream). No external input.
- **V5 Input validation**: Payloads are already validated by upstream agents; this plan just changes the persistence target. signal_id is bound as ::uuid (type-validated at DB level).
- **V7 Error handling**: FK violation race (enrichment INSERT before signal_ledger INSERT) handled by existing _RETRY_BACKOFF_S retry loop. Must preserve.
- **V8 Data protection**: New tables inherit DB encryption-at-rest. No PII added.
- **V10 Communications**: All DB connections via existing asyncpg pool (TLS handled at infra layer).
- **Threat: Race condition (enrichment arrives before quant row exists)** — preserved by retry/backoff loop already in SwarmLedgerWriterAgent. Mitigation: keep _RETRY_BACKOFF_S = (0.1, 0.5, 2, 5) unchanged.
- **Threat: Stale i8 enrichment for missing bar rows** — for intelligence_ai_enrichment, there is no FK to intelligence_features (PK is (ts, symbol, tf) only), so phantom rows are now allowed by design. This is the intentional change vs old constraint of UPDATE-only.
- **Threat: Downstream auditors silently pass on NULLs** — after this migration, swarm_multiplier/adjusted_confidence/swarm_agent_count on signal_ledger remain as legacy nullable columns and will be NULL for new signals. Any auditor reading them from signal_ledger (rather than LEFT JOIN signal_ai_enrichment) will see NULLs. Mitigation: Plan 04 Task 3 includes an auditor cross-check that greps signal_auditor_agent.py and parity_auditor_agent.py for these column names and classifies each reference; any unsafe read becomes a follow-up TODO. Recorded as a key_link in this plan for traceability.
</threat_model>
