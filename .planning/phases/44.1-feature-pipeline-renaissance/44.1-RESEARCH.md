## Summary

Phase 44.1 consolidates three services (indicator_service, market_analysis_service, timeframes_builder_service) into a single FeaturePipelineService. The spec is fully locked by CONTEXT.md — no architectural decisions remain open. Research confirms all patterns to replicate are directly readable in the existing codebase.

The three critical correctness requirements all have direct implementations to copy: (1) the `asyncio.to_thread` + threading.Lock pattern for CPU-bound plugins lives at market_analysis_service.py lines 246–260; (2) the `smc_trend_direction` rename lives at lines 293–295; (3) the `_prev_i1_features` injection lives at market_analysis_service line 129 and surrounding code. These must be copied exactly, not reimplemented.

The TWS daemon `development.market.bars` topic currently publishes string-typed dicts (all OHLCV values as strings). The migration to typed BarMessage is a one-way schema change — all consumers of that topic must be updated in lockstep with the TWS daemon publish change. The FeaturePipelineService is the only consuming service in the hot path after cutover.

**Primary recommendation:** Build shared modules first (BarHistory, BarAccumulator, BarMessage, IntelligenceEvent extension), write unit tests, then build FeaturePipelineService as a composition of those tested modules. Simplify SignalGeneratorService last after FeaturePipelineService is validated in production.

### Pattern 1: asyncio.to_thread + threading.Lock (CPU-bound plugins)

Exact pattern from market_analysis_service.py lines 246–260. MUST be replicated verbatim for GARCH and HMM plugins.

```python
# Source: services/market_analysis_service.py lines 246–260
def _get_state_lock(self, key: tuple[str, str, str]) -> threading.Lock:
    """Get or create a threading lock for given state key."""
    return self._plugin_states_locks.setdefault(key, threading.Lock())

# Inside _run_tier():
state_key = (pname, symbol, timeframe)
lock = self._get_state_lock(state_key)

def _sync_compute(_p=p, _lock=lock, _key=state_key, _frames=frames):
    with _lock:
        _p._state = self._plugin_states.setdefault(_key, {})
        _out = _p.compute_full(_frames)
        # CRITICAL: Write plugin _state back after compute_full().
        # GARCH/HMM fully reassign _state — omitting this causes stale state.
        self._plugin_states[_key] = _p._state
        return _out

out = await asyncio.to_thread(_sync_compute)
```

**Why the write-back is critical:** GARCH and HMM plugins fully reassign `_state` during `compute_full()`. Without writing `_p._state` back to `self._plugin_states[_key]`, every subsequent bar for that (plugin, symbol, tf) starts with an empty state dict. This silently produces wrong indicator values.

### Pattern 7: startup seed ROW_NUMBER() window query

D-27 requires a single window query instead of 61×5 individual queries. The signal_generator_service `_seed_bar_history_from_db` uses 61×5 separate queries — this is the anti-pattern to avoid.

WITH ranked AS (
    SELECT *,
           ROW_NUMBER() OVER (PARTITION BY symbol, tf ORDER BY ts DESC) AS rn
    FROM intelligence_features
    WHERE symbol = ANY($1)
      AND ts > NOW() - INTERVAL '7 days'

WHERE rn <= 200
ORDER BY symbol, tf, ts ASC;

### Anti-Patterns to Avoid

- **Multiple DB queries at startup per (symbol, tf):** signal_generator_service._seed_bar_history_from_db() runs asyncio.gather on 61×5 individual queries. FeaturePipelineService must use the single ROW_NUMBER() window query (D-27).
- **String coercions in bar processing:** The existing `float(payload.get("open", 0))` pattern throughout all three services is eliminated by the typed BarMessage schema. No `float(bar["open"])` in feature_pipeline_service.py.
- **Importing from services/ in other services:** market_analysis_service.py line 33 `from services.indicator_service import parse_indicators_message` — this cross-service import is deleted. FeaturePipelineService owns all I1–I6 computation internally.
- **Global state in shared modules:** BarHistory and BarAccumulator must be pure classes with no module-level state. `_pattern_reliability_cache` at module level in signal_generator_service is the anti-pattern (acceptable there as a TTL cache, but not acceptable in shared core modules).
- **asyncio.Lock for CPU-bound plugins in threads:** Use `threading.Lock`, not `asyncio.Lock`. `asyncio.Lock` is not thread-safe and will deadlock inside `asyncio.to_thread`.

## Common Pitfalls

### Pitfall 1: asyncio.Lock vs threading.Lock for CPU-bound plugins
**What goes wrong:** Using `asyncio.Lock` inside `asyncio.to_thread()` causes a deadlock or RuntimeError because asyncio locks require the event loop and are not thread-safe.
**Why it happens:** Developers confuse "asyncio service" with "everything uses asyncio primitives."
**How to avoid:** `_plugin_states_locks` must be a dict of `threading.Lock` (not `asyncio.Lock`). The existing market_analysis_service.py uses `threading.Lock` (line 117: `_plugin_states_locks: dict[tuple[str, str, str], threading.Lock]`).
**Warning signs:** Import of `threading` is missing from the new service file.

### Pitfall 2: Plugin _state write-back omitted
**What goes wrong:** GARCH and HMM plugins produce stale results on every bar after the first because their `_state` is re-initialized to `{}` on every call.
**Why it happens:** `compute_full()` mutates `p._state` in place, but `p._state` is a reference to the dict stored in `_plugin_states[key]`. Some plugins fully reassign `p._state = new_dict` — breaking the reference.
**How to avoid:** Always include `self._plugin_states[state_key] = p._state` after `compute_full()`, inside the lock.
**Warning signs:** GARCH vol_regime always returns the same default value; HMM regime_state never updates.

### Pitfall 3: smc_trend_direction rename omitted
**What goes wrong:** I3Structure's `trend_direction` is silently overwritten by SMC's `trend_direction` in the flat features dict. I4–I6 plugins reading `features["trend_direction"]` get the SMC value instead of the I3 structure value. I7 plugins reading the IntelligenceEvent get wrong trend_direction data.
**Why it happens:** Both I3 and SMC output a field named `trend_direction` — the rename is the only disambiguator.
**How to avoid:** Copy lines 293–295 exactly. Run the regression test: feed a 200-bar fixture and assert `i3_result["trend_direction"] != smc_result.get("smc_trend_direction", sentinel)`.
**Warning signs:** I7 trend-following setups fire incorrectly; `smc_trend_direction` field missing from IntelligenceEvent.smc.

### Pitfall 4: _prev_i1_features not populated on first bar
**What goes wrong:** I2 plugins (MACDEvents, RSIEvents) receive empty `prev_features` on all bars if the injection is placed wrong in the execution order.
**Why it happens:** The injection must happen BEFORE I1 runs, and the store must happen AFTER I1 runs — ordering is critical.
**How to avoid:** Verify that `frames["prev_features"]` is set before `_run_tier(TIER_I1, ...)`, and `self._prev_i1_features[key] = i1_result` is set after. On the first bar per (symbol, tf), `prev_features` is `{}` which I2 plugins handle correctly (returns empty crossover events).
**Warning signs:** MACDEvents never fires; RSIEvents has zero crossovers in integration test.

### Pitfall 5: BarAccumulator not seeded for partial windows on startup
**What goes wrong:** If FeaturePipelineService starts 8 minutes into a 15m window, the accumulated partial bar state is lost. The first 15m bar after the service starts reflects only the post-startup 1m bars, producing a low-volume 15m bar.
**Why it happens:** The BarAccumulator is initialized empty on startup.
**How to avoid:** D-30 mandates replaying 1m bars from the development.market.bars Redpanda topic back to the last 5m window boundary (~5 minutes of messages). Use `seek_to_offset` or timestamp-based seek. The existing timeframe_builder.py `_initialize()` method has the same warmup logic (lines 241–280) — but it reads from Redis; BarAccumulator restores from Kafka topic replay instead.
**Warning signs:** First HTF bars after restart have abnormally low volume; BarAccumulator emits a bar for a window it already emitted before restart (dedup logic needed).

### Pitfall 6: TWS daemon topic publish schema mismatch
**What goes wrong:** FeaturePipelineService tries to deserialize `BarMessage.model_validate(payload)` but gets validation errors because TWS daemon still publishes string dicts.
**Why it happens:** Step 2 of the migration plan (update TWS daemon) must happen in the same cutover window as Step 1 (build FeaturePipelineService). If Step 2 is forgotten, the new service cannot consume any bars.
**How to avoid:** Include TWS daemon publish change in the same plan step as BarMessage schema creation. Test with a fixture that uses both old (string dict) and new (BarMessage) formats and confirm validation behavior.
**Warning signs:** FeaturePipelineService logs `ValidationError` on every bar; `development.intelligence` goes silent.

### Pitfall 7: IntelligenceEvent import breakage
**What goes wrong:** Adding `session_type: SessionType` to `IntelligenceEvent` requires `SessionType` to be importable from the schemas module. If `SessionType` is defined in `src/core/schemas/bar_message.py` and `src/intelligence/schemas.py` imports it, there is a cross-module import path to establish.
**Why it happens:** New module (`src/core/schemas/bar_message.py`) must exist before `src/intelligence/schemas.py` can import from it.
**How to avoid:** Create `src/core/schemas/__init__.py` and `src/core/schemas/bar_message.py` before modifying `src/intelligence/schemas.py`. Verify with `python -c "from src.intelligence.schemas import IntelligenceEvent"`.
**Warning signs:** `ImportError` at market_analysis_service.py or signal_generator_service.py startup.

### Pitfall 8: Kafka seek for BarAccumulator partial restore
**What goes wrong:** Using `auto_offset_reset="latest"` for the partial state restore consumer skips all historical messages — no bars are replayed.
**Why it happens:** A new consumer with `auto_offset_reset="latest"` starts at the current end of the topic.
**How to avoid:** Use a separate short-lived `KafkaConsumerClient` with `auto_offset_reset="earliest"` and a distinct group_id (or seek by timestamp). Consume until the current end (detected by checking message timestamps against `datetime.now(UTC) - timedelta(minutes=5)`), then discard the consumer.

### BarHistory class skeleton
```python
# src/core/bar_history.py
from collections import deque
from collections.abc import Sequence
from typing import TYPE_CHECKING
import pandas as pd
from src.core.schemas.bar_message import BarMessage

class BarHistory:
    def __init__(self, maxlen: int = 200) -> None:
        self._maxlen = maxlen
        # Keyed by "{symbol}:{tf}"
        self._data: dict[str, deque[BarMessage]] = {}

    def append(self, bar: BarMessage) -> None:
        key = f"{bar.symbol}:{bar.tf}"
        if key not in self._data:
            self._data[key] = deque(maxlen=self._maxlen)
        self._data[key].append(bar)

    def get(self, symbol: str, tf: str) -> deque[BarMessage]:
        return self._data.get(f"{symbol}:{tf}", deque())

    def to_dataframe(self, symbol: str, tf: str) -> pd.DataFrame:
        bars = self.get(symbol, tf)
        if not bars:
            return pd.DataFrame()
        return pd.DataFrame([
            {"timestamp": b.ts, "open": b.open, "high": b.high,
             "low": b.low, "close": b.close, "volume": b.volume}
            for b in bars
        ])

    def is_warm(self, symbol: str, tf: str, min_bars: int) -> bool:
        return len(self.get(symbol, tf)) >= min_bars

    def seed(self, symbol: str, tf: str, bars: list[BarMessage]) -> None:
        key = f"{symbol}:{tf}"
        self._data[key] = deque(bars[-self._maxlen:], maxlen=self._maxlen)

    def migrate_symbol(self, old_symbol: str, new_symbol: str) -> None:
        for tf in ["1m", "5m", "15m", "1h"]:
            old_key = f"{old_symbol}:{tf}"
            new_key = f"{new_symbol}:{tf}"
            if old_key in self._data:
                self._data[new_key] = self._data.pop(old_key)
```

### ROW_NUMBER() seed query (D-27)
```sql
-- Single query replaces 61×5 individual queries
WITH ranked AS (
    SELECT symbol, tf, ts, bar,
           ROW_NUMBER() OVER (PARTITION BY symbol, tf ORDER BY ts DESC) AS rn
    FROM intelligence_features
    WHERE symbol = ANY($1)
      AND ts > NOW() - INTERVAL '7 days'
)
SELECT symbol, tf, ts, bar
FROM ranked
WHERE rn <= 200
ORDER BY symbol, tf, ts ASC;
```

## Open Questions

1. **TWS daemon BarMessage schema migration scope**
   - What we know: TWS daemon currently publishes string dicts; BarMessage requires typed float/int fields; `session_type` must be set from instrument config at publish time
   - What's unclear: The exact mapping from instrument config fields to SessionType enum values — crypto uses `CRYPTO`, ETF/equity uses `RTH`/`ETH`, futures uses `RTH`/`ETH`
   - Recommendation: Read `src/config/settings.py` Instrument model during planning; map `asset_class` field to `SessionType` in TWS daemon publish path

2. **BarAccumulator session break detection**
   - What we know: D-14 requires partial bars to close at session break, not carry forward; `SessionType.CLOSED` signals market closed
   - What's unclear: The exact session boundary timestamps for each SessionType — RTH ends at 16:00 ET, ETH begins at 18:00 ET; gaps exist between sessions
   - Recommendation: Reuse `src/intelligence/context/session_context.py` which already handles ET-aware session detection (used by CVDPlugin for daily reset)

3. **Redpanda seek for BarAccumulator partial restore**
   - What we know: D-30 requires seeking to last 5m window boundary (~5 minutes of messages)
   - What's unclear: The exact KafkaConsumerClient API for seeking by timestamp — aiokafka's `seek_to_end()` / `seek()` vs timestamp-based lookup
   - Recommendation: Use `KafkaConsumerClient` with `auto_offset_reset="earliest"` and consume until messages are within 5 minutes of now, then stop; simpler than timestamp-based seek
