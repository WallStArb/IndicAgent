# Phase 49.1: Regime Gate Fix — Write All Signals to Signal Ledger

**Gathered:** 2026-03-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Remove the accidental data loss caused by coupling ledger writes to winner selection in
`signal_generator_service.py`. Write ALL ranked signals to `signal_ledger` — with
`regime_type_at_fire` label — regardless of whether any signal is regime-eligible.

**What this phase IS:**
- Decouple `signal_ledger` write from winner selection (two independent concerns, one DAG path)
- Populate `regime_type_at_fire` on every `LedgerEntry` so ML training can segment per regime
- Fix forward — new bars will have complete labeled data from deploy day onward

**What this phase IS NOT:**
- Dashboard changes (deferred — data collection only)
- Backfill of existing NULL rows (forward-only; existing NULLs are from the broken-gate period)
- Changes to winner selection logic (regime gating of which signal fires stays unchanged)
- New Kafka topics, new services, or new migrations

</domain>

<decisions>
## Implementation Decisions

### D-01 — Write-path: Unconditional, DAG-clean persist stage

**Decision:** Move the entries-building loop and DB INSERT outside of `if winner:`. The
persist stage runs whenever `all_ranked` is non-empty — unconditional. Winner selection
(Kafka publish + cooldown gate update) remains gated on `winner` being non-None.

**Renaissance rationale:** Winner selection (execution concern) and data collection (ML
training concern) are distinct modules with different invariants. Coupling them was an
accidental entanglement that caused permanent data loss. The clean DAG is:

```
Ranked signals → [always]     build entries from all_ranked → DB INSERT
              → [if eligible] select_winner → publish to signals topic
```

These are independent output paths. The persist stage has no logical dependency on whether
a winner was found. Separation of concerns, modularity, no hidden inter-stage dependencies.

**Code structure (planned):**
```python
# Stage 6a: Persist ALL ranked signals (unconditional)
entries = _build_entries(all_ranked, winner, signal_computed_at, ...)
if entries and self.db_manager:
    await insert_signals_with_features(self.db_manager.pool, entries, {})
    ledger_written = True

# Stage 6b: Winner execution (unchanged logic, just re-scoped)
if winner:
    await self._kafka_producer.publish(topic_signals(...), ...)
    self._update_gate(...)
```

**Existing LedgerEntry status field is already correct:**
- `regime_eligible=True` → `SignalStatus.PENDING`
- `regime_eligible=False` → `SignalStatus.REGIME_SUPPRESSED`
- DB CHECK constraint already permits both — no migration needed.

### D-02 — regime_type_at_fire: Semantic string labels, populated in entries loop

**Decision:** Map HMM integer to semantic string:
- `hmm_regime=0` (ranging) → `"ranging"`
- `hmm_regime=1` (trend-up) → `"trending"`
- `hmm_regime=2` (trend-down) → `"trending"`

Collapses trend direction intentionally — consistent with `_REGIME_MAP` which treats 1 and 2
identically for `regime_type="trend"` plugins. Self-documenting in SQL queries and ML
feature matrices.

**Where populated:** In the entries-building loop (or extracted helper), using `regime_data`
dict already available in scope. One mapping constant at module level:
```python
_HMM_REGIME_LABEL = {0: "ranging", 1: "trending", 2: "trending"}
```

**Guards:**
- If `regime_data is None` → `regime_type_at_fire = None` (graceful degradation, same as
  today for missing data)
- If `hmm_regime` is None or unrecognized → `regime_type_at_fire = None`

**Why not granular (trending_up / trending_down):** Adds ML segmentation buckets that hit
the N≥30 gate later. We don't yet know if up vs down trend regime produces meaningfully
different signal performance — earn the right to that granularity through data first.

### D-03 — Backfill: Forward-only fix

**Decision:** No backfill script. Existing NULL rows in `signal_ledger` are from the broken
gate period — they represent bars where ALL signals were regime-suppressed and never written.
The data cannot be recovered (it was never collected). Fix going forward: from deploy day,
every bar has complete labeled data.

**Renaissance rationale:** "Let the system run. Build the automation, then trust it." Prefer
automation over manual repair tasks. The missing data is gone — energy is better spent
ensuring future data is correct. No repair_cis_nulls.py saga repeat.

### D-04 — Quality gate: Confidence modifier only, no hard floor

**Decision:** Quality gate remains a pure confidence multiplier (Hurst × entropy × drift
penalty). No hard floor before ledger write. Every signal that makes it through raw I7
plugin compute is worth recording.

**Renaissance rationale:** "Never drop data that could contain signal." A signal with
calibrated_confidence=0.02 after quality gate is still labeled training data — it tells us
the plugin fired under noisy conditions and what the outcome was. Negative-IC signals are
as valuable as positive-IC ones for model building. Adding a floor creates a dead zone of
unknown behavior.

**Existing hard gates remain intact:**
- CIS dual-fire gate (`raw_cis > 0.28 AND filtered_cis > 0.35`) operates before plugin
  compute — this is a quality gate on composite score, not on individual signals
- Plugin `regime_type` validation at startup (hard crash on missing) stays

### D-05 — Dashboard: Deferred

Not in scope for this phase. Data collection fix only. Dashboard observability of
regime-suppressed signals is a future phase concern (can be addressed alongside Phase 51
validation framework or as a standalone todo).

### Claude's Discretion

- Extract a `_build_entries()` helper function from the inlined entries loop if the loop
  needs to be called from a location outside the current `if winner:` indentation. Claude
  decides whether to extract or just restructure the indentation.
- Whether to add a `signals_written_total` metric counter for suppressed-only bars (vs.
  reusing existing `signals_generated_total`). Renaissance says instrument everything — add it.

## Existing Code Insights

### Reusable Assets
- `_REGIME_MAP` in `aggregator.py` — defines valid hmm integer values (0, 1, 2) and their semantic meaning. Use as reference for `_HMM_REGIME_LABEL` mapping constant.
- `SignalStatus.REGIME_SUPPRESSED` enum value — already exists, already in DB CHECK constraint. Zero new DB work needed.
- `regime_data` dict — already in scope in `_aggregate()` method, contains `hmm_regime` integer needed for label.
- `all_ranked` — already built before the `if winner:` block, contains all signals with calibrated confidence, regime_eligible flags, and full LedgerEntry fields. No new computation needed.

### Established Patterns
- Pure function pipeline stages: `apply_regime_gate`, `apply_quality_gate`, `select_winner` — each in its own module. If extracting a `_build_entries()` helper, it should follow the same pattern (pure function, no side effects, testable in isolation).
- `_PIPELINE_STAGE_INPUT/OUTPUT` Prometheus counters at each stage — add for new persist stage if it becomes a named stage.
- Service `__new__` test pattern: `tests/unit/service_tests/` bypasses `__init__`. Any new instance attribute added must be manually set in test setup.

### Integration Points
- `BarIntelligenceRecord.ledger_written` (bool) — currently only `True` when winner exists. After fix, should be `True` whenever DB INSERT succeeds regardless of winner.
- `insert_signals_with_features()` in `signal_ledger.py` — takes `list[LedgerEntry]` and a features dict. Existing function, no changes needed.

<specifics>
## Specific Requirements from Discussion

- **Renaissance invariant to preserve:** `select_winner()` regime filter stays — only
  eligible signals can fire for execution. The fix is purely on the data collection side.
- **No new Kafka topics:** regime_gated topic already publishes all signals (including
  suppressed). No new pub/sub infrastructure needed.
- **Compute cost:** Zero additional compute. The entries loop was already iterating
  `all_ranked` (including suppressed signals) inside `if winner:`. Moving it outside changes
  the trigger condition, not the work done.
- **Zero migration:** `regime_suppressed` status already in CHECK constraint. `regime_type_at_fire`
  column already exists (was just always NULL). No SQL migration needed.

</specifics>
