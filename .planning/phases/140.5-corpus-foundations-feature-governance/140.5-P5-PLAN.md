<objective>
Create context_features table for daily-cadence macro features. Populate it by extracting vix_z, flight_quality, and yield_slope_z from the existing _build_cross_asset_series() computation pattern. Wire ic_engine to LEFT JOIN context_features and apply a lower observation gate (1000 obs vs 20K for intraday) for these features.

Purpose: vix_z, flight_quality, and yield_slope_z currently inject the same daily value into every intraday bar row for the same calendar day. A VIX reading at 9:30 and 9:35 are not independent observations — they are the same reading duplicated ~78 times per day. The IC engine's stride correction does not fix date-level duplication; it corrects temporal dependence at the bar level. Leaving these in feature_vectors inflates their Spearman IC through artificial autocorrelation.
Output: context_features populated; IC engine measures vix_z/flight_quality/yield_slope_z at their true daily observation frequency.
</objective>

    BEGIN;

    -- context_features: one row per (feature_date, feature_name, symbol)
    -- symbol IS NULL for market-wide features (VIX, yield curve, macro indicators)
    -- symbol is non-null for symbol-scoped features (future use: earnings surprise, etc.)
    --
    -- Primary key uses empty string sentinel '' for market-wide features to avoid
    -- PostgreSQL NULL != NULL behavior in unique constraints.
    -- Application code must pass symbol='' (empty string) for market-wide features.
    CREATE TABLE IF NOT EXISTS context_features (
        feature_date   DATE                     NOT NULL,
        feature_name   TEXT                     NOT NULL,
        symbol         TEXT                     NOT NULL DEFAULT '',
        value          DOUBLE PRECISION         NOT NULL,
        source         TEXT                     NOT NULL CHECK (source IN ('ibkr', 'fred', 'derived')),
        computed_at    TIMESTAMPTZ              NOT NULL DEFAULT now(),
        PRIMARY KEY (feature_date, feature_name, symbol)
    );

    -- Index for IC engine join: WHERE feature_name = $1 AND feature_date = DATE($bar_ts) AND symbol = ''
    CREATE INDEX IF NOT EXISTS context_features_name_date ON context_features (feature_name, feature_date, symbol);

    -- APR key: lower observation gate for daily-cadence features
    -- Daily features have ~252 obs/year; at 5 years = ~1260 obs. The 20K intraday gate
    -- was not calibrated for daily observation frequency and would permanently block measurement.
    -- 1000 obs ~ 4 years of daily data. Tradeoff documented: lower statistical power,
    -- wider bootstrap CI, higher type-II error risk vs. intraday features.
    INSERT INTO config_schema (config_key, data_type, description, namespace)
    VALUES (
        'alpha.ic.min_obs_daily_features',
        'integer',
        'Minimum independent observations for IC Sharpe gate applied exclusively to features sourced from context_features (daily cadence). Daily features have ~252 obs/year; this gate is ~4 years of history. [initial_estimate] Do NOT apply the intraday 20K gate to daily-cadence features — calibrated for different observation frequency.',
        'alpha'
    )
    ON CONFLICT (config_key) DO NOTHING;

    INSERT INTO config_state (config_key, config_value, version)
    VALUES ('alpha.ic.min_obs_daily_features', '1000', 1)
    ON CONFLICT (config_key) DO NOTHING;

    COMMIT;

    Computation:
    Port _build_cross_asset_series() logic from services/backfill_feature_factory.py into this script.
    The function builds three daily-cadence series from market_data_ohlcv:

    1. vix_z: SPY realized vol z-score
       - Fetch 1d bars for SPY: SELECT timestamp, close FROM market_data_ohlcv WHERE symbol='SPY' AND timeframe='1d' ORDER BY timestamp ASC
       - log_return = log(close / close.shift(1))
       - realized_vol = rolling std of log_return over 20 bars
       - vix_z = (realized_vol - rolling_mean(realized_vol, 252)) / rolling_std(realized_vol, 252)
       - Key: date(timestamp), value: vix_z float

    2. flight_quality: TLT/SPY cumulative divergence (risk-off signal)
       - Fetch 1d bars for TLT and SPY
       - tlt_ret = log(tlt.close / tlt.close.shift(1))
       - spy_ret = log(spy.close / spy.close.shift(1))
       - divergence = (tlt_ret - spy_ret) rolling mean over 20 bars, z-scored over 252 bars
       - Key: date(timestamp), value: divergence float

    3. yield_slope_z: TLT/SHY log-return ratio z-score (yield curve slope proxy)
       - Fetch 1d bars for TLT and SHY
       - slope = log(tlt.close / shy.close) — daily level
       - yield_slope_z = (slope - rolling_mean(slope, 252)) / rolling_std(slope, 252)
       - Key: date(timestamp), value: yield_slope_z float

    For all three series: skip NaN rows (warmup period). Only write dates where all three values are non-NaN.

    Write to context_features via psycopg2 execute_batch:
    ```sql
    INSERT INTO context_features (feature_date, feature_name, symbol, value, source, computed_at)
    VALUES (%(feature_date)s, %(feature_name)s, '', %(value)s, 'derived', NOW())
    ON CONFLICT (feature_date, feature_name, symbol) DO UPDATE
        SET value = EXCLUDED.value, computed_at = EXCLUDED.computed_at
    ```
    symbol='' (empty string, not NULL) for all three market-wide features.
    source='derived' for all three (computed from IBKR OHLCV, not fetched directly from IBKR or FRED).

    Write all three features in a single execute_batch call per feature (three calls total).

    Argument parsing: --dry-run (print row count without writing), --symbols to override the fetched symbols for debugging.

    Feature data loading change:
    For features NOT in CONTEXT_FEATURES: existing query on feature_vectors unchanged.
    For features IN CONTEXT_FEATURES: use a different query that joins context_features with
    DISTINCT ON (DATE(fv.bar_ts)) to produce exactly ONE observation per calendar day.

    CORRECT SQL (using PostgreSQL DISTINCT ON idiom):
    ```sql
    SELECT DISTINCT ON (DATE(fv.bar_ts))
        DATE(fv.bar_ts)    AS obs_date,
        cf.value           AS feature_value,
        fv.{return_col}    AS forward_return
    FROM feature_vectors fv
    INNER JOIN context_features cf
        ON DATE(fv.bar_ts) = cf.feature_date
        AND cf.feature_name = %(feature_name)s
        AND cf.symbol = ''
    WHERE fv.tf = %(tf)s
      AND fv.bar_ts >= %(start_ts)s
      AND fv.bar_ts <= %(end_ts)s
    ORDER BY DATE(fv.bar_ts), fv.bar_ts ASC
    ```
    DISTINCT ON (DATE(fv.bar_ts)) combined with ORDER BY DATE(fv.bar_ts), fv.bar_ts ASC selects
    exactly one row per calendar day — the earliest bar of the day. This is the standard PostgreSQL
    idiom for "first row per group."

    IMPORTANT: Do NOT use GROUP BY DATE(fv.bar_ts), cf.value, fv.{return_col}. That grouping
    does NOT collapse intraday duplication because fv.forward_return varies per intraday bar
    (different forward returns for each 5m bar even on the same day). It would produce one row
    per unique (date, cf.value, forward_return) — effectively one row per bar, not one per day.

    The forward_return column here is from the earliest bar of the day (first 5m bar ~9:30).
    This is appropriate: the daily context_features value represents a daily regime reading,
    and pairing it with the opening bar's forward return is the correct causal alignment.

    Observation gate: For context_features features, use self._min_obs_daily (1000) instead of
    the standard n_raw_bars >= sharpe_window_size * sharpe_min_windows gate. Add a clear comment:

    IC Sharpe computation: The Spearman IC computation itself is unchanged. The input is now
