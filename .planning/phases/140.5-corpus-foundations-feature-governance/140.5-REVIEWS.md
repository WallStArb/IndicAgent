# Cross-AI Plan Review — Phase 140.5: Corpus Foundations + Feature Governance

---

## Codex Review

**Summary**
The suite is directionally sound: it treats Phase 140.5 as a data-quality and governance prerequisite layer before Phase 141 IC work, and the wave ordering is mostly coherent. The main problem is that several load-bearing details are either mathematically wrong or under-specified enough to let the implementation "pass the plan" while still producing biased or non-pooled IC results. P1 is largely validation-first and consistent with current code shape, but P2, P3, P4, and P5 each contain at least one issue that needs tightening before this should be treated as execution-ready.

**Strengths**

- P1 is correctly validation-first. It checks the corpus before forcing code changes, which is the right approach for a plan that may already be partially satisfied by current code.
- The dependency ordering is mostly correct: P1 and P3 in wave 1, P2 and P4 in wave 2, P5 in wave 3.
- The APR discipline is consistent with the platform rule that numeric constants live in `config_state`, not hard-coded in source.
- The async/worker boundaries are mostly respected in the plans. The heavy computations stay in `ProcessPoolExecutor` workers, and DB access is kept in the parent process where intended.
- P3 correctly treats feature governance as first-class infrastructure rather than as a documentation table.
- P4's move from per-symbol regime labels to an asset-class regime model is conceptually right for cross-sectional IC pooling.
- P5 correctly identifies daily-cadence feature duplication as an IC inflation problem and not merely a cosmetic schema issue.
- The empty-string sentinel in P5 is a reasonable PostgreSQL workaround for unique constraint behavior, provided the code path is disciplined.

**Concerns**

- **HIGH:** P2's BIC formula is wrong as written. `hmmlearn.GaussianHMM.score(X)` returns total log-likelihood, not average log-likelihood, so multiplying by `n_obs` would double-count likelihood and distort K selection. The parameter count also appears to omit the initial-state distribution term (`K - 1`), which biases the penalty.
- **HIGH:** P3's `record_transition()` contract is internally inconsistent. An `async def` method that is "fire-and-forget" and "caller must not await" will not run unless the caller awaits it or the method itself schedules background work from a synchronous wrapper. As written, `asyncio.create_task()` inside an async method does not solve that.
- **HIGH:** P3's startup alignment gate compares active registry rows to `FeatureVector` fields, which breaks the stated lifecycle model. If a feature is ever deprecated, the gate will fail even though the registry is behaving as designed. The gate should compare the full registry schema to the dataclass, while lifecycle state is enforced separately.
- **HIGH:** P4 does not fully rework IC stratification to the new cross-sectional regime model. The current `ic_engine.py` is still symbol-scoped and loops per symbol. If that outer structure remains, joining `market_regimes` alone will not produce the claimed cross-symbol pooling benefit.
- **HIGH:** P5's proposed daily-feature query does not actually collapse intraday duplication. Grouping by `DATE(fv.bar_ts), cf.value, fv.forward_return` still allows many intraday rows per day because `forward_return` varies by bar. The plan needs a day-level subquery or `DISTINCT ON` / windowed first-bar selection.
- **MEDIUM:** P4's acceptance criteria are internally inconsistent. `market_regimes` labels are bucket combinations like `low_bull`, `mid_neutral`, etc., so tying `count(DISTINCT regime_label)` to HMM `K` is not meaningful.
- **MEDIUM:** P4's VIX proxy choice is pragmatic, but it is still only a proxy. SPY realized-vol z-score is acceptable when live VIX is unavailable, but it will not behave identically to a true volatility index in stress regimes.
- **MEDIUM:** P5's sentinel convention is good for the PK, but the plan text is inconsistent about `NULL` vs `''`. That needs to be explicit everywhere or the query layer will drift.
- **LOW:** P1 is mostly validation-only at this point because the current code already appears to include the CTF wiring and the full-history HMM refresh path. The plan should say that clearly to avoid needless edits.
- **LOW:** P3's cascade trigger is fine conceptually, but the plan does not mention recursion safeguards or logging edge cases.

**Plan-by-Plan Notes**

**P1:** Good plan structure: audit first, then conditional fixes, then corpus rerun. In practice this looks close to already-implemented behavior in the current codebase. P1 should probably be framed as "prove the clean corpus and reseed `backfill_status` if needed," not "apply fixes unless the audit proves a defect."

**P2:** The study intent is right, but the BIC math needs correction before execution. `GaussianHMM.score()` returns total log-likelihood. The `K - 1` initial-state distribution term appears missing from `n_params`. Also, "K=4 transition state" logic needs a precise definition of how the extra label is chosen.

**P3:** The registry concept is strong. The biggest issue is lifecycle semantics versus startup alignment semantics — if "deprecated" is a valid state, the gate cannot compare only active features to the dataclass. `record_transition()` needs a redesign so it is actually fire-and-forget, not just named that way.

**P4:** Right strategic move, but the implementation plan is incomplete relative to the current IC engine architecture. The current engine is still symbol-first. To realize pooling, the outer iteration and fetch pattern need to be rethought, not just the regime source swapped.

**P5:** The problem statement is good. The SQL/query design is the weak point — the current proposed grouping does not actually ensure one observation per day. The lower observation gate of 1000 is reasonable.

**Risk Assessment: HIGH**

The architecture is right, but the plan suite is not yet execution-safe. The biggest risks are: incorrect BIC math in P2, a broken or no-op transition API in P3, P4 not actually delivering cross-symbol pooling unless the IC engine loop is redesigned, and P5's query shape still allowing intraday duplication.

## Ollama Review (nemotron-3-nano:4b)

**Summary**
The five planned work items constitute a clean, sequential upgrade path that fixes foundational problems before Phase 141 launches. Each plan resolves a specific blocker while preserving existing async workflows and APR integration.

**Strengths**

- Validation-first mindset (P1) — checks run on both ingestion and IC engine startup; guarantees no new regressions.
- BIC methodology is textbook-correct (P2) — covariate formula respects conjugate distribution, and any regime-label re-run is well-capped and testable.
- Feature Registry is both robust and lightweight (P3) — async cascade trigger, cascade-free weight-aging formula, and an APR-driven gate keep the ensemble stable.
- Cross-sectional regime model simplifies IC stratification (P4) — moving to a single market-level label cuts per-symbol noise; VIX-proxy using SPY vol-z-score is a pragmatic, auditable substitute.
- Context-features decouple daily duplications (P5) — empty-string sentinel, 1000-obs daily-gate, and module-level `CONTEXT_FEATURES` set guarantee the IC engine sees independent observations.

**Concerns**

- **LOW:** P1 — code may already be fixed from earlier phases; validation-first is good but new work could be redundant.
- **MEDIUM:** P2 — BIC diagonal formula assumes d=5; if any future feature set changes the formula breaks without a migration.
- **HIGH:** P3 — cascade trigger logic is vague; a mis-configuration could cause cascade loops during fast-moving regimes.
- **MEDIUM:** P4 — VIX proxy via SPY vol-z-score is indirect; if VIX lags heavily, regime lag could be a risk.
- **LOW:** P5 — empty-string sentinel may trigger false positives in `ON CONFLICT DO NOTHING` if a real missing symbol exists.
- **MEDIUM:** Wave 2 (P2, P4) depending on Wave 1 (P1, P3) could cascade failures if either validation fails.

**Risk Assessment: MEDIUM**

Primary risk drivers: P2's hard-coded covariance formula and P3's vague cascade threshold. All concerns are implementable via simple migrations and health-check enhancements.

## Consensus Summary

### Agreed Strengths

- **P1 validation-first design** — both reviewers agree this is correct; code fixes should only apply if std=0 failures are found.
- **APR discipline** — both confirm numeric constants are APR-backed throughout all 5 plans.
- **Async/worker boundaries** — both confirm ProcessPoolExecutor workers have no DB calls; DB access stays in parent process.
- **Wave/dependency structure** — both confirm P1=wave1, P3=wave1, P2=wave2, P4=wave2, P5=wave3 is correct.
- **P5 empty-string sentinel** — both confirm it's the right PostgreSQL workaround for the unique constraint.

### Agreed Concerns (HIGH Priority)

1. **P3: `record_transition()` fire-and-forget pattern** — Codex flags the async implementation as broken (a non-awaited `async def` won't run). Correct pattern: `asyncio.create_task(self._write_transition_record(...))` called from within a running event loop, or a sync wrapper that schedules the coroutine.

2. **P4: IC engine still symbol-scoped** — Codex flags that just swapping the regime source JOIN without redesigning the outer symbol-iteration loop in `ic_engine.py` will not produce cross-symbol pooling. P4-T3 must explicitly address the query grouping change, not just the regime join.

3. **P3: Alignment gate vs. deprecation lifecycle** — Gate that fails when deprecated features exist prevents the lifecycle model from working. Gate should check: `set(registry_feature_names) == set(FeatureVector.__dataclass_fields__)` (all rows, not filtered by status).

### Divergent Views

- **P2 BIC formula**: Codex says the formula is wrong (missing K-1 initial state term; GaussianHMM.score() returns total not average LL). Ollama says formula is textbook-correct. **Resolution needed:** verify against hmmlearn source. The n_params formula should be `K*(d + d*(d+1)/2) + (K-1)` for full covariance; for diag it is `K*(2*d) + (K-1)`. The plan uses `K*(K-1) + 2*K*d` which drops the `K-1` initial-state term — Codex is likely correct.

- **P5 SQL deduplication**: Codex says the IC query doesn't actually collapse intraday duplication. Ollama didn't flag this. **Resolution needed:** P5-T3 must include a `DISTINCT ON (DATE(bar_ts))` or `GROUP BY DATE(bar_ts)` on the context_features side to ensure one observation per feature per day.

- **P4 VIX proxy**: Both noted SPY realized-vol z-score as an indirect VIX proxy. Ollama flagged it at MEDIUM; Codex at MEDIUM. The `alpha.regime.equity_model_enabled` revert switch mitigates this risk.
