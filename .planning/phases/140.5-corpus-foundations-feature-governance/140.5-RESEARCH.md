## 1. Executive Summary

Phase 140.5 installs five mandatory foundations before Phase 141 touches a single IC score. P1 audits and corrects silent-constant features in the batch corpus path; some fixes are already in code from prior phases but a validation run is needed to confirm std > 0 before re-running the full pipeline. P2 validates K=3 for the HMM state count via BIC before trusting regime labels in IC stratification. P3 builds the `feature_registry` table and `FeatureRegistryService`, giving the IC engine and ensemble trainer an on/off governance switch for all 61 features. P4 replaces incomparable per-symbol HMM regime labels with a single cross-sectional equity regime model stored in `market_regimes`, enabling cross-symbol IC pooling within a regime cell. P5 separates daily-cadence macro features (`vix_z`, `flight_quality`, `yield_slope_z`) from `feature_vectors` into a `context_features` table with a lower observation gate, eliminating artificial autocorrelation from date-duplicated daily values.

**Primary recommendation:** Next migration is **172**. P1 requires a corpus validation run before scheduling the re-run; the code fixes may already be in place (confirm with std audit before writing any new code). P2, P3, P4, P5 are all net-new work.

### P2 — HMM State Count K via BIC

**Current K source:** APR key `feature.hmm.n_components = 3` (confirmed in live DB). Read in `regime_writer.main()`:
```python
n_components = int(cfg.get_sync("feature.hmm.n_components", 3))
```

**5D observation vector** is built by `_build_obs_matrix()` in `services/regime_writer.py`:
- `[0]` log_return
- `[1]` realized_vol (rolling std over `feature.hmm.vol_window`, default 20)
- `[2]` momentum = sum(log_returns[-momentum_window:]) / (realized_vol + eps), APR `feature.hmm.obs_momentum_window = 20`
- `[3]` vol_of_vol (rolling std of realized_vol over `feature.hmm.obs_vol_of_vol_window = 20`)
- `[4]` rel_volume = log(volume) - rolling mean(log(volume), vol_window)

`valid_start = max(vol_window, momentum_window, vol_of_vol_window) - 1`

**GaussianHMM fit:** `covariance_type="diag"`, `n_iter=200`, `random_state=42` (APR `alpha.hmm.random_state`). `StandardScaler` is fit+transform before both `.fit()` and `_causal_decode()`.

**`regime_writer.py` does NOT have `--refit` flag.** Main args are: `--symbols`, `--tf`, `--workers`. A `--refit` flag would need to be added if K changes require re-running only regime labels (without redoing feature_vectors compute).

**BIC formula for diag GaussianHMM:**
```
n_params = K*(K-1)    # transition matrix (K*(K-1) free params, each row sums to 1)
         + K*d        # emission means
         + K*d        # emission variances (diagonal cov)
         = K*(K-1) + 2*K*d
BIC = -2 * log_likelihood + n_params * ln(n_obs)
```
Note: The todo uses `n_params = K*d + K*d(d+1)/2 + (K-1)` for full covariance. Since `regime_writer` uses `covariance_type="diag"`, use the diagonal formula above.

**BIC script design:** New `scripts/bic_k_selection.py` (one-time analysis). Load OHLCV for representative symbols (SPY, TLT, GLD, EWT). Build same 5D obs matrix, fit GaussianHMM for K in {2,3,4,5}. Write BIC table to stdout + optional CSV. K decision written to `docs/analysis/bic_k_selection.md`. If K changes, update `feature.hmm.n_components` APR key via migration and re-run regime_writer.

**Log-likelihood access:** `model.score(obs_matrix)` returns average log-likelihood; multiply by `n_obs` for total.

### P4 — Cross-Sectional Equity Regime Model

**Current regime source:** `feature_vectors.regime` column (TEXT, nullable), populated by `regime_writer.py`. The IC engine reads it via:
```sql
SELECT DISTINCT symbol, tf, regime
FROM feature_ic_scores
WHERE is_pooled = false AND reliable = true
  AND ic_sharpe IS NOT NULL AND regime IS NOT NULL
ORDER BY symbol, tf, regime
```
And then joins `feature_vectors WHERE regime = $3` for scoring.

**VIX data:** No VIX or VXX contract in the 58-ETF universe. The current vix_z proxy uses SPY realized volatility (see `feature_cache.py` docstring). For P4 cross-sectional model, VIX level can be approximated from SPY realized vol z-score already in `feature_vectors.vix_z`, or computed fresh from `market_data_ohlcv` for SPY.

**SPY bars:** Available in `market_data_ohlcv WHERE symbol = 'SPY' AND timeframe = ?`. All TF bars are in the table.

**Breadth computation:** % of 58 ETFs above 200MA requires computing 200MA for each ETF from `market_data_ohlcv`. The 200MA for daily TF is straightforward. For the cross-sectional model, use 1d bars.

**market_regimes table design:**
```sql
CREATE TABLE market_regimes (
    asset_class  TEXT        NOT NULL,
    tf           TEXT        NOT NULL,
    ts           TIMESTAMPTZ NOT NULL,
    regime_label TEXT        NOT NULL,
    regime_prob_vector JSONB,
    PRIMARY KEY (asset_class, tf, ts)
);
```

**IC engine regime join:** Replace `feature_vectors.regime` read with a JOIN on `market_regimes` on `(asset_class='equity', tf, DATE_TRUNC(tf_interval, bar_ts))`. The exact SQL truncation unit per TF: 5m→'5 minutes', 15m→'15 minutes', 1h→'1 hour', 1d→'1 day'. Note: TimescaleDB chunks complicate cross-table JOINs -- a lateral join or pre-built temp table may be needed.

**Per-symbol HMM features remain:** `hmm_regime_prob`, `hmm_entropy`, `hmm_duration` stay in `feature_vectors` as predictive signals -- they just stop being the IC stratification key. The feature_registry can mark them `tier=2_theory` (already planned).

**APR keys:** `alpha.regime.vix_low_pct`, `alpha.regime.vix_high_pct`, `alpha.regime.breadth_bear`, `alpha.regime.breadth_bull`, `alpha.regime.equity_model_enabled`.

**Fitting service:** New oneshot `services/equity_regime_model.py`, analogous to `regime_writer.py`. ProcessPoolExecutor with one task per TF (4 tasks). Reads all ETF bars from `market_data_ohlcv`. Writes to `market_regimes` via psycopg2 execute_batch.

### P5 — Context Features Table

**Daily-cadence features currently in feature_vectors (3 features):**
- `vix_z` -- SPY realized-vol z-score, keyed by DATE in `cross_asset_by_date` dict; same value for ALL 5m/15m/1h bars on same calendar day
- `flight_quality` -- TLT/SPY cumulative divergence, daily cadence
- `yield_slope_z` -- TLT/SHY log-return ratio z-score, daily cadence

These are built in `_build_cross_asset_series()` in `backfill_feature_factory.py` which returns a `dict[date, (vix_z, flight_quality, yield_slope_z)]`. Every intraday bar at date D gets the same triple.

**How IC engine strides for autocorrelation:** In `_load_apr()`, `actual_stride = max(subsample_min_stride, lookahead_bars)` where `alpha.ic.subsample_min_stride = 5`. This corrects temporal dependence at the bar level. It does NOT correct for date-level duplication (78 identical 5m bars per day all getting the same vix_z value).

**`alpha.ic.min_observations = 500`** is the floor for IC computation (`_load_apr()`, `min_observations` key). The IC Sharpe gate is separate: `n_raw_bars >= sharpe_window_size * sharpe_min_windows` = 2000 * 30 = 60,000 raw bars. Daily-cadence features have ~252 obs/year; at 5 years = ~1,260 -- structurally below both gates if the daily-feature gate is applied at the daily observation frequency.

**context_features PRIMARY KEY note:** `PRIMARY KEY (feature_date, feature_name, COALESCE(symbol, ''))` is not directly expressible as a PostgreSQL table constraint. Use:
```sql
PRIMARY KEY (feature_date, feature_name, symbol)
```
with `symbol TEXT DEFAULT ''` (empty string for market-wide features), or use a partial unique index:
```sql
CREATE UNIQUE INDEX ctx_mkt_wide ON context_features (feature_date, feature_name) WHERE symbol IS NULL;
CREATE UNIQUE INDEX ctx_sym ON context_features (feature_date, feature_name, symbol) WHERE symbol IS NOT NULL;
```

**IC engine join pattern:**
```sql
SELECT fv.*, cf.value AS context_value
FROM feature_vectors fv
LEFT JOIN context_features cf
  ON DATE(fv.bar_ts) = cf.feature_date
  AND cf.feature_name = 'vix_z'
  AND cf.symbol IS NULL
WHERE fv.symbol = $1 AND fv.tf = $2 AND fv.regime = $3
```

## 5. Patterns and Conventions to Follow

**Batch service pattern:** All Phase 140.5 compute services follow the `regime_writer.py` / `backfill_feature_factory.py` model:
- psycopg2 sync for DB reads/writes
- `ProcessPoolExecutor` for CPU-bound work
- No DB calls inside worker functions (fetch async before, flush after)
- Workers receive DSN, not connection (connections not picklable)
- `_NoopTracer` for subprocess OTel
- `setup_service_logging("logs/<name>.log")` at module level

**APR loading:** Sync pattern uses `_load_config_service(conn)` from `services/_batch_utils.py`. For async services (ensemble_trainer), use `_load_apr(conn)` asyncpg pattern.

**asyncpg JSONB:** Pass dicts directly (no `json.dumps()`). asyncpg handles serialization.

**Migration format:** SQL file in `production/migrations/NNN_description.sql`. Begins with `BEGIN;`, ends with `COMMIT;`. APR inserts use `ON CONFLICT (config_key) DO NOTHING`. Comments include migration number and phase reference.

**config_state write pattern (for APR key value changes):**
```sql
UPDATE config_state SET config_value = 'X', version = version + 1 WHERE config_key = 'key';
INSERT INTO config_history (timestamp, config_key, version, config_value, changed_by, reason)
SELECT NOW(), 'key', version, 'X', 'migration_NNN', 'reason' FROM config_state WHERE config_key = 'key';
```

**ProcessPoolExecutor chunksize=1:** Used consistently to prevent head-of-line blocking on slow symbols.

**No `--refit` flag on regime_writer.py:** Must be added if K changes in P2. Current args are only `--symbols`, `--tf`, `--workers`.

## 6. Risks and Gotchas

**Risk 1: P1 code may already be done.** Before writing any new P1 code, run the std validation query. If CTF std > 0 and HMM std > 0 and VP/SR is NULL, only a corpus re-run is needed. Spending time on code that's already there is waste.

**Risk 2: backfill_status gotcha.** Before re-running `--compute-only`, seed all rows to status='pending' (NOT 'complete'). If status='complete', the row is silently skipped. See memory note.

**Risk 3: regime_writer must run AFTER backfill_feature_factory.** The `feature_vectors.hmm_regime_prob` values initially written by compute_batch (simple 2D HMM) are overwritten by regime_writer. If only backfill runs (not regime_writer), hmm_regime_prob will have low variance.

**Risk 4: VP/SR columns are nullable already.** The `\d feature_vectors` output shows no NOT NULL constraint and no DEFAULT for `poc_dist_atr`, `va_position`, `sr_support_dist`, `sr_resist_dist`. Migration 172 for VP/SR may be a no-op DDL (just comment-only migration). Confirm with `\d feature_vectors` and `SELECT count(*) FROM feature_vectors WHERE poc_dist_atr IS NULL` before writing DDL.

**Risk 5: feature_vectors.regime_label_source CHECK constraint.** The column has `CHECK (regime_label_source = ANY (ARRAY['filtered','unknown']))`. This column is on `feature_vectors`, NOT `feature_ic_scores`. The IC engine writes `regime_label_source='forward_filter'` to `feature_ic_scores` (different table). Do not confuse. `feature_vectors.regime_label_source` stays as 'filtered' (set by the baseline migration DEFAULT).

**Risk 6: BIC script must use diag covariance formula.** `regime_writer.py` uses `covariance_type="diag"` in GaussianHMM. The BIC n_params formula must match: `K*(K-1) + 2*K*d` not the full-covariance formula.

**Risk 7: `market_regimes` JOIN with TimescaleDB partitioned `feature_vectors`.** Cross-table JOINs on the hypertable partitioned by `bar_ts` can be slow. Consider a LEFT JOIN or pre-materializing the regime lookup per TF before the feature scan.

**Risk 8: context_features PRIMARY KEY with nullable symbol.** PostgreSQL NULL != NULL in unique constraints. Use empty string sentinel `''` for market-wide features or dual partial unique indexes. Avoid `COALESCE` in PRIMARY KEY.

**Risk 9: P2 K change requires full corpus re-run.** If K=4 wins, all 58 symbols × 4 TFs must be re-decoded by regime_writer, then IC engine must re-run with new regime labels. Plan a 3-5 hour window for the pipeline.

**Risk 10: `alpha.ic.min_obs_daily_features` must NOT gate intraday features.** Apply only to features sourced from `context_features`. The IC engine needs to check feature source (from `feature_registry.tier` or a new `context_features` flag) before choosing which gate to apply.
