<objective>
Eliminate two reliability/scaling weaknesses in the hot path, add a missing span, and add per-tier latency histograms. (1) Lines 507 and 598 of `intelligence_pipeline_agent.py` use non-blocking `enqueue` which silently drops intel and journal messages under backpressure — switch to `await enqueue_blocking`. (2) `PluginStateManager.get_all_states_for()` is an O(N) scan across all plugin states; add a `_states_by_key` secondary index for O(1) lookup. (3) Wrap `_process_bar_inner` in `observed_span` recording symbol and tf. (4) Record per-tier execution latency as a histogram at the existing tier boundaries in `feature_pipeline_executor.py`.

Purpose: Silent drops corrupt downstream feature/journal continuity; the O(N) scan grows linearly with symbol count; the missing span leaves the hottest code path un-traced; per-tier latency is currently invisible (only aggregate I1/I7 latency is recorded by 105-03).
Output: Lossless output queueing, O(1) state lookup, traced hot path, per-tier latency histogram.

Prerequisite: Phase 105 must have executed and passed verification before this plan runs — specifically 105-03 (histogram infrastructure in intelligence_pipeline_agent.py). This plan does not declare a depends_on against Phase 105 (cross-phase plan IDs are not modeled in this phase's wave graph); 105 completion is an external precondition enforced by the orchestrator, not an intra-106 dependency. The `observed_span` here is span instrumentation, distinct from 105-03's metric-type histogram fix; the new tier-latency histogram complements 105-03's aggregate I1/I7 histograms by adding per-tier granularity.

<threat_model>
- **Deadlock from blocking enqueue:** Switching to `enqueue_blocking` means the producer awaits when the queue is full. If the queue drain task is itself stalled, the whole pipeline backs up rather than dropping. This is the desired behavior (backpressure beats silent loss) but must not be applied to the signal enqueue at line 529, which is ALREADY blocking — only lines 507 and 598 change. Mitigation: change exactly two call sites; confirm line numbers by reading.
- **Secondary index drift:** If `_states_by_key` is updated in only some write paths, reads return stale/partial state — worse than O(N) correctness. Mitigation: update the index in EVERY write path (`update`, `update_batch`, and any direct `_plugin_states[...] =` assignment). Add a unit test asserting index/primary parity.
- **Checkpoint duplication:** Serializing `_states_by_key` doubles checkpoint size and risks divergence on restore. Mitigation: do NOT serialize it; rebuild it in a loop after `_plugin_states` is loaded from checkpoint.
- **Span overhead on hot path:** `observed_span` per bar is acceptable (one span per bar, not per plugin). Do NOT wrap per-plugin execution in spans here. Mitigation: single span around `_process_bar_inner` only.
- **Tier-latency double counting / per-plugin granularity creep:** The histogram must record ONE measurement per tier group per bar, not per plugin. Per-plugin timing already exists via `intelligence_pipeline_plugin_duration_ms`. Mitigation: record at the coarse tier boundaries in `feature_pipeline_executor.run()` (around the `run_i1` and `run_tiers` calls), not inside per-plugin loops.
</threat_model>
