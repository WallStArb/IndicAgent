### Pattern 1: Stateless Primitive Functions
**What:** Pure functions taking numpy arrays, returning scalar floats. No class state, no IO.
**When to use:** All rolling-window computations (momentum, volatility, volume primitives).
**Example:**
```python
def _rolling_kurtosis(returns: np.ndarray, window: int) -> float:
    """Rolling kurtosis over window. Returns 0.0 on insufficient data."""
    if len(returns) < window + 2:  # +2 for kurtosis minimum
        return 0.0
    window_returns = returns[-window:]
    mean = float(np.mean(window_returns))
    std = float(np.std(window_returns))
    if std < 1e-10:
        return 0.0
    # Pearson kurtosis (fourth moment)
    kurt = float(np.mean(((window_returns - mean) / std) ** 4)) - 3.0
    return kurt if math.isfinite(kurt) else 0.0

# Source: Existing pattern in feature_factory.py (_skewness, _pearson_acf1)
```

### Pattern 3: Batch Series Precomputation
**What:** _*_series_full helpers compute entire series in O(n), avoiding per-bar O(n²) cost.
**When to use:** All primitives called in compute_batch() path (backfill performance critical).
**Example:**
```python
def _ret_kurtosis_series_full(closes: np.ndarray, window: int) -> np.ndarray:
    """Rolling kurtosis series. result[i] == streaming _rolling_kurtosis at bar i.
    O(n × window) total — called once, vs per-bar O(n²)."""
    n = len(closes)
    if n < window + 3:
        return np.zeros(n, dtype=float)
    log_rets = np.diff(np.log(np.maximum(closes.astype(float), 1e-10)))
    kurt_vals = np.array(
        [_rolling_kurtosis(log_rets[k : k + window]) for k in range(len(log_rets) - window + 1)],
        dtype=float,
    )
    # Prepend window zeros for cold-start bars
    return np.concatenate([np.zeros(window + 2, dtype=float), kurt_vals])

# Source: Existing pattern in feature_factory.py (_ret_skew_z_series_full, _ret_acf1_z_series_full)
```

### Anti-Patterns to Avoid
- **Stateful primitive functions:** Never store deque/window state in function objects. All state passed via parameters.
- **Hard-coded window lengths:** Never embed magic numbers in primitive bodies. All windows must come from FeatureFactoryConfig.
- **IO in compute():** FeatureFactory.compute() must remain pure — no DB reads, no Kafka, no ConfigService.get() calls.
- **Violating frozen contract:** FeatureVector is frozen dataclass — never mutate after construction.
- **Breaking batch parity:** compute() and compute_batch() must return identical values for same bar. Always test parity after adding primitives.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Rolling statistics | Manual loops with list.append | numpy operations on array slices | 10-100x faster; vectorized; tested |
| Z-score computation | Manual mean/std calculation | scipy.stats.zscore or numpy ops | Handles edge cases (std=0); numerically stable |
| Percentile ranks | Manual sorting & ranking | scipy.stats.percentileofscore or numpy.percentile | Correct interpolation; handles ties |
| Log returns | Manual (close[t] - close[t-1]) / close[t-1] | np.diff(np.log(np.maximum(closes, 1e-10))) | Numerically stable; handles zero/negative prices |
| Correlation | Manual covariance/std products | np.corrcoef or scipy.stats.pearsonr | Handles NaN; numerically stable |

**Key insight:** The Renaissance Primitives catalog is intentionally "boring" — these are standard statistical transforms, not novel algorithms. Use battle-tested numpy/scipy implementations rather than hand-rolling math. This reduces bug surface and improves performance.

## Common Pitfalls

### Pitfall 1: Cold Start Handling
**What goes wrong:** New primitives return NaN/inf or raise exceptions on insufficient history (len(bars) < window).
**Why it happens:** Rolling statistics require minimum samples; edge cases not handled.
**How to avoid:** Always guard with `if len(arr) < min_required: return fallback_value`. Use explicit minimums (e.g., kurtosis needs window+2, autocorrelation needs window+1).
**Warning signs:** Test corpus with short histories (< 100 bars) fails with IndexError or ValueError.

### Pitfall 2: Batch Compute Performance Degradation
**What goes wrong:** Adding primitives without _*_series_full helpers makes backfill O(n²) instead of O(n).
**Why it happens:** Per-bar compute() calls rolling functions on full window each time vs. precomputing once.
**How to avoid:** For any primitive used in compute_batch(), implement corresponding _*_series_full() helper and call in _precompute_series().
**Warning signs:** Backfill runtime increases 10x+ after adding primitives; profile shows time in compute() loop.

### Pitfall 3: APR Parameter Drift
**What goes wrong:** FeatureFactoryConfig field added but APR seed missing; config.get() returns fallback instead of seeded value.
**Why it happens:** Migration adds config_state row but not config_schema, or vice versa.
**How to avoid:** Always add both config_schema (metadata) and config_state (seed) in same migration. Test by reading value via ConfigService after migration.
**Warning signs:** Primitive uses hard-coded default instead of APR value; config.get_sync() returns fallback unexpectedly.

### Pitfall 4: Schema Column Name Mismatch
**What goes wrong:** FeatureVector field name doesn't match feature_vectors column name after migration.
**Why it happens:** ALTER TABLE uses different naming convention than dataclass field (snake_case vs camelCase, typos).
**How to avoid:** Use exact field name from FeatureVector dataclass in ALTER TABLE ADD COLUMN. Verify with information_schema.columns query.
**Warning signs:** FeatureWriter fails with column does not exist; DB error mentions undefined column.

### Pitfall 5: Feature Registry Row Count Gate
**What goes wrong:** FeatureRegistryService raises RuntimeError on startup (row count != 61).
**Why it happens:** _REGISTRY_ROW_COUNT constant not updated after adding new features.
**How to avoid:** Update _REGISTRY_ROW_COUNT to 144 in feature_registry_service.py as part of schema migration.
**Warning signs:** Service fails startup with "registry row count mismatch"; FeatureRegistryService.load() raises.

### Adding a Rolling Window Primitive (APR-backed)

# In feature_factory.py helper:

def _updown_ratio(closes: np.ndarray, window: int) -> float:
    """Ratio of up bars to down bars over window. Returns 1.0 on insufficient data."""
    if len(closes) < window:
        return 1.0
    window_closes = closes[-window:]
    up_bars = float(np.sum(window_closes[1:] > window_closes[:-1]))
    down_bars = float(np.sum(window_closes[1:] < window_closes[:-1]))
    return up_bars / down_bars if down_bars > 1e-10 else 1.0

# In _precompute_series() (for batch efficiency):

def _week_of_month_sin(bar_ts: datetime) -> float:

## Open Questions

1. **Primitive grouping in implementation order**
   - What we know: 83 primitives organized into 10 categories (bar anatomy, lagged returns, temporal, volume, return distribution, realized variance, alt vol estimators, vol dynamics, breakout distance)
   - What's unclear: Should we implement all categories in one phase, or split across multiple phases?
   - Recommendation: Implement all 83 in one phase (142.5) — IC engine evaluates them together anyway. Splitting adds overhead without reducing risk (primitives are independent).

2. **Feature registry granularity**
   - What we know: FeatureRegistryService tracks lifecycle per feature (61 rows currently)
   - What's unclear: Should we group Renaissance primitives (e.g., one row per category, or one row per primitive)?
   - Recommendation: One row per primitive (144 total rows) — IC engine measures per-feature IC, not per-category. Grouping would lose granularity.

3. **APR parameter seeding strategy**
   - What we know: Gradient-named primitives (fast/slow, short/long) need separate APR keys per scale
   - What's unclear: What default values to seed for new primitives? Follow existing patterns?
   - Recommendation: Use existing window patterns as seeds (fast=5-10, mid=20, slow=60-100). All marked `[initial_estimate]` and `ML learning target`.

4. **Interaction primitives implementation**
   - What we know: Some Renaissance primitives are products/ratios of other primitives (e.g., vol_body_product = body_ratio × volume_z)
   - What's unclear: Should interaction primitives be computed in FeatureFactory, or as a post-processing step?
   - Recommendation: Compute in FeatureFactory — keeps all primitives in one pure-function contract. Post-processing would break DAG invariance (stateful intermediate results).
