## Antigravity Review (independent)

**Verdict:** REQUEST CHANGES
**Severity distribution:** 5 HIGH / 3 MEDIUM / 2 LOW

### Executive Summary

The plans correctly use TDD, keep `FeatureFactory` stateless/DAG-compliant, and parameterize all lookback windows via APR. But in their current state, execution would produce a build that crashes at daemon startup and fails integration tests — five HIGH-severity runtime-blocking bugs and structural mismatches.

### HIGH severity

1. **Cold-start crash — missing `_cold_start_vector` updates (Plans 01-04).** `FeatureVector` is a frozen dataclass with non-optional fields; the constructor requires every field. Plans 01, 02, 03, 04 add fields to the dataclass but never add matching neutral/fallback values to `_cold_start_vector()` in `feature_factory.py` (only Plan 05 does this, for its own 14 fields). Any cold-start bar (history count < 2) processed while Waves 1-4's fields exist raises a `TypeError` and crashes the pipeline daemon.
2. **Missing `feature_registry` DB seeding (Plan 06).** `FeatureRegistryService` hard-gates on `len(rows) == _REGISTRY_ROW_COUNT` at startup. Plan 06's migration adds columns to `feature_vectors` but never inserts the corresponding 83 metadata rows into `feature_registry`. The table stays at 61 rows against a code expectation of 144-146 → `RuntimeError` at startup.
3. **`_REGISTRY_ROW_COUNT` out of sync (Plans 04/05/06).** The constant is correctly bumped through Plans 01→75, 02→97, 03→118, 04→126, but neither Plan 05 nor Plan 06 update it further — it stays stuck at 126 even after the DB is fully seeded. Even if finding #2 is fixed, the row-count gate still fails.
4. **Column count mismatch — 85 actual vs 144 asserted.** Summing Plan 06's migration task line items across categories yields 85 new columns (`61 + 85 = 146` total), not the 83 stated in the outline (`61 + 83 = 144`). The integration test `test_renaissance_columns_exist` in `tests/integration/test_feature_vectors_schema.py` asserts 144 and will fail. Root cause: Volume Structure is labeled "10" but lists 12 items; Return Distribution labeled "8" but lists 7; Realized Variance labeled "13" but lists 14.
5. **8 Price-Volume Interaction primitives have zero implementation.** Plan 06 adds their APR params, DB columns, and an integration-test assertion for their presence — but no plan (01-05) computes them in `FeatureFactory`. The columns exist but will always be `NULL`.

### MEDIUM severity

- **M1 — Open-to-Close Split (4) and Cross-Timeframe Divergences (3) silently dropped.** Present in the source spec (`signal-renaissance-primitives-ohlcv.md`), absent from every plan and the migration, with no explicit deferral note in the outline.
- **M2 — Baseline assumption gap: `session_time_pos`, `month_sin/cos`.** Research assumes these already exist in baseline `FeatureFactory`; codebase only has `dow_sin/cos` and `month_position`. Not implemented anywhere in these plans, so they simply remain missing.
- **M3 — `142.5-VALIDATION.md` references a 14-task/5-wave structure that no longer matches the consolidated 7-plan/4-wave structure**, making the verification map useless for tracking execution.

### LOW severity

- **L1 — Migration numbered `177`; current highest in `production/migrations/` is `201`.** Confirmed by directly checking migration files — actual next number is `202`.
- **L2 — Plan 05 frontmatter `files_modified` omits `src/intelligence/schemas.py`**, which Task 2 Step 4 does modify.

## Consensus Summary

### Agreed strengths (both reviewers)

- DAG invariants respected — `FeatureFactory` stays compute-only, stateless, and vectorized.
- APR mandate correctly applied to every lookback window.
- TDD protocol followed — Plan 00 establishes a red-state test surface before implementation.

### Agreed concerns — highest priority, both reviewers independently flagged these

1. **The plans do not implement everything the migration/APR/tests expect.** Both reviews landed on the same root defect from different angles: antigravity traced it to the 8 unimplemented Price-Volume Interaction primitives specifically; the internal pass traced it to a broader 3-way primitive-count mismatch (100 spec / 83 outline / ~77-79 implemented). These are the same gap described at different granularity — resolve by reconciling the primitive inventory once, not twice.
2. **Migration number `177` is wrong.** Both reviews independently checked the filesystem and confirmed the actual next number is `202`.
3. **Schema/column-count arithmetic doesn't tie out.** Antigravity found the precise mechanism (mislabeled category totals summing to 85, not 83, columns); the internal pass caught the same symptom as a 100/83/79 discrepancy. Fix the category labels and the total falls out correctly.
4. **Undocumented scope omissions** (Open-to-Close Split, Cross-Timeframe Divergences, Price-Volume Interactions) need an explicit IN/OUT decision recorded in the outline — not silently dropped.

### New in this pass (antigravity only — runtime-blocking, not previously caught)

- **`_cold_start_vector` will crash on any cold-start bar** once Plans 01-04's fields exist, because those plans never add fallback values for their new fields (only Plan 05 does). This is a distinct, more severe finding than the registry-count issue previously identified — it's a guaranteed `TypeError` on the very first cold-start bar processed, independent of database state.
- **`feature_registry` table itself is never seeded** with the 83 new rows (previously the concern was framed only as "`_REGISTRY_ROW_COUNT` constant not updated" — antigravity clarifies both the DB-seeding INSERT statements and the code constant are missing, and either alone still crashes startup).

### Divergent framing (not a real disagreement, worth noting)

- The two reviews count "how many primitives are missing/unimplemented" differently (77 vs 79 vs the internal pass's 79/83/100 triple). This is because the internal pass and antigravity partially disagree on whether "existing" temporal pairs and Interaction primitives should count against the phase's ~83 target. Resolve this by having the plan outline state, category-by-category, the canonical count — then both framings collapse to the same number.
