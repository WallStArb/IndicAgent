## Design decisions made here (Claude's discretion, recorded in the summary)

- Fresh scopes: `unstratified` (proposer cells, `regime = '_all'`), `regime_volatility`
  (disclosure, `regime` = the label), `member_window` (monitoring, one row per window,
  `regime = '_all'`). Term structure is the proposer's cells across the tf's horizons; it needs no
  scope of its own. With scope in the PK, `unstratified` and the last `member_window` row may share
  every other key column, which is exactly the collision todo 391 describes.
- Fresh rows set `training_window_end` to the latest target exit bar used by the cell
  (`TargetStack.max_target_end()`, or the window's for `member_window`), always before
  `oos_start`, so "no target window reaches oos_start" (D-19, checked by 186-28) is the query
  `training_window_end < oos_start` on v2. That is the only meaning the column carries in v2 and
  the only one the `COMMENT ON COLUMN` states; the legacy table's other meaning (a bar bound
  equal to oos_start) never enters v2, because the legacy table is never written and 186-28 drops
  it whole.
- Unit = (job, tf, feature block). Writer name in the spec is `ic_measure.<job>`. Identity:
  `code_key = kernel_code_key(job modules)`, `apr_snapshot` = every APR value the job read,
  `input_digest` = sha256 of canonical JSON of {per-symbol bar digests, feature block digest
  (names plus the sha256 of the aligned float values in (bar_ts, symbol, feature) order),
  regime label digest for disclosure, member list for monitoring}. A rerun with the same identity
  is skipped before IC compute; a changed identity replaces the unit's rows atomically
  (`bulk_load(..., replace_where=...)`, delete and COPY in one transaction).
- The writer is a synchronous psycopg oneshot (the `forward_return_writer.py` shape, with the D-06
  `job_completed_total` emitted by hand), because `bulk_load` and the write session are
  synchronous psycopg; `build_target_panels` (async, S0) runs through `asyncio.run` per tf from
  sync code. Compute is in-process and sequential per unit; the dry-run wall-clock is recorded so
  186-28 can decide on a worker pool from a measurement.
- Registration: `_DAG_ORDER` plus `_ONESHOT_UNITS` and a checked-in oneshot unit file.
  `_AGENT_ID_TO_UNIT` and `alert.lag.*` are keyed by the Kafka consumer-lag metric
  (`PERSISTENCE_CONSUMER_LAG`, label `agent_id`); a batch oneshot never emits it, and ic-engine and
  feature-lifecycle (same shape) have neither. Task 1 confirms this by reading
  `src/core/agent/base.py` and `base_batch.py`; if confirmed, no `_AGENT_ID_TO_UNIT` entry and no
  `alert.lag.*` key are added and the summary states why (outline wording adjusted on evidence).
  If a lag metric with `agent_id` is emitted for oneshots, add both.
