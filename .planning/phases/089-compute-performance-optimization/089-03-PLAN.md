<threat_model>
**Threat:** Batching the Kafka drain risks message loss under back-pressure if batch accumulation logic is wrong (e.g., dropping items on cancellation, partial flush on error).

- **Message loss under cancellation:** If the drain loop accumulates N items then the task is cancelled before publish, those N items must NOT be silently dropped. Mitigation: on `asyncio.CancelledError`, the loop must re-enqueue any in-flight batch back to the queue before propagating cancellation, OR publish synchronously before re-raising. Default to publish-before-re-raise.
- **Order guarantee within (topic, key):** Kafka guarantees per-partition order; batching must preserve insertion order. Mitigation: use `list.append` (FIFO) for batch accumulation; do not reorder.
- **Per-message error isolation:** If item N+5 in a batch raises during publish, items 0..4 are already sent and items 6..9 are not. Acceptance: errors on individual publish calls must not abort the batch (publish all, raise the first error after).
- **Empty-queue tight loop:** A naive batch loop could busy-wait. Mitigation: keep the existing `await asyncio.wait_for(get(), timeout=1.0)` for the first item; only attempt non-blocking `get_nowait()` for items 2..N.
- **No new endpoints, no auth, no DB writes.**
</threat_model>

<objective>
Convert `OutputQueue.drain_loop` from one-item-per-iteration to batch drain (up to N items, default 10, configurable via Settings).

Purpose: Amortize Kafka round-trip overhead across bursts; the queue fills faster than it drains during multi-symbol bar arrival, so per-item awaits are pure overhead. After this plan, drain throughput is bounded by Kafka network round-trip × ceil(burst/N), not burst × per-item-await.

Output: Modified `output_queue.py` with batch-aware drain loop and a unit test covering empty-queue, full-batch, partial-batch, and cancellation cases.

This plan runs in parallel with Plan 02 (different file, no shared imports).
</objective>

    Part A — extend `OutputQueue.__init__` with `drain_batch_size: int = 10` parameter. Store as `self._drain_batch_size`. Backward-compatible default.

    Part B — modify `drain_loop` body:
      ```
      while not self._stop_event.is_set():
          # Block for the first item (preserve current behavior — no busy loop)
          try:
              first = await asyncio.wait_for(self._queue.get(), timeout=1.0)
          except asyncio.TimeoutError:
              continue
          batch = [first]
          # Drain up to N-1 more items non-blocking
          while len(batch) < self._drain_batch_size:
              try:
                  batch.append(self._queue.get_nowait())
              except asyncio.QueueEmpty:
                  break
          # Publish the batch — preserve order; isolate per-item errors
          first_exc = None
          for item in batch:
              try:
                  await self._publish_one(item)  # existing publish helper
              except Exception as exc:
                  if first_exc is None:
                      first_exc = exc
                  self._logger.error("output_publish_failed", error=str(exc), item_key=item.get("key"))
              finally:
                  self._queue.task_done()
          if first_exc is not None:
              # surface to outer error handling — same behavior as today
              raise first_exc
      ```

    Part C — cancellation safety: wrap the inner publish block with `try/except asyncio.CancelledError` that re-enqueues any unpublished items in `batch` back to `self._queue` via `put_nowait` (best-effort) before re-raising. If the queue is full, log a critical message — this is acceptable because cancellation means the agent is shutting down anyway.

    Part D — wire from orchestrator: in `services/intelligence_pipeline_agent.py` where `OutputQueue` is constructed, pass `drain_batch_size=settings.intelligence_output_drain_batch_size`.
