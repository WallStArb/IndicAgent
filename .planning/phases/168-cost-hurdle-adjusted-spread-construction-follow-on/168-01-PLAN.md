Create `scripts/analysis/phase168_margin_calibration.py`: a read-only, re-runnable script that
measures `bps_per_feature_unit` — the empirical conversion from one unit of `ctf_momentum`
cross-sectional leg gap into basis points of realized gross spread — from the already-persisted
Phase 167 baseline construction.

Connection and config:
- Use `Settings().database_url.replace("postgresql+asyncpg://", "postgresql://")` and
  `connect_with_codecs(db_dsn)` (bare connection, read-only reporting branch — never
  `BaseBatch.create_pool()`; this script persists nothing).
- Load APR via `load_apr_dict_async(conn)` plus `cfg(...)`. Read
  `alpha.construction.cost_hurdle_bps_round_trip` (default `[1, 3, 5, 10]`) only to report the
  resulting margin at the binding tier `max(cost_bps)`. Do NOT read a hysteresis key — none
  exists yet; this script is what produces its value.
- Read the OOS boundary with the exact query
  `SELECT config_value::timestamptz FROM config_state WHERE config_key = 'alpha.validation.oos_start'`.
  Raise `RuntimeError` naming the missing key if it is NULL — a missing boundary would silently
  collapse the in-sample/OOS split into a single segment.

Measurement query (a single DB-side aggregation returning one row per bar; do NOT stream 2M+
panel rows into Python). Join `construction_spreads cs` to `feature_vectors fv` on
`fv.tf = cs.tf AND fv.bar_ts = cs.bar_ts`, filtered by `cs.construction_name = $1` (bound
placeholder, never interpolated), `cs.tf = $2`, and `cs.gross_spread_fast IS NOT NULL`. Group by
`cs.bar_ts, cs.gross_spread_fast` and select:
  - `cs.bar_ts`
  - `cs.gross_spread_fast`
  - `leg_value_gap`, computed as
    `avg(fv.ctf_momentum) FILTER (WHERE fv.symbol = ANY(cs.long_leg_symbols))`
    minus
    `avg(fv.ctf_momentum) FILTER (WHERE fv.symbol = ANY(cs.short_leg_symbols))`
Bind `ctf_momentum_decile_ls` as `$1` and `15m` as `$2`.

Query-plan verification (MANDATORY, before treating this script as done — see
`docs/foundation/performance-investigation-sop.md`: measure, do not assume). `feature_vectors`'
only indexes are `feature_vectors_pkey` on `(symbol, tf, bar_ts)` and `feature_vectors_bar_ts_idx`
on `(bar_ts DESC)`; neither leads with `(tf, bar_ts)`, so the join predicate above gives the
planner nothing to drive the `feature_vectors` side from and can degrade to a full sequential
scan of a multi-million-row table:
- Run the measurement query under
  `EXPLAIN (ANALYZE, BUFFERS)` against the live DB (via `psql`, or by prefixing the same SQL in a
  throwaway invocation) and read the `feature_vectors` access node.
- If that node is a bare `Seq Scan on feature_vectors`, add an explicit bar_ts range restriction
  so `feature_vectors_bar_ts_idx` becomes usable: bind `$3` and `$4` and add
  `AND fv.bar_ts >= $3 AND fv.bar_ts <= $4`, where `$3`/`$4` are the baseline partition's
  `min(bar_ts)`/`max(bar_ts)`, fetched in a preceding one-row query
  (`SELECT min(bar_ts), max(bar_ts) FROM construction_spreads WHERE construction_name = $1 AND tf = $2`).
  This is semantically a no-op — every joined `cs.bar_ts` already lies inside that window — so it
  cannot change the measured result; it only gives the planner a driveable range.
- Re-run `EXPLAIN (ANALYZE, BUFFERS)` and confirm the `feature_vectors` node is an index-driven
  access (`Index Scan`, `Index Only Scan`, or `Bitmap Heap Scan` fed by a `Bitmap Index Scan`).
- Record the final plan's `feature_vectors` node type and the query's total execution time in the
  plan summary (168-01-SUMMARY.md) either way.

Segment and reduce:
- Split rows into `in_sample` (`bar_ts < oos_start`) and `oos` (`bar_ts >= oos_start`).
- Drop rows where `leg_value_gap` is NULL, fails `math.isfinite`, or is `<= 0` — a non-positive
  decile-to-decile gap is a data-integrity signal, not a usable calibration point. Count drops
  and report the count once per segment; never log per row.
- For each segment, BEFORE dividing, run the degenerate-universe guard (fail loud, never NaN —
  CLAUDE.md: "Silent wrong answers are worse than loud crashes"). Raise `RuntimeError` whose
  message names the segment and the specific degenerate condition when any of:
    * `n_bars == 0` after drops — message must say the segment has no valid calibration bars
      remaining after dropping null/non-finite/non-positive `leg_value_gap` rows, and report
      `n_dropped`;
    * `mean_leg_value_gap` is `0.0`, fails `math.isfinite`, or is `<= 0` — message must say the
      mean leg value gap is degenerate and report the observed value.
  Only the IN-SAMPLE segment's failure is fatal to the run (it is the seed source). An OOS-segment
  degeneracy must be reported as `oos: DEGENERATE (<reason>)` with `drift_ratio` printed as
  `unavailable`, and must not abort the in-sample measurement — the OOS value is a diagnostic, and
  losing a diagnostic must not block seeding.
- Assert the units convention for `gross_spread_fast` explicitly rather than assuming it: it is a
  RAW dimensionless log-return spread (`spread_from_legs` returns a difference of mean
  `return_fast` values), NOT a value already in basis points — which is precisely why the formula
  below multiplies by `10000.0`. Encode this as a runtime check: raise `RuntimeError` naming the
  observed value if `abs(mean_gross_spread_fast) >= 1.0`, since a magnitude at or above 1.0 would
  mean the column is not a fractional return and the `10000.0` factor would be wrong. State the
  same convention in the module docstring and print it as a literal `units:` line in the summary
  block so the seeded APR value's derivation is unambiguous to the migration author.
- For each segment compute
  `bps_per_feature_unit = 10000.0 * mean(gross_spread_fast) / mean(leg_value_gap)`.

Derived margin (reported only — this script writes no config):
- `margin = binding_cost_bps / (2.0 * bps_per_feature_unit)` where `binding_cost_bps = max(cost_bps)`.
- Record the derivation in the script's module docstring: one single-symbol swap in one leg
  raises that leg's mean by `(v_challenger - v_weakest) / n_leg`, raising gross spread by
  `bps_per_feature_unit * (v_challenger - v_weakest) / n_leg` bp, while costing
  `binding_cost_bps * one_way_turnover` where a single one-leg swap yields
  `one_way_turnover = 1 / (2 * n_leg)` by that function's own definition. `n_leg` cancels,
  leaving the break-even condition
  `v_challenger - v_weakest > binding_cost_bps / (2 * bps_per_feature_unit)`.

Output: print a summary block and emit one structlog line containing, for BOTH segments:
`n_bars`, `n_dropped`, `mean_gross_spread_fast`, `mean_leg_value_gap`, `bps_per_feature_unit`,
`derived_margin`. Also print `drift_ratio` (OOS value divided by in-sample value) and an explicit
`DRIFT OK` or `DRIFT WARNING` line using a 0.5x-to-2.0x acceptance band (RESEARCH Pitfall 5).
The output must state that the IN-SAMPLE value is the one to seed and the OOS value is a
diagnostic only — calibrating on OOS data would leak the very window D-04's gate is measured over.

Use `except Exception as error:` (never `exc`) per CLAUDE.md. Exit non-zero on RuntimeError.
