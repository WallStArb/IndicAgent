# Phase 44.3 Plan 02: LLMWriterService i8 UPSERT Wiring Summary

**One-liner:** LLMWriterService gains i8 persistence via `development.intelligence.i8` subscription and plain `UPDATE intelligence_features SET i8` — consolidating all LLM data in one service with no phantom rows.

## What Was Built

Extended `LLMWriterService` to own i8 persistence, migrating it from `FeatureWriterService` (removed in plan 01). The service now subscribes to three Kafka topics and handles all LLM-related TimescaleDB writes.

### New Capabilities

| Component | Description |
|-----------|-------------|
| `_UPSERT_I8_SQL` | Plain `UPDATE intelligence_features SET i8 = $4::jsonb WHERE ts = $1 AND symbol = $2 AND tf = $3` — no phantom rows |
| `_i8_buffer` | Per-instance list buffer for i8 tuples `(ts_dt, symbol, tf, i8_json)` |
| `_process_i8_message()` | Parses i8 payload using `_parse_ts()`, builds i8 JSONB dict, appends to buffer |
| `_flush_i8()` | Calls `db_manager.execute_batch(_UPSERT_I8_SQL, batch)`, increments `i8_writes_total` |
| `topic_intelligence_i8` subscription | Added to `_setup_kafka_clients()` topic list alongside existing topics |
| i8 routing in `_process_loop()` | Routes `kafka_topic == i8_topic` messages to `_process_i8_message()` |
| Flush wiring | `_flush_i8()` called in `_maybe_flush()` finally block + `_shutdown()` |
| `i8_writes_total` | Prometheus counter for successful i8 UPSERTs |
| `i8_update_miss_total` | Prometheus counter for timing-window 0-row UPDATEs |

### Design: Plain UPDATE vs INSERT ON CONFLICT

The plan mandates `UPDATE` (not `INSERT ON CONFLICT DO UPDATE`) for i8 to avoid phantom rows. If `FeatureWriterService` hasn't yet flushed the base I1-I6 row for a `(ts, symbol, tf)` triplet when the i8 message arrives, an `INSERT ON CONFLICT` would create a stub row with only `i8` populated — missing all intelligence columns. A plain `UPDATE` that finds no matching row is silently safe (0 rows affected) and counted by `i8_update_miss_total` for observability. The i8 payload will be retried on the next flush cycle.

## Ownership Consolidation

After plans 01+02, all LLM data persistence lives in `LLMWriterService`:
- `llm_calls` hypertable writes (existing)
- `llm_calls` outcome back-fill UPDATEs (existing)
- `llm_model_scores` 15-min recompute (existing)
- `intelligence_features.i8` UPDATE (new in this plan)
