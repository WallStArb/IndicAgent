<objective>
Extract SignalProcessor as the final DAG node and collapse the orchestrator to a thin DAG router. SignalProcessor owns the I7 signal path: CIS scoring, regime gating, calibration, ToD adjustment, ranking, winner selection, and DLQ preparation. It returns a structured result to the orchestrator instead of enqueuing directly (Pitfall 8). After this plan, _process_bar_inner is the explicit DAG description from D-08 with full 4-way output routing.

**HIGH finding 2 (SignalProcessor ↔ CacheManager coupling) from REVIEWS.md:** The original plan had `SignalProcessor(cis_scorer, cache: CacheManager, settings)` directly holding CacheManager — this is lateral coupling that violates D-07. Fix: SignalProcessor receives cache values via a `CacheSnapshot` dataclass passed into `process()`. The orchestrator builds the snapshot from `self._cache_mgr` at the start of each bar:
```python
snapshot = CacheSnapshot(
    perf_weights=self._cache_mgr.perf_weights,
    calibration_curves=self._cache_mgr.calibration_curves,
    tod_priors=self._cache_mgr.tod_priors,
    drift_penalties=self._cache_mgr.drift_penalties,
    cis_weights=self._cache_mgr.cis_weights,
    cis_weights_version=self._cache_mgr.cis_weights_version,
)
result = await self._sig_proc.process(event, tiered, bar, symbol, tf, raw_signals=raw_signals, cache_snapshot=snapshot)
```
This means `SignalProcessor.__init__` does NOT take a `cache` parameter. The class never imports or references CacheManager. The orchestrator is the only mediator (true D-07 compliance).

**HIGH finding 4 (missing output paths) from REVIEWS.md:** The god class publishes to FOUR output topics, all of which must be preserved by the orchestrator:
1. `topic_intelligence_i7_signals` (signals_payload from prepare_signals_or_dlq success path)
2. `topic_signal_dlq` (dlq_payload from CIS assertion failure)
3. `topic_signals_aggregated` (winner payload — god class line 1544)
4. `topic_intelligence_journal` (via `_enqueue_intel_journal` helper — god class line 1683-1727)

Plus the canonical `IntelligenceEvent` publish that `_process_bar_inner` already does (not changed by this plan).

`SignalProcessor.process(...)` returns a `SignalProcessorResult` dataclass carrying all four payloads (`signals_payload`, `dlq_payload`, `winner_payload`, `i7_result`). The orchestrator routes each non-None field to the appropriate topic. **`_enqueue_intel_journal` REMAINS in the orchestrator** as a helper that uses the OutputQueue — it is not in scope for extraction in this plan. Confirm before finalizing: the journal helper does only `_enqueue` (non-blocking) and topic routing, no business logic.
