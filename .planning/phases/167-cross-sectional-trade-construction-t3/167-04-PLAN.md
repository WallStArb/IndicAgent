- `mean_gross_spread_over_bars(panel_by_bar: Mapping[Any, tuple[list[str], list[float],
  Mapping[str, float | None]]], decile_fraction: float) -> tuple[float | None, int]`
  The single shared per-draw reduction. For each `bar_ts` in the mapping, calls `decile_legs` on
  that bar's `(symbols, feature_values)`; if it returns `None` the bar is SKIPPED (identical
  degeneracy rule to the write path in Plan 03), otherwise calls `spread_from_legs` against that
  bar's returns and accumulates. Returns `(mean_spread_over_eligible_bars, n_eligible_bars)`, or
  `(None, 0)` when no bar was eligible. Used for BOTH the observed value and every null draw, so
  the two can never be computed over different bar sets.

- `shuffled_ranking_null_p(panel_by_bar: Mapping[Any, tuple[list[str], list[float],
  Mapping[str, float | None]]], decile_fraction: float, observed_mean_spread: float,
  n_shuffles: int, seed: int) -> tuple[float, float, float, int]`
  Returns `(null_p, null_mean, null_std, n_eligible_bars)`. Permutes each bar's feature values
  WITHIN that bar only (symbol list, universe size, and return mapping all untouched), re-runs
  `mean_gross_spread_over_bars` on the permuted panel, and computes
  `null_p = mean(draw_means >= observed_mean_spread)`. The returned `n_eligible_bars` is the
  count from the permuted draws and MUST equal the observed pass's count - the caller asserts
  this.

- `evaluate_spread_gate(rows: Iterable[Mapping[str, Any]], min_n: int, bootstrap_max_n: int,
  bootstrap_batch: int, bootstrap_random_state: int) -> list[dict[str, Any]]`
  Pure grouping/verdict core. Each input row carries `scale` (`"fast"` or `"slow"`), `cost_bps`
  (int), `cluster_id` (a `date`), and `pnl_r` (the net spread for that scale and tier). Delegates
  to `counterfactual_tracker.evaluate_frame_gate` with
  `group_key=lambda row: (row["scale"], row["cost_bps"])`. Returns one verdict dict per cell;
  `evaluate_frame_gate` populates the group key's two elements into fields named `tf` and
  `regime`, so this function must rename them to `scale` and `cost_bps` before returning
  (`alpha_scorer.py` handles the identical rename, see its module docstring's SHAPE CONSTRAINT
  note).

- `write_verdict_artifact(verdict_name: str, payload: Mapping[str, Any],
  out_dir: Path = Path("logs/construction_verdicts")) -> Path`
  Serializes `payload` to `{out_dir}/{verdict_name}_{YYYYmmddTHHMMSSZ}.json` (UTC, from
  `datetime.now(UTC)`) and additionally to `{out_dir}/{verdict_name}_latest.json`. Creates
  `out_dir` if absent. Coerces any non-finite float (NaN, +-inf) to JSON `null` and any
  non-serializable value via `default=str`, so the artifact is always parseable by a strict JSON
  reader. Returns the timestamped path. Reused unchanged by Plan 05 for the Gate 2 verdict.

<design_decisions>
1. **Gate 1 is evaluated on the OOS window (`bar_ts >= alpha.validation.oos_start`), not the full
   history.** The design doc's Gate 1 text says "Shadow spread portfolio on the OOS window."
   Note the direction: `counterfactual_tracker.py`'s FRAME-04 gate uses `bar_ts < oos_start`
   because it is deliberately an IN-SAMPLE exit gate; this gate is the opposite and must use
   `>=`. Copying the `<` comparison from that file would silently evaluate the wrong segment and
   produce a verdict that looks valid. The live value of `alpha.validation.oos_start` is
   `2025-12-24T05:15:00Z`, giving roughly 130 OOS trading days for the 15m corpus - enough
   day-clusters for a bootstrap CI.

2. **The in-sample segment is reported as a labeled diagnostic, never as the gate.** T3's
   published numbers (fast 5.9bp/bar `ci_lower`=5.6bp, slow 11.1bp/bar `ci_lower`=9.7bp) were
   measured over the FULL 2006-2026 history. Reporting the in-sample segment alongside the OOS
   verdict makes that comparison possible without letting in-sample evidence contaminate the
   verdict. Label it explicitly as `segment="in_sample_diagnostic"` in the log payload and in the
   verdict artifact, and never include it in the pass/fail computation.

3. **The verdict is reported per (scale, cost_bps) cell - all eight - and the binding Gate 1
   verdict requires the MOST CONSERVATIVE tier to pass at BOTH scales.** T3's own cost treatment
   was a sweep, not a single number (D-05), and reporting only the cheapest tier would be the
   optimistic reading. Taking the maximum configured `cost_bps` (10 by default) as binding is the
   conservative reading and matches the discipline that produced Phase 148's honest DO-NOT-PROMOTE
   verdict. The full binding rule, stated once here as the single source of truth so it cannot
   drift later: **Gate 1 passes iff, at `max(cost_bps)`, BOTH the `fast` and `slow` cells have
   `passes is True`, AND both scales' `null_p` is strictly below `0.05`.** Plan 06 Task 3 must
   reproduce this sentence verbatim in `trade-construction-layer.md` so the acceptance rule lives
   in the governing doc and not only in a plan file.

4. **The shuffled-ranking null is recomputed live at every evaluation.** It cannot be derived from
   persisted `construction_spreads` rows - a permutation of the ranking produces different legs,
   so the raw panel must be re-queried for the OOS window. That window is small (roughly 3,400
   bars x 80 symbols), so 40 permutations are cheap. Hardcoding "the null was cleared at
   P=0.0000" from this session's script output would be exactly the anti-pattern RESEARCH.md
   names for the cost hurdle, applied to the null instead.

5. **No new bootstrap implementation.** `frame_gate_passes` is reused verbatim via
   `evaluate_frame_gate`. RESEARCH.md's Todo 186 Scope Assessment is explicit: a spread return is
   ONE scalar per bar, not a pooled panel, so the day-clustered BCa/CLT bootstrap is the correct
   object and todo 186's cross-sectional block bootstrap is NOT required for this phase. Do not
   add a task for it.

6. **The null universe is defined by construction, not by assertion.** Addresses Codex's HIGH
   concern ("the plan does not spell out what happens with tied feature values, missing values,
   or bars with too few eligible symbols - those edge cases can materially change the null
   distribution") and its follow-up suggestion ("state whether the within-bar permutation
   preserves universe size, decile fraction rounding, and symbol eligibility filters exactly").
   The resolution is structural rather than defensive: both the observed value and every null
   draw go through the SAME function, `mean_gross_spread_over_bars`, over the SAME
   `panel_by_bar` mapping, with only the feature vector permuted. Therefore:
   - Universe size per bar is identical in observed and null (permutation is a reordering of one
     bar's values across that same bar's symbols).
   - `n_leg` rounding is identical, because it is derived from the same `n` and the same
     `decile_fraction`.
   - Symbol eligibility is identical, because eligibility was already applied by the panel query
     and the permutation never adds or removes a symbol.
   - Bars where `decile_legs` returns `None` are skipped identically in observed and in every
     draw, since degeneracy depends only on `n` and `decile_fraction`, neither of which a
     permutation touches.
   - Tied values permute like any other values; `decile_legs`' `(feature_value, symbol)`
     tie-break applies unchanged, so a tied draw yields a deterministic split rather than an
     arbitrary one.
   - Missing feature values cannot appear: `decile_legs` raises on them (Plan 02 design
     decision 5) and the panel query filters `ctf_momentum IS NOT NULL` upstream.
   Because "identical by construction" is a claim about code that can be broken by a later edit,
   `shuffled_ranking_null_p` returns `n_eligible_bars` and `_run_evaluate_gate` asserts it equals
   the observed pass's count, failing loudly if the two ever diverge. Task 2's tests verify these
   properties on a panel deliberately containing both a degenerate bar and a fully-tied bar,
   rather than asserting them in prose.

7. **The full verdict is persisted as JSON before anyone reads it.** Addresses Codex's
   suggestion and this phase's own T-167-17 threat (verdict transcription fidelity). Log lines
   are session-scoped and rotate; `trade-construction-layer.md`'s prose is hand-written and
   editable. Neither is a durable, diffable source of truth for "what did the gate actually say."
   `write_verdict_artifact` adds one: a timestamped JSON file carrying the entire payload -
   the eight-cell OOS grid, both `null_p` values, the binding tier, `gate1_passes`, the in-sample
   diagnostic cells, the OOS boundary, the day-cluster count, and every APR value in force.
   Timestamping means a later run never overwrites an earlier verdict, so the record accumulates.
   This is an audit-trail addition only: it introduces no new statistic, no new bootstrap, and no
   new threshold. Non-finite floats are coerced to JSON `null` because `frame_gate_passes`
   legitimately returns `nan` for an under-powered cell, and a bare `NaN` token is invalid JSON
   that a strict reader would reject - silently losing the very record this exists to preserve.
</design_decisions>

|----------|-------------|
| `config_state` (`alpha.validation.oos_start`, `alpha.scoring.*`, `alpha.construction.*`) -> gate verdict | Operator-mutable values determine which segment is evaluated and what counts as passing; a wrong or missing value silently changes a research verdict |

| Observed measurement vs. null draws -> `null_p` | If the two are averaged over different bar sets, `null_p` compares unlike quantities and the null verdict is meaningless while looking valid |
| Gate verdict -> durable record | Log lines rotate and prose is editable; without a machine-readable artifact the verdict has no diffable source of truth |

writes at all; its only filesystem side effect is the verdict artifact. ASVS V2/V3/V4/V6 all
