<objective>
Turn Plan 02's pure functions into a real recurring service: `CrossSectionalSpreadTracker`, a
`BaseBatch` oneshot that incrementally scans the 15m equity panel, forms the decile spread at
each bar, computes turnover against the previous run's persisted leg membership, applies the
live cost-hurdle sweep, and writes one `construction_spreads` row per bar.

Purpose: this is the difference between a research script and a monitored construction. The two
genuine engineering problems RESEARCH.md identifies (Pattern 1: incremental watermark scoping;
Pattern 2 / Pitfall 4: turnover across run boundaries) are both solved here, and both are proven
by an integration test rather than assumed.

Output: the service class, its `--backfill` CLI entrypoint, and an integration test that runs
the service twice against a seeded test database and asserts incremental behavior.
</objective>

`class CrossSectionalSpreadTracker(BaseBatch)`:
- `job_name = "cross-sectional-spread-tracker"` (kebab-case, D-06 contract)
- `compute_version = "1.0.0"` (stamped on every persisted row)
- `__init__(self, db_dsn: str, backfill: bool = False) -> None`
- `async def execute(self, pool: asyncpg.Pool) -> None` (BaseBatch's abstract method)

Panel query contract (the exact filter set D-01/D-04 lock, reproduced from the T3 script's
`_FV_SQL` at lines 63-78):
- `feature_vectors fv` JOIN `forward_returns fr` on `(symbol, tf, bar_ts)` JOIN `instruments i`
  on `symbol`
- `fv.tf = '15m'`, `fv.ctf_momentum IS NOT NULL`
- `fr.return_type = 'executable_open_to_open'` (CLAUDE.md Invariant 1 - non-negotiable)
- `fr.complete_fast = true AND fr.complete_slow = true`
- `i.is_active = true AND i.contract_details->>'asset_class' = 'equity'`
- incremental mode adds `AND fv.bar_ts > $2` (the watermark); `--backfill` omits it
- `ORDER BY fv.bar_ts ASC` (required - the streaming scan detects bar boundaries by change)

CLI surface (extended by Plans 04 and 05):
- `python services/cross_sectional_spread_tracker.py` - incremental compute-and-persist
- `python services/cross_sectional_spread_tracker.py --backfill` - full-corpus first pass

<design_decisions>
1. **No systemd timer in this phase - decided explicitly, not defaulted.** RESEARCH.md Open
   Question 3 / Assumption A4 leaves this genuinely open, so this plan resolves it. Decision:
   manual/on-demand only, with a documented runbook note (Plan 06). Four reasons, in order of
   weight: (a) `alpha_scorer.py`, `counterfactual_tracker.py`, and `tag_calibrator.py` are all
   manual/on-demand with no systemd unit - registering one here would make this service the
   outlier; (b) CLAUDE.md's "prove edge before production infra" - a construction that has not
   yet cleared its own Validation Gates does not earn scheduled infrastructure; (c) CLAUDE.md
   records that all indicagent systemd timers are confirmed disabled as of 2026-07-02, so a
   registered timer would create a false impression of a cadence that does not actually run;
   (d) RESEARCH.md's counterargument - that Gate 1 needs an accumulating OOS track record - is
   answered by the `--backfill` pass, which populates the full 2006-2026 history in one shot and
   hands Gate 1 roughly 130 OOS day-clusters immediately rather than waiting on calendar time.
   Revisit only if this construction clears all three gates and heads toward Phase 156-159.
   Corollary: do NOT add this service to `service_auditor._DAG_ORDER` and do NOT seed an
   `alert.lag.*` key for it.

2. **Streaming server-side cursor, not a full-corpus DataFrame.** The T3 script loads all ~8.79M
   panel rows into one pandas DataFrame; correct for a one-off, but exactly the unbounded
   client-side accumulation shape that has caused OOM incidents in `ic_engine` and
   `counterfactual_tracker` in this codebase. Because the query is `ORDER BY bar_ts ASC`, the
   service holds only the current bar's cross-section (at most ~80 rows) plus the previous bar's
   leg frozensets, emitting one output row at each `bar_ts` boundary. Peak memory becomes
   independent of corpus size.

3. **`ON CONFLICT (construction_name, tf, bar_ts) DO NOTHING`, not `DO UPDATE`.** A re-run over
   an already-processed range must be a no-op, not a rewrite: `construction_spreads` rows are an
   immutable measurement record, and silently rewriting them would let a config change
   retroactively alter a gate verdict's inputs with no audit trail. If the construction genuinely
   changes, `compute_version` changes and the table is truncated via
   `infrastructure_truncate_derived_tables.sh` (registered in Plan 01).

4. **No ProcessPoolExecutor.** Unlike `ic_engine`/`counterfactual_tracker`, which parallelize per
   symbol, this job is one sequential pass over ordered bars with a cross-sectional reduction at
   each - there is no per-symbol independence to exploit, and the turnover chain is strictly
   sequential by construction. This is why Plan 01 seeds no
   `infra.cross_sectional_spread_tracker.workers` key.
</design_decisions>
