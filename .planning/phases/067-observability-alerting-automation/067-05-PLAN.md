## Renaissance Goal

**Close the observability gap for two PnL-critical services.**

**CrossAssetService** computes spread z-scores (ES/NQ, ES/RTY) that feed directly into I7 signal plugins. When it crashes silently, spread signals disappear, degrading signal quality and leaking PnL. Detection time today: manual log inspection, hours to days.

**LLMWriterService** persists LLM call audits + model scores. When it crashes, training data has gaps and model scores go stale. Detection time today: manual log inspection, hours to days.

**After migration:** Both services inherit BaseAgent's crash metrics, setup tracking, stall detection, and alert publishing. Grafana alerts fire within 60 seconds. Telegram notification reaches ops instantly. Service restarts within 5 minutes. PnL impact minimized.

## Renaissance Decision Framework

### Jim Simons' 5 Questions

**1. What's the SIGNAL here?**
- CrossAssetService: ES/NQ, ES/RTY spread z-scores → consumed by I7 plugins → DIRECT PnL impact
- LLMWriterService: LLM call audits, model scores → training data quality → INDIRECT PnL impact

**2. What's the COST of NOT knowing?**
- CrossAssetService crash: No spread signals → degraded I7 performance → lower win rate → PnL leak
- LLMWriterService crash: Training data gaps → stale model selection → suboptimal PnL
- MTTD (Mean Time To Detect): Hours to days (manual log inspection)

**3. What's the COST of KNOWING?**
- One-time: ~450 lines (CrossAssetService ~150, LLMWriterService ~100, tests ~200)
- Ongoing: <0.1% runtime overhead (metrics cached at init, stall detection uses monotonic clock)
- Time: 2-3 hours

**4. Is this MEASURING or INFERENCE?**
- **Measuring:** agent_crash_total (COUNT of crashes), agent_setup_* (bootstrap health), max_idle_seconds (stall detection)
- **NOT Inference:** WHY it crashed (stack traces in logs), WHAT to do (human judgment)

**5. Where's the FEEDBACK LOOP?**
```
Service crashes → agent_crash_total++ → Grafana alert (CRITICAL)
               → Telegram (instant) → manual restart → PnL resumes
```
Time to detection: <60 seconds. Time to resolution: ~5 minutes.

### Renaissance Principles Compliance

| Principle | How This Plan Complies |
|-----------|------------------------|
| **Single Responsibility** | ONLY convert legacy services → BaseAgent. No new features, no observability patterns. |
| **Modularity** | Each service migrates independently. CrossAssetService doesn't block LLMWriterService. |
| **Reuse** | BaseAgent features ALREADY EXIST. Migration = "use existing features" not "build new." |
| **Efficiency** | Metrics cached at init (no per-message allocation). Stall detection uses monotonic clock (no syscalls). |
| **Simplicity** | Single pattern: inherit from BaseAgent. No configuration files, no agent-specific logic. |
| **Instrument Everything** | Crash + stall metrics are foundational. Measure WHAT MATTERS for PnL first. |
| **Earn the Right** | Shadow mode first (metrics collected, no alerts). Tune thresholds from real data. Then enable alerts. |
| **Data Quality** | No impact on data flow. Migration is observability-only, no logic changes. |

## Threat Model

- **Migration breaks existing behavior:** Risk is LOW. BaseAgent is a superset of existing functionality. Legacy services use `setup_service_logging`, `start_metrics_server`, SIGINT handlers — BaseAgent provides all of this. Migration REPLACES custom lifecycle with STANDARD lifecycle.
- **Metrics overhead:** Negligible. Metrics are cached at init (`self._crash_total = AGENT_CRASH_TOTAL.labels(...)`). Runtime cost is one `inc()` call on crash (rare event).
- **Stall detection false positives:** Possible if `max_idle_seconds` is too aggressive. Mitigation: Shadow mode first (collect metrics, no alerts). Tune threshold from real data (95th percentile of idle time).
- ** systemd unit changes:** REQUIRED. Old unit calls `CrossAssetService().start()`, new unit calls `CrossAssetComputeAgent().start()`. Document in plan.
- **Kafka topic changes:** NONE. CrossAssetService still publishes to `cross_asset` topic. LLMWriterService still consumes from `llm.calls` + `llm.outcomes`. No downstream impact.
