## Renaissance Decision Framework

### Why This Can't Be Deferred

**My previous (wrong) reasoning:**
> "Measure first with Plan 05, let data speak. Most agents don't NEED stall detection."

**Renaissance correction:**

**1. You can't measure what you don't instrument**
- `agent_crash_total` doesn't tell you WHY an agent crashed
- `agent_stall_detected` doesn't exist if `max_idle_seconds=0` (disabled)
- Consumer lag doesn't exist if agents don't emit `PERSISTENCE_CONSUMER_LAG`
- **Renaissance principle:** Build the instrument FIRST, then measure

**2. Stall detection costs almost nothing**
- Runtime overhead: <0.1% (monotonic clock check every 10-60 seconds)
- One-time cost: ~100 lines (add `max_idle_seconds=300` to `__init__`, call `_record_message_consumed()`)
- **Renaissance principle:** Efficiency vs Simplicity — cheap to enable, expensive to be blind

**3. "Let the system run" requires visibility**
- If 40% of agents have no stall detection, we're NOT letting the system run
- We're flying blind on 40% of the pipeline
- **Renaissance principle:** "Let the system run" assumes you can SEE the system running

**4. Consumer lag IS the bottleneck signal**
- Consumer lag tells you WHERE the pipeline is slow
- Consumer lag tells you WHICH agent is the bottleneck
- Without it, you can't optimize compute costs
- **Renaissance principle:** Compute costs matter. Measure them.

### Renaissance Verdict

**DO IT NOW.** Here's why:

1. ✅ **Instrument Everything:** Complete the observability foundation
2. ✅ **Simplicity:** Single pattern (`max_idle_seconds=300`, `_record_message_consumed()`)
3. ✅ **Efficiency:** <0.1% runtime overhead
4. ✅ **Modularity:** Each agent enabled independently
5. ✅ **Reuse:** BaseAgent features ALREADY EXIST
6. ✅ **Data Quality:** No data drops, just visibility
7. ✅ **Compute Costs:** Consumer lag identifies bottlenecks

**Jim Simons would say:**
> "Why would you fly blind on 40% of your pipeline? Enable the instrumentation. If the agents never stall, great — we spent 100 lines for peace of mind. If they do stall, we'll know NOW, not next week."

## Threat Model

- **Stall detection false positives:** Possible if `max_idle_seconds` is too aggressive. Mitigation: Use conservative default (300s = 5 min), tune from real data.
- **Consumer lag overhead:** Negligible. One Prometheus metric emit per 15-second loop.
- **Message recording overhead:** Negligible. One monotonic clock timestamp per message.
- **Backward compatibility:** Full. Adding `max_idle_seconds` and `_record_message_consumed()` doesn't break existing behavior.

- [ ] **Override `_report_consumer_lag()` in each agent:**
  ```python
  # services/bar_auditor_agent.py
  async def _report_consumer_lag(self) -> None:
      """Report consumer lag for bars topic."""
      if not self._consumer or not self._consumer._consumer:
          return

      try:
          # Get lag from Kafka consumer
          lag = await self._consumer.get_consumer_lag()
          for tp, offset in lag.items():
              PERSISTENCE_CONSUMER_LAG.labels(
                  agent=self.name,
                  topic=tp.topic,
                  partition=tp.partition
              ).set(offset.lag)
      except Exception as exc:
          self.logger.warning("consumer_lag_fetch_failed", error=str(exc))
  ```
