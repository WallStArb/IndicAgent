## Findings, ranked

### 1. HIGH - fabricated 1d "restatements" from partial-session bars (--revisions backfill and the live 1d path)
- scripts/ops/bars/ops_raw_backfill.py:409-450 (superseded_runs_cte), :606 run_revisions; live path scripts/infrastructure/backfill/_history_fetch_item.py:251-289 + _d1_gaps.py:273-281 (the planner deliberately asks the forming session).
- Verified: of the 7,440 smart_trades rows the reconstruction logged as origin raw revisions, 929 come from requests answered before 20:00 UTC on the bar's own date (932 before the next day). Example: AAPL 2026-09-30, request answered 18:01 UTC, old_close 336.06 / old_volume 18,144,016 vs raw 333.02 / 26,694,290. That is a forming bar completing, not IBKR restating its history. These rows now count as vendor revision evidence (split detection, refusal statistics, plan 07 gates).
- Live repeat: the 1d planner asks today's forming session (`forming` logic), the fetcher timer runs every 15 min, and ohlcv_raw is last-wins, so every intraday run writes the partial bar and the next run logs the previous partial as an origin raw revision.
- Fix: backfill: exclude from superseded runs any run whose first serve was answered before the session close of bar_date (NYSE session map), and delete the 929 rows' loads (or re-run --revisions with --force after the filter). Live: do not offer a 1d bar to raw whose session has not closed at answered_at (keep the request row; the bar is not a vendor answer for the day), or store it under a distinct kind. Neither should be left as an origin raw revision.

### 2. HIGH - resuming the fetcher before plan 06 silently stops 1d (canonical and split detection) while reporting success
- _d1_gaps.py:166-170 (planner reads ohlcv_observation), services/split_detection.py:60-83 (_OVERLAP_PAIRS_SQL reads ohlcv_observation by fetch_run_id), fetcher run-end daily stage (_DERIVATION_SCRIPT, bar_derivation reads D1).
- 1d answers now land only in ohlcv_raw. Consequences: (a) every session after the cutover stays a "gap" forever, re-asked each run; (b) `overlap_pairs(conn, fetch_run_id)` returns nothing, so no split is ever recorded in corporate_action; (c) with no corporate_action, `_WAIVER_SQL` never licenses a 5m escalation (ohlcv_history_fetcher.py:221-228), so a post-split 5m overlap breach is reported unwaived forever; the update-lane overlap (3 days x 78 bars = 234 < revision_ratio_min_stored 500) is still written, so raw/canonical 5m become mixed-scale silently; (d) the daily stage derives nothing new, canonical 1d freezes at the cutover while items report ok.
- Fix: keep the fetcher timer held until plan 06 (planner, coverage) AND the plan that moves split detection and the daily rule onto raw. Add a guard in the fetcher (refuse to start when the cutover record holds any reader module it invokes in-process).

### 3. HIGH - the fetcher runs held modules in-process; the window's per-unit hold does not cover them
- scripts/ops/bars/ops_raw_cutover_window.py:206-220; READER_MODULES lists bar_derivation, split_detection, ohlcv_coverage_writer, bar_hold. The fetcher service invokes bar_derivation.py as a subprocess and split_detection/bar_hold/coverage in-process.
- `resume --unit indicagent-ibkr-history-fetcher.timer` after clearing only that unit starts the timer, which starts the (uncleared) fetcher service, which runs bar_derivation even though indicagent-bar-derivation.service is uncleared. resume_unit checks only the named unit.
- Fix: resume_unit refuses a timer whose target service is uncleared, and refuses any unit whose ExecStart module imports or spawns another uncleared module (or simply: the fetcher pair is resumable only with bar-derivation cleared).

### 4. HIGH - Alpaca 5m load never reaches canonical, and the loader reports success
- services/bar_load.py:96-144, ops_bar_nightly.py:139-144, bar_source_policy 5m row = (primary ibkr, no fallback), src/intelligence/bars/selection.py:77-93.
- Verified: ZWS 5m canonical 2024-01-02..2026-10-09 is 53,928 alpaca rows with zero IBKR raw. A nightly `load_series` writes (alpaca, sip_rth) raw, then select_and_write ranks only ibkr: select_slot returns None, no canonical row. The coverage upsert (DESTINATION_GRID, provider alpaca) still credits new rows. ops_bar_nightly ignores `result.refused`/`n_held` entirely and prints APPLIED. The fetcher planner (reads canonical for 5m) then sees the slots missing.
- Separately, wherever IBKR raw exists in the Alpaca window, an Alpaca load rewrites canonical to IBKR. (The IBKR-over-Alpaca direction is acknowledged in the 05 summary; the "Alpaca rows never selected + coverage credited" direction is not.)
- Fix: do not run ops_bar_nightly / ops_bar_load until plan 07 seeds Alpaca policy spans; make load_frame skip the coverage upsert when selection wrote nothing for an alpaca-only slot set; make ops_bar_nightly count refused/held and exit non-zero like ops_bar_load.

### 5. MEDIUM - Alpaca extended-hours bars stored as kind sip_rth and will be promoted to canonical 5m once Alpaca is ranked

### 6. MEDIUM - canonical selection has no slot lock: concurrent writers of different (vendor, kind) can crash or leave canonical not equal to selection over committed raw
- services/bar_selection.py:121-144 (plain INSERT for new slots, ON CONFLICT upsert for changed), lock is per series only (ohlcv_raw_writer.py:73, :266).
- Scenario A: T1 fetcher writes ibkr/named rows for X 5m, T2 store_bars (backfill_feature_factory, no FetcherLock) writes ibkr/venue rows for the same slots. Neither sees the other's uncommitted raw; both find the canonical slot absent and INSERT; T2 fails on the unique key after T1 commits and rolls back its whole chunk (raw plus request rows). Scenario B (after plan 07 ranks alpaca): T2 computes its winner without T1's raw, waits on T1's row lock, then overwrites T1's canonical choice: canonical now disagrees with policy over committed raw, silently, until a rebuild.
- Fix: in apply_raw_contract take `pg_advisory_xact_lock(hashtextextended(symbol||'|'||timeframe, 1))` for each (symbol, timeframe) in sorted order right before select_and_write (after all series locks; consistent order, no cycle), and make the new-row write ON CONFLICT DO UPDATE.

### 7. MEDIUM - an unchanged re-offer of a refused series duplicates the whole pending hold every time; the item then loops to exclusion
- services/ohlcv_ingress_contract.py:323-374; _history_fetch_item.py:372-385, :759-762.
- A refused 5m chunk (up to 150 days, about 11,600 bars) fails the item (status error) so the next run is full-window; the refused new bars are absent from canonical so the planner re-asks them; the same chunk is refused again and every changed and new row is written again as origin pending under a new load. With max_consecutive_failures = 5 that is about 6 x the chunk per series before the series is excluded from fetching (no new bars at all thereafter). Nothing dedupes pending rows against an identical earlier hold.
- Fix: in hold_pending skip offered rows whose identical value is already pending for the same key (or record only the load row on an identical re-offer), and have the queue treat a refusal as a held state (no refetch) rather than a failure that forces the full window.

Any refusal through apply_raw_contract inserts origin 'pending' and raises a check violation, rolling back the chunk including its request rows. Acknowledged in the 05 summary; listed so it is a resume precondition, not a note.

### 9. MEDIUM - cutover `open` that aborts and is re-run loses the timers' resume action
- ops_raw_cutover_window.py:154-191. Timers are stopped before the bounded wait; on WindowError nothing is recorded. The documented remedy ("rerun open once they exit") records active_at_open=False for the timers it already stopped, so resume_action = "none" and `resume` never restarts the fetcher timer. The live record is correct (timers recorded "start"), so this is latent.
- Fix: write the record (with the pre-stop active state) before stopping anything, or persist active_at_open on first open and reuse it on retry.

### 10. MEDIUM - archive-over-canonical reconcile assumes the archive serve is the later one without evidence
- ops_raw_backfill.py:678-703, :805-811; bulk pass order archive -> observation -> canonical with ON CONFLICT DO NOTHING.
- The canonical row carries no serve time. The old system wrote the archive in two ways where the archive value is OLDER than canonical: a refused chunk archived (archive_refusal_rows) followed by a later waived or accepted write to canonical. In that case raw current now holds the old (refused) value and the newer accepted canonical value is logged as "superseded". I verified that the 75 historical refused loads (583,026 archived rows, all 5m ibkr, 2026-10-10..13) were cross-vendor (MCD: 536 changed slots were alpaca canonical, 10,998 ibkr_named equal), so they do not trigger this; GE 2021-09..11 (4,661 rows, archive archived 2026-10-12 12:14, canonical differs by about 0.007%) could not be ordered from the data. Not shown to have fired.
- Fix: order by evidence: compare archived_at with the latest ohlcv_load (destination market_data_ohlcv, applied) covering the key; when canonical is later, keep canonical as raw current and log the archive value.

### 12. LOW - request sink restore can duplicate rows after an ambiguous commit
- services/ohlcv_request_writer.py (flush, `except BaseException: restore`). A CancelledError or connection loss during COMMIT after the server committed restores the rows; the next flush re-inserts them, hits the request_id key, and the buffer is stuck failing. Fix: on restore after an exception raised from the commit itself, check existence of the request_ids before re-flushing.

## Verified sound
- Series advisory lock: transaction-scoped, taken before the stored read in preview_series and write_raw, re-entrant, sorted series order within a call; every caller runs the whole contract synchronously inside one transaction (persist helper, store_bars, load_frame), so no lock is held across an await or network call. One apply per transaction in all callers.
- preview/write agreement: under the lock the agreement check cannot fire except on a code bug.
- Refused series: write_raw is never called, selection skips the (symbol, timeframe), coverage is not moved, request rows commit with NULL digest. A refused value cannot reach raw current or canonical through this path (given 477 applied).
- Same-key-twice raise: every provider path hands one request's chunk per call (on_chunk per chunk, on_observation per request, venue walks per venue); the defensive re-persist filters by `persisted`. I found no legitimate fetch that offers one key twice with different values.
- Transaction boundary: raw, load, revision, request rows and coverage in one transaction; raw before request rows inside it, so no orphan either way. All store_bars callers use autocommit connections, so `conn.transaction()` is a real top-level transaction.
- Daily kind: SMART TRADES -> smart_trades, venue walks -> venue_<route>; intraday kind from the bar label.
- Waiver: passes straight through to should_refuse; a waived write replaces raw and logs origin raw revisions.
- Migrations 475 (rerunnable: mapping UPDATE filtered on NULL, pkey drop/re-add by name, NOT NULL idempotent; ordinary table, no VACUUM owed), 476 (ON CONFLICT DO NOTHING), 477 (DROP IF EXISTS, constraint only).
- Cutover record: resume refuses uncleared units; `resume --all` refuses while any unit is uncleared; ctl runs before the record drops a unit.
