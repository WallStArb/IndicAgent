# Review: plans 191-11 and 191-09

Scope: 3b23c8c5b..8da3e31cb (191-11), 1513a7d50..12f43ee1b (191-09). Read-only; SELECT-only checks.

## Findings (ranked)

1. MEDIUM - R6 `changed` term has no lower bound, and `lost_new` can be masked.
   `ops_capture_completeness.py` checks `current <= new + changed` (unledgered) and
   `new - removed - current <= 0` (lost_new), but nothing checks that changed rows still exist.
   `current` counts every raw row whose load_id is a ledgered load, so a changed row (whose old
   value was backfill, load_id NULL) inflates `current` and can hide the deletion of a new row in
   the same (source, timeframe). Live evidence: tradier 1d has changed=574, current=0 and the
   check prints OK; ibkr 1d has new+changed=197,479 vs current=190,964 (6.5k unaccounted, passes
   because only `new` is bounded). Live run today: unexplained=0 everywhere, so no known gap, but
   the check cannot prove it. Fix: require `current >= new - removed + changed_of_ledgered_rows`
   per series, or count per load_id (current rows by load_id vs n_new+n_changed minus later
   overwrites via ohlcv_revision.load_id), and make tradier's 574 explainable (stamp or exclude).
   Also the ledger counters are self-reported by the writer; `served` is never compared with
   an independent source (ohlcv_request n_bars), so `ledger_gap` only checks writer arithmetic.

2. MEDIUM - D7 `value_as_of` mixes clocks and treats NULL served_at as always held.
   `current` rows with served_at NULL (backfill-written) count as held at any `at`, so a
   backfill row inserted after the run end pairs as if present (lookahead, 1d only, small).
   The 5m restamp load (refusal-rejudge-191) moved served_at forward without a value change;
   any as-of read of those rows returns None. Not hit by the 1d adjusted pairing, but the helper
   is general. Compares ohlcv_load.loaded_at (displaced) with raw served_at (current) plus a 5 s
   `load_match_s` window; fine for 1d, brittle elsewhere. Fix: document the 1d-only scope in the
   docstring or treat NULL served_at as unknown (None) and add a restamp guard.

3. LOW/INFO - 491 lineage semantics are correct, but the signal is large.
   Join is safe: raw key plus (vendor, kind) is unique, CASE pins vendor and kind per source,
   IS NOT DISTINCT FROM on OHLCV, so at most one match and no cross-vendor match. Inner JOIN to
   ohlcv_request drops raw rows with no request (stated, returns NULL). 2,285 newly NULL bars are
   real restatements, verified: CTVA canonical 47.86 vs raw smart_trades 8.59 on 2023-12-19
   (IBKR rebased TRADES history; 1,848 CTVA bars NULL). Not a defect, but nothing in the
   daily stage re-derives them yet: confirm 191-12 or the integrity report owns that, else
   canonical stays stale on 241 names.

4. LOW - 492 ohlcv_venue_head: correct. `substr(kind, 7)` strips `venue_`; `LIKE 'venue\_%'` is
   escaped; smart_head uses route='SMART' to exclude legacy import. A name with venue rows and
   no SMART row gets pre_move true, same as 442. The reported 10 smart_head_date diffs are real
   new SMART serves.

5. LOW - Deleted scripts: no live caller. Repo-wide grep (excluding docs and .planning), plus
   production/ and /etc/systemd/system and crontab: only comment/string mentions remain in
   `_fetcher_lock.py`, `ops_legacy_restamp.py`, `bar_reconciliation_audit.py:159` and
   `test_single_writer_registry.py:123` (retire note for 191-16). No unit, timer or cron.
   Migration 490: deletes history, state, schema by literal key in one transaction, idempotent,
   reader grep recorded, backup path named; safe. Rollback CSV existence under
   data/backups/191-11/ was not re-verified.
