# Review: phase 191 plans 01-03 (ohlcv_raw writer, selection, request writer, raw backfill, migrations 473/474)

Reviewer: Claude (Opus 5.5), 2026-10-13. Read-only: code reading plus SELECT queries on the live database. Nothing in the repo was edited.

## Ranked findings

### 1. HIGH: kind `venue` merges different IBKR listing-venue routes into one key, so cross-venue differences become "self-restatements" and all but one venue answer is lost

- Where: `src/intelligence/bars/vendor_kind.py:119-120` (`observation_kind`: any non-SMART IBKR TRADES route -> `venue`), used by `scripts/ops/bars/ops_raw_backfill.py:99-105`, `:170-207` (current_obs) and `:399-440` (superseded runs, partitioned by `symbol, bar_date, vendor, kind` with no route).
- What is wrong: AMEX, ARCA, BATS, ISLAND and NYSE answers for the same symbol and day share the raw key `(ts, symbol, 1d, ibkr, venue)`. The value-run detection then reads a route switch as the vendor changing its own answer. That breaks design principle 3 (revision vs disagreement) and the owner rule that a cross-source difference never counts as a restatement.
- Evidence (live DB):
  - 99,036 (symbol, bar_date) pairs carry more than one IBKR venue route, and in 99,018 of them the routes give different values.
  - `ohlcv_observation` holds about 718k IBKR venue-route rows, and `ohlcv_raw` holds 117,947 `ibkr/venue/1d` rows. One answer per day survives, and which one depends on fetch order.
  - `--revisions` already ran (loads at 2026-10-13 19:06-19:07 UTC, caller `raw-backfill-191`). It wrote 575,647 `ibkr/venue` revision rows, against 7,440 for `smart_trades`. In a sample of 20,000 of those venue revisions, 16,980 (85%) have an old value served by a different route than the current raw row.
  - Example: AAL 2005-12-09. The revision holds NYSE close 33.88, and raw holds ARCA close 33.95.
- Failing scenario: split detection (and any restatement-rate reader) sees about 570k fabricated IBKR self-restatements. When step 8 drops `ohlcv_observation`, the non-selected venue answers are gone for good. Going forward, if the fetcher's listing-venue route for a name changes (say NYSE to ARCA), the raw-first contract counts the switch as a `changed` overlap on `(ibkr, venue)`. `should_refuse` then fires on what is really a cross-source difference.
- Minimal fix:
  - Make the route part of identity. Use one kind per route (`venue_arca`, `venue_nyse`, ...; CVR rows, no migration) or add the route into `kind`. Also partition current_obs and superseded runs by route.
  - Delete the `raw-backfill-191` venue revision loads and their revisions (they cascade by FK). Then reload the venue rows and rerun `--revisions`.

### 2. HIGH: `--delta` cannot carry a changed value into raw (ON CONFLICT DO NOTHING), and once it runs the window is marked current, so the stale value is permanent

- Where: `scripts/ops/bars/ops_raw_backfill.py:67` (`_CONFLICT ... DO NOTHING`), `:290-294` (skip by equal counts) and `:342-375` (counts recorded after a reload).
- What is wrong: delta reloads a window only when a source count changed. Even then, every pass is `DO NOTHING`, so a key that already exists in raw keeps its old value. A restatement in the same vendor's store never reaches raw. The equal-count skip also misses a value changed in place with no count change: an archive last-wins upsert, or an accepted canonical restatement whose old value went to `ohlcv_revision` rather than the archive.
- Evidence: LION 2026-10-12 1d `ibkr/smart_trades`.
  - Raw holds volume 1,201,576 (served_at 02:28).
  - An observation fetched 09:19 says 1,201,681.
  - The progress file shows delta reloaded LION 2026 at 19:03:01 (observation count 384 -> 385) and recorded it as current. Raw still holds 1,201,576.
  - RAL (799,438 vs 799,538), VTS and BEPC are in the same state.
  - These are the "value_mismatches 56" that 191-03-SUMMARY expects plan 04's delta to clear. By construction it cannot clear them.
- Minimal fix: in delta mode, make the observation and archive passes `ON CONFLICT DO UPDATE ... WHERE (open,high,low,close,volume) IS DISTINCT FROM EXCLUDED...`. Write the displaced value to `ohlcv_revision` (origin raw, with a reconstruction load) in the same statement chain; do not overwrite silently. Replace the count-equality skip with a per-window `max(archived_at, fetched_at)` watermark, or always run the twin-diff for windows touched since the last load.

### 3. HIGH: the archive-first pass order drops the accepted canonical value wherever the archive holds a refused restatement under the same label, and writes no revision

- Where: `scripts/ops/bars/ops_raw_backfill.py:347-351` (pass order archive, observation, canonical; all DO NOTHING) and the docstring at `:8-11`.
- What is wrong: the pass order assumes the archive is the more truthful store. But the archive also holds refused chunks (design doc, Problem: "A refusal ... upserts the refused rows over the archive rows"). For a key where canonical holds the accepted IBKR value and the archive holds a later refused IBKR restatement, raw takes the refused value. The accepted value is not written anywhere in raw or `ohlcv_revision`.
- Evidence: AEP 5m 2026-09-23 13:30.
  - Canonical `ibkr_named` volume 48,913.
  - Archive `ibkr_named` volume 49,013, archived 2026-10-12 23:23, which is the `ohlcv_load` refused at ratio 0.4631.
  - Raw `ibkr/named` holds 49,013, and `ohlcv_revision` has nothing for the key.
  - The four check shards report 6,066 such `canonical_vs_archive` disagreements (340 + 180 + 5,082 + 464).
- Failing scenario:
  - Plan 07's selection gate compares selection-from-raw with canonical and finds about 6k slots that differ. D-191-C says to resolve differences by seeding a span that reproduces canonical, which is impossible here because the canonical value is not in raw under any (vendor, kind).
  - After the swap, canonical rebuilt from raw holds the refused values.
  - `--check` exits 1 permanently (`finalize_report` fails on any `canonical_vs_archive > 0`), so the only way to pass is to widen an exclusion.
- Minimal fix: for keys where canonical and archive share a label and differ, keep the archive value in raw (the later serve, `served_at = archived_at`). Write the canonical value to `ohlcv_revision` (origin raw, request_id NULL) under one reconstruction `ohlcv_load` per (symbol, vendor). Then count these keys as explained in the check and stop gating on them.

### 4. HIGH: a refusal is not durable; the next selection that touches the slot promotes the refused values into canonical

- Where: `services/ohlcv_raw_writer.py:299-333` (a refused series is still last-wins replaced in raw) together with `services/bar_selection.py:121-144` and `src/intelligence/bars/selection.py:96-111` (selection reads only current raw and policy). The caller is `services/ohlcv_ingress_contract.py:565-641` (read only, not reviewed in depth).
- What is wrong: the design says a self-restatement above the threshold is "refused from canonical selection and flagged". The writer, though, replaces the raw current row with the refused value, and selection is a pure function of current raw with no refusal state. The refusal only holds inside the one `apply_raw_contract` call that skipped selection for that (symbol, timeframe).
- Failing scenario:
  - IBKR 5m AEP: 1,125 stored overlap, and a refetch restates 521 (ratio 0.46 > 0.02). The series is refused and raw now holds the 521 new values.
  - The next nightly IBKR fetch for AEP overlaps the same days. Its values match raw, so it is unchanged and not refused, and its span goes to `select_and_write`, which reads raw and writes the refused values into `market_data_ohlcv`.
  - The plan 07 full rebuild does the same for every refused slot. AEP's raw row already holds the refused 49,013 (finding 3).
- Minimal fix: persist the refusal as data that selection reads. Either add a held-span record keyed by (symbol, timeframe, vendor, kind, span, load_id) that `select_slot` treats as ineligible until released, or do not last-wins replace a refused series' changed rows: log them as pending and keep the stored value current. Add a test: refuse, then an unchanged re-offer, then assert canonical is unchanged.

### 5. MEDIUM: `bar_selection` never removes or downgrades a canonical row when selection yields nothing or a NULL-volume winner, so canonical is path-dependent

- Where: `services/bar_selection.py:124-134` (`if not winners: continue`; `winner.volume is None: n_skipped += 1; continue`) and `selection.py:93` (returns None).
- What is wrong: selection is meant to make canonical a function of raw and policy. Here a stale canonical row survives whenever the current answer is "no ranked winner" or "winner has NULL volume".
- Failing scenarios:
  - (a) Today the live 5m policy is `ibkr` only from 1990 (no Alpaca span; D-191-C defers seeding to plan 07). Over a span holding only Alpaca raw rows, selection writes nothing and the 220M Alpaca canonical rows remain. Where both exist, it replaces Alpaca with IBKR. The outcome depends on which slots happen to be touched.
  - (b) An Alpaca row was canonical, then the policy primary IBKR serves the slot with NULL volume. The IBKR row is "selected" but skipped, so canonical keeps the Alpaca row, which disagrees with what selection says.
- Minimal fix: pass the touched span as a removal scope (the `classify(..., removal_scope=...)` support already exists). For a None winner, delete the canonical row or flag it, with lineage. For a NULL-volume winner, fall to the next eligible candidate that has volume, or treat the slot as missing, rather than leaving the previous row. Also gate `apply_raw_contract` wiring on the plan 07 span seeding, because the live 5m policy disagrees with today's canonical.

### 6. MEDIUM: reconstructed revisions carry the reconstruction time and a misleading `old_source`, which changes readers keyed on `loaded_at` and `old_source`

- Where: `scripts/ops/bars/ops_raw_backfill.py:512-531` (the `ohlcv_load` row takes `loaded_at` default now) and `:543` (`old_source = VENDOR_KIND_TO_LABEL.get(..., plan.vendor)`, which gives `'ibkr'` for `smart_trades`, `smart_adjusted` and `venue`). The same fallback is in `services/ohlcv_raw_writer.py:160-161`.
- What is wrong:
  - The 1,606 reconstruction loads are stamped 2026-10-13 19:06-19:07 for restatements dating back to 2005.
  - `scripts/ops/bars/ops_data_bar_check.py:133-135` takes `MAX(l.loaded_at)` as `last_revision_at`, and `known_answer_status` (`:229-237`) requires `last_revision_at < scrub_at` for "replaced".
  - `'ibkr'` is the label that migrations 472 and 475 map to `(ibkr, generic)`, so `old_source` now claims a kind the row does not have.
- Failing scenario: a known-answer 1d key with a reconstructed revision flips from `replaced` to `open`, because its revision now "postdates" the scrub. Not run; inferred from the code.
- Minimal fix: readers order revisions by `ohlcv_request.answered_at` through `ohlcv_revision.request_id` (as D-191-D already says for split detection) and never by `loaded_at`. Fix `ops_data_bar_check`. Write `old_source` as NULL-free but honest: either a dedicated label per raw kind, or keep `'ibkr'` but stop every reader inferring kind from `old_source`.

### 7. MEDIUM-LOW: selection ranks intraday slots by UTC calendar date, not session date

- Where: `src/intelligence/bars/selection.py:107` (`timestamp.astimezone(UTC).date()`).
- What is wrong: post-market bars after 00:00 UTC belong to the previous session but are ranked by the next day's policy span.
- Evidence: AAPL Alpaca 5m has 8,331 bars with UTC hour < 5 (for example 2026-03-07 00:55 UTC, the 2026-03-06 post-market).
- Failing scenario: an Alpaca span seeded at plan 07 with `valid_to = 2026-03-07` ranks those bars under the next span, so their vendor differs from the rest of the same session. This is latent today (all 1m, 5m and 4h defaults are single spans from 1990).
- Minimal fix: compute the slot's session date from the exchange calendar (asset-agnostic: from instrument data), or define policy bounds as timestamptz.
- Aside: kind `sip_rth` holding post-market bars contradicts its CVR description. Not investigated further.

### 8. LOW: the balance check offsets canonical diffs by a count, not by rows

- Where: `scripts/ops/bars/ops_raw_backfill.py:781` (`max(0, can.twin_diff - canonical_vs_archive)`).
- What is wrong: a genuinely stale canonical twin (finding 2's in-place restatement case) is masked whenever an unrelated key in any window has an archive disagreement. `exit_code` still fails today only because `canonical_vs_archive > 0` gates separately. Once finding 3 is "explained", the masking becomes silent.
- Minimal fix: count canonical diffs with a row-level anti-join against the disagreement keys.

### 9. LOW: no row lock between the stored-row read and the upsert in `write_raw`

- Where: `services/ohlcv_raw_writer.py:293-333`.
- What is wrong: under READ COMMITTED, two same-vendor writers of one series (say a manual `ops_*` rerun beside the fetcher, or two Alpaca loads) can both read value X. Each then logs revision old = X and upserts. The intermediate value Y is never logged (lost revision), or two revisions record the same old value. New-row inserts have no ON CONFLICT, so the other interleaving is a loud unique violation. The preview vs write consistency check in the contract catches only changes between `preview_series` and `write_raw`'s own read.
- Status: `FetcherLock` serialises IBKR today, so this is not observed.
- Minimal fix: `pg_advisory_xact_lock(hashtext(symbol||timeframe||vendor||kind))` per series before the read, or `SELECT ... FOR UPDATE`.

### 10. LOW: the backfill admits the canonical-only kind `fallback` into raw

- Where: `scripts/ops/bars/ops_raw_backfill.py:83-87` (`vendor_labels` excludes only vendor `derived`, so `ibkr_fallback -> (ibkr, fallback)` is mapped).
- What is wrong: this bypasses D-191-A and `CANONICAL_ONLY_KINDS`, which the writer enforces. Raw has zero `fallback` rows today (1d canonical is excluded and the archive has none), so it is latent for a delta run.
- Minimal fix: also exclude `CANONICAL_ONLY_KINDS` in `vendor_labels()`.

### 11. LOW: within one chunk, a duplicate key with a different value silently drops the earlier value

- Where: `services/ohlcv_raw_writer.py:276-281` and `:343-345`.
- What is wrong: a vendor answer that holds two values for one key is itself evidence. It is not recorded or raised.
- Minimal fix: raise on a same-key, different-value duplicate within a chunk, or log the earlier value as a revision.

### 12. LOW: request buffer is handed over by reference; concurrent appends during the async flush are lost by `clear()`

- Where: `services/ohlcv_request_writer.py:136-137`, `:193`, `:213`, `:240-257`.
- What is wrong: `take_rows()` returns the live list, and `clear()` replaces it after the COPY. A coroutine calling `on_request` during the `await` between the COPY's consumption and `clear()` loses its ledger row silently. The raw rows it served then point at a `request_id` with no ledger row (no FK). No caller exists yet (`RequestSink(` and `AsyncRequestSink(` have no uses).
- Minimal fix: swap the buffer atomically (`rows, self._requests = self._requests, []`), and put the rows back on failure.

### 13. LOW: `ohlcv_revision.load_id` FK is ON DELETE CASCADE

- What is wrong: deleting `ohlcv_load` rows deletes revision evidence. The Tradier retirement plans to delete Tradier `ohlcv_load` rows, which cascades the 574 reconstructed Tradier revisions and any legacy ones. Cleaning up finding 1 also relies on this cascade, which shows how easily evidence goes.
- Status: pre-existing, outside these commits, recorded for the Tradier step.

## Reviewed and found sound

- Migrations 473 and 474: idempotent seeds (`ON CONFLICT DO NOTHING`, `config_history` guarded by NOT EXISTS), provenance tags, sensible bounds. Both keys are live (3600, 7200). The reader guard (`test_table_and_apr_key_readers.py`) covers them. There is no dedicated migration test, and none is needed beyond that.
- 475 (context): fails loudly on an unmapped `old_source` and widens the PK as designed. Live constraint confirmed.
- `classify`: exact equality, None equals None, NaN raises. Stored and incoming are both float64; `market_data_ohlcv`, `ohlcv_raw` and `ohlcv_observation` are all double precision and bigint, so there is no float4 clamp and no spurious "changed" rows.
- Writer validation runs before any SQL: CVR codes, canonical-only kinds, synthetic_fill, naive timestamps, future guard, finite OHLC, integral non-negative volume. Revisions are written before replacements in the same caller transaction. Batch size respects the bind-parameter limit.
- Aware-datetime keys compare and hash consistently across tz. The session TimeZone is UTC, so the backfill's `%(lo)s::date` casts are correct here, though they would shift a day under a non-UTC session.
- Observation ordering: `fetched_at` never ties across requests on one key (0 cases), and ordering by `fetched_at` agrees with ordering by `ohlcv_request.answered_at` for the last serve on every key (0 disagreements). The value-run logic (revert handling, served_at of the first serve of the last run) is correct apart from finding 1's partition.
- `selection.select_slot` and `select_all` are deterministic and shuffle-independent (sorted slots, `(sort_order, kind)` tie-break). Overlapping policy rows raise, a missing policy raises, and the function does not depend on the wall clock.
- Request writer: the SET LOCAL ROLE idle-connection guards, buffer-intact on failure, and the 19/20-column width check.
- Backfill transactions: per-window REPEATABLE READ snapshot covers counts and inserts, and commits per window. The ohlcv_raw chunks are uncompressed (339 chunks, no policy yet), so there is no compressed-DML hazard yet.
