<decisions>
## Implementation Decisions

### Renaissance Design Lens

The user framed this through a senior quant/Jim Simons lens — every component earns its place:

- **No manual tasks.** Everything provisioned as code (Docker Compose, Grafana YAML). No clicking
  in the Grafana UI to set up datasources. No "run this command once" instructions.
- **Automation over documentation.** The config IS the runbook. A server reboot should bring
  Tempo back without operator intervention (restart policy: unless-stopped).
- **Compute cost awareness.** Tempo on local filesystem object storage (not S3/GCS) — zero
  additional cost. Retention capped to prevent unbounded disk growth.
- **Separation of concerns.** Tempo is an infrastructure concern. No changes to application code.
  The env var `OTEL_EXPORTER_OTLP_ENDPOINT` is the interface; set it in systemd units and the
  SDK routes spans automatically.
- **Modularity.** Datasource provisioning goes in `grafana/provisioning/datasources/` — the same
  pattern as the existing Prometheus datasource. No divergence from the established pattern.

### Docker Compose vs standalone container

The project already runs `timescaledb` and `redpanda` as standalone Docker containers (no
Compose). Tempo should follow the same pattern for consistency — `docker run` managed manually,
not Compose, unless the project migrates everything to Compose.

However: if there is no existing `docker-compose.yml`, a standalone `docker run` command (wrapped
in a script or systemd unit) is correct. Check existing infra before deciding.

### Storage backend

Local filesystem (`/var/tempo` inside container, mounted to host). Object storage (S3/GCS) is
unnecessary at this scale — the DAG produces O(1000) spans/minute at peak, not millions.

### Retention

Set a finite retention period (e.g., 72h or 7d) to prevent unbounded disk growth. The user said
"storage is the cheapest thing we own" for signal data, but trace data is ephemeral debugging
aid — not training data. 72h rolling window is sufficient for debugging; 7d for incident
post-mortems.

### Grafana datasource

Provisioned via YAML file in `grafana/provisioning/datasources/tempo.yaml` — same pattern as
Prometheus. Grafana reads this on startup; no UI interaction required.

### OTEL_EXPORTER_OTLP_ENDPOINT in systemd units

Each agent's systemd unit file gets `Environment=OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318`.
This is the HTTP/proto OTLP receiver endpoint on Tempo. After Phase 52.6, `init_tracing()` reads
this env var; if set, spans flow to Tempo. If not set, spans are no-ops (safe).

Only agents that have `init_tracing()` in their `__main__` block (wired in Phase 52.6) should
get the env var.

### Claude's Discretion

- Exact Tempo Docker image version (pin a specific version, not `latest`)
- Exact retention duration within the 72h–7d range
- Whether to write a helper script (`scripts/start_tempo.sh`) or a systemd unit for Tempo itself
- Directory layout for Tempo config YAML and storage volume

</decisions>

<specifics>
## Specific Ideas

From `docs/ideas/base-agent-enhancement.md` (Section "Infrastructure Follow-On"):

> Single Docker container + Grafana datasource. Set
> `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318` in each systemd unit file. No code changes
> required — the SDK is already initialized, spans are no-ops until the endpoint is live.

Renaissance rationale (from the same doc):

> Traces live in the same Grafana instance as Prometheus metrics — click a lag spike on a
> Prometheus panel and jump directly to the trace that caused it.
> Grafana Exemplars wire Prometheus histograms to specific trace IDs natively.
> Traces stored in local object storage (filesystem at this scale) — cheap long-term retention.
> Single Docker container, one Grafana datasource config.

</specifics>
