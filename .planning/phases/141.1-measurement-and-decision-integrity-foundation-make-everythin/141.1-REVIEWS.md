# Cross-AI Plan Review — Phase 141.1

**Self-review skip:** running inside Claude Code CLI (`CLAUDE_CODE_ENTRYPOINT=cli`) — the `claude` CLI reviewer was skipped for independence, per project convention.

## Codex Review

**Summary**

The phase is directionally strong: it splits the work into four narrowly scoped tracks, mirrors the roadmap's pre-commitment pattern, and correctly prioritizes the OOS clamp and the stale-weight fix before Phase 142A starts measuring anything downstream. The main weakness is that two parts of the design still rely on assumptions that are not yet proven by the codebase: the `regime_scope` backfill heuristic may misclassify historical rows, and the "per-run" weight epoch is only derived from the freeze timestamp, which is not truly run-unique provenance.

**Findings**

- **HIGH**: Plan 02's backfill for `regime_scope` is not provably correct for historical data. The migration assigns all non-`POOLED` / non-`_pooled` rows to `cross_sectional`, but the audit already says the table has mixed regime vocabularies and that the provenance problem is real. If any historical `symbol_hmm` rows already exist, this migration will permanently mislabel them and the new column will encode false certainty.
- **HIGH**: Plan 04's `WEIGHT_EPOCH` is deterministic, but not actually run-unique. Deriving the epoch from `TRAINING_WINDOW_END` means two separate runs with the same freeze point share the same key, so this is boundary identity, not per-run lineage. That may be acceptable for "same-epoch resume overwrites," but it does not fully deliver the stated provenance goal and can still collapse distinct reruns into one epoch.
- **MEDIUM**: Plan 01 and Plan 03 both depend on clean, complete corpus state but only partially define failure behavior for partial or malformed inputs. The OOS clamp only handles empty-string `oos_start`, not malformed timestamps; the OOS harness and cost calibration script gate on total table counts, but not on missing timeframes, missing symbols, or incomplete per-tf coverage. That can produce noisy runtime failures or misleading "valid" reports on partial Phase B outputs.
- **MEDIUM**: Plan 03's auto-creation of a follow-up todo under `.planning/todos/pending/` from a runtime script is operationally awkward. It mixes execution-time analysis with repo mutation and may create merge noise or race with other planning work. The report-only behavior is cleaner and lower risk; file creation should probably be opt-in or separated.
- **LOW**: Plan 01's verification is stronger than the runtime contract. The grep checks confirm the clamp exists, but they do not prove the script still logs the raw max, the OOS boundary, and the effective freeze point in a human-readable block.
- **LOW**: Plan 03 is slightly broader than the phase theme — cost-hurdle calibration extends from measurement integrity into operational tradeability. Not wrong, just worth keeping explicitly bounded.

**Strengths**

- The work is well partitioned across files and waves, with the only intentional overlap (`ops_corpus_pipeline_run.sh`) serialized by dependency.
- Plan 01 correctly treats OOS as a pre-committed holdout, and the read-only harness avoids contaminating the training corpus.
- Plan 02 is the right schema-level fix: the new column is additive, the scope comes from source rather than label strings, and the insert-path coverage is explicit.
- Plan 03 uses audited `ConfigService.set` writes instead of raw SQL, which preserves provenance in `config_history`.
- Plan 04 fixes the worst behavioral bug in the ensemble writer: `DO NOTHING` silently preserving stale weights.
- The plans consistently distinguish diagnostic tooling from authoritative gates, matching the roadmap's pre-commitment discipline.

**Suggestions**

- Plan 02: add a stronger historical backfill strategy or a validation step proving no pre-existing `symbol_hmm` rows are being relabeled as `cross_sectional`. If that proof is not available, keep the column nullable longer and backfill only from explicit provenance.
- Plan 04: make it explicit in the docstring/summary that `WEIGHT_EPOCH` is a freeze-point epoch, not a globally unique run ID. If true run lineage matters later, state it as deferred work, not implied to be solved now.
- Plan 01: add explicit validation for malformed `alpha.validation.oos_start` values and a clearer failure mode for empty/partial holdout inputs.
- Plan 03: gate automatic follow-up todo creation behind a flag, or limit the script to writing the report and printing proposed todo text.
- All four plans: add a short note defining behavior on partially built Phase B data.

**Risk Assessment**

**HIGH** — The overall structure is sound, but two correctness-critical assumptions remain shaky: historical `regime_scope` provenance and weight-epoch uniqueness. Either one can undermine the very measurement integrity this phase is trying to establish, so the phase is not just hardening; it is gatekeeping the validity of later IC and ensemble results.

## AGY (Antigravity) Review

**Executive Summary:** The plans are conceptually sound and follow the project's design standards, but two High-Severity bugs were found: (1) Plan 02's migration backfill SQL incorrectly labels all historical per-symbol HMM regime-stratified rows as `cross_sectional` instead of `symbol_hmm`; (2) Plan 04's `alpha_events` insertion will silently discard alpha events from new weight epochs due to `ON CONFLICT DO NOTHING` combined with an `event_id` hash that omits `weight_version`. Addressing these before execution is critical to prevent data corruption and silent pipeline starvation.

### Plan 01 — OOS Holdout Enforcement
- **Strengths:** Clamping `TRAINING_WINDOW_END` to `oos_start` closes the single most important statistical rigor gap identified in the audit. Graceful NULL/empty handling via `LEAST`+`NULLIF`. Pre-committing `OOS-EVAL-PROTOCOL.md` enforces proper research hygiene.
- **[MEDIUM] Log-Return Formula Redundancy:** The plan builds a local `_executable_returns` helper, duplicating `forward_log_return` in `services/forward_return_writer.py`.
- **[LOW] Empty Database Crash:** If `feature_vectors` is empty, `MAX(bar_ts)` is NULL → empty bash string → `datetime.fromisoformat` crashes with `ValueError`.
- **Suggestion:** Import `forward_log_return` instead of duplicating; add a bash guard for empty `TRAINING_WINDOW_END`.

### Plan 02 — `regime_scope` Schema Fix
- **Strengths:** Separates HMM labels from cross-sectional labels; `_resolve_regime_scope` is pure, stateless, unit-testable.
- **[HIGH] Database Backfill Misclassification — verified against live data:** The proposed backfill SQL (`... WHEN regime = '_pooled' THEN 'pooled' ELSE 'cross_sectional' END`) defaults all non-pooled rows to `cross_sectional`. The live database contains thousands of historical per-symbol HMM rows (e.g. `DIA`, `EEM`, `SPY` with `is_pooled = false` and `regime_label_source = 'forward_filter'`) that would be misclassified under this query.
- **[MEDIUM] Redundancy with `regime_label_source`:** The table already has a `regime_label_source` column representing a similar concept — the relationship/sync between the two must be explicit.
- **Suggested corrected backfill:**
  ```sql
  UPDATE feature_ic_scores SET regime_scope = CASE
      WHEN regime = '_pooled' THEN 'pooled'
      WHEN symbol = 'POOLED' OR regime_label_source = 'market_regimes' THEN 'cross_sectional'
      WHEN regime_label_source = 'forward_filter' THEN 'symbol_hmm'
      ELSE 'cross_sectional'
  END WHERE regime_scope IS NULL;
  ```
  Plus a sync-validation test checking resolved `regime_scope` matches `regime_label_source` mapping rules on write.

### Plan 03 — Cost Hurdle Calibration
- **Strengths:** Uses audited `ConfigService.set()` (propagates `config_history`) instead of raw SQL; isolates calibration logic in a standalone script (no Wave 1 file conflicts); doesn't touch `ic_engine.py`.
- **[LOW] ConfigService Initialization:** Must ensure the `asyncpg` pool is initialized (`await config_service.initialize()`) before calling `set()`.

### Plan 04 — Weight-Epoch / Silent-Retrain Fix
- **Strengths:** `DO UPDATE SET` correctly fixes the silent-staleness bug for same-epoch retries. Externalizing the 90-day cliff to APR (`alpha.ensemble.weight_stale_max_days`) matches project convention.
- **[HIGH] Silent Starvation of `alpha_events` — NEW finding, not caught by Codex or the plan-checker:** In `alpha_publisher.py`, `event_id = BaseBatch.content_key(symbol, tf, bar_ts_ns, self.ensemble_version)` omits `weight_version`. Because insertion uses `ON CONFLICT (event_id, bar_ts) DO NOTHING`, a new weight epoch produces the *same* `event_id` as the prior epoch for the same bars — the insert silently conflicts and does nothing. **`alpha_events` will never reflect updates from new weight epochs.** This is exactly the same class of silent-staleness bug Plan 04 exists to fix, just one layer downstream, in the emission path instead of the training path.
- **[LOW] Epoch String Format Fallback:** `tr -cd '0-9'` on an empty `TRAINING_WINDOW_END` evaluates to literal `run_`.
- **Fix:** `event_id = BaseBatch.content_key(symbol, tf, bar_ts_ns, self.ensemble_version, weight_version)`. Recommend an automated test (`tests/unit/test_ensemble_weight_epoch.py`) asserting `event_id` differs when `weight_version` varies.

**Threat Model & Security Compliance:** Aligns well with STRIDE — Tampering mitigated by `DO UPDATE SET` + `ConfigService` validation; Repudiation mitigated by audit-logged `ConfigService.set()`; Information Disclosure not applicable (local DB/files only).

**Overall Risk Assessment: MEDIUM** — plans are high-quality and well-structured; the Plan 02 backfill bug and Plan 04 event-ID collision are both critical if left unfixed (data corruption in `feature_ic_scores`, silent data omission in `alpha_events`), but both are simple, well-specified fixes.

## Consensus Summary

### Agreed Strengths (2+ reviewers)
- Plan 01's OOS clamp correctly closes the most important rigor gap in the audit (Codex, AGY).
- Plan 04's `DO UPDATE SET` correctly fixes the *training-side* silent-staleness bug (Codex, AGY, Ollama).
- Plan 03's use of audited `ConfigService.set()` over raw SQL is the right call (Codex, AGY).
- Overall phase structure/partitioning across 4 plans and 2 waves is sound (Codex, AGY).

### Agreed Concerns — HIGHEST PRIORITY (independently found by 2+ reviewers)

1. **Plan 02's `regime_scope` backfill will misclassify historical per-symbol HMM rows as `cross_sectional`.** Found independently by both Codex (reasoning from the audit's stated provenance problem) and AGY (verified directly against live data — cites `DIA`, `EEM`, `SPY` rows with `regime_label_source = 'forward_filter'` that the proposed `CASE` statement would mislabel). **This is the strongest consensus finding in this review — two independent reviewers, one with direct DB evidence, converging on the same bug.** Fix: drive the backfill off the existing `regime_label_source` column, not a bare pooled/non-pooled split. AGY's suggested corrected SQL is in its section above.

2. **Plan 04's per-run epoch identity is weaker than the "silent-retrain fix" framing implies**, in two distinct ways caught by different reviewers:
   - Codex: `WEIGHT_EPOCH` is derived from `TRAINING_WINDOW_END`, so it's boundary identity, not true per-run uniqueness — two separate runs with the same freeze point collapse into one epoch.
   - AGY (a different, more severe angle Codex did not find): `alpha_publisher.py`'s `event_id` generation omits `weight_version` entirely, so `ON CONFLICT (event_id, bar_ts) DO NOTHING` will silently swallow every new epoch's `alpha_events` inserts — the exact silent-staleness failure mode this phase exists to eliminate, now relocated one step downstream into emission. **This is a genuinely new bug, not previously identified by the planner or plan-checker.**

### Divergent Views
- Ollama flagged a *third* angle on Plan 04 (no runtime validation that `$WEIGHT_EPOCH` is non-empty/consistent between trainer and publisher, and an unverified atomicity claim under concurrent runs) that neither Codex nor AGY raised — worth folding in as a smaller hardening item, though its partial-coverage caveat above means it should be weighted less than the two full reviews.
- No reviewer disagreed on direction; all three that produced full/partial reviews rate Plan 04 as needing another pass before execution.

### Recommendation

**Do not execute Plan 04 as written.** The `alpha_publisher.py` `event_id`/`weight_version` omission (AGY) is a real, previously-undiscovered bug that would defeat the entire purpose of this phase's weight-epoch fix at the emission layer. **Plan 02's backfill also needs correcting** before migration 192 runs, per the `regime_label_source`-driven fix both Codex and AGY converged on.
