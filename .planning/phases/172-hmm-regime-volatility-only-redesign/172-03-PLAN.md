<objective>
Generalize `regime_writer.py`'s label-mapping and state-grouping helpers to accept a label
vocabulary, and add a dedicated 2-column `(realized_vol, vol_of_vol)` observation-matrix builder.
These are the pure functions the volatility labeling path is assembled from; nothing in this plan
touches a database, a config value, or the existing trend path's behavior.

Purpose: `172-RESEARCH.md` Pattern 1 establishes that `_build_label_map`'s rank-by-column-0 logic
is directly reusable for volatility (low realized_vol sorts to `calm`, high to `turbulent`,
exactly analogous to the existing sort by `log_return`), and that parametrizing it is a
backward-compatible signature extension rather than a rewrite. Pattern 2 requires a dedicated
2-column builder rather than a slice of the 5-column matrix, both to skip the wasted
`momentum`/`rel_volume`/`log_return` compute and to make column-index confusion between two
matrices with different semantics impossible. Pitfall 4 warns that the K=2 edge case is exactly
the kind of behavior a vocab refactor silently drops.

This plan is deliberately split from the cell-level compute and write path (plan 172-04) so the
executor works against a bounded slice of a 1945-line file with tight, synthetic-data-only tests.

Output: four generalized or new pure functions in `regime_writer.py` plus unit coverage for both
vocabularies.
</objective>

tuple[np.ndarray, list]` directly after `_build_obs_matrix`. Build the 2-column matrix from
scratch using the same `_rolling` helper and the same one-bar log-return shift as

Set `valid_start = vol_window + vol_of_vol_window - 2` and column-stack
`[realized_vol[valid_start:], vol_of_vol[valid_start:]]` in that order. Return
`(obs, ts_shifted[valid_start:])`. Guard insufficient input with the same early-return shape
`_build_obs_matrix` uses, adjusted to `(0, 2)`, and set its threshold to
`len(log_returns) < vol_window + vol_of_vol_window - 1` to match the new start index.

Do not copy `_build_obs_matrix`'s `valid_start = max(windows) - 1`. That expression is correct for
the three columns computed by a single rolling pass over `log_returns`, but `vol_of_vol` is a
rolling std of `realized_vol`, which `_rolling` itself zero-pads for its first `vol_window - 1`
entries. Under `max(windows) - 1` the first `vol_window - 1` emitted `vol_of_vol` values are
computed over windows that still contain those zeros, so they are warmup artifacts presented as
valid observations. `vol_window + vol_of_vol_window - 2` is the first index at which the entire
`vol_of_vol` lookback window lies inside real data. At the seeded windows of 20 and 60 this
discards 19 additional bars per cell out of a series of at least 20000, so the cost is immaterial
and the emitted matrix contains no fabricated-input rows.

Do not change `_build_obs_matrix`. The same artifact exists there, but that builder feeds the
legacy `regime` column whose 26.8M existing rows were produced under its current behavior; editing
it would silently change the meaning of a column this phase is deliberately leaving untouched. It
is filed as pending todo 286 instead.

State the divergence in the docstring in one sentence, naming both start-index expressions, so a
future reader does not "restore parity" with the composite builder and reintroduce the artifact.
Note also that plan 172-01's null-arm gate measures the volatility axis through the composite
matrix's columns 1 and 3 and therefore under the legacy start index; the 19-bar difference is not
material to a block-reliability statistic computed over tens of thousands of bars, but say so
rather than leaving the reader to notice the mismatch.

their formulas and windows, and state explicitly that column 0 is `realized_vol` because
`_build_label_map` ranks states by `means[:, 0]`, so putting `vol_of_vol` first would give the
emitted labels a different meaning. Note that the axis is the only one that cleared the null-arm
block-reliability control, and that trend and volume columns are deliberately absent rather than
pending.

Add a `_make_vol_switching_closes(n, seed)` helper to the test file producing a series whose

assertion in the behavior block. The existing `_make_trending_up_closes` and
`_make_ranging_closes` helpers do not exercise the calm-versus-turbulent boundary and are not a
substitute.
