<planner_findings>
Planner decisions resolving the phase's open questions. These are locked; do not re-litigate.

**Open Question 3 — cluster_id scheme: RESOLVED.** Run `_cluster_features` on the broadcast matrix
(research's own recommendation, and a genuine improvement over the deleted block's never-actually-
FDR-corrected singleton IDs), then add a `_BROADCAST_CLUSTER_ID_OFFSET = 10000`. The offset is
mandatory, not cosmetic: `_cluster_features` returns fcluster IDs starting at 1, and the BH-FDR
representative-selection loop groups by `(regime, lookahead_bars, cluster_id)` across ALL rows in
`all_results` — without an offset, broadcast features would silently merge into per-symbol
clusters' representative selection and lose their own FDR entry. `feature_ic_scores.cluster_id` is
`smallint` (max 32767), so 10000 plus roughly 40 broadcast features fits with wide margin. The
10000 ID space is free because Plan 02 deleted its only prior user. **Implemented in Plan 04; stated
here because Plan 03 must not consume the 10000 space for anything else.**

**Open Question 1 — fingerprint `pass_type`: RESOLVED as "fold into the existing
`pass_type='cross_sectional'` row." No new `pass_type`, no `ic_cell_fingerprints` CHECK-constraint
migration, no `feature_ic_scores_regime_scope_chk` migration.** Three pieces of live evidence, all
verified during planning:

  1. The broadcast cell shares `_compute_cross_sectional_tf`'s single chunked fetch (that is the
     entire point of D-05's "reuse the array the per-symbol path already has"). It therefore
     CANNOT be skipped or recomputed independently without duplicating a multi-hour fetch.
  2. `_checkpoint_content_key()` hashes AST-normalized source of every first-party module in
     `sys.modules` under `src/` and `services/` — it is module-set-level, not function-level. A
     change to broadcast-cell code moves `code_content_key` for BOTH pass types identically. A
     separate fingerprint row could never diverge from the `cross_sectional` one, so it would be
     pure overhead plus the collision risk research flagged as Pitfall 2.
  3. `_ARCHIVE_BEFORE_DELETE_CROSS_SECTIONAL_SQL` and
     `_FINGERPRINT_INVALIDATE_DELETE_CROSS_SECTIONAL_SQL` already scope by
     `symbol='POOLED' AND tf AND regime_scope='cross_sectional' AND regime=<label> AND training_window_end`.
     Broadcast rows match that predicate exactly, so archive-then-delete-then-recompute already
     covers them with zero SQL change.

  Corollary, load-bearing for Plan 04: broadcast rows MUST carry `regime_scope='cross_sectional'`.
  `ic_cell_fingerprints.pass_type` and `feature_ic_scores.regime_scope` each have a live CHECK
  constraint limited to `('pooled','symbol_hmm','cross_sectional')` — verified against the running
  database. Any new value costs a migration for zero benefit.

**The gap this decision exposes, which Task 3 closes.** `_watermark_concept_registry` hashes only
`name || '=' || status`. A broadcast-flag flip lives in `metadata`, which that hash does not see —
so flipping a feature's classification would leave every cell fingerprint valid and every cell
silently skipped, permanently serving results computed under the old column split. That is exactly
research's Pitfall 1 failure mode arriving through a different door.

**Read/write population alignment with Plan 01: LOCKED, do not widen and do not narrow.** Plan 01
writes the `broadcast` metadata key only to gate-joined `status='active'` rows. This plan's read
predicate is `metadata->>'broadcast' = 'true'` over the gate-joined `domain='feature'` population
with NO status filter, and that asymmetry is deliberate in both directions:
  - **No status filter on the read.** A feature that is flagged broadcast today and later moves
    `active -> deprecated` is still a symbol-invariant column in `feature_vectors` and must stay
    excluded from the per-symbol cell. Adding a status filter would silently re-admit it and
    reintroduce the exact bug this phase fixes.
  - **No `COALESCE` default and no separate handling for the unflagged.** An absent `broadcast` key
    evaluates to NULL, `NULL = 'true'` is not true, so the row is simply not selected — the feature
    stays in the per-symbol cell, i.e. exactly today's behavior. That is the correct conservative
    default for the 2 tombstones and 5 candidate rows Plan 01 never writes, and it means there is no
    third "unknown" state to handle anywhere in this plan.
</planner_findings>
