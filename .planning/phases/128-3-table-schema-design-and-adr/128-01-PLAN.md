    **## Context** — Describe the signal_ledger monolith problems: 47 columns mixing detection/hypothesis/execution concerns, ML training bias (null counterfactual_pnl_r on suppressed signals), shadow tracking confusion (shadow_mae/mfe columns on the same row as live execution fields). State that the monolith was a correct v1 design that has now outgrown its single-table structure.

    **## Decision** — 3-table separation is adopted. Three tables with distinct responsibilities:
    - signal_events: detection layer, one row per plugin fire. Contains raw_confidence, factor_scores, context_features, ctf_score, ctf_confirmed, zone_friction_score, status. Hypertable partitioned on ts.
    - trade_frames: hypothesis layer, one row per entry_type per signal. Contains counterfactual_pnl_r (first-class, always populated by CounterfactualTracker regardless of execution). Regular table.
    - trade_executions: execution layer, one row per live trade execution. Contains actual_pnl_r. Most frames have zero rows here. Regular table.
    Cardinality: 1 signal_event to N trade_frames (one per entry_type); 1 trade_frame to 0-1 trade_executions.

    **## Full Schema Tables** — Include ALL columns from CONTEXT.md D-02 (signal_events, 26 columns), D-03 (trade_frames, 20 columns), D-04 (trade_executions, 13 columns), and D-05 (signal_ledger_full view SQL exactly as written in CONTEXT.md). For each table present columns as a markdown table with Column, Type, and Notes columns. Include all index annotations from the CONTEXT.md column tables.

    **## G0 Audit — signal_id Hash Consistency** — Document the pre-migration gate. State: make_signal_id() hashes (symbol, feature_ts_ns, feature_tf, open, high, low, close, volume, setup_plugin, direction). entry_type is NOT in the hash. Audited all make_signal_from_frame() call sites (gap_analysis_setup.py, divergence_stack.py, and 20 other plugins) — no plugin currently generates multiple signals with different entry_types from the same fire event. Current state: 1:1 signal-to-frame mapping. N-frame cardinality is a Phase 130+ expansion target. Gate status: CLEARED. Phase 129 migration may proceed.

    **## Phase 130 Writer Grouping Contract** — Document D-09: Phase 130 signal_writer must group incoming signals by signal_id (from Kafka payload), insert ONE signal_events row per group using detection fields from the first signal, then insert N trade_frames rows (one per entry_type). Today all plugins emit one entry_type per fire so N=1, but the writer must be designed for N from day one.

    **## Dropped Columns** — List all signal_ledger columns not carried forward: signal_type (redundant with setup_plugin), feature_ts (duplicate of ts), feature_tf (duplicate of timeframe), feature_schema_version (superseded by signal_schema_version int4), pipeline_lag_ms (computable as signal_computed_at - ts), staleness_score (no new home in 3-table design), staleness_trigger_reason (no new home in 3-table design). Note that shadow_mae, shadow_mfe, shadow_outcome, shadow_tracking_start_ts are archived into trade_frames.frame_details JSONB during Phase 129 migration (not dropped — preserved as historical training data).

    **## FK Design on Hypertable** — Explain why FOREIGN KEY (signal_id, signal_ts) REFERENCES signal_events (signal_id, ts) is required (not single-column FK). TimescaleDB partitions by ts; unique constraints on hypertables must include all partitioning columns. This is why signal_ts timestamptz is a first-class column on trade_frames — it is the FK anchor, not a convenience denormalization.

    **## Hypertable Configuration** — signal_events: chunk_time_interval 7 days, compress_segmentby 'symbol,timeframe', compress_orderby 'ts DESC', compress after 7 days, policy runs every 12 hours. trade_frames and trade_executions are regular tables (no hypertable).

    **## Alternatives Considered** — Section must include:
    1. 2-table design (signal_events + trade_outcomes) — rejected because execution tracking gets dirty: a single trade_outcomes row cannot cleanly separate counterfactual P&L (always available) from actual P&L (only on live trades). ML training requires a clean counterfactual_pnl_r that is always populated; mixing execution state into the same row creates partial-null rows with silent ML bias.
    2. Flat monolith (enhanced signal_ledger) — rejected because it perpetuates the root cause. Adding counterfactual_pnl_r to signal_ledger without separating concerns creates a 60+ column table with multiple competing NULL patterns. ML training queries would require complex WHERE clauses to avoid training on contaminated rows.

    **## Consequences** — Migration scope: Phase 129 executes the DDL, migrates signal_ledger data, retains signal_ledger read-only for 48 hours, then Phase 130 rewrites writers/trackers/APIs. CounterfactualTracker (Phase 130 daemon) is a dependency for populating counterfactual_pnl_r. direction column converts from integer (1/-1) to text (long/short) — all query callers and writers must be updated in Phase 130. signal_schema_version converts from text to int4. signal_ledger_full view is the backward-compatibility surface; signal_ledger_full (migration 095) is superseded.

    File should be ~400-600 lines, structured markdown. Use ## section headers. Include a header block with Status, Date, and Deciders fields.
