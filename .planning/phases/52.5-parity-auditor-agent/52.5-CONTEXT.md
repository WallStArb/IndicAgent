# Phase 52.5: Parity Auditor Agent — Context

**Gathered:** 2026-03-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Build `ParityAuditorAgent` — a timer-based (5-min) autonomous process that compares `intelligence_features` vs `feature_snapshots_shadow` per (symbol, tf), stores field-level violations in `feature_parity_violations`, emits `parity_match_rate` Prometheus metrics per pair, and self-certifies by publishing `SHADOW_PARITY_CERTIFIED` to the system events topic once every active (symbol, tf) achieves `CERTIFICATION_THRESHOLD` consecutive clean cycles.

**Out of scope:** Primary-write cutover logic, schema changes to `intelligence_features`, new signal tracking features, any modifications to `FeatureSnapshotWriterAgent`.

</domain>

<decisions>
## Implementation Decisions

### Certification State Persistence

- **D-01:** Derive certification state from `feature_parity_violations` — no new state table. The data IS the state.
  - Per cycle, for each (symbol, tf): query `feature_parity_violations` for the last `CERTIFICATION_THRESHOLD × 5 minutes` and count 5-min windows with zero violations. If all windows are clean, the pair is certified.
  - Rationale: `feature_parity_violations` already stores the ground truth. A clean cycle is a 5-min window with no violation rows. Deriving certification from this query gives restart-safe state with zero additional infrastructure. Fully automated — no manual reset ever needed.
  - `CERTIFICATION_THRESHOLD = 12` (12 × 5 min = 60 consecutive clean minutes).
  - DO NOT add a separate `parity_certification_state` table. DO NOT use in-memory counters.

### Comparison Window

- **D-02:** Time-based window — `ts >= NOW() - INTERVAL '10 minutes'` (2 × timer interval).
  - Self-consistent across all TFs: 1m gets ~10 rows, 5m gets ~2 rows, 1h gets 0–1 rows. When a row exists in the window, it gets compared. When it doesn't (infrequent TFs), the cycle contributes no violations — correct behavior.
  - Self-adjusting: if `COMPARISON_INTERVAL_SECS` changes, the window automatically scales.
  - DO NOT use count-based N per TF. DO NOT hardcode TF-specific row counts.

### Shadow-Only Rows (in shadow but not in primary)

- **D-03:** Track as `shadow_ahead_rows_total{symbol, tf}` Prometheus counter. Never store as `FieldViolation`.
  - Rationale: Shadow-only rows are timing races (shadow writes ~seconds before primary catches up). Storing them as violations would produce constant false parity failures on every cycle. The Prometheus counter instruments the phenomenon fully — a steadily growing counter signals a primary writer problem and is actionable.
  - Primary-only rows (primary has a row but shadow doesn't) = skip, not a violation (shadow hasn't caught up yet — handled by 52.3-CONTEXT D-03).

### Port Assignment

- **D-04:** Port **:9120** for `ParityAuditorAgent` Prometheus metrics. Port 9119 is already assigned to `FeatureSnapshotWriterAgent` (Phase 52.3, D-04). Do NOT use 9119.

### BaseAgent Version

- **D-05:** Inherit from Phase 52.2 `BaseAgent` (`src/core/agent/base.py`). Phase 52.6 enhances BaseAgent — that enhancement comes AFTER this phase. Use the 52.2 interface as-is. When 52.6 ships, `ParityAuditorAgent` may benefit from the enhanced lifecycle contract (that migration is out of scope here).

### Kafka Topic for SHADOW_PARITY_CERTIFIED

- **D-06:** Publish `SHADOW_PARITY_CERTIFIED` to `topic_system_events(settings.env_name)`. The `topic_audit(settings.env_name)` topic is for violation/audit events (per 52.3 design doc). Use the correct topic per event type — `system_events` for certification signal, `audit` for parity violation events if desired.
  - Never hardcode topic strings — always via `stream_keys.py`.

### Existing PLAN.md Corrections (Planner Must Apply)

- **D-07:** The existing `PLAN.md` (Task 4, `_compare_cycle` step 2) says "rows only in primary = skip." Per D-03 above, also add: "rows only in shadow = increment `shadow_ahead_rows_total` counter, do not create FieldViolation."
- **D-08:** The existing `PLAN.md` lists `:9119` as the metrics port (Task 5). Correct to `:9120`.
- **D-09:** The existing `PLAN.md` `ParityRepository` specifies `fetch_certification_state` and `update_certification_state` methods. Per D-01, these are NOT needed — remove them. Certification is derived from a query over `feature_parity_violations`, not stored separately.

<specifics>
## Specific Design Notes

- **Renaissance framing (user-explicit):** Design to Jim Simons standard. Instrument everything — every violation, every shadow-ahead race, every certification state change must be observable via Prometheus or structlog. No manual tasks anywhere. Automation is the goal. Data quality is validated through proof, not assertion.
- **Automated gate:** `SHADOW_PARITY_CERTIFIED` is the machine-generated signal that triggers primary-write cutover (a future phase). The auditor earns the right through proof — 60 consecutive clean minutes, not human judgment.
- **Separation of concerns:** `ParityRepository` owns all SQL. `ParityAuditorAgent` owns timer loop + certification state + Kafka publication. `_compare_rows()` is a pure function — no I/O, fully unit-testable. These three concerns must stay cleanly separated.

</specifics>
