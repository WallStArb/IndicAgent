## Decisions Made

1. **Defaulted the 5 new `FeatureVector` fields (and `FeatureFactoryConfig.canary_rng_seed`)**, breaking this dataclass's stated "no defaults, every field must be supplied by the caller" convention. Rationale: RESEARCH.md's Pitfall 6 already flagged this as a real-cost item (not "registry rows only"), but the actual blast radius extends further than RESEARCH.md scoped — beyond the row-count gate, ~10 test files across the suite construct `FeatureVector(...)`/`FeatureFactoryConfig(...)` with every field hand-typed (not `**kwargs` from `dataclasses.fields()`), and `feature_vector_persistence.py`'s INSERT contract independently required extending. Defaults keep every one of those pre-existing hardcoded constructors working unchanged, while every real production compute path (`compute()`, `compute_batch()`, `_cold_start_vector()`, both `FeatureFactoryConfig` production entrypoints) explicitly supplies a real value — never relies on the default in a live code path. Documented inline in `schemas.py`/`feature_factory.py` so this isn't mistaken for an oversight later.
2. **Migration claimed number 223** (not 222, already taken by 143.1-01's concurrently-executing migration in the same wave) — verified live via `ls production/migrations/` at execution time per the plan's explicit collision warning, confirmed idempotent on re-run.
3. **Canary integrity gate added as a non-numbered bash function**, mirroring the existing `check_regime_consistency()` pattern, rather than renumbering `ops_corpus_pipeline_run.sh`'s 8 numbered steps to 9 (would have touched every `run_step N "..."` call site and the `"Step %d/8"` banner format string for a gate that structurally belongs between two existing steps, not as a step in its own right).
4. **Acausal-placebo canary is genuinely acausal only in `compute_batch()`** (the backfill/corpus path, which has the full-history array in scope), and is provably inert (always `0.0`) in the live single-bar `compute()` path, which by definition never has future bars. This asymmetry is intentional and tested in both directions — the corpus-run integrity gate this canary feeds only ever reads `feature_ic_scores` populated from the backfill path anyway.
5. **Binomial tail bound defaults**: `p=0.05` (BH-FDR's own standard alpha — the false-clear rate BH-FDR itself admits by design), `tail_alpha=0.01` (1% chance this gate hard-fails purely from expected statistical noise). Both CLI-overridable; recorded in `methodology-change-ledger.md` E7 before any real corpus run exercises the gate, per this project's pre-commitment convention.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Extended `feature_vector_persistence.py`'s INSERT contract for the 5 new fields**
- **Found during:** Task 1, after adding the 5 `FeatureVector` fields
- **Issue:** Not in the plan's `files_modified` list, but `feature_vector_persistence.py`'s `FEATURE_VECTOR_INSERT_SQL`/`feature_vector_to_insert_params()` is the sole choke point both the live `FeatureVectorWriter` and batch `backfill_feature_factory.py` write paths use to persist `FeatureVector` fields to the DB. Without extending it, the 5 new canary values would be computed correctly in memory and then silently discarded before reaching the database — the exact bug class this file's own docstring documents from 2026-07-08 (91/152 columns silently NULL for an entire corpus). `tests/unit/test_feature_vector_persistence_completeness.py` (a pre-existing structural guard, not written by this plan) would have failed immediately.
- **Fix:** Added `_CANARY_FIELD_NAMES` (a derived slice from `dataclasses.fields(FeatureVector)`, same discipline as the existing `_RENAISSANCE_PRIMITIVE_FIELD_NAMES`), extended the INSERT SQL column list/placeholders and the params tuple by 5 (161→164... actually 159→164, see file history).
- **Files modified:** `src/intelligence/features/feature_vector_persistence.py`
- **Verification:** `test_feature_vector_persistence_completeness.py`'s 4 structural tests all pass; manually verified 155 fields / 164 SQL columns / 164 placeholders / 164-element params tuple via direct Python introspection.
- **Committed in:** `e51a92ad` (Task 1 commit)

**2. [Rule 3 - Blocking] Wired `canary_rng_seed` into the 2 real production `FeatureFactoryConfig` construction sites**
- **Found during:** Task 1
- **Issue:** Not in the plan's `files_modified` list, but `FeatureFactoryConfig` is a frozen dataclass built once per process by exactly 2 production entrypoints (`services/backfill_feature_factory.py`, `services/feature_vector_pipeline.py`). Since `canary_rng_seed` is defaulted (see Decision 1), omitting these two wire-ups wouldn't crash anything, but it would mean production never actually reads the APR key — the seed would silently stay at its Python-level default forever regardless of `config_state`, defeating the entire point of making it an APR key.
- **Fix:** Added `canary_rng_seed=int(cfg.get_sync("alpha.ic.canary_rng_seed", 90042))` (backfill) and the async-prewarmed equivalent (`feature_vector_pipeline.py`, plus a `_THRESHOLD_KEYS` entry so the value is prewarmed into the config cache before `get_sync` reads it).
- **Files modified:** `services/backfill_feature_factory.py`, `services/feature_vector_pipeline.py`
- **Verification:** Grepped both files for `alpha.ic.canary_rng_seed`; unit tests for both files' existing `FeatureFactoryConfig` construction still pass unchanged (defaults mean the new kwarg is additive, not breaking).
- **Committed in:** `e51a92ad` (Task 1 commit)

**3. [Rule 1 - Bug] Fixed 5 pre-existing test files' stale hardcoded FeatureVector field-count / insert-param-count assertions**
- **Found during:** Task 1, running the affected test files after adding the 5 new fields
- **Issue:** `tests/unit/test_feature_factory.py`, `tests/unit/intelligence/test_feature_factory_p7.py` hardcoded `== 150` FeatureVector field-count assertions; `tests/unit/services/test_backfill_feature_factory.py`, `tests/unit/services/test_feature_vector_writer.py`, `tests/unit/services/test_feature_vector_writer_column_mapping.py` hardcoded `== 159` insert-param-count assertions. All 5 would fail immediately once the schema legitimately grew, with no code defect underneath — the exact class of "number that itself needs remembering to update" `feature_vector_persistence.py`'s own docstring warns about, just manifesting in test assertions instead of the INSERT SQL itself.
- **Fix:** Bumped `150`→`155` and `159`→`164` at each assertion site; updated accompanying docstrings/comments to explain the new total. No test coverage removed or weakened — same structural invariants, updated numbers.
- **Files modified:** the 5 test files listed above
- **Verification:** All 5 files pass; full `tests/unit/` suite (5763 tests) confirms no other file was affected by the count change.
- **Committed in:** `e51a92ad` (Task 1 commit)
