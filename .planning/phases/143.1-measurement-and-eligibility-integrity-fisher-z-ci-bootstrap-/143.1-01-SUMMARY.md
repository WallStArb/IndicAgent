# Phase 143.1 Plan 01: Corrected Circular Block Bootstrap CI Summary

**One-liner:** Replaced the empirically-miscalibrated `_fisher_z_ci` with a corrected circular block bootstrap at all 3 `ic_engine.py` CI call sites; the plan's own staged-validation gate did NOT clear (5m residual), so Plan 07's corpus-wide re-run stays blocked pending a project-owner decision (todo 099).

## What Was Built

**1. Corrected bootstrap (`src/intelligence/statistics/ic_math.py`)**
- Restored `_circular_block_bootstrap_ic`, fixing the pre-ranking bug that caused the 2026-06-26 removal: inputs are now RAW unranked paired observations, re-ranked via `rankdata` inside the bootstrap loop every iteration, instead of resampling already-globally-ranked values.
- Per-iteration allocation (not a single `(n_boot, n_blocks, block_size)` broadcast) — avoids the ~7.5GB/worker OOM the broadcast form hits at production scale.
- Circular-wrap block index construction unchanged from the removed version (never the bug).

**2. Production wiring (`services/ic_engine.py`)**
- All 3 former `_fisher_z_ci` call sites (`_compute_symbol_tf`'s regime block, the daily context-features loop, `_compute_cross_sectional_tf`) now call `_circular_block_bootstrap_ic` with raw paired arrays already in scope. Zero remaining `_fisher_z_ci(` call sites in this file.
- `alpha.ic.bootstrap_resamples`, `alpha.ic.bootstrap_block_size.{tf}`, `alpha.ic.bootstrap_seed` read via `ConfigService.get_sync` — never hardcoded. Worker-safe RNG derivation keeps `ProcessPoolExecutor` workers compute-only.
- Migration 222 (221 was already claimed by a concurrent session's `alpha_frames_compression` migration) strips the `[deprecated]` prefix from the 6 `alpha.ic.bootstrap_*` `config_schema` rows.

**3. Staged-validation gate (`scripts/ops/alpha/ops_ic_null_calibration.py --ci-method bootstrap`)**
- Pre-committed the pass threshold in the ledger BEFORE running the diagnostic: `<=2` SUSPECT cells of 66-72 evaluated, no single `(tf, is_pooled)` stratum with `>1`.
- Measured: 6/29 (20.7%) SUSPECT, down from 11/29 (37.9%) under Fisher-z — real, substantial improvement — **but gate NOT cleared**: `tf=5m, is_pooled=false` has 3 SUSPECT (bound is `<=1`).
- Two independent robustness checks confirmed this isn't a diagnostic artifact: 5x more null-permutation precision didn't reduce it (worsened to 8/29), and `bootstrap_block_size` swept 78→780 produced an identical 4/7 SUSPECT count for 5m at every value, with `se_ratio` flat-to-worsening as block size grew.
- Residual concentrated in autocorrelation/momentum-family features (`ret_autocorr_1`/VNQ, `ctf_momentum`/XHB+IBB, `month_sin`/EFA) at 5m.

**4. Corpus-scale runtime benchmark (`--benchmark` flag, this session)**
- Timed `_circular_block_bootstrap_ic` directly on synthetic arrays sized to the corpus's actual `n_independent` distribution — isolates the bootstrap's own cost from the script's unrelated multi-table asyncpg fetch (not representative of production; `ic_engine.py` already holds data in memory when it calls the bootstrap).
- Cost is per-`(symbol-or-POOLED, regime, tf, lookahead)` group (one vectorized call covers all ~150 features), scales slightly superlinearly in `n` (empirical exponent ≈1.1-1.15).
- 6,219 groups corpus-wide; avg-sized-group serial total ≈11,875s (≈3.3hr); ≈990s (≈16.5min) at `ic_engine`'s existing 12-worker parallelism.
- Pre-committed a 60-minute wall-clock budget in the ledger (≈3.6x the central estimate, sized for the heavy right tail — the single largest observed 5m POOLED cell alone costs 687s).

## Technical Decisions

1. **Gate failure is a real finding, not a plan failure.** The plan's own hard-sequencing rule ("Plan 07's corpus-wide re-run must not start until this passes") is honored: the corrected bootstrap CODE ships (unconditionally correct relative to what it replaced — fixes a proven bug, nearly halves the SUSPECT rate) but the downstream corpus-wide re-run stays blocked. Filed as `todo 099` with full investigation detail (ruled-out causes, not-yet-investigated hypotheses, explicit decision options for the project owner).
2. **Benchmark isolated from DB fetch.** The first benchmark attempt (via the diagnostic's normal fetch path, unstrided) ran 18+ minutes on a single cell without finishing — traced to two bugs in the benchmark harness itself (missing stride subsampling, and DB-fetch/Python-side row conversion dominating wall-clock for large regime-filtered series), not to the bootstrap. Fixed by applying the same `stride = max(subsample_min_stride, lookahead_bars)` production applies, then further isolated pure bootstrap cost with synthetic arrays sized from real `n_independent` values — a cleaner, more representative measurement.
3. **No re-run of Task 3's gate needed for Task 4.** Confirmed via direct `config_state` query that Task 3's block-size robustness sweep (78→780) was diagnostic-only and never wrote to production APR values — the benchmark runs at the same live parameters Task 3 calibrated against.
4. **Runtime budget recorded as an E6 addendum, not a new ledger entry.** Same Component A decision, same plan — avoids fragmenting one decision's record across two numbered entries.
