**Researched:** 2026-07-11
**Domain:** Statistical measurement correctness (bootstrap CI) + sign-symmetric ensemble eligibility, inside an existing IC-measurement codebase (no new external stack)

## Summary

This phase has no genuine "what library should we use" question — it is a correctness fix inside code that already exists, already has a proven pattern to imitate (the diagnostic that found the bug), and already has the schema columns it needs (`ic_sign` is already stored). The real risk in this phase is **wiring precision**: `ic_engine.py` computes IC through three structurally similar but functionally distinct code paths (per-symbol regime-stratified, daily-cadence context features, and cross-sectional POOLED), and a fix applied to the wrong one of the three will compile, pass tests, and run to completion while having **zero effect** on the actual defect. This research found exactly one such case: **CONTEXT.md's Component E "Gate 2" citation (`ic_engine.py:812-814`) points at the per-symbol function, whose output can never reach the ensemble** (see "Critical correction" below) — the walk-forward fix must additionally (or instead) land in `_compute_cross_sectional_tf`, not only where CONTEXT.md's line reference points.

The second major finding is that **Component A's "swap in circular block bootstrap while preserving the function signature" is not achievable as a same-signature swap** — `_fisher_z_ci(ic_vector, n)` only needs the point estimate and N; a correct bootstrap needs the raw, unranked, paired `(X, Y)` observations, which are already in scope at every call site but are not passed today. This is a signature change at 3 call sites in `ic_engine.py`, plus a scope decision about 2 more call sites in `ensemble_ic_engine.py` and `ops_oos_holdout_eval.py` that CONTEXT.md's canonical refs do not mention.

The third major finding is that **Component D cannot be "just registry rows"** as CONTEXT.md's framing suggests — `FeatureRegistryService.load()`/`load_sync()` enforces a hard row-count-equals-`len(FeatureVector fields)` gate that will crash both `ic_engine.py` and `ensemble_trainer.py` at startup if canary rows are added to `feature_registry` without matching new `FeatureVector` dataclass fields (and vice versa). This has real cost implications for the "single corpus re-run" plan: canaries require a `feature_factory.py`/schema change, which requires **Step 1** (`backfill_feature_factory.py`, a full corpus rebuild) — not just an `ic_engine.py`-only re-run like A/E/F.

**Primary recommendation:** Sequence exactly as CONTEXT.md locks (093→A→F→E→A/B re-run), but before writing plan tasks, resolve the three items above explicitly as plan-level decisions: (1) apply Gate 2's sign-consistency fix to `_compute_cross_sectional_tf` (not just the line CONTEXT.md cites), (2) accept that Component A requires new function signatures at each call site (not a drop-in), and (3) treat Component D as a full-corpus-rebuild-cost item (`--from-step 1`), not a cheap side-channel.

## Common Pitfalls

### Pitfall 1: Fixing Component E's Gate 2 in the wrong function (CRITICAL — verified by code read, not assumption)

**What goes wrong:** CONTEXT.md cites `services/ic_engine.py:812-814` for Gate 2's walk-forward fold-sign fix. That line range is inside `_compute_symbol_tf()` (the **per-symbol** IC computation function). Its output rows always carry `"symbol": symbol` (the literal per-symbol ticker, e.g. `'SPY'`) — **never** `symbol='POOLED'`, even for its own internal "pooled-across-regime" pass (`is_pooled=True` there means "pooled across this one symbol's regimes", tagged `regime='_pooled'`, not `regime != '_pooled'`).

`ensemble_trainer.py`'s `_ELIGIBILITY_BASE_WHERE` (the ONLY predicate that determines what reaches ensemble weighting) requires `symbol = 'POOLED' AND is_pooled = true AND regime != '_pooled'`. The only function in `ic_engine.py` whose output can ever satisfy `symbol = 'POOLED'` is `_compute_cross_sectional_tf()` (verified: `_CROSS_SECTIONAL_SYMBOL = "POOLED"` at line 143, and its own docstring states "stored with symbol=_CROSS_SECTIONAL_SYMBOL ('POOLED')"). `_compute_cross_sectional_tf()` has its own, separate walk-forward block at approximately **lines 1443-1447** (`wf_pass_count_nd = (fold_ic_arr > 0).sum(axis=0); passes_wf_nd = wf_pass_count_nd == walk_forward_folds`) — this is the block that actually gates ensemble eligibility, and CONTEXT.md's canonical refs do not cite it.

**Why it happens:** `ic_engine.py` has three near-identical `fold_ic > 0` walk-forward blocks (per-symbol at ~811-814, daily context-features at ~1040-1041, cross-sectional POOLED at ~1443-1447) that look interchangeable at a glance but feed structurally different downstream consumers.

**How to avoid:** The plan MUST include a task to apply the sign-consistency fold criterion (`fold_ic * ic_sign > 0`) to **`_compute_cross_sectional_tf()`'s** walk-forward block (this is the one that matters for Component E's actual goal — unlocking contrarian features into the ensemble). For full corpus-wide consistency (Component A's own "not targeted" principle, and because `_fisher_z_ci` is also called in all three places), the per-symbol and context-features blocks should receive the same treatment too, but doing ONLY the per-symbol one (as a literal reading of CONTEXT.md's line citation would produce) yields a change that **compiles, runs, and has zero measurable effect on `alpha_events`' long/short imbalance** — the exact failure mode this phase exists to prevent elsewhere.

**Warning signs:** After landing the fix and re-running the corpus, if `alpha_events`' short-side row count is still ~0 (per the 99.99% long-only baseline), the fix landed in the wrong function.

### Pitfall 2: Treating Component A as a same-signature drop-in replacement

**What goes wrong:** `_fisher_z_ci(ic_vector: np.ndarray, n: int) -> tuple[ndarray, ndarray]` only takes the already-computed IC point estimate and the sample size. A correct circular block bootstrap needs the **raw, unranked, paired `(X, Y)` observations** to resample and re-rank per replicate — a fundamentally different input shape. This is not obtainable from `(ic_vector, n)` alone.

**Why it happens:** CONTEXT.md's framing ("swap in ... while preserving the function signature all callers expect") is aspirational, not a verified fact — this research task existed partly to check it.

**How to avoid:** Plan for a genuine signature change at each call site: `ic_engine.py` line 772 (`_compute_symbol_tf`, has `X_sub_nd[valid_mask]`/`Y_scale` in scope pre-rank), line 1009 (context-features loop, has `x_daily`/`y_daily` in scope), line 1418 (`_compute_cross_sectional_tf`, has `X_sub_nd[valid_mask]`/`Y_scale` in scope). All three already hold the raw arrays needed; passing them through instead of ranked-only inputs is mechanical, not a redesign — but it is a signature change, and every caller needs updating in the same commit (not left calling the old two-arg form for some cells and the new form for others, which would be a silent inconsistency).

### Pitfall 3: Reintroducing the exact pre-ranking bug the diagnostic found

**What goes wrong:** The removed `_circular_block_bootstrap_ic()` (git commit `c6f5056b^`, `services/ic_engine.py`) took **pre-ranked** `ranks_X`/`ranks_Y` as input, built a circular-block resampled index array `idx`, then called `_vectorized_ic(ranks_X[idx], ranks_Y[idx])` — i.e., it resampled already-globally-ranked values and never re-ranked the resampled subset. Spearman correlation is defined on ranks-within-the-sample; reusing global ranks on a non-contiguous resampled subset silently narrows the resulting CI (confirmed in the revert commit message: "producing CIs that were systematically too narrow").

**Why it happens:** It is the natural (wrong) thing to do when `ranks_X`/`ranks_Y` are already sitting in scope from the point-estimate computation just above.

**How to avoid:** The new implementation must take **raw** `X`/`Y` (or explicitly re-rank inside the bootstrap loop on the resampled subset every iteration: `rankdata(X_raw[idx], axis=0)`, `rankdata(Y_raw[idx])`, matching the pattern CONTEXT.md points to in `_circular_shift_null` only at the level of "circular wraparound mechanic," not literally reusing that function — see next pitfall).

**Warning signs:** Unit test for the new bootstrap function should explicitly assert that resampling + re-ranking a subset produces DIFFERENT results than resampling pre-ranked values on synthetic data where the two are known to diverge (e.g., an AR(1) series with a resampled block that changes local rank order).

### Pitfall 4: Conflating `_circular_shift_null` (null generator) with a block-bootstrap CI estimator

**What goes wrong:** CONTEXT.md says "reuse the correct pattern already proven in `_circular_shift_null`." `_circular_shift_null(Y, rng)` does a **single global circular shift** of `Y` to destroy `X`-`Y` alignment while preserving `Y`'s own autocorrelation — this generates a null distribution (tests "is there a relationship at all"), it does not generate a sampling distribution of the IC point estimate itself (which is what a CI needs). Literally calling `_circular_shift_null` in a loop would produce a null-distribution-shaped output, not a CI.

**Why it happens:** Both mechanisms use "circular" wraparound to avoid boundary discontinuities, which makes them look more similar than they are.

**How to avoid:** The "proven pattern" to reuse is the **circular-wrap mechanic** (`np.roll`-style wraparound, or the already-existing `starts = rng.integers(0, n, n_blocks); idx = (starts[:, None] + offsets).ravel()[:n] % n` block-index construction from the removed `_circular_block_bootstrap_ic`), applied to a genuine **moving/circular block bootstrap of the paired series** (resample blocks of `(X, Y)` pairs together, preserving pairing, re-rank per replicate, take percentile CI) — not a call to `_circular_shift_null` itself. Recommend restoring the removed `_circular_block_bootstrap_ic` function (it already has the memory-safe per-iteration-allocation form — see next pitfall) with the pre-ranking bug fixed, as a new production function; keep `_circular_shift_null` as-is for the diagnostic's own separate use.

### Pitfall 5: Reintroducing the OOM the removed bootstrap already fixed once

**What goes wrong:** The removed function's own comment documents a *prior* vectorized form that allocated `(n_boot, n_blocks, block_size)` in one broadcast — 7.5 GB per worker at production scale (n=469K, block_size=10), OOM-killing under `ProcessPoolExecutor` parallelism.

**Why it happens:** The naive vectorized bootstrap implementation is the "obvious" one to write from scratch.

**How to avoid:** The version right before removal (commit `c6f5056b^`) already fixed this via **per-iteration allocation** (`for b in range(n_boot): ... boot_ics[b] = ...`, ~3.75 MB per iteration instead of one giant broadcast) — reuse that shape as the starting point, not the original naive form. `git show c6f5056b^:services/ic_engine.py` (lines ~344-382) has the exact reference implementation to restore-and-fix.

### Pitfall 6: Component D's canary rows crashing both `ic_engine.py` and `ensemble_trainer.py` at startup

**What goes wrong:** `FeatureRegistryService.load()`/`load_sync()` (`src/intelligence/feature_registry_service.py`) raises `RuntimeError` if `len(feature_registry rows, all statuses) != len(dataclasses.fields(FeatureVector))` (currently 150). Both `ic_engine.py` (`main()`, ~line 2244) and `ensemble_trainer.py` (`_execute_inner`, ~line 469) additionally do an exact-set-equality check between `feature_registry` names and `FeatureVector` field names, raising `RuntimeError` on any drift (`"feature_registry drift: {symmetric_difference}"`). Inserting 5-10 `feature_registry` rows for canaries **without** adding matching `FeatureVector` dataclass fields breaks both startup gates immediately — the corpus run never gets past initialization.

**Why it happens:** CONTEXT.md's framing ("No new tables, no new service — this is registry rows + one assertion") reads as if this is metadata-only work; the row-count/alignment gates make it structurally impossible to add registry rows in isolation.

**How to avoid:** Component D's "pure noise" and "dead feature" canaries must be implemented as genuine new `FeatureVector` dataclass fields in `src/intelligence/schemas.py`, computed in `src/intelligence/feature_factory.py` (seeded RNG per bar — new APR key for the seed per CLAUDE.md's APR mandate; a literal constant; a near-constant with epsilon noise), with a migration adding the corresponding `feature_vectors` columns, PLUS the `feature_registry` metadata rows (status kept at `'candidate'`, never promoted, so `ensemble_trainer.py`'s `feature_status_at_eval = 'active'` filter excludes them from eligibility automatically as a second line of defense). This makes `_REGISTRY_ROW_COUNT` (derived as `len(dataclasses.fields(FeatureVector))`) auto-correct with no special-casing of the gate itself. The "acausal placebo" canary (an existing feature deliberately paired against a shifted-forward return) can likely be measured as a diagnostic inside `ic_engine.py`'s existing loop without a new column — it reuses an existing feature's values, just mis-paired at measurement time — but this needs an explicit plan decision, not an assumption.

**Cost consequence:** Because this requires new `feature_vectors` columns, Component D requires re-running `scripts/ops/corpus/ops_corpus_pipeline_run.sh` from **Step 1** (`backfill_feature_factory.py --compute-only`, a full feature-factory recompute across all 58+ symbols/4 TFs/full history), not merely from Step 5 (`ic_engine.py`) as A/E/F would otherwise only need. Since all six components are bundled into "one corpus re-run" per the locked sequencing, this means the actual re-run for this phase is a **full pipeline run from Step 1**, not a cheap `ic_engine.py`-only invocation — plan the wave/timing accordingly (this is a multi-hour operation per the project's own corpus-rebuild history in STATE.md, not a quick script).

### Pitfall 7: `_fisher_z_ci`'s "full corpus-wide" scope is ambiguous across 3 call sites CONTEXT.md doesn't mention

**What goes wrong:** `ic_math.py` is explicitly a shared Ring 1 module "so a change to ic_engine.py's internals can no longer silently break its siblings" (its own docstring). Grep confirms `_fisher_z_ci` is called from: `services/ic_engine.py` (3 sites: 772, 1009, 1418), `services/ensemble_ic_engine.py` (1 site: line 778, inside the EIC-04 gate's own CI computation on the ensemble's composite `alpha_score`), and `scripts/ops/corpus/ops_oos_holdout_eval.py` (1 site: line 213). CONTEXT.md's canonical refs list only `ic_engine.py`'s functions.

**Why it happens:** The shared-module extraction (todo 048, 2026-07-02) deliberately fanned this function out to 3 files; "full corpus-wide replacement" is ambiguous about whether it means "every call site of this shared function" or "every cell `ic_engine.py` computes."

**How to avoid:** Surface this as an explicit plan decision (see Open Questions) rather than silently picking a scope. If `ensemble_ic_engine.py`'s EIC-04 CI is left on Fisher-z while `ic_engine.py`'s feature-level CI moves to bootstrap, that is an internally consistent choice (EIC-04's CI is on a composite/aggregated score at much higher N, where the asymptotic approximation is more defensible) but it should be a **stated** decision, not an oversight — and CONTEXT.md itself explicitly defers "should EIC-04's PASS verdict be reconsidered" to the project owner, which is a related but distinct question from "should EIC-04's CI *computation* also move to bootstrap for consistency."

### Component A: what NOT to reproduce (the pre-ranking bug, verified from git history)

```python
# Source: git show c6f5056b^:services/ic_engine.py (removed commit c6f5056b,
# "refactor(ic_engine): replace circular block bootstrap with Fisher z-transform CI")
# THE BUG: ranks_X/ranks_Y are ALREADY GLOBALLY RANKED before this function is called.
# Resampling indices into already-ranked arrays and never re-ranking the resampled
# subset silently narrows the CI -- this is the exact defect the 2026-07-09 diagnostic
# proved exists in production.
def _circular_block_bootstrap_ic(
    ranks_X: np.ndarray,   # <-- BUG: pre-ranked, not raw
    ranks_Y: np.ndarray,   # <-- BUG: pre-ranked, not raw
    block_size: int,
    n_boot: int,
    rng: np.random.Generator,
) -> tuple[np.ndarray, np.ndarray]:
    n, p = ranks_X.shape
    n_blocks = math.ceil(n / block_size)
    boot_ics = np.zeros((n_boot, p))
    offsets = np.arange(block_size)
    for b in range(n_boot):
        starts = rng.integers(0, n, size=n_blocks)
        idx = (starts[:, None] + offsets).ravel()[:n] % n
        boot_ics[b] = _vectorized_ic(ranks_X[idx], ranks_Y[idx])  # <-- BUG: no re-rank
    ci_lower = np.percentile(boot_ics, 2.5, axis=0)
    ci_upper = np.percentile(boot_ics, 97.5, axis=0)
    return ci_lower, ci_upper
```

**The fix shape** (not locked code, but the structural correction): accept raw `X`/`Y`, and inside the loop, `rankdata(X_raw[idx], axis=0)` / `rankdata(Y_raw[idx])` before calling `_vectorized_ic`. The circular-wrap index construction (`starts`/`offsets`/`idx`) is already correct and reusable as-is — only the ranking step needs to move inside the loop.

### Component F: the join point that already has zero marginal cost

```python
# Source: services/ic_engine.py:1282-1293 (_compute_cross_sectional_tf's chunk_sql) --
# the exact query POOLED-strata IC measurement runs. feature_cols already expands to
# EVERY FeatureVector field, including true_range_pct (TR/C, raw non-negative, NOT
# z-scored -- unlike atr_z, which IS z-scored and therefore unusable as a sigma-scale
# denominator: dividing by a mean-0/std-1 quantity is not a volatility normalization).
chunk_sql = f"""
    SELECT fv.bar_ts, {feature_cols}, {return_cols}, {complete_cols}
    FROM feature_vectors fv
    INNER JOIN forward_returns fr
        ON fr.symbol = fv.symbol AND fr.tf = fv.tf AND fr.bar_ts = fv.bar_ts
        AND fr.return_type = 'executable_open_to_open'
    WHERE fv.tf = %(tf)s AND fv.bar_ts = ANY(%(ts_chunk)s)
    ORDER BY fv.bar_ts
"""
# true_range_pct is already a column in X_raw (index = _FEATURE_NAMES.index("true_range_pct")).
# vol_normalized_return = return_x / true_range_pct (epsilon-guarded, matching the
# existing _ret_vol_ratio() pattern in feature_factory.py:1461-1469) needs ZERO new
# query, ZERO new join -- just a new derived array from data already fetched here.
```

CONTEXT.md's alternative ("or a trailing realized-vol window") is a genuinely different, more expensive path: no rolling-window volatility measure currently exists anywhere accessible to `ic_engine.py` (`forward_returns` has no vol column at all — verified via `\d forward_returns`: only `return_fast/mid/slow/extended`, no sigma/std/vol field) — it would need new SQL window-function computation or a new upstream column. Recommend `true_range_pct` as the minimal-diff path unless there's a reason to prefer a smoothed multi-bar window (noisier single-bar TR% vs. a stabler but newly-computed rolling window is the real tradeoff here).
