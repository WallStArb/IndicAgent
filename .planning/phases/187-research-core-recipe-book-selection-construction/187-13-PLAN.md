<objective>
Conclusions become records and the markdown ledger becomes a rendering (design 10.2.3 summary cards, 10.2.6 generated ledger, 14.2).

Legacy verdicts: phase 186 wrote the cards (`docs/research/summary-cards/`, lint in `tests/unit/test_summary_cards.py`; the README says phase 187 loads every card as a `kind = 'legacy_verdict'` attempt). Only `kind: legacy_verdict` cards load; the six `dead_cache` cards record dropped caches, not verdicts, and stay files. Each card maps to a concept: the five deprecated old-verdict rows plan 11 retyped to `family` match by name (card_id without `legacy-`, hyphens to underscores); any other card gets a new `family` identity row written by S6 in the same transaction (an old verdict is a tested idea; S6 writes research identities). Row fields: kind legacy_verdict, mode real, vintage `legacy` (these predate vintage_1 and never join the selection universe), spec_path = recipe.spec or recipe.script, spec_hash = sha256 of the card file bytes, code_commit = recipe.recipe_commit, status completed at insert time through the normal started -> terminal path in one transaction, evidence = the card front matter plus `card_path`. Idempotent by card_id (skip when a legacy_verdict row with evidence->>'card_id' exists). Card numbers are copied, never recomputed.

Ideas: the hand ledger's sections 1-3 hold ideas that exist nowhere else. An import script parses them into (domain, name, description, sources) rows, prints the mapping table in a dry run (matched to an existing concept, or new), and writes new ones through register_idea (plan 12). The owner reviews nothing here: ambiguous parses are listed in the summary and logged as ideas with the raw ledger text as description, never dropped.

Generated ledger and job: the renderer reads concept_research_stage, research_run (headline columns), research_run_series through select_books' selection function (plan 06; the selection set is computed, never stored), and the legacy rows. Output is deterministic (sorted, no wall-clock timestamp except a "rendered from DB state as of <max written_at>" line). Unit CI has no database (design 10.2.6), so tests render from fixture rows. The job is a oneshot service plus timer (daily, after the nightly backfill window; pick a time that does not overlap 04:40 UTC Alpaca capture or the fetcher's heavy window, e.g. 07:15 UTC), registered in `_DAG_ORDER` at priority 8 with a comment (plan 16 replaces `_DAG_ORDER` with the manifest). It has no Kafka consumer, so no `alert.lag.*` key (the ibkr-history-fetcher precedent); it emits `job_completed_total{job="research_ledger_render", status}`. When the rendered text differs from the file, it writes the file atomically and runs `git commit -m "docs(research-ledger): nightly render" -- docs/research/research-ledger.md` (retry on index.lock up to the APR count `infra.research_ledger_render.git_lock_retries`, seeded in a migration), never pushes, never touches another path; no change means no commit.

Standing rules (CLAUDE.md, all of phase 187): no em dashes, no AI attribution; commit on main with `git commit -m "..." -- <paths>`, never amend, never stage another session's files; substantive code class: /simplify then /review then the FULL unit suite `.venv/bin/pytest tests/unit/ -n auto` before each commit; after any edit under src/intelligence/research/ or src/intelligence/statistics/ run `.venv/bin/python -m scripts.research.determinism.repro_frozen <scratch_dir> --logs /home/bg/dev/indicagent/logs` and require bit-identical; new spec fields only through spec.py `_OPTIONAL_*_FIELDS` (the family 1 and family 2 spec hashes must not move: one family 2 evidence run is owner-approved after 191-25 and may go at any time); the S6 ledger stays the sole writer of research_run and of every new attempt table; migration numbers go stale: re-check `ls production/migrations | tail -3` at execution and commit a live-applied migration in the same breath; every new tunable is an APR key seeded in a migration; do not edit src/intelligence/bars/, the fetcher or feature writers (other lanes).

The APR seed for the git lock retry count goes in a small migration, number next free at execution (re-check `ls production/migrations | tail -3`).
