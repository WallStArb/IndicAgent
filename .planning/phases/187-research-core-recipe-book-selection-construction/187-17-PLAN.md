<objective>
`single_writer` enforced by the database (design 14.5: every service connects as the postgres superuser). One login role per writer node, grants only on its own tables, a read-only role for readers, all generated from the plan 16 manifest.

High blast radius: every daemon's DSN changes. So the plan is staged: generate, diff, review, apply grants (additive and harmless while services still connect as postgres), then switch DSNs service by service.

Credentials: one password per role, generated at apply time, stored in `/etc/indicagent/db/<role>.env` (owner bg, mode 0600, containing `DATABASE_URL=postgresql://<role>:<pw>@localhost:5432/indicagent`), never in git. Each unit gets a systemd drop-in `/etc/systemd/system/<unit>.service.d/10-db-role.conf` with `EnvironmentFile=/etc/indicagent/db/<role>.env`; Settings already reads DATABASE_URL, so no service code changes. CLI writer nodes (for example run_spec.py, the S6 ledger node) document `set -a; . /etc/indicagent/db/<role>.env; set +a` in operations-database.md.

Grant shape per writer node: CONNECT, USAGE on schema public; SELECT on declared inputs (tables and views); SELECT, INSERT, UPDATE, DELETE on declared outputs as the manifest declares the write verbs (append-only tables get no UPDATE/DELETE beyond what their triggers allow); USAGE on owned sequences; EXECUTE where a node calls a function. Hypertable grants propagate to chunks (confirm on one hypertable in the integration test). Shared-writer exceptions from the manifest (for example concept_registry: ConceptRegistryService and the S6 ledger) are granted to both, by name. The existing NOLOGIN `bar_derivation_writer` becomes a member-of grant of the bar-derivation node's login role, or is replaced if the generator's model covers it; decide from the diff and record.

Rollout order: manifest restart priority descending (top-level and audit nodes first, ingest last), oneshots at their next run or a manual `systemctl start` when idle. Per node: apply drop-in, daemon-reload, restart, then check the five BaseDaemon health signals or `job_completed_total{status="ok"}` and the service log for permission errors; any error reverts that node (remove drop-in, restart) and stops the rollout for diagnosis. Lanes owned by other sessions (the IBKR history fetcher, bar derivation, feature writers, regime writer while the 186-26 rebuild or phase 191 plans run): grants applied, DSN switch only when `systemctl` and `pgrep` show the lane idle and no backfill is live (never during a fingerprinted batch run: a restart is fine, an edit is not, and none is needed); otherwise listed by name in the summary with a captured todo.

Standing rules (CLAUDE.md, all of phase 187): no em dashes, no AI attribution; commit on main with `git commit -m "..." -- <paths>`, never amend, never stage another session's files; substantive code class: /simplify then /review then the FULL unit suite `.venv/bin/pytest tests/unit/ -n auto` before each commit; after any edit under src/intelligence/research/ or src/intelligence/statistics/ run `.venv/bin/python -m scripts.research.determinism.repro_frozen <scratch_dir> --logs /home/bg/dev/indicagent/logs` and require bit-identical; new spec fields only through spec.py `_OPTIONAL_*_FIELDS` (the family 1 and family 2 spec hashes must not move: one family 2 evidence run is owner-approved after 191-25 and may go at any time); the S6 ledger stays the sole writer of research_run and of every new attempt table; migration numbers go stale: re-check `ls production/migrations | tail -3` at execution and commit a live-applied migration in the same breath; every new tunable is an APR key seeded in a migration; do not edit src/intelligence/bars/, the fetcher or feature writers (other lanes).
</objective>
