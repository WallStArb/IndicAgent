- [ ] CONSTRAINT: hypertable-bulk-update — A single `UPDATE signal_events WHERE status='pending' AND ts < NOW() - INTERVAL '2 days'` across 200K+ rows **crashes the PostgreSQL backend** regardless of `statement_timeout = 0`. Must always batch at 5000 rows/iteration. Already fixed in `_reconcile_outcomes` (commit `26c15f4f`). Do not revert to single-statement approach.

**Do not proceed until all boxes are checked.**

## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| asyncpg `timeout=None` is not "no timeout" | Passing `timeout=None` to asyncpg `fetchval`/`fetch` falls back to the pool's `command_timeout` (30s), not infinity. Does not suppress the timeout. | advisory | Use batching so each call completes in <30s. If unbounded query is unavoidable, use `asyncpg.connect(command_timeout=None)` directly — but beware of `idle_in_transaction_session_timeout=30s` at DB level. |
| Bulk hypertable UPDATE crashes PG backend | `UPDATE signal_events ... WHERE status='pending' AND ts < NOW() - INTERVAL '2 days'` on 200K+ rows causes `ConnectionDoesNotExistError` — PG backend OOM/crash. Even psql crashes. 1000-row test worked fine. | blocking | Always batch at ≤5000 rows. Fixed in `_reconcile_outcomes`. |
| `_verify_replay` fan-out overcounting | `LEFT JOIN trade_frames ... LEFT JOIN trade_executions` on signal_events inflates `total` count when multiple executions exist per frame. `target_no_pnl` was counting duplicate rows. | advisory | Verify numbers via direct `SELECT COUNT(*) FROM signal_events` for ground truth. |
