<objective>
Add `threading.RLock` protection to the three naked module-level globals in `src/config/settings.py` (`_settings_singleton`, `_active_contracts_cache`, `_active_contracts_last_refresh`). Use double-checked locking in `get_active_contracts()` so the DB query is NOT held under the lock. Cover the `invalidate_active_contracts_cache()` race surfaced in RESEARCH.md Pitfall 3. Add a comment to `CacheManager.snapshot()` documenting why lock-free reads are correct in an asyncio context (D-10). Add a concurrent-callers unit test proving the locks close the race.

Purpose: Phase 089's per-key plugin worker pool puts the ThreadPoolExecutor under real contention. `_default_settings()` and `get_active_contracts()` are now hot paths called from multiple threads. The current check-then-set patterns are textbook read-modify-write races. Closing them is correctness, not optimization. THREAD-02 (CacheManager asyncio locks) was already shipped in Phase 089; this plan only adds a documentation comment on `snapshot()` — it does NOT re-add asyncio locks.

Output: settings.py with RLock-protected module state, cache_manager.py with snapshot() invariant comment, new unit test covering the threading.
</objective>
