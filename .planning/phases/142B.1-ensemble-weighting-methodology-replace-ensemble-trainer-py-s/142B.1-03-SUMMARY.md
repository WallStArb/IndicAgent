# Phase 142B.1 Plan 03: E1 Shrinkage — Compute Pass, Hard Out-of-Fold Gate, ensemble_trainer Wiring Summary

**`ops_ic_shrinkage.py` shrinks every reliable `feature_ic_scores.ic_sharpe_hac` toward a leave-one-out `(group_name, regime, tf)` peer-group prior, validates the mechanism with a genuine train-T/held-out-T+1 out-of-fold test, and — on real-corpus PASS — flips `alpha.ensemble.ic_input` to `ic_shrunk`, which `ensemble_trainer.py` now consumes via an APR toggle that defaults to byte-for-byte v1 behavior.**

## Accomplishments

- `scripts/ops/alpha/ops_ic_shrinkage.py` implements both E1 responsibilities as pure, independently unit-tested functions wrapped by thin DB orchestration:
  - **Compute pass** (`compute_shrinkage_updates`): leave-one-out `(group_name, regime, tf)` prior + `shrink_ic()` (from Plan 02) over every `reliable=true, ic_sharpe_hac IS NOT NULL` row, bulk-UPDATEd by the 6-column PK via `bulk_update_by_key` — `ic_engine.py`'s write path is completely untouched.
  - **Out-of-fold gate** (`build_out_of_fold_errors` + `evaluate_out_of_fold_gate`, D-05 HARD GATE): reconstructs a train-window-T / held-out-window-T+1 split (scale-specific embargo) of the already in-sample corpus per cross-sectional POOLED reliable cell, computes a *fresh* window-T-only leave-one-out prior (not Part A's full-corpus prior), and compares `|ic_shrunk_T - ic_realized_T+1|` vs `|ic_raw_T - ic_realized_T+1|`. PASS is strict inequality on the mean (a tie FAILs). The `alpha.ensemble.ic_input` flip via `ConfigService.set()` lives strictly inside the PASS branch — verified both by a source-parsing unit test and by matching threat-model disposition T-142B1-03-02.
- `services/ensemble_trainer.py`: `EnsembleConfig` gained an `ic_input` field (via `_cfg(cfg, "alpha.ensemble.ic_input", "ic_sharpe_hac")`), a pure `_resolve_ic_input_column()` helper that fails loud on an unknown value, and `_process_stratum` now SELECTs `ic_shrunk`/`shrinkage_weight`, remaps the resolved column to the `"ic_sharpe"` key `select_features_per_stratum` expects, and adds `AND ic_shrunk IS NOT NULL` to the WHERE clause only when `ic_input='ic_shrunk'`. Default path is byte-for-byte identical to pre-plan behavior.
- `scripts/ops/corpus/ops_corpus_pipeline_run.sh`: inserted `ic_shrinkage` as step 5, strictly between `ic_engine` (4) and `ensemble_trainer` (now 6); `alpha_publisher` becomes step 7. Banner total updated `/6` → `/7`. All other step ordering, symbol-arg handling, and OOS-holdout/weight-epoch logic is unchanged.
- **Live operational verification against the real corpus** (not just unit tests): ran `ops_ic_shrinkage.py` directly against the production `indicagent` database.
  - Compute pass: 13,567 reliable cells read, 13,567 rows updated with `ic_shrunk`/`shrinkage_weight`, zero NaN/Inf, `shrinkage_weight` bounded in `[0.9249, 0.9996]` (consistent with large `n_independent` values dominating a small `k=100`).
  - Out-of-fold gate: 3,160 cross-sectional cells evaluated across 23 (tf, regime) strata. Mean shrunk error `0.045612` < mean raw error `0.046824` → **PASS**. `alpha.ensemble.ic_input` flipped to `'ic_shrunk'` live in `config_state`, with a `config_history` audit row (`version=2`, `changed_by='ops-ic-shrinkage'`) recording the exact PASS evidence.
  - Verified in DB: zero non-candidate (`reliable=false`) rows touched; all 13,567 candidate rows populated; no NaN/Inf in any `ic_shrunk` value.

## Decisions Made

- **Peer group key is exactly `(group_name, regime, tf)`, symbol- and lookahead-agnostic** — matches D-06's literal wording. A POOLED row and a per-symbol row in the same feature family, regime, and tf are peers of each other; this is a deliberate reading, not an oversight (confirmed by re-reading D-06 and RESEARCH.md Pitfall 2 together, which both describe the peer group only in terms of feature family × regime × tf).
- **Out-of-fold test built fresh, not reused from existing vintages** — a DB query confirmed `feature_ic_scores` currently has exactly one `training_window_end` per cell (no historical second vintage exists yet to serve as a genuine "next window"). The correct construction per RESEARCH.md Pitfall 4 (predict a *future held-out* window, not same-window fit) required reconstructing a train-T/held-out-T+1 split from raw `feature_vectors`/`forward_returns` data, scoped to `bar_ts < alpha.validation.oos_start` so Phase 144's true OOS boundary is never touched.
- **SQL-side cross-sectional averaging (`GROUP BY bar_ts`) instead of `ensemble_ic_engine.py`'s Python-side `_aggregate_pooled_series` pattern** — the regime is already pinned by the query's `WHERE mr.regime_label = %s` clause before any averaging happens, so Pitfall 5's "group before averaging" discipline holds by construction without needing the Python-side reduction step that module uses purely for its own unit-testability. This was materially faster against the live 10M+-row `feature_vectors` table (measured: ~2-3s per stratum fetch, ~60s total for all 23 strata) and was required to make the operational verification tractable within a reasonable time budget.
- **Exit code 0 on both gate PASS and FAIL** — deliberately diverges from `ops_ensemble_ic_gate.py`'s exit-1-on-FAIL convention. That script is a CI/systemd phase gate meant to halt progression; `ops_ic_shrinkage.py`'s gate decides an internal APR toggle, and a FAIL is a legitimate negative finding that must not stop the corpus pipeline from proceeding to `ensemble_trainer` (which will simply keep reading `ic_sharpe_hac`).
