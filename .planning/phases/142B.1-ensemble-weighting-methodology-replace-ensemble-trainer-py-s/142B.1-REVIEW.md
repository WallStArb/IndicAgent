# Phase 142B.1: Code Review Report

**Reviewed:** 2026-07-04T00:00:00Z
**Depth:** standard
**Files Reviewed:** 17
**Status:** issues_found

## Summary

This phase merges five plans (E1 shrinkage, E2 mean-variance combination, migration 196,
and the A/B judge infra) plus a mid-execution fix that threaded `weight_version` scoping
into `services/ensemble_ic_engine.py` and its idempotency/worker-fetch tests. The pure-math
modules (`shrinkage.py`, `weights.py`) are well-specified, well-tested, and free of
correctness defects — degenerate-input handling (`n_eff<=0`, singleton peer groups,
ill-conditioned covariance, zero-sum weight vectors) is deliberate and unit-tested. The
`resolve_stratum_weights` branch-selection logic in `ensemble_trainer.py` correctly falls
back to `cluster_deflate_weights` on an ill-conditioned mean-variance solve and logs the
fallback (never a silent skip).

The `weight_version` threading requested for special attention is **incomplete**: the
per-run epoch is correctly filtered into every SQL fetch and tagged onto every written row,
but two places were missed. First, `EnsembleICEngine._assert_prerequisites`'s primary
crash-loud gate (`alpha_events` emptiness) checks the *whole table*, not the resolved
`weight_version` — a scoped/mistyped `--weight-version` run silently completes with zero
rows instead of raising, which directly contradicts the module's own documented invariant
("Crashes loud at startup when alpha_events... is empty"). Second, the post-write
`hold_max_bars` APR calibration step runs unconditionally regardless of which
`weight_version` produced the measurements, so a challenger/diagnostic run can silently
overwrite live trading configuration with unproven data. Both are classified BLOCKER below.

Several lower-severity schema/hygiene gaps round out the findings: migration 196's
`config_history` inserts aren't actually idempotent despite the migration header's claim,
`alpha_ensemble_ic`'s primary key was never extended to include `weight_version`, and there
is unescaped dynamic SQL column interpolation in `ops_ic_shrinkage.py` without the safety
comment its sibling pattern in `ensemble_trainer.py` carries.

## Critical Issues

### CR-01: `EnsembleICEngine` crash-loud gate is not scoped to `weight_version` — silent zero-row run

**File:** `services/ensemble_ic_engine.py:398-405` (gate), called at `services/ensemble_ic_engine.py:804`

**Issue:** `_assert_prerequisites` raises `RuntimeError` when `alpha_events` is empty:

```python
async def _assert_prerequisites(conn: asyncpg.Connection, tfs: list[str] | None = None) -> None:
    """Three COUNT checks; raise RuntimeError (crash loud) if any is empty."""
    n_alpha = await conn.fetchval("SELECT count(*) FROM alpha_events")
    if not n_alpha:
        raise RuntimeError(...)
```

This `count(*)` is over the **entire table**, not filtered by the `weight_version` that was
just resolved a few lines earlier (`_execute_inner`, line ~793-801) and used to build
`tf_list` via `SELECT DISTINCT tf FROM alpha_events WHERE weight_version = $1`. If
`--weight-version` (or the APR default `alpha.ensemble.weight_version`) refers to a variant
that has zero `alpha_events` rows — a typo, a challenger that hasn't been generated yet by
`ensemble_trainer.py --weight-version <x>` + `alpha_publisher.py --weight-version <x>`, or a
stale APR value — this gate still passes as long as *some other* weight_version has rows in
the table. Tracing forward: `tf_list` is `[]`, `symbol_tf_pairs` is `[]` (also filtered by
the same `weight_version`), `symbol_to_tfs` collapses to `{"POOLED": []}`, the sole dispatched
worker's `for tf in tfs:` loop never executes, `rows_to_write` ends up empty, the `executemany`
write is skipped (`if rows_to_write:`), `_calibrate_hold_max_bars` returns `0`, and the run
logs `ensemble_ic.run_complete` with `n_rows=0` and exits **successfully**. This is exactly
the "silent wrong answer" class of failure the module's own docstring says it exists to
prevent ("Crashes loud at startup when alpha_events, forward_returns, OR market_regimes is
empty"), and it is untested — `tests/unit/test_ensemble_ic_pooled_dispatch.py`'s
`TestWeightVersionScoping` verifies the SQL/row-building layer is filtered, but nothing
exercises `_assert_prerequisites` under a `weight_version` with zero rows.

**Fix:**
```python
async def _assert_prerequisites(
    conn: asyncpg.Connection, weight_version: str, tfs: list[str] | None = None
) -> None:
    n_alpha = await conn.fetchval(
        "SELECT count(*) FROM alpha_events WHERE weight_version = $1", weight_version
    )
    if not n_alpha:
        raise RuntimeError(
            f"EnsembleICEngine startup gate FAILED: alpha_events has zero rows for "
            f"weight_version={weight_version!r}. Run ensemble_trainer.py + "
            f"alpha_publisher.py with --weight-version {weight_version!r} first, or check "
            f"for a typo / stale alpha.ensemble.weight_version APR value."
        )
    ...
```
and update the call site at line 804 to pass `weight_version` (already resolved a few lines
above this call).

### CR-02: `_calibrate_hold_max_bars` writes live trading config unconditionally, ignoring which `weight_version` produced the data

**File:** `services/ensemble_ic_engine.py:892-968` (method), called unconditionally at `services/ensemble_ic_engine.py:895`

**Issue:** After the IC measurement write, `_execute_inner` always calls:

```python
n_keys_written = await self._calibrate_hold_max_bars(pool, corpus_all_results, config)
```

`_calibrate_hold_max_bars` writes `alpha.frame.hold_max_bars.<regime>.<tf>` via
`ConfigService.set(...)` — a live, operator-facing APR key documented elsewhere as governing
real position holds (`"hold_max_bars is a per-symbol execution parameter"`, docstring at
line 923). This write path has no `weight_version` guard whatsoever. The CLI's own help text
frames `--weight-version` as the mechanism for scoring "a challenger's alpha_events rows, not
the champion's" (`services/ensemble_ic_engine.py:983-986`) — i.e. this tool is explicitly
designed to be invoked against unproven/experimental weight variants for A/B measurement
(mirrors `ops_ensemble_weight_compare.py`'s champion/challenger workflow). Every such
challenger run will silently recalibrate the production `alpha.frame.hold_max_bars.*` keys
consumed by live trading logic from data that has not passed the D-10/D-12 win-decision gate
in `ops_ensemble_weight_compare.py`. A losing or not-yet-evaluated challenger can therefore
corrupt live execution parameters purely by being measured.

**Fix:** Gate the calibration step on the resolved `weight_version` matching the currently
"live" champion (e.g. compare to `alpha.ensemble.weight_version`'s APR default, or add an
explicit `--calibrate-hold-max-bars` opt-in flag defaulting to off for non-default
`weight_version` runs):
```python
if weight_version == apr_default_weight_version:
    n_keys_written = await self._calibrate_hold_max_bars(pool, corpus_all_results, config)
else:
    self.logger.info(
        "ensemble_ic.hold_max_bars_calibration_skipped",
        reason="scoped_weight_version_run",
        weight_version=weight_version,
    )
    n_keys_written = 0
```

## Warnings

### WR-01: `feature_ic_scores` peer-group bucketing omits `lookahead_bars`, mixing IC estimates across timescales into one prior

**File:** `scripts/ops/alpha/ops_ic_shrinkage.py:161-166`

**Issue:** `compute_shrinkage_updates` buckets candidate rows purely on
`(group_name, row["regime"], row["tf"])`:

```python
buckets.setdefault((group_name, row["regime"], row["tf"]), []).append(idx)
```

`lookahead_bars` is not part of the key, so the same feature measured at `lookahead=1` and
`lookahead=60` (very different typical IC-Sharpe magnitudes — fast-horizon and
extended-horizon IC are not directly comparable) become "peers" of one another inside the
same leave-one-out prior, alongside every other feature in the family at any lookahead. The
docstring asserts this matches "D-06's literal spec" verbatim, so this may be intentional,
but it is worth flagging: shrinking a fast-lookahead cell toward a prior partly built from
slow-lookahead cells of the same family (and vice versa) risks systematically biasing
`ic_shrunk` in a way the out-of-fold gate (`evaluate_out_of_fold_gate`) may not detect if the
corpus happens to be dominated by one lookahead's cell count.

**Fix:** At minimum, add a code comment (or a `RESEARCH.md` cross-reference) confirming this
cross-lookahead pooling was deliberately validated, not an oversight; consider adding
`lookahead_bars` (or the coarser `scale` name) to the bucket key and re-running the
out-of-fold gate to confirm the tighter peer group still passes D-05.

### WR-02: `alpha_ensemble_ic` primary key was never extended to include `weight_version`

**File:** `production/migrations/195_alpha_ensemble_ic.sql:55` (existing `PRIMARY KEY (event_row_id, scored_at)`), `production/migrations/196_ensemble_shrinkage_mean_variance.sql:175-181` (column added, PK untouched)

**Issue:** Migration 196 adds `alpha_ensemble_ic.weight_version` specifically so two weight
variants' measurements can coexist without blending (per the migration's own Section 3
comment). However the table's actual uniqueness constraint — `PRIMARY KEY (event_row_id,
scored_at)` from migration 195 — was never widened to include `weight_version`. The
`ON CONFLICT (event_row_id, scored_at) DO UPDATE` in `_ENSEMBLE_IC_INSERT_SQL`
(`services/ensemble_ic_engine.py:357`) therefore has no DB-level awareness of
`weight_version` at all: two rows for the identical `(symbol, tf, regime, lookahead)` cell
under two *different* `weight_version`s only avoid colliding because their `scored_at` values
happen to differ (each invocation pins a fresh `datetime.now(UTC)`). In today's
single-invocation-at-a-time operational model this is not currently exploitable, but it is a
latent design gap: nothing at the schema level actually prevents a future code path (or a
concurrent/scripted double-run) from silently overwriting one variant's row with another's.

**Fix:** Consider a follow-up migration widening the PK/unique index to
`(event_row_id, weight_version, scored_at)` so the schema itself enforces the invariant the
column was added to guarantee, rather than relying on incidental timestamp separation.

### WR-03: Duplicated `_effective_weight_version` helper across two services

**File:** `services/ensemble_ic_engine.py:113-118`, `services/ensemble_trainer.py:251-258`

**Issue:** Both files independently define an identical function:
```python
def _effective_weight_version(cli_weight_version: str | None, apr_default: str) -> str:
    return cli_weight_version if cli_weight_version else apr_default
```
with near-identical docstrings noting they "mirror" each other. This is a straightforward
DRY violation — if the precedence rule ever needs to change (e.g. to also validate the
resolved value is non-empty), both copies must be updated in lockstep or they silently drift.

**Fix:** Move this one-line helper into `services/_batch_utils.py` (already the shared
import surface for both files, e.g. `cfg`, `connect_db_from_url`,
`load_apr_dict_async`) and import it from both call sites.

### WR-04: Unescaped dynamic SQL column interpolation in `ops_ic_shrinkage.py` lacks the safety justification its sibling pattern documents

**File:** `scripts/ops/alpha/ops_ic_shrinkage.py:359-361`

**Issue:**
```python
feature_names = sorted({c["feature_name"] for c in stratum_cells})
col_list = ", ".join(f'AVG(fv."{name}") AS "{name}"' for name in feature_names)
sql = _STRATUM_FETCH_SQL_TEMPLATE.format(col_list=col_list)
```
`feature_names` is interpolated directly into a SQL string via an f-string with no
parameterization, no `quote_ident`, and no validation that `name` cannot contain a `"`
character (which would break out of the quoted identifier). The analogous construction in
`services/ensemble_trainer.py:613` (`col_list = ", ".join(f'fv."{c}"' for c in col_subset)`)
carries an explicit comment — `"Safe: col_subset names come from information_schema, not
user data"` — justifying why this is acceptable; this file has no equivalent comment, and
the provenance here (`feature_ic_scores.feature_name`, ultimately from `feature_registry`) is
one hop further from a hard schema guarantee than `information_schema.columns`.

**Fix:** Add the same explicit safety-provenance comment, or better, validate each
`feature_name` against `^[a-zA-Z_][a-zA-Z0-9_]*$` before interpolating (cheap, defensive, and
removes the need to reason about provenance at every call site).

### WR-05: Migration 196's `config_history` inserts are not actually idempotent, contradicting the migration's own "Safe to re-run" claim

**File:** `production/migrations/196_ensemble_shrinkage_mean_variance.sql:82-86, 108-113, 136-141, 162-166`

**Issue:** The migration header states: "All statements idempotent: ADD COLUMN IF NOT
EXISTS, idempotent DO-block for the CHECK constraint..., ON CONFLICT DO NOTHING per key
insert... Safe to re-run." This is true for `config_schema` and `config_state` (both use
`ON CONFLICT (config_key) DO NOTHING`), but each of the four `config_history` INSERTs has no
conflict guard at all:
```sql
INSERT INTO config_history (timestamp, config_key, version, config_value, changed_by, reason)
VALUES (NOW(), 'alpha.ic.shrinkage_k', 1, '100', 'migration_196', '...');
```
Because `timestamp` defaults to `NOW()` (different on every execution), re-running this
migration — which the header explicitly invites — will append a fresh duplicate audit row
for all four keys every time, each claiming `version=1` with a different `changed_by`
timestamp. This doesn't corrupt `config_state` (which stays correct via `ON CONFLICT DO
NOTHING`), but it does pollute the `config_history` audit trail with misleading repeated
"initial" entries, undermining exactly the provenance guarantee `config_history` exists to
provide.

**Fix:** Guard each `config_history` insert with an existence check, e.g.:
```sql
INSERT INTO config_history (timestamp, config_key, version, config_value, changed_by, reason)
SELECT NOW(), 'alpha.ic.shrinkage_k', 1, '100', 'migration_196', '...'
WHERE NOT EXISTS (
    SELECT 1 FROM config_history WHERE config_key = 'alpha.ic.shrinkage_k' AND version = 1
);
```

## Info

### IN-01: `_parse_insert_columns` derives column order via naive comma-split string parsing

**File:** `services/ensemble_ic_engine.py:375-386`

**Issue:** `_parse_insert_columns` extracts the column list by locating the first `(` and
matching `)` in the INSERT SQL text and splitting on `,`. This is fine for the current
flat column list but would silently mis-parse if any future column name involved a
function call or nested parens inside the column list. Low risk today (purely a maintenance
trap), but worth a one-line comment noting the assumption ("no nested parens in the column
list") so a future editor doesn't add one without noticing.

### IN-02: `CorpusManifest` path for `ensemble_ic_engine` is not scoped by `weight_version`

**File:** `services/ensemble_ic_engine.py:769`

**Issue:** `CorpusManifest("ensemble_ic_engine", Path(".planning/corpus_manifests"))` writes
to a fixed manifest name regardless of `weight_version`. Running the tool back-to-back for a
champion and a challenger (the exact workflow `ops_ensemble_weight_compare.py` is built to
support) will have the second run's manifest overwrite the first's, losing per-variant
provenance/observability — a purely cosmetic/observability gap, not a correctness bug, since
the actual measurement rows are safely persisted to `alpha_ensemble_ic` regardless.

**Fix:** Include `weight_version` in the manifest name, e.g.
`CorpusManifest(f"ensemble_ic_engine_{weight_version}", ...)`.
