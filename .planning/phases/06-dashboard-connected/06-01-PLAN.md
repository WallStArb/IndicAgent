      TimeframeBuilder aggregates incoming 1m OHLCV bars into 5m/15m/1h/4h/1d bars.

      API expected by timeframes_builder_service.py (see lines 249-298):
        - `__init__(streams_manager: RedisStreamsManager)` — store streams_manager
        - `async start() -> None` — initialize accumulators, start processing loop
        - `async stop() -> None` — cancel task, flush pending accumulators
        - `async subscribe_to_symbols(symbols: list[str]) -> None` — register symbols to watch
        - `get_metrics() -> dict` — return counts: bars_1m_processed, bars_5m_built, bars_15m_built, bars_1h_built, bars_4h_built, bars_1d_built, symbols_active

      Bar accumulation logic per timeframe:
        - Period boundary: `bar_open_ts = floor(bar_ts_seconds, TF_minutes * 60)` where TF_minutes is 5/15/60/240/1440
        - First bar in period: accumulated = { open: bar.open, high: bar.high, low: bar.low, close: bar.close, volume: bar.volume, period_ts: bar_open_ts }
        - Subsequent bars: high=max(acc.high, bar.high), low=min(acc.low, bar.low), close=bar.close, volume+=bar.volume
        - Emit when next 1m bar has a DIFFERENT period_ts: emit the completed accumulator, start new accumulator

      Stream keys (MUST use stream_keys.py helpers):
        - Input: `{env_prefix}market:{SYMBOL}:1m` (reads from market_data stream the indicator_service writes from)
        - Actually reads from `{env_prefix}indicators:{SYMBOL}:1m` stream (that's where OHLCV + indicators are published)
        - Output: `{env_prefix}market:{SYMBOL}:{TF}` for each TF in [5m, 15m, 1h, 4h, 1d]

      IMPORTANT: Check what stream the service should actually read from. The research mentions "market:SYMBOL:1m" but the indicator_service publishes to `indicators:SYMBOL:1m`. Check stream_keys.py + timeframes_builder_service.py config for the exact input stream name. Use whatever stream the service is configured to consume (look at `self.config["service"]["input_stream"]` or similar in the service).

      Use structlog for logging. Use Settings() to get env_prefix.
      Keep the class focused: no metrics server, no HTTP — that lives in the service shell.

      Cases:
        - Single 5m period: 5 1m bars with timestamps minute 0,1,2,3,4 → emits 1 5m bar on minute 5 arrival
        - Open/High/Low/Close/Volume accumulation:
            1m bars: [O=100,H=102,L=99,C=101,V=100], [O=101,H=103,L=100,C=102,V=150]
            → 5m partial: O=100, H=103, L=99, C=102, V=250
        - Period boundary: bar at minute 5 (new period) triggers emit of 0-4 period
        - Multiple TFs independently: 1m bar triggers 5m emit but not 15m emit until 15 bars
    </behavior>
