<objective>
Add the post-run transition-writer hook to ic_engine.main() — the single place lifecycle state can change,
because it only changes when new IC measurements land. This one hook delivers LIFECYCLE-03 (demote decaying
active features to shadow_only + promote recovered ones through Plan 02's record_transition_sync),
LIFECYCLE-04 (regime-shift guard), and LIFECYCLE-05 (IC staleness gauge + alert). It writes a
gate-evaluation fact per run to integrity_monitor (observability only; feature_transition_log stays the sole
authoritative transition record), regression-locks LIFECYCLE-02, and ships LIFECYCLE-06 diagnostics SQL.

REVIEW-DRIVEN CHANGES (from 143-REVIEWS.md, both HIGH findings CONFIRMED against live schema):

1. FEATURE-vs-CELL AGGREGATION (finding 1) is now specified explicitly. feature_registry.feature_name is
   the sole PK (one row per feature globally); ic_engine builds feature_status_at_eval from the feature's
   registry status at run start (ic_engine.py line 1764) — so ALL of a feature's cells carry the SAME
   status stamp, and the ensemble filter feature_status_at_eval='active' is effectively per-feature.
   Therefore the transition unit is the FEATURE. To collapse many per-(symbol,tf,regime) IC cells into one
   feature-level decision, this plan uses the SAME feature-level aggregation ensemble_trainer already uses:
   ensemble_trainer._meta_eligible includes a feature iff it passes in >= alpha.ensemble.meta_fdr_min_fraction
   (default 0.50) of its cross-sectional cells. The demotion rule is the exact complement — demote when the
   feature materially fails in >= (1 - meta_fdr_min_fraction) of its active cells this run — so demotion and
   ensemble-inclusion share ONE constant and the same pass/fail semantics, avoiding a second invented
   threshold. NOTE (plan-checker finding, 2026-07-06): this does not guarantee the two can never diverge —
   _meta_eligible's fdr_pass_rows query has no training_window_end filter and aggregates across ALL
   historical runs for a feature, while this hook's demotion check aggregates THIS RUN only, so the
   denominators differ. The demotion formula below is nonetheless fully self-contained and deterministic
   given one run's feature_ic_scores rows — the shared constant reduces threshold sprawl, it does not
   guarantee cross-consistency with ensemble_trainer's separate historical eligibility check. Deterministic
   given one run's feature_ic_scores rows, expressible as a single GROUP BY feature_name aggregate.

2. WEIGHT RESTORATION (finding 2) is resolved by DROPPING pre_shadow_weight (see Plan 02 objective for the
   ensemble_trainer.py evidence). ensemble_weights is written EXCLUSIVELY by ensemble_trainer.py and
   recomputed from scratch each run with no warm-start. So promotion "restores" weight by the status flip
   alone: flip registry shadow_only->active -> next ic_engine run stamps feature_status_at_eval='active' ->
   next ensemble_trainer run recomputes a fresh weight from the feature's current IC. There is a deliberate
   one-run lag (the hook runs at end-of-run, after this run's stamps are already written); this is the
   correct, natural cadence. The hook NEVER writes ensemble_weights — that would violate the sole-writer DAG
   invariant. The hook only READS ensemble_weights (standing weight for the materiality gate).

3. IDEMPOTENCY (secondary finding) is handled by keying the run's gate-evaluation fact on training_window_end
   and short-circuiting if it already exists, plus Plan 02's optimistic from_status lock making individual
   transitions rerun-safe.

FABLE REVIEW-DRIVEN CHANGES (independent pass on the revised plans — see 143-REVIEWS.md "Fable Review"
section, new findings N3/N4/N5):

4. LOOKAHEAD OVERCOUNTING (N3, MEDIUM). The POOLED cross-sectional population carries FOUR rows per
   (feature_name, tf, regime) this run — one per lookahead_bars (1/5/20/60, the fast/mid/slow/extended
   horizons, alpha.ic.lookahead.* APR keys). A "cell" for this hook's purposes is (feature_name, tf, regime)
   — NOT (feature_name, tf, regime, lookahead_bars). Summing n_independent or counting fail/pass across all
   4 lookahead rows per cell overcounts by ~4x (the 4 horizons are overlapping views of the same underlying
   bars, not 4 independent observations) and silently weakens the 2000-observation recovery floor to an
   effective ~500. FIX: filter the per-run query to lookahead_bars = config's mid-horizon value
   (cfg.get_sync("alpha.ic.lookahead.mid", 5) — already the project's canonical "primary" horizon per the
   gradient-naming convention) BEFORE any aggregation. Each cell then has exactly one row; demote_fraction,
   pass_fraction, and new_observations are computed over these single-lookahead cells with no double-counting.
   Fast/slow/extended lookaheads are ignored for lifecycle-gate purposes (they remain fully intact in
   feature_ic_scores and ensemble_trainer's own eligibility check, which is unaffected by this hook).

5. WEIGHT_VERSION PINNING (N4, MEDIUM). The standing-weight JOIN must NOT resolve
   `ORDER BY computed_at DESC LIMIT 1` (globally most-recent row) — that silently tracks whatever
   ensemble_trainer last wrote, including a future E1/E2 champion/challenger `--weight-version` override
   epoch (ensemble_trainer.py line ~382, `_effective_weight_version`), which would make the materiality gate
   start reading a challenger's weights instead of the champion's the moment that A/B ships. FIX: resolve
   the champion weight_version explicitly via the SAME APR key ensemble_trainer defaults to when no CLI
   override is given: cfg.get_sync("alpha.ensemble.weight_version", "v1"). Bind this into
   ICEngineConfig/LifecycleGateConfig as ensemble_weight_version and use it as a literal parameter in the
   JOIN (`ew.weight_version = %s`), not a subquery over MAX(computed_at).

6. ZERO-CELL RUNS (N5, MEDIUM). The hook is inserted unconditionally after the
   `if equity_model_enabled and corpus_cs_rows:` block — a per-symbol-only run or a run with the equity
   model disabled yields ZERO POOLED cells for this training_window_end, making every fraction in steps 3-4
   a division by zero. FIX: after step 1's query, if zero rows are returned, log
   "ic_engine.lifecycle_hook_no_cells" and return immediately WITHOUT writing an integrity_monitor fact (a
   fact would mark this training_window_end as "already evaluated" and could incorrectly short-circuit a
   later run that DOES have POOLED cells for the same window).

Purpose: Close the loop — features that lose IC get demoted automatically and recovered ones get promoted
back through the same evidence bar, while a regime dislocation is prevented from being misread as mass decay.
No new daemon, no new state machine, no Kafka subscription, no ensemble_weights write.

Output: 2 migrations, 3 OTel metrics, the ic_engine hook, a diagnostics SQL file, hook + staleness +
ensemble-regression tests.
