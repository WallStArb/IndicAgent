<objective>
Add the post-run transition-writer hook to ic_engine.main() — the single place lifecycle state can
change, because it only changes when new IC measurements land. This one hook delivers LIFECYCLE-03
(demote decaying active features to shadow_only + promote recovered ones through Plan 02's
record_transition_sync, materiality-gated at weight x |ic_ci_lower| > alpha.decay.materiality_threshold),
LIFECYCLE-04 (regime-shift guard: if >= alpha.decay.regime_shift_fraction of active cells fail
simultaneously, hold ALL weights, no transitions, human review), and LIFECYCLE-05 (IC staleness gauge
+ IC_ENGINE_STALE alert). It writes a gate-evaluation fact per run to the new integrity_monitor table
(observability only; feature_transition_log stays the sole authoritative transition record). It
regression-locks LIFECYCLE-02 (ensemble_trainer already filters active — no new code) and ships
LIFECYCLE-06 ad-hoc decay SQL.

Purpose: Close the loop — features that lose IC get demoted automatically and recovered ones get
promoted back through the same evidence bar, while a regime dislocation is prevented from being misread
as mass feature decay. No new daemon, no new state machine, no Kafka subscription.

Output: 2 migrations, 3 OTel metrics, the ic_engine hook, a diagnostics SQL file, hook + staleness +
ensemble-regression tests.

Critical constraints (from research pitfalls):
- ic_engine.py is a plain sync psycopg2 argparse script — NO class, NO BaseBatch, NO self._pool, NO
  await/async def anywhere in the diff. Use the existing open `write_conn`.
- Call FeatureRegistryService.record_transition_sync (Plan 02), NEVER the async record_transition().
- Insertion point: after the `_write_cross_sectional_results(write_conn, corpus_cs_rows)` block and
  before `IC_ENGINE_RUN_LATENCY_SECONDS.record(elapsed)` (ic_engine.py ~line 2050). registry_svc and
  write_conn are already in scope.
- Reuse existing APR keys: alpha.decay.materiality_threshold (0.005), alpha.decay.regime_shift_fraction
  (0.60), alpha.decay.recovery_min_observations (2000). Two keys are new: alpha.ic.staleness_alert_days
  (this plan's migration 205) and alpha.decay.recovery_min_passes (Plan 02's migration 202, default 2) —
  read both via cfg.get_sync, never hard-code the 2 or the 5.
- Demotion (active -> shadow_only) is a SINGLE-RUN materiality gate only — weight x |ic_ci_lower| >
  decay_materiality_threshold. There is no consecutive-fail counter or "consecutive-fail policy" to
  check; ROADMAP's LIFECYCLE-03 text does not specify one, and Plan 02 deliberately does not add a
  consecutive_shadow_fails column. Do not gate demotion on any counter beyond this run's IC facts.
- Sequencing: LIFECYCLE-00 (Plan 01) must have run so regime labels the guard reads are trustworthy;
  do NOT run the live hook against the 4/7 zero-IC candidate features before Plan 01's occupation gate
  is in effect. This ordering is enforced by depends_on.
