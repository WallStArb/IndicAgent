<objective>
Close the live-path cross-asset gap: make `FeatureVectorPipeline` emit real values for all 10
cross-asset `FeatureVector` fields instead of the `0.0` placeholders it writes today.

Purpose: Addresses cross-AI review concern (Codex, HIGH) - "`151-04` explicitly leaves
`FeatureCache.update_cross_asset()` broken on the live path, with the new and existing cross-asset
fields frozen at `0.0`... a serious correctness gap," and Codex's explicit suggestion to "consider
making the live-path cross-asset gap a blocker for any phase that expects live feature consumers."

The review-pass investigation (recorded in full in plan 151-04's `<interfaces>`) found the harm is
sharper than the review's own framing: `indicagent-feature-vector-pipeline.service` is `active
running` and writes live rows straight into `feature_vectors`, the table this phase's entire IC
measurement reads. Measured 2026-07-24: 9,183 rows at 5m spanning 2026-06-23 -> 2026-07-07 carry
`vix_z = flight_quality = yield_slope_z = 0.0` across all 80 symbols, alongside 139,093
correctly-valued batch rows in the same window. A `0.0` placeholder is indistinguishable from a
measured value once it is in the table - a silent wrong answer, which this project treats as worse
than a loud crash. Shipping plan 151-04's 7 additional cross-asset columns into the same broken path
would triple the surface.

This plan lands in wave 5, deliberately AHEAD of plan 151-07's corpus recompute, so the recompute
does not have to be repeated to clean up rows the live daemon writes during it.

Output: one shared Ring-1 cross-asset builder used by both paths, live-path wiring with a
once-per-UTC-day refresh, a live-vs-batch parity test, and a fail-safe degradation path.
</objective>
