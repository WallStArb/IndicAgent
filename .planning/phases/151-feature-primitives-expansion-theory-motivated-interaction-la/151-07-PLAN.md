**The partition-completion manifest - the resumability mechanism.**
State file: `cache/feature_factory_recompute_manifest.json`. See `<interfaces>` for why `cache/` and
why NOT `backfill_status`. No new DB table and no new migration in this plan.

Shape:
  `{"version": 1, "pipeline_version": "<--pipeline-version>", "started_at": "<iso8601>",
    "partitions": {"<SYMBOL>:<tf>": {"status": "in_progress"|"complete"|"failed",
      "expected_rows": N, "rows_deleted": N, "rows_inserted": N,
      "started_at": "<iso8601>", "completed_at": "<iso8601>"}}}`

Write it with the tmp+rename idiom from `state_manager.py:176-178`, not a bare `write_text` - a
plain write can itself be interrupted and leave a truncated manifest, which defeats the entire
point. Timestamps via `format_iso_ts()` (`src/core/service_utils.py`), never an inline
`.isoformat().replace(...)`.

Per-partition sequence, in exactly this order:
1. Read the manifest ONCE at startup. If its `pipeline_version` differs from this run's
   `--pipeline-version`, treat it as stale and start fresh; log that decision once.
2. If the manifest marks this (symbol, tf) `complete`, SKIP it entirely - no DELETE, no compute, no
   insert. Log once with `resumed_skip`. This is what makes a crash cheap instead of catastrophic.
3. Otherwise capture `expected_rows` =
   `SELECT count(*) FROM feature_vectors WHERE symbol=%s AND tf=%s`, mark the partition
   `in_progress`, and FLUSH the manifest to disk BEFORE issuing the DELETE. A partition found
   `in_progress` on a later run is known-suspect and gets a full delete-and-rebuild - idempotent,
   therefore always safe to repeat.
4. Issue exactly one `DELETE FROM feature_vectors WHERE symbol = %s AND tf = %s;`, then run the
   existing compute plus `_batch_insert` loop unchanged. Commit the DELETE together with the FIRST
   insert batch, then continue with the existing per-batch commits. Do NOT hold one transaction open
   across an entire multi-million-row partition. Record the chosen boundary in the SUMMARY.
5. After the FINAL batch commits, assert `rows_inserted == expected_rows` - delete-then-reinsert is
   row-count-neutral by construction. Only then mark the partition `complete` with both counts and
   flush. On mismatch, mark it `failed` with both numbers, log once, and continue to the NEXT
   partition: never mark it complete, and never abort the whole run over one partition.
6. Log ONCE per partition: symbol, tf, rows_deleted, rows_inserted, status. Never per row.

The DELETE and every manifest write run in the MAIN process on the single serial write connection,
never inside a `ProcessPoolExecutor` worker - CLAUDE.md's rule: workers are compute-only, and
concurrent writers on the same hypertable cause index-page deadlocks. Read the current code to
confirm where the insert happens and place the DELETE immediately before it in the same place; do
not assume.

Do not touch `FEATURE_VECTOR_INSERT_SQL`. Do not add an UPDATE path.
