<objective>
Wire the per-symbol half of the regime-conditioning workstream: extend `_build_regime_passes()`
with an APR-gated `earnings_season` stratification pass so every per-symbol (symbol, tf) cell also
gets measured separately on in-season and off-season bars, reusing `_compute_one_regime_cell`
verbatim. Then isolate the new `regime_scope` value from the in-file IC lifecycle guard so the new
labels do not surface as data-contract violations.

Purpose: D-01a gates building this workstream on plan 176-01's multi-feature sweep (see the
pre-execution gate above); once that gate passes, D-03 locks reuse of the existing stratification
machinery over a parallel mechanism, and locks SoC — `ic_engine.py` reads the persisted column and
never recomputes calendar math. `_build_regime_passes` is a pure, DB-free function with existing
unit coverage, which makes it the correct surgical extension point.

Output: a third regime pass, an APR switch defaulted true, and a lifecycle guard that ignores
earnings-season cells.

Design decision that supersedes a 176-RESEARCH.md recommendation, with rationale: RESEARCH
proposed adding `earnings_season_flag` as a third explicit column in the per-symbol
`SELECT bar_ts, regime_volatility, {feature_cols}` fetch. Verified live this planning session,
`_FEATURE_NAMES = [f.name for f in dataclasses.fields(FeatureVector)]` — so after plan 176-03 the
flag is ALREADY in `{feature_cols}` and therefore already in `X_raw`/`X_aligned`. Adding it again
would fetch the same column twice. Derive the label array from
`X_aligned[:, _FEATURE_NAMES.index("earnings_season_flag")]` instead. This still reads the
persisted value (D-03 satisfied) at strictly lower cost.
</objective>
