<objective>
Populate `earnings_season_flag` and `days_since_quarter_end` on the already-existing
`feature_vectors` corpus with a direct, scoped SQL backfill. Migration 350 (plan 176-02) added the
columns as NULL on every pre-existing row; plan 176-03 made new rows compute them. Nothing yet fills
the ~40M rows that already exist, and `ic_engine` cannot condition on a column of NULLs.

Purpose: CONTEXT.md's Phase Boundary ends this phase at "a real `feature_ic_scores`
FDR/walk-forward gate pass". That gate measures persisted values. D-03's SoC principle explicitly
forbids the cheap shortcut (having `ic_engine` derive the calendar flag from `bar_ts` in memory) —
the measurement layer reads the persisted column, so the column must actually be written.

**Mechanism changed by Fable's cross-AI review (2026-09-23, REVIEWS.md "Fable Review" section 2.)**
This plan previously ran `services/backfill_feature_factory.py --compute-only --refresh` across the
whole corpus: recomputing all ~300 feature columns through the full compute pipeline in order to
populate two of them. Both new columns are pure functions of `bar_ts` alone — no bar history, no
per-symbol state, no warmup — so the entire compute pipeline is unnecessary work, and running it
opened a blast radius (Codex rated it the phase's top HIGH operational risk) that required an
elaborate collateral-damage verification apparatus to contain.

A direct `UPDATE feature_vectors SET earnings_season_flag = ..., days_since_quarter_end = ...` in
plain SQL date arithmetic touches only those two columns and structurally cannot disturb anything
else — there is nothing else the statement can write to. That converts the collateral-damage
question from something measured after the fact (pre/post checksums) into something proven from the
statement's own SET list before it runs, which is strictly stronger. It also drops the work by
roughly two orders of magnitude: two scalar date expressions per row instead of a ~300-feature
compute pass.

What it does NOT drop: `feature_vectors` is a compressed TimescaleDB hypertable, so the write must
follow `docs/foundation/timescaledb-compressed-column-migration.md`'s decompress -> mutate ->
recompress -> **mandatory bare `VACUUM`** pattern. That pattern is well-trodden and CI-enforced
(`tests/unit/test_compressed_hypertable_migration_vacuum_check.py`, todo 305), unlike the bespoke
pre-flight/batching/telemetry machinery the `--refresh` path needed. Omitting the `VACUUM` is what
turned migration 312 into a 768GB disk-full incident; it is not optional here either.

Output: both columns populated across a recorded scope, the round trip's real cost and disk
behaviour measured, and a written manifest of exactly what was covered.

Sequencing is load-bearing, not advisory. STATE.md's Roadmap Evolution section sequences this
phase's corpus work behind todo 340 and Phase 175 for contention reasons, and a live
`backfill_feature_factory.py --compute-only --symbols IHF --workers 1` run (todo 340's confirmation
re-run) was observed active at plan time on 2026-09-22 16:45. Task 1's pre-flight gate is the
enforcement point — do not launch this backfill blind.
</objective>

Why this lives in `production/migrations/` rather than `scripts/`: it is a one-shot, idempotent,
state-changing SQL artifact that performs a `decompress_chunk` / `compress_chunk` round trip, and
`tests/unit/test_compressed_hypertable_migration_vacuum_check.py` (todo 305) sweeps
`production/migrations/*.sql` and FAILS THE BUILD on any file pairing `decompress_chunk(` with
`compress_chunk(` and no bare `VACUUM <table>;`. Filing it here buys the missing-VACUUM guard for
free. Migration 350 is plan 176-02's schema migration, so this is 351.

Window boundaries — read from APR, never hardcoded (D-03's no-magic-numbers rule; migration 350
seeded all three keys):

    feature.earnings_season.start_days   seeded 14
    feature.earnings_season.end_days     seeded 42

In SQL, source them in the statement itself rather than substituting them from the shell:

    WITH w AS (
      SELECT
        (SELECT config_value::int FROM config_state
          WHERE config_key = 'feature.earnings_season.start_days') AS start_days,
        (SELECT config_value::int FROM config_state
          WHERE config_key = 'feature.earnings_season.end_days')   AS end_days
    )

A NULL from either subselect means the APR seed is missing — the statement must abort rather than
silently write NULL flags. Assert both are non-NULL in Task 1's pre-flight AND guard inside the SQL.

Date arithmetic — the SQL equivalent of plan 176-03's `_days_since_quarter_end(bar_ts)`. Quarter
ends are Mar 31 / Jun 30 / Sep 30 / Dec 31; the value is 0 on a quarter-end date itself, and
otherwise counts calendar days since the most recent quarter end (crossing the year boundary to the
prior Dec 31 in Q1). `bar_ts` is `timestamptz` and every project timestamp is UTC (CLAUDE.md DAG
invariant 6), so take the date in UTC explicitly:

    -- d := (bar_ts AT TIME ZONE 'UTC')::date
    CASE
      WHEN d = (date_trunc('quarter', d) + interval '3 months' - interval '1 day')::date THEN 0
      ELSE d - (date_trunc('quarter', d)::date - 1)
    END

Verified by hand against the reference: Mar 31 2026 -> 0; Apr 1 2026 -> 1; Jan 1 2026 -> 1 (prior
year's Dec 31). `earnings_season_flag` is then `start_days <= days_since_quarter_end <= end_days`,
inclusive on BOTH boundaries, cast to the column's numeric type as 1.0 / 0.0.

Plan 176-03's production function returns RAW calendar days as a float (its own behavior block pins
`_days_since_quarter_end(datetime(2026, 3, 31, tzinfo=UTC)) == 0.0` and `(2026, 4, 1) == 1.0`), not
a normalized fraction — so the SQL writes raw days, matching. Before writing the SQL, read
`176-03-SUMMARY.md` and confirm the landed function still matches this; if 176-03 normalized the
value after all, mirror whatever it actually did. The 20-sample agreement check in Task 3 is the
enforcement either way.

Compressed round trip — copy the pattern verbatim from
`docs/foundation/timescaledb-compressed-column-migration.md`, substituting the two-column `UPDATE`
for its `ALTER COLUMN TYPE` step. Reference implementations in-repo:
`production/migrations/201_feature_vectors_float32.sql`,
`production/migrations/312_feature_vectors_float32_drift_fix.sql` (both retroactively corrected
2026-08-13 to include the mandatory step 4). Gotchas from that doc that apply here:
  - `decompress_chunk()`'s keyword flag is `if_compressed => true` (`if_not_compressed` does not exist)
  - `VACUUM` must be BARE and top-level — it cannot run inside `BEGIN`/`COMMIT` or a `DO` block
  - plain `VACUUM`, not `VACUUM FULL` (no ACCESS EXCLUSIVE lock, no rewrite space needed)
  - recompression runs as its own statement outside the DDL transaction, so a partial failure there
    cannot roll back an already-committed correct UPDATE

Disk headroom is the live risk this pattern carries. Migration 312 grew `feature_vectors` from ~57GB
to 768GB and PANIC-crashed Postgres twice on ENOSPC, purely from the omitted VACUUM. With the VACUUM
present the pattern is sanctioned, but decompressing every chunk at once still needs room for the
uncompressed heap. Task 1 asserts headroom before anything runs.

DB access (CLAUDE.md): PGPASSWORD=postgres psql -U postgres -h localhost -d indicagent
Reference window classifier for correctness spot-checks: the pure functions in
`scripts/analysis/earnings_season_conditional_ic_reverification.py` (plan 176-01).
