<objective>
Convert the three classification columns now backed by Python enums to PostgreSQL ENUM types,
making invalid values impossible to write — rejected at the DB level, not discovered when a
query silently returns 0 rows. Also document the exit_reason value space and prove every live
writer path round-trips through the new ENUM types.

After this plan, the signal ledger's classification layer is fully type-safe end-to-end:
Python enum (compile-time contract) -> PostgreSQL ENUM type (write-time enforcement).
No silent wrong answers. No derivation of classifications at query time.

**Hypertable lock risk (resolves review finding #4, HIGH):** `signal_events` is a TimescaleDB
hypertable. `ALTER TABLE signal_events ALTER COLUMN status TYPE signal_status_type` requires a
rewrite of every chunk and acquires an ACCESS EXCLUSIVE lock. Running it against a live,
service-writing table risks long blocking and lock contention. This plan adds an explicit
maintenance strategy: stop the writer services for the hypertable conversion, then restart.

**Phantom values are NOT dead code (resolves review finding #5, HIGH):** `chandelier_stop`
(lifecycle_tracker.py:347) and `condition_expired` (lifecycle_tracker.py:372,379) are LIVE code
paths. They currently produce 0 DB rows only because the current signal regime has not triggered
them — not because they are dead. The `chk_te_exit_reason` CHECK must explicitly list both. The
`outcome` side is already handled: Plan 01 added `CONDITION_EXPIRED` as the 9th SignalOutcome and
maps `chandelier_stop -> stopped_in_trade`. Comments in lifecycle_tracker.py must say "live code
path, currently 0 rows due to signal regime" — never "dead code".
</objective>

         ALTER COLUMN status TYPE signal_status_type
