<objective>
Convert the three classification columns now backed by Python enums to PostgreSQL ENUM types,
making invalid values impossible to write — rejected at the DB level, not discovered when a
query silently returns 0 rows. Also document and neutralize phantom exit_reason values
(chandelier_stop, condition_expired) that exist in lifecycle_tracker.py source but have never
appeared in the DB.

After this plan, the signal ledger's classification layer is fully type-safe end-to-end:
Python enum (compile-time contract) → PostgreSQL ENUM type (write-time enforcement).
No silent wrong answers. No phantom codes. No derivation of classifications at query time.
</objective>

  <action>
    Write `151_phase134_pg_enum_types.sql`. The migration must be idempotent where possible
    (use `IF NOT EXISTS` on type creation; wrap column casts in DO blocks if needed).

    **Step 1: Create ENUM types**
    ```sql
    CREATE TYPE signal_outcome_type AS ENUM (
      'never_activated','stopped_at_entry','stopped_in_trade',
      'target_1','target_1_2','target_full',
      'ttl_expired_ahead','ttl_expired_behind'
    );

    CREATE TYPE entry_type_type AS ENUM (
      'at_close','at_pullback','at_limit','at_reclaim','zone_proximal'
    );

    CREATE TYPE signal_status_type AS ENUM (
      'pending','active','regime_suppressed','expired'
    );
    ```

    **Step 2: Drop existing CHECK constraints (now redundant — ENUM type enforces values)**
    ```sql
    ALTER TABLE trade_executions DROP CONSTRAINT IF EXISTS chk_te_outcome;
    ALTER TABLE trade_frames DROP CONSTRAINT IF EXISTS chk_tf_entry_type;
    ```

    **Step 3: Cast columns to ENUM types**
    ```sql
    ALTER TABLE trade_executions
      ALTER COLUMN outcome TYPE signal_outcome_type
      USING outcome::signal_outcome_type;

    ALTER TABLE trade_frames
      ALTER COLUMN entry_type TYPE entry_type_type
      USING entry_type::entry_type_type;

    ALTER TABLE signal_events
      ALTER COLUMN status TYPE signal_status_type
      USING status::signal_status_type;
    ```

    **Step 4: Add CHECK constraint on exit_reason (TEXT — keep as TEXT, not ENUM)**
    `exit_reason` is a coarser operational code, not a taxonomy label. It can have values like
    'chandelier_stop' and 'condition_expired' even if currently empty (future code could write
    them). Keep as TEXT but add a CHECK to document the valid set:
    ```sql
    ALTER TABLE trade_executions
      ADD CONSTRAINT chk_te_exit_reason
      CHECK (exit_reason IN ('stop_loss','chandelier_stop','condition_expired',
                              'ttl_expired','ttl_expired_ahead','ttl_expired_behind',
                              'target_1','target_1_2','target_full'));
    ```

    Apply migration:
    `PGPASSWORD=postgres psql -U postgres -h localhost -d indicagent -f production/migrations/151_phase134_pg_enum_types.sql`

    Verify types created:
    `PGPASSWORD=postgres psql -U postgres -h localhost -d indicagent -c "SELECT typname FROM pg_type WHERE typname IN ('signal_outcome_type','entry_type_type','signal_status_type') ORDER BY typname;"`
    Must return 3 rows.

    Verify column types:
    `PGPASSWORD=postgres psql -U postgres -h localhost -d indicagent -c "SELECT column_name, udt_name FROM information_schema.columns WHERE table_name IN ('trade_executions','trade_frames','signal_events') AND column_name IN ('outcome','entry_type','status') ORDER BY table_name, column_name;"`
    Must show `signal_outcome_type`, `entry_type_type`, `signal_status_type` in `udt_name`.
  </action>
