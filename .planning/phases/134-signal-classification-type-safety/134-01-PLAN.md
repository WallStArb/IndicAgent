<objective>
Persist `SignalOutcome` to `trade_executions.outcome`. Today lifecycle_replay computes the 9-class
taxonomy (`stopped_at_entry`, `stopped_in_trade`, `target_1`, `condition_expired`, etc.) via
`_classify_stop_outcome()` / the `Transition.outcome` field but never writes it to the DB — it
exists only in memory and logs. This forces every downstream query to re-derive the
classification, which is where the Plan 05 stopped_at_entry gate bug came from. The fix: add
`outcome TEXT` to `trade_executions`, wire BOTH the replay path AND the live repository execution
path to write it, and backfill historical rows from existing `actual_mfe`/`actual_bars` data.

**`condition_expired` resolution (review finding #2):** The live lifecycle code at
`lifecycle_tracker.py:379` emits `outcome="condition_expired"` as a verbatim Transition outcome.
This string is NOT in the current 8-value `SignalOutcome` enum, so a CHECK constraint enumerating
only 8 values would reject any production row from that path. This plan resolves it explicitly:
add `CONDITION_EXPIRED = "condition_expired"` as the 9th `SignalOutcome` member. This makes the
live writer path valid end-to-end without a lossy remap, and Plan 03's PG ENUM type will include
it as the 9th value.

After this plan, `stopped_at_entry` rate = `COUNT(*) FILTER (WHERE outcome='stopped_at_entry') /
COUNT(*)` with no derivation. The classification logic lives in exactly one place
(_classify_stop_outcome + the Transition.outcome field), written once, never re-derived.
</objective>
