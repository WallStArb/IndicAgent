<threat_model>
Risk vectors for this test plan:
- **False-green tests:** A test that mocks too much can pass even if the fix is reverted. Each test
  must assert against the ACTUAL fixed behavior (winner identity, .set vs .add call, constructor
  kwarg), not against a re-mock of the fix.
- **get_connection mock pitfall (CLAUDE.md):** `get_connection()` returns an async context manager,
  not a coroutine. Mock with `MagicMock(side_effect=async_cm_func)`, NOT `AsyncMock`, or `async with`
  breaks and the test fails for the wrong reason.
- **OTel call assertions:** Assert `.set`/`.add`/`.record` via a Mock on the instrument; do not import
  the real OTel SDK gauge in a unit test (it would no-op silently and give a false green).
- **Inverted shadow-filter assertion:** The promotion test must assert `is_shadow = TRUE` (not FALSE)
  and the demotion test must assert `is_shadow = FALSE` — mirroring the corrected 105-04 Task 3.
  Asserting the wrong direction would lock in the bug the review caught.
</threat_model>
