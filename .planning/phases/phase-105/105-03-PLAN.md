<objective>
Fix OTel metric type mismatches (HF-8, HF-9). Five shadow governance metrics are created as
up_down_counters and called with `.add(absolute_value)`, so Grafana shows N× the true value after N
audit cycles. Pipeline latency instruments are up_down_counters instead of histograms, so there is
zero percentile visibility on the hottest path; two of them are never even recorded.

Purpose: Make telemetry trustworthy before Phase 106 latency-driven hardening. Shadow promotion
decisions and pipeline latency SLOs both depend on these metrics reading correctly.

Output: metrics.py shadow metrics use create_gauge; intelligence_pipeline_agent latency instruments
are histograms with real .record() calls; counts are proper counters. Existing tests green.

Note: This plan changes the metric DEFINITIONS in metrics.py. Plan 105-04 changes the shadow_auditor
`.add()` -> `.set()` CALL SITES. 105-04 depends on this plan so the gauges exist first.
</objective>

<threat_model>
Risk vectors for this bug-fix plan:
- **Metric-name continuity:** Changing the instrument type must NOT change the metric name string,
  or Grafana dashboards and Alertmanager rules break. Keep every metric name byte-identical.
- **Gauge/counter call-site mismatch:** create_gauge instruments expose `.set()`, not `.add()`.
  Changing the definition here without changing the `.add()` call sites would crash shadow_auditor.
  The call-site change lives in plan 105-04, which depends_on this plan — sequencing is the mitigation.
- **Histogram unit drift:** New histograms must use `unit="ms"` to match the existing
  PLUGIN_DURATION_MS convention, else dashboards mis-scale.
- **Span/record placement:** Adding `.record()` in the hot path must reuse already-computed latency
  variables; do not add new `time.perf_counter()` calls inside the inner loop that would add overhead.
</threat_model>
