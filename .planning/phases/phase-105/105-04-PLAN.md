<objective>
Fix the shadow signal suppression bypass (HF-1, SG-1 through SG-7) — the highest-business-impact bug.
Shadow-mode plugins marked is_shadow=TRUE in shadow_registry can currently win select_winner() and
route to live trading because (a) is_shadow is never stamped on the signal dict in executor.py and
(b) signal_processor.py passes the full ranked list (including shadows) to select_winner(). The
shadow auditor's promotion/demotion gates also use the wrong is_shadow filter direction and reset
swarm-agent demotion counters to zero every cycle.

This plan also moves the shadow metric CALL SITES to `.set()` (the gauge DEFINITIONS were changed to
point_gauge in plan 105-03, which this plan depends_on).

Purpose: Guarantee shadow plugins are observed but never traded live, and that the promotion gate
counts the shadow plugin's OWN shadow observations while the live-plugin demotion gate counts only
live resolved signals.

Output: executor stamps is_shadow; signal_processor filters shadows from winner selection and stamps
non-live status; shadow_auditor uses is_shadow=TRUE on promotion and is_shadow=FALSE on demotion,
skips swarm agents, and calls .set().
</objective>

<threat_model>
Risk vectors for this bug-fix plan (this is the security-critical one):
- **Shadow bypass via wrong fix order:** If the winner filter (signal_processor) ships before the
  is_shadow stamp (executor), the `shadow_cache.get(setup_plugin)` lookup still works (it reads the
  cache, not the signal field), but signal_writer would persist is_shadow=False for every signal,
  so the auditor's is_shadow filters become meaningless and shadow data contaminates the gate.
  Mitigation: STRICT internal order — Task 1 (executor stamp) -> Task 2 (signal_processor filter +
  status) -> Task 3 (auditor queries + metrics). Do not reorder.
- **INVERTED promotion filter (HF-1 SG-2 — CRITICAL):** Shadow-mode plugins accumulate signal_ledger
  rows with `is_shadow = TRUE` (they fire in shadow mode; Task 1+2 stamp TRUE on those rows). The
  PROMOTION gate evaluates a shadow plugin's readiness to go live, so it MUST count those shadow rows:
  `AND is_shadow = TRUE`. Filtering `is_shadow = FALSE` on the promotion query would yield n=0 for
  every shadow plugin and BLOCK promotion forever. Only the live-plugin DEMOTION gate uses
  `is_shadow = FALSE` (live signals are the evidence for demoting an already-live plugin).
- **Persistence vs winner divergence:** The full `ranked` list (including shadows) MUST still be
  persisted to signal_ledger for observation. Only the `select_winner()` CANDIDATE list is filtered.
  Filtering persistence would destroy shadow evaluation data. Keep `ranked` for persistence.
- **Status string correctness:** Shadow signals must receive a status that lifecycle never activates.
  The valid status literals are "pending", "active", "regime_suppressed" (per CLAUDE.md). Use
  "regime_suppressed" for shadow signals (lifecycle never activates this status) unless the codebase
  already has a dedicated "shadow" status string — verify in signal_processor before choosing.
- **Demotion neutralization (SG-4):** Without the swarm_agent skip, the auditor evaluates swarm
  agents against signal_ledger (which has no rows for them), gets n=0, and resets
  demotion_consecutive_count to 0 every cycle, making auditor-side demotion impossible. The skip
  restores demotion.
</threat_model>
