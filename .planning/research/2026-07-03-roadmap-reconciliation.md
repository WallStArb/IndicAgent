# ROADMAP Reconciliation — Order and Priority vs. the Post-Review Doc Ecosystem

**Date:** 2026-07-03 · **Author:** Fable 5 (dispatched via Claude Code Agent tool) · **Type:** research/review, read-only
**Scope:** `.planning/ROADMAP.md` phase ORDER and PRIORITY from Phase 142B onward, assessed against everything decided this week: the topdown/bottomup architecture reviews (2026-07-02), the intel-10/11 and canonical-simulator Fable reviews (2026-07-03), intel-10 v3 / intel-12 / intel-13 / intel-14 / intel-15 as rewritten, canonical-simulator v2, the one-model-one-book foundation invariant, and the 2026-07-01 backlog matrix (refreshed through 2026-07-03). This is the sequencing pass the just-completed Phase 143/146/147 text-fix pass was not.
**Verdict up front:** the spine holds — 142B.1 (in flight) → 142B → 144's two-gate promotion, with 143 independently startable, is still the right order and no finding below reorders it. The drift is concentrated in four places: (1) the v3.15 Conditioning milestone exists as a header but owns no phases, so the ROADMAP's physical order still runs AnalogEngine *before* the conditioning work intel-13 names as its hard prerequisite; (2) Phase 142B's task list is missing two requirements canonical-simulator v2 makes time-critical (one must be decided *before* SHADOW-REVIEW.md is frozen); (3) Phase 143.5's conditional gate dangles on CORPUS-07, which Phase 141 closed without ever running, and 143.5/144's v2.x-retirement half describes retiring a system the bottomup audit showed is already dead in fact; (4) the v3.3 milestone the topdown review dissolved (D6) still exists and still physically contains Phase 151, the single most order-sensitive phase in the tree. Everything else this week produced is additive, not reordering.

## 1. Findings

### F1. The v3.15 milestone is a header with no body, and the ROADMAP's physical order still contradicts it — Phase 151 must move out of v3.3 before any v3.2 planning starts. [HIGH — the one real ordering error]

The milestone list (line 29) correctly carries the v3.15 Conditioning & Identity Foundation bullet, "sequenced between v3.1 and v3.2 because AnalogEngine's retrieval hard-filters on regime labels." But it says "Phases TBD," and the phase that *is* v3.15's core deliverable — Phase 151 (`regime_group`) — still sits inside the "v3.3 Foundational Hardening" section, physically *after* Phases 145-147. Meanwhile:

- intel-13 (Sequencing section): "**Hard prerequisite, not a preference:** intel-12's conditioning-layer unification must land first... building the substrate on top of known-suspect strata bakes the bias into stored vectors. This is the concrete reason v3.15 is sequenced before v3.2 in the roadmap." The roadmap does not actually encode that sequence anywhere a planner would hit it.
- Phase 145's **Depends on** line says only "Phase 142A OOS validation showing `ic_ci_lower > 0`" — no conditioning dependency at all. ANALOG-02 carries a soft 2026-07-01 note about regime-label bias, but a dependency expressed as a cautionary note inside requirement text is exactly how D4-style silent reversions happen (the same mechanism todo 055 flags for 145/146's body text).
- Topdown D5/D6: Phase 151 + todo 026 P2b/P2c/P3 + todo 041 (tag taxonomy) + the volatility_regime substitution test batch into one ic_engine re-run in v3.15; Phase 148 joins evidence-gated; **v3.3 dissolves** ("a milestone whose scope is TBD and whose contents all belong earlier is a numbering artifact, not a plan"). The milestone list still carries v3.3 as "planned; scope TBD — review before v3.2 completes."

**Concrete fix (sketch):**

1. Insert a `## v3.15 Conditioning & Identity Foundation (Phases 151, 148)` section between the v3.1 and v3.2 sections. Move Phase 151 into it unchanged (its body text is current — the 2026-07-01 review annotations are accurate). Move Phase 148 into it with a note: "evidence-gated; joins the v3.15 ic_engine re-run batch if todo 041's taxonomy audit shows tag calibration is load-bearing for group routing, else trails." Add to the section header: "Batched into ONE ic_engine re-run with todo 026 P2b/P2c/P3, todo 041, and intel-12's first substitution test (per topdown D5). Build trigger: todo 026's Step 1 gate — already run 2026-07-02, result asset-class-dependent (SPY separates, TLT doesn't), so the pre-committed fallback question (topdown Open Q4) needs an operator call at v3.15 planning."

Change Phase 145's **Depends on** to: "v3.15 complete (Phase 151 regime_group live + todo 026 P2b/P2c/P3 resolved) — intel-13 hard prerequisite: retrieval hard-filters on regime labels and embeddings are expensive to re-embed. Remaining occupants: Phase 152 keeps its own operator gate (breadth after proof — correct, unchanged) and Phase 149 keeps its own alt-data gate; both can live under a "Deferred / independently gated" section or at the tail of v3.2. Neither has any real dependency on a "v3.3" identity.

The finding is that the ROADMAP's phase sections never absorbed the decision, so anyone planning "the next phase after 144" from the section order alone would plan Phase 145 without conditioning, which is the exact bias-baked-into-vectors failure D5 exists to prevent.

### F2. Phase 142B's task list is missing two canonical-simulator v2 requirements, and one of them is time-critical because SHADOW-REVIEW criteria freeze at launch. [HIGH]

canonical-simulator v2 (rewritten 2026-07-03, priority `critical`) raises two 142B-planning items that exist nowhere in the ROADMAP's 142B text:

1. **`corpus_run_id`/`weight_epoch` provenance column on `alpha_frames`** (its Open Question 3, F5 of the source review): "costs one column now vs. a provenance hole forever. Should be raised at 142B planning." The 142B P1 migration is the moment. Without it, every counterfactual claim in the frames ledger is unattributable to the weight epoch that produced it — directly against the binding rule ("every claim carries corpus-run/weight-epoch provenance") and it undoes half the point of 141.1's weight-epoch fix at the exact table that matters most.
2. **The gross-vs-net reporting decision** (its Open Question 2): SHADOW-REVIEW.md's Sharpe/drawdown criteria are frozen at 142B launch, and on gross counterfactual P&L they will read optimistic by construction — 98.3% of alpha_events sit in the band todo 030's calibration found cost-marginal, and the `alpha.quant.cost_hurdle.*` keys are now calibrated (141.1), so applying them as a *reporting column* (not a gate change; the pre-commitment stands) is cheap and available. This decision cannot be deferred past 142B launch: once SHADOW-REVIEW.md is committed, adding net-of-cost criteria post-hoc is exactly the gate renegotiation the phase forbids.

Related staleness in the same block: 142B's **Schema design** line — "No cost model (`alpha.cost.*`) — real cost data (slippage, commission) does not exist until v4.0" — was written before 141.1 closed todo 030. It remains true that no *fill-calibrated* cost model exists, but calibrated external cost-hurdle inputs now do, and the sentence as written tells a 142B planner there is nothing to apply. **Replacement text (sketch):**

> **Schema design:** ... `alpha_frames` table + `alpha.frame.*` APR keys. `alpha_frames` carries `corpus_run_id`/`weight_epoch` provenance columns from the P1 migration (canonical-simulator binding rule — every counterfactual claim attributes the machinery that produced it). No fill-calibrated cost model (that is v4.0, where fill data exists) — but the externally-calibrated `alpha.quant.cost_hurdle.*` keys (todo 030, closed in 141.1) are applied as a **net-of-cost reporting column** on closed frames. Whether SHADOW-REVIEW criteria are stated gross, net, or both is decided and committed in SHADOW-REVIEW.md itself at launch, never after.

This is additive to 142B, not a resequencing of it — topdown §1.9's "keep 142B as planned, don't generalize early" ruling stands and nothing here injects a replay core. It also cleanly triggers the cost kernel's "second consumer" extraction rule (canonical-simulator F4) inside 142B rather than as a standalone build, which is the design intent.

### F3. Phase 143.5's gate dangles on a requirement that was never run, and the 143.5→144 retirement chain describes retiring a system that is already dead in fact. [HIGH — quiet invalidation, the Phase-143-style case]

I7-05's prerequisite simplifies to 'CORPUS-07 evaluated + survivors registered.'" The ROADMAP's 143.5 still specs the full I7-01..05 conversion apparatus, 3 plan waves ("first 10 plugins, remaining ~25 plugins"), mixing-weight APR keys, and an `alpha_score` column on `signal_events`.

**Concrete fix (sketch):**

Reframe SCORE-04 as documentation ("record why no v2.x comparison population exists — pipeline dead since 2026-06-22 — in the retirement decision record") or delete it. The phase's *promotion* half (SCORE-01/02/03, the two gates) is unchanged and stays the milestone exit.
