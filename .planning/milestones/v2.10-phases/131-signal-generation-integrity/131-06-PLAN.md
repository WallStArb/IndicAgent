<objective>
Fix B6: the _assert_backfill_integrity() function triggers a PG timeout or OOM when called after inserting 537K signals, crashes with `psycopg2.OperationalError: server closed the connection unexpectedly`, and leaves the corpus at 537K instead of the expected ~1M.

Two separate issues to fix:
1. The assertion query is a full-table-scan JOIN on signal_events + trade_frames with no chunking. At 537K rows this is a large query; at 1M rows it will time out or OOM.
2. The REBUILD_STATUS is set to FAILED on any exception from the post-commit block, including a crash in the integrity assertion after all data was successfully committed. Data integrity (was data written correctly) is distinct from query infrastructure (can we run the audit query).

Fix:
1. Batch _assert_backfill_integrity() by symbol: run the was_selected invariant check one symbol at a time, using the existing symbols list parameter. Accumulate violations across symbols and report all at the end.
2. Wrap the integrity assertion in a try/except. If the assertion itself crashes (OperationalError, timeout), log a WARNING and exit 0 (data may be fine; the audit infrastructure failed). Only sys.exit(1) when the invariant is actually violated (violations list is non-empty).
3. Set REBUILD_STATUS=FAILED only inside the `if violations:` branch, not in a broader exception handler around the entire post-commit block.

Purpose: The Phase 127 rebuild was cut short (537K vs expected 1M signals) because a post-commit infrastructure crash set the status to FAILED and the run was treated as failed. The data written was valid; the audit could not complete. This fix separates data integrity from audit infrastructure reliability.

Output: run_historical_pipeline.py with batched integrity check and correct REBUILD_STATUS semantics.
</objective>
