### Critical Break 1: LLM-04 — signal_id Linkage Dead

**Affected requirements:** LLM-04 (back-fill), LLM-05 (score recompute depends on outcome rows)

**Root cause:** `signals:aggregated` stream does not carry the `signal_ledger` UUID assigned at INSERT time. `ai_narrative_service._build_llm_call_payload` reads `signal_id` from the stream message and gets an empty string — stored as NULL in `llm_calls`. `llm_writer_service._UPDATE_OUTCOME_SQL` runs `WHERE signal_id = $1::uuid` — this matches zero rows. No narrative record ever gets its outcome back-filled. Score recompute runs on schedule but has no rows with non-null `outcome` to learn from. `is_significant` is never set. `_preferred_models` is never populated with adaptive winners.

**Fix required:** `signal_generator_service._process_bar()` must retrieve the assigned `signal_id` UUID from `signal_ledger.insert_signals()` and publish it in the `signals:aggregated` stream payload. `ai_narrative_service` can then read it. OR: use an alternative join key such as `(symbol, tf, called_at BETWEEN signal_ts AND signal_ts + interval '2 min')` for approximate back-fill.

### Critical Break 2: LLM-05 — Regime Vocabulary Mismatch

**Affected requirements:** LLM-05

**Root cause:** `_apply_score_routing` reads Redis cache keys built as `llm_scores_cache(env, call_type, regime)` using hardcoded regime vocabulary: `"trending"`, `"ranging"`, `"volatile"`, `"__all__"`. But `llm_calls.regime` is populated from `signal_data["regime_context"]`, which plugins set to values like `"bullish"`, `"bearish"`, `"breakout_bullish"`, `"ranging"` (only `MeanReversion` and `CHoCHReversal` happen to emit `"ranging"` which accidentally matches one of the four expected keys). The score cache is built by `_UPSERT_SCORE_SQL` grouping by the raw stored regime value — so cache keys like `llm_scores:{env}:per_signal:bullish` exist in Redis, but `_apply_score_routing` only ever looks up `llm_scores:{env}:per_signal:trending`. Cache miss every time. `_preferred_models` stays empty. Adaptive routing never activates.

**Fix required:** Either (a) standardize plugin `regime_context` emission to canonical vocabulary (`trending`/`ranging`/`volatile`) by mapping from HMM regime value, or (b) translate raw `regime_context` to canonical bucket in `_build_llm_call_payload` before storing, or (c) make `_apply_score_routing` query the actual distinct regime values from `llm_model_scores` rather than using a hardcoded list.
