`FeatureRegistryService.record_transition_sync` semantics to port (read the method in full):
  - psycopg `with conn.transaction():` NOT a bare `with conn:` — psycopg (unlike psycopg2) CLOSES
    the connection on a bare `with conn:` exit, and ic_engine reuses one caller-owned connection
    across many transitions. This is a documented empirical finding; preserve it exactly.
  - optimistic lock `WHERE ... AND status = %s` (from_status); rowcount 0 -> raise the internal
    `_TransitionNoOp` sentinel -> whole transaction (including the log INSERT) rolls back ->
    return False. Rerun-safe by construction.
  - when `to_status == 'shadow_only'`, the SAME UPDATE resets `consecutive_shadow_passes = 0` and
    `observations_since_demotion = 0` (Fable review N1, HIGH): without it a feature that decayed,
    recovered, and decayed again would re-promote after a single passing run on its second shadow
    period instead of re-earning the full bar.
  - automated reasons may never target 'deprecated'; raises ValueError BEFORE any write.
  - on success, mutates the in-memory cache so a subsequent `is_promotion_eligible` in the same
    process sees fresh state.

`FeatureRegistryService.advance_shadow_counters_sync` semantics to port:
  one `conn.transaction()`; `consecutive_shadow_passes = CASE WHEN %s THEN +1 ELSE 0 END` and
  `observations_since_demotion = observations_since_demotion + %s`; cache mutated to match.

`FeatureRegistryService.is_promotion_eligible(name, recovery_min_observations, recovery_min_passes)`:
  pure in-memory predicate, both floors caller-supplied from APR, no calendar input.

Post-Plan-02 `ConceptRegistryService` (async side, do not disturb): `decide_comparison_action`,
`record_comparison_outcome`, `GateState` (now carrying `fdr_required`), `ComparisonDecision`,
`ConceptNotFoundError`, `_rowcount`, `_LOAD_CONCEPT_SQL` (FOR UPDATE), `_CAS_PROMOTE_SQL`,
`_TRANSITION_INSERT_SQL`, `_GATE_CACHE_UPDATE_SQL`, `_GATE_PROMOTE_UPDATE_SQL`.
