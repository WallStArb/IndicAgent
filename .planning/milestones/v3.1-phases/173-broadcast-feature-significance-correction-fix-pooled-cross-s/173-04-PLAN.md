<planner_findings>
Locked planner decisions. Do not re-litigate.

**Fingerprint participation (Open Question 1, resolved in Plan 03's findings — restated because
this plan is where it becomes load-bearing).** The broadcast cell folds into the EXISTING
`pass_type='cross_sectional'` fingerprint row. No new `pass_type`. Broadcast rows MUST carry
`regime_scope='cross_sectional'` so that `_ARCHIVE_BEFORE_DELETE_CROSS_SECTIONAL_SQL` and
`_FINGERPRINT_INVALIDATE_DELETE_CROSS_SECTIONAL_SQL` — which already scope by
`symbol='POOLED' AND tf AND regime_scope='cross_sectional' AND regime=<label> AND training_window_end`
— sweep them on recompute with zero SQL change. Both `ic_cell_fingerprints.pass_type` and
`feature_ic_scores.regime_scope` carry live CHECK constraints limited to three values; any new
value costs a migration for zero benefit, since `_checkpoint_content_key()` is module-set-level and
a separate fingerprint could never diverge.

**Cluster ID offset (Open Question 3, resolved).** Run `_cluster_features` on the broadcast matrix,
then add `_BROADCAST_CLUSTER_ID_OFFSET = 10000`. Mandatory: `_cluster_features` returns fcluster IDs
starting at 1, and `_compute_cross_sectional_tf`'s trailing BH-FDR loop groups by
`(regime, lookahead_bars, cluster_id)` across ALL rows in `all_results`. Without the offset a
broadcast feature would silently merge into a per-symbol cluster's representative selection and
lose its own FDR entry. The 10000 space is free — Plan 02 deleted its only prior user. Roughly 40
broadcast features against a `smallint` ceiling of 32767 leaves wide margin. `10000` is a schema-
space partition constant, not a tunable, so it is APR-exempt (same class as the `5` in
`momentum_z_5`); declare it as a module constant with a comment saying so.

**Partial-cross-section handling for the aggregate return (a gap D-04 does not specify).** A
`bar_ts` group contributes an aggregate return for a scale ONLY if every row in that group has
`complete AND isfinite` for that scale. Rationale, from first principles rather than convenience:
an equal-weighted index whose membership silently changes bar to bar is not a consistent outcome
variable — a mean over a drifting peer subset would make the measured relationship partly an
artifact of which symbols happened to have data. Strict all-peers-present is deterministic and
introduces no new tunable. It will drop bars; that is D-06's blessed behavior, not a bug. Task 1
requires instrumenting the drop rate so a pathological rate is visible immediately rather than
presenting as a mysterious `min_reliable_n` skip. If the observed drop rate exceeds 50% in the
smoke run, file a todo proposing a coverage-fraction APR key — do NOT silently loosen the rule.

**The e-value pilot does not extend to broadcast rows.** `cumulative_e_value` is `None` for every
broadcast row in this phase. The pilot (`_e_value_pilot_active`, tf=5m only) is a scoped experiment
on the per-symbol pooled cross-sectional cell; silently extending it to a brand-new cell type would
compound evidence across two different measurement definitions. Note this in the SUMMARY as a
deliberate scope call, and note that the prior-fetch query in `_compute_cross_sectional_tf` will
return priors for broadcast feature names from pre-phase vintages that this cell ignores.

**`alpha.ic.broadcast_variance_threshold` wiring — this plan performs the wiring Plan 01
deliberately deferred. There is no conflict and there is only ONE key.** Plan 01 Task 1 registers
`alpha.ic.broadcast_variance_threshold` (seed `1e-9`, `[initial_estimate]`) and explicitly names two
readers in its `config_schema.description`: the offline classifier
`scripts/ops/alpha/ops_broadcast_feature_audit.py`, and this plan's compute-time invariance
assertion. Plan 01 does not touch `services/ic_engine.py` purely because Plan 02 owns that file in
wave 1 and a second wave-1 writer would conflict — not because the engine never reads the key.

Task 1 below adds `broadcast_variance_threshold: float` to `ICEngineConfig`, loaded via
`cfg.get_sync("alpha.ic.broadcast_variance_threshold", 1e-9)` — same key name, same default, same
units, same semantics (a per-`bar_ts` cross-symbol `max - min` tolerance) — and adds the field name
to `_COMPUTATIONAL_CONFIG_FIELDS`, which is correct because the value gates a crash and therefore
affects computed output. Do NOT introduce a second, differently-named key: the offline classifier
decides "is this symbol-invariant?" and the compute path asserts the same predicate still holds, so
two independently-tunable values would allow a feature classified broadcast offline to crash the
compute path, or vice versa.

**bar_ts grouping algorithm is prescribed, not a menu (see Task 1 step 2).** One explicit
boundary-scan implementation is specified. `np.unique`, `np.sort`, `np.argsort`, and any pandas
groupby are FORBIDDEN in this code path: `np.unique` on an object/datetime array sorts internally
and allocates additional full-length temporaries, which is precisely the memory profile the
2026-07-08 OOM incident produced and which the float32 conversion in this function exists to avoid.

    Implementation outline:

    1. Early-return `([], 0)` if `broadcast_mask` is None or marks zero columns.

    2. **Derive group boundaries by a single forward boundary scan. This algorithm is prescribed;
    do not substitute another.** `bar_ts_arr` is already sorted ascending and `bar_ts`-contiguous
    (`chunk_sql` carries `ORDER BY fv.bar_ts` and chunks are built from ordered `ts_chunk` slices),
    so group starts are exactly the positions where the value changes:

      - compute a length-`N-1` boolean of adjacent inequality between `bar_ts_arr[1:]` and
        `bar_ts_arr[:-1]`;
      - build `group_starts` as an `np.intp` array of length `changes + 1`: element 0 is `0`, and
        the remainder is `np.flatnonzero(<that boolean>) + 1`.

      Total extra allocation is one bool array of length `N-1` plus one `intp` array of length
      `n_groups`. **`np.unique`, `np.sort`, `np.argsort`, and pandas groupby are FORBIDDEN here** —
      each sorts and/or allocates additional full-length temporaries over the largest cell, which is
      exactly the 2026-07-08 OOM profile this function's float32 conversion exists to avoid. Use
      `np.add.reduceat` / `np.logical_and.reduceat` keyed on `group_starts` for every group
      aggregation below except the invariance guard, which needs the NaN-safe forms specified in
      step 4 (`np.fmax.reduceat`/`np.fmin.reduceat`, never `np.maximum.reduceat`/
      `np.minimum.reduceat`); `reduceat` consumes the boundary array directly and needs no sort.

      Assert contiguity crash-loud, without materializing a full-length distinct-value structure:
      take `bar_ts_arr[group_starts]` (length `n_groups`, small) and raise a `RuntimeError` if its
      Python-`set` length is less than `len(group_starts)`. A repeated representative means one
      `bar_ts` appeared in two non-adjacent runs, i.e. the `ORDER BY` invariant this whole design
      rests on has broken; the run must stop rather than double-count a timestamp.

    3. Materialize the broadcast submatrix ONCE as `X_bc = X_raw[:, broadcast_mask]`, shape
    `[N, n_broadcast]` — roughly `n_broadcast / 298` of `X_raw`'s footprint, the single bounded
    intermediate this function allocates. Steps 3 and 4 both read it; `del X_bc` as soon as step 4
    finishes. The collapsed matrix is then `X_bc[group_starts]`, shape `[n_groups, n_broadcast]`.
    Do NOT write `X_raw[group_starts][:, broadcast_mask]` — that gathers all 298 columns first and
    allocates a wider intermediate for no benefit.

    4. **Cross-symbol-invariance assertion.** Compute per-group `max - min` over `X_bc` keyed on
