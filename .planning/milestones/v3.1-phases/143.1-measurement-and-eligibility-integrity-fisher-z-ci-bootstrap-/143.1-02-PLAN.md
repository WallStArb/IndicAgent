Component D (todo 068, high priority; Component C's dependency). Add 5 canary/control predictors as genuine `FeatureVector` fields - two independently-seeded pure-noise columns (Gaussian, uniform), a constant, a near-constant, and one acausal (look-ahead-leaking) placebo - plus a loud, expectation-aware, false-halt-aware corpus-run integrity assertion. Five fields meets CONTEXT.md's locked "5-10 feature_registry rows" floor (the two noise variants are independently useful: two distributionally-distinct RNG sources agreeing they're both null is stronger evidence the pipeline itself is clean). Negative controls (noise/dead) must never clear the significance gate; the acausal placebo positive control must clear it spectacularly (proving the pipeline can detect leakage). A POOLED-family violation halts the corpus run with a manifest error, not a warning.

Why not "just registry rows": `FeatureRegistryService.load()`/`load_sync()` enforce a hard row-count-equals-`len(FeatureVector fields)` gate plus an exact name-set-equality check; adding registry rows without matching dataclass fields crashes both `ic_engine.py` and `ensemble_trainer.py` at startup (RESEARCH Pitfall 6). Canaries MUST be real fields. This also makes the phase's single corpus re-run a full pipeline run from Step 1 (`backfill_feature_factory.py`), not an `ic_engine.py`-only invocation - land this plan before Plan 07.

Output: new FeatureVector canary fields, feature_factory computation, migration (feature_registry is_control/control_expectation columns + extended CHECK + feature_vectors columns + registry rows + APR seed), the assertion script, unit coverage. Runs parallel to Plan 01 (no file overlap).
