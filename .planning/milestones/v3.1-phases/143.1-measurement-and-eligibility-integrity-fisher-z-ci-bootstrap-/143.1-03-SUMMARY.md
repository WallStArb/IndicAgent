## Decisions Made

1. **`vol_normalized_return()` placed in `ic_math.py`, not `ic_engine.py` or `feature_factory.py`.** Rationale: Ring 1, pure function, importable by both `ic_engine.py` (co-located wiring helper) and the standalone diagnostic script without either depending on the other's internals -- the same extraction rationale `ic_math.py`'s own module docstring states for why `_fisher_z_ci`/`_circular_block_bootstrap_ic` live there instead of in `ic_engine.py` directly.
2. **`_cross_sectional_vol_normalized_target()` is defined but not called from the production hot path.** Satisfies the plan's explicit "do NOT flip the production target to vol-normalized here" requirement literally, while keeping the array producible from the exact in-scope variables `_compute_cross_sectional_tf` already assembles (`X_sub`, `valid_mask`, `returns_scale`) -- a future promotion decision (if Component F's full-corpus A/B favors it) is then a one-line wiring change inside the existing per-scale loop, not a redesign.
3. **The A/B script's vol-normalized "qualifying" criterion is a per-stratum BH-FDR family, not a corpus-level family, and does NOT recompute the bootstrap CI.** A full bootstrap-CI recompute across every `(tf, regime)` stratum's full feature set would turn this diagnostic into a second corpus-wide re-run -- defeating the purpose of a fast pre-Plan-07 sanity check. This scoping decision is stated in both the script's module docstring and the ledger entry, not left implicit.
4. **Script defaults to a bounded sample (`--max-regimes-per-tf=2`) with an `--all-regimes` escape hatch for Plan 07.** Fully recomputing POOLED IC for every `(tf, regime)` stratum is corpus-scale work (same chunked fetch `_compute_cross_sectional_tf` uses); the bounded default keeps this plan's own execution cheap while leaving the identical code path usable for the definitive full-corpus run later.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Fixed asyncpg named-parameter incompatibility in the A/B diagnostic script**
- **Found during:** Task 2, live-testing the script against the DB
- **Issue:** Initial draft used psycopg2-style `%(name)s` named parameters in three SQL query strings (`_REGIMES_SQL`, `_BASELINE_SQL`, `_REGIME_TS_SQL`), copied from `services/ic_engine.py`'s psycopg2 convention. `asyncpg` (this script's DB driver, matching `ops_ic_null_calibration.py`'s house style) only supports positional `$1/$2/...` parameters -- the named-parameter form would have raised `asyncpg.exceptions.PostgresSyntaxError` on first invocation.
- **Fix:** Rewrote all three queries and their three call sites to use positional `$1/$2/$3[/$4]` parameters, matching the convention already used correctly elsewhere in the same file (`_LATEST_VINTAGE_SQL`, `_load_config_int`, the chunked `chunk_sql`).
- **Files modified:** `scripts/ops/alpha/ops_vol_normalized_target_ab.py`
- **Verification:** Live-ran the script end-to-end against the current corpus (`--tf 1d --max-regimes-per-tf 1`) after the fix -- completed successfully in seconds, produced a correct, non-empty report.
- **Committed in:** `83d0576e` (Task 2 commit -- caught during the same session before this commit, not left as a latent bug)
