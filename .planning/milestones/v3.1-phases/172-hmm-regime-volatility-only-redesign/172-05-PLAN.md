<objective>
Relabel the corpus on the volatility axis: gate on plan 172-01's measured verdict, reconcile the
APR values the run executes under, generalize plan 171-03's NULL-out and provenance tooling to the
new column family, then run `regime_writer.py --regime-column regime_volatility` in stages and
prove coverage.

Purpose: this is the expensive, corpus-scale, effectively irreversible step. Its blast radius is
the same class as changing `HMM_RANDOM_STATE`, so nothing here may be verified by "the command
exited 0". Three things have to be true before it starts and provable after it finishes. Before:
the wider-scope null-arm control returned GO, and the APR keys hold the values that control
actually measured rather than the plan-time guesses migration 307 seeded. After: every cell in
scope is accounted for, the labels are all registered vocabulary codes, the warmup prefix is
genuinely unlabeled, and the legacy `regime` column is untouched.

On tooling: `scripts/ops/corpus/ops_regime_null_out_and_verify.py` already implements per-cell
NULL-out, manifest resumability, a post-NULL all-NULL assertion, and a post-relabel
warmup-prefix provenance check. It does not generalize as written, because five module-level SQL
constants bake in `REGIME_WRITER_OWNED_COLUMN_NAMES` and the literal column name `regime`. Every
one of those is a pure string-construction site over an ownership tuple, so parametrizing by
column family is a contained edit that keeps the resumability, the cell-at-a-time write
discipline, and the tested failure modes intact. Extending it is strictly better than building a
second, less-tested equivalent.

Output: a two-family verification tool, an APR reconciliation migration, a machine-readable
coverage report, and one written relabel record.
</objective>
