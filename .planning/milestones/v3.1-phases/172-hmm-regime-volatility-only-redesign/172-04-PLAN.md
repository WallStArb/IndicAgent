<objective>
Wire the volatility labeling path end to end for a single (symbol, tf) cell: fetch, fit
walk-forward against the 2-column observation matrix from plan 172-03, and persist the 8
`regime_volatility` columns migration 307 added. Add the CLI dispatch that selects which regime
column family a run writes.

Purpose: plans 172-02 and 172-03 delivered the schema, the APR keys, the ownership tuple, and the
pure functions. Nothing yet calls them. This plan is the compute and persistence path that turns
those pieces into a runnable labeler, and it is deliberately scoped to one cell's worth of
behavior plus unit tests. The corpus-scale run is plan 172-05's job and must not start here.

The dispatch decision this plan makes: `--regime-column {regime,regime_volatility}`, defaulting to
`regime`. One invocation writes exactly one family. Computing both in the same run was rejected
because a volatility run would then also rewrite `feature_vectors.regime`, and 26.8M of those rows
currently carry the retired full-history-fit method's output; rewriting a subset of them would
blend two labeling methods under one column, which is the exact failure
`_compute_symbol_tf_walk_forward`'s docstring names as its unenforced precondition and which plan
171-03's NULL-out tool exists to prevent. Plan 172-02 already committed this phase to a phased
cutover where `regime_volatility` lands alongside an untouched `regime`; a mutually exclusive
column selector makes that structural rather than conventional.

Output: three new functions, one generalized function, a new CLI flag, and unit coverage for each.
</objective>
