<objective>
`ensemble_weights` and `ensemble_alpha` both write with `ON CONFLICT ... DO NOTHING` keyed partly on a static APR `weight_version='v1'`. Re-running the trainer after IC scores change **silently keeps the stale weights** — no error, no warning. This is exactly the "silent wrong answer" the design mindset forbids, and it directly threatens Phase 142A: the ensemble IC would be measured on weights that no longer match the corpus that produced them. The same silent-staleness bug class also hides one layer downstream in the emission path: `alpha_publisher.py` builds its `alpha_events` `event_id` from `content_key(symbol, tf, bar_ts_ns, ensemble_version)` — WITHOUT `weight_version` — so under `ON CONFLICT (event_id, bar_ts) DO NOTHING` a new weight epoch produces the SAME event_id as the prior epoch and its inserts silently no-op; `alpha_events` never reflects fresh epochs.

Fix with a minimal per-run epoch identity plus an idempotent upsert, applied at BOTH the training write and the emission event_id:
1. Derive a per-run weight epoch from the corpus freeze point in the orchestrator and thread it to BOTH `ensemble_trainer` (producer) and `alpha_publisher` (consumer) so they always agree on the same `weight_version`.
2. Replace `ON CONFLICT DO NOTHING` with `ON CONFLICT DO UPDATE` in ensemble_trainer so a same-epoch re-run overwrites with recomputed values (idempotent) instead of silently keeping stale weights — and so it can never corrupt history (each per-(tf,regime) snapshot is written atomically).
3. Fold `weight_version` into the alpha_publisher `event_id` so a new epoch yields a DISTINCT event_id and its `alpha_events` rows actually land (the DO NOTHING no longer swallows fresh epochs).
4. Fold in todo 043: move the hardcoded `if days_since > 90` staleness cliff to APR `alpha.ensemble.weight_stale_max_days`, matching its already-APR-backed sibling `weight_half_life_days`.

This is the MINIMAL version per the roadmap — a real per-run epoch, NOT the full `corpus_runs`/`run_id` lineage table (explicitly deferred as separable hardening). Note on epoch identity: WEIGHT_EPOCH is freeze-point/boundary identity, not a globally unique per-run ID — two separate runs sharing the same freeze point (TRAINING_WINDOW_END) share one epoch by design. This is safe because DO UPDATE makes a same-epoch re-run idempotent (overwrite, not collide); it is boundary identity, not per-run provenance. Full corpus_runs/run_id lineage remains explicitly deferred. This plan is Wave 2 and depends on Plan 01 because both edit `scripts/ops/corpus/ops_corpus_pipeline_run.sh`; sequencing prevents a merge conflict on that shared file.

Partial-corpus note: if run against a partially-built Phase B corpus, the epoch derivation, upserts, and event_id fix all operate correctly on whatever rows exist — they do not require full corpus completion; the fix takes effect on the next corpus re-run.
</objective>
