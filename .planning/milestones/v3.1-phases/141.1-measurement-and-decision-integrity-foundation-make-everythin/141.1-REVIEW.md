## Summary

Phase 141.1 has four sub-threads: (1) an OOS holdout clamp in the corpus orchestrator plus
a pre-commitment protocol doc, (2) a `regime_scope` disambiguation column on
`feature_ic_scores` with a backfill migration, (3) a per-run weight-epoch mechanism
(`--weight-version`) threaded through `ensemble_trainer.py` / `alpha_publisher.py` with
`DO UPDATE` upserts replacing `DO NOTHING`, and (4) two standalone diagnostic/calibration
scripts (`ops_oos_holdout_eval.py`, `ops_cost_hurdle_calibration.py`).

I isolated the actual phase-scoped diff (commits `7a63f84f`..`3192d3e2`, i.e.
`git diff 8e64fa82..3192d3e2` for `ic_engine.py`/`ensemble_trainer.py`/`alpha_publisher.py`)
rather than the full multi-phase file history, since these three services accumulated a
large amount of pre-existing, out-of-scope content. Findings below are scoped to what this
phase actually changed, with two exceptions noted explicitly where a phase-141.1 change sits
directly next to a pre-existing correctness gap worth flagging because it undermines the
phase's own stated goal (decision integrity).

The weight-epoch upsert change (`DO NOTHING` → `DO UPDATE`) is a real, well-reasoned fix for
a genuine idempotency trap, and is well covered by `test_ensemble_weight_epoch.py`. The
`regime_scope` migration's backfill CASE and the insert-time resolver are provably
consistent (both mirror the same three-branch logic and are checked against each other by
`test_regime_scope.py`), and migration 192 self-validates via a `DO $$` block that raises if
the backfill and mapping ever diverge — a genuinely good practice.

The two blockers below are about the actual OOS enforcement claim in
`docs/plans/OOS-EVAL-PROTOCOL.md`: the enforcement point described in the doc is real
(`ops_corpus_pipeline_run.sh`), but `ic_engine.py`'s own `--training-window-end` handling
and the interim diagnostic scorer both have paths that can silently defeat the very
protection this phase exists to add, without violating the letter of the "no bare
`MAX(bar_ts)`" rule the doc states.

## Critical Issues

### CR-01: `ic_engine.py --training-window-end` omission falls back to bare `MAX(bar_ts)`, silently defeating the orchestrator's OOS clamp for any manual/ad-hoc run

**File:** `services/ic_engine.py:2000-2019`
**Issue:** The OOS-EVAL-PROTOCOL doc states the clamp is enforced by the orchestrator
passing `--training-window-end "$TRAINING_WINDOW_END"` to `ic_engine.py` (and
`forward_return_writer.py`). But `ic_engine.py` itself has no independent enforcement — when
invoked without `--training-window-end` (which is exactly how the usage docstring at the top
of the file, lines 32-35, tells operators to invoke it: `python services/ic_engine.py`,
`python services/ic_engine.py --symbols VUG --tf 1h`), it silently falls back to
`SELECT MAX(bar_ts) FROM feature_vectors` — i.e. the full corpus including the OOS holdout
window — with only a `_logger.warning` that most operators running ad-hoc symbol/TF-scoped
IC recomputation will never see (structlog to a log file, not stdout by default in this
context).

This is precisely the "bare `MAX(bar_ts)` query" the protocol doc calls a "protocol
violation" (OOS-EVAL-PROTOCOL.md line 47) — except the violation isn't in the orchestrator
(which correctly clamps), it's one layer down, in the tool the orchestrator calls, which
remains independently invokable and defaults to the unsafe behavior. Anyone re-running
`ic_engine.py --symbols SPY --tf 1h` directly (a documented, encouraged usage pattern per the
file's own docstring) to patch a single symbol/TF cell will silently consume OOS data with no
guardrail beyond a log line.

**Fix:** Either (a) make `--training-window-end` required (no default) so a bare invocation
crash-loudly fails instead of degrading, or (b) default the fallback to
`LEAST(MAX(bar_ts), alpha.validation.oos_start)` inside `ic_engine.py` itself — matching the
orchestrator's clamp — rather than an unclamped `MAX(bar_ts)`, and keep the loud WARNING for
observability. Given this phase's explicit charter ("Measurement and Decision Integrity
Foundation"), option (a) is more consistent with the project's "silent wrong answers are
worse than loud crashes" principle:
```python
if not args.training_window_end:
    raise RuntimeError(
        "ic_engine.py requires --training-window-end (OOS holdout enforcement point "
        "lives in ops_corpus_pipeline_run.sh; a bare MAX(bar_ts) fallback would silently "
        "consume the OOS holdout window). Pass the clamped value from the orchestrator, "
        "or SELECT LEAST(MAX(bar_ts), oos_start) manually for ad-hoc runs."
    )
```

### CR-02: `ops_oos_holdout_eval.py` computes IC over the ENTIRE OOS window on every invocation with no "look budget" enforcement — the doc's "look-once" cadence rule is unenforceable by construction

**File:** `scripts/ops/corpus/ops_oos_holdout_eval.py:315-387`; `docs/plans/OOS-EVAL-PROTOCOL.md:87-94`
**Issue:** OOS-EVAL-PROTOCOL.md states: "The interim diagnostic scorer may be run more
freely since it is never a gate, but its output must not be used to tune any in-sample
parameter" — this is a documented, unenforced convention, not a code-level control. Nothing
in `ops_oos_holdout_eval.py` prevents its markdown output from being read and then acted on
(e.g., an operator sees "5m severe drop" and lowers `alpha.ic.min_reliable_n` or adjusts a
feature-selection threshold "to see if it helps," exactly the renegotiation-after-seeing-the-
number the doc explicitly forbids one section earlier for the authoritative scorer).

This is not a bug in the traditional sense — it is a documented process rule with zero
code-level enforcement in a phase whose stated purpose is closing exactly this kind of gap
(compare: the `TRAINING_WINDOW_END` clamp got a hard code-level enforcement point precisely
because "zero readers" + a convention wasn't good enough per the doc's own "Why this exists"
section, lines 11-22). The interim scorer as shipped repeats the same failure pattern one
level up: it is a convention with no teeth, and the doc says so itself ("may be run more
freely" + "must not be used to tune" — a should, not a can't).

**Fix:** At minimum, have `ops_oos_holdout_eval.py` write a persistent, git-visible or
DB-visible "OOS look log" (append-only, timestamped) each time it runs, so a reviewer can
audit how many times the holdout was queried and correlate that against APR parameter
changes in `config_history` — turning the honor-system rule into an auditable one. This does
not need to block runs (the doc is explicit the diagnostic scorer is not a gate), but an
unenforced, un-logged "must not" is a data-integrity control that exists only in prose.

## Warnings

### WR-01: `_gap_verdict` tolerance denominator can be dominated by the near-zero mean, producing a `material` verdict on statistical noise

**File:** `scripts/ops/corpus/ops_cost_hurdle_calibration.py:149-163`
**Issue:** `scale = max(abs(mean_gap), abs(mean_nogap), 1e-12)` and the verdict is
`material` when `abs(mean_gap - mean_nogap) / scale >= tolerance` (1%). When one of the two
means is very close to zero (a realistic scenario for `return_fast`, which averages near
zero over a large population) and the other is not, `scale` is dominated by the larger
magnitude mean, and a tiny absolute difference can register `>= 1%` relative to that scale
purely from sampling noise, not a real gap-contamination effect. There is no significance
test (e.g., a t-test or minimum sample-size gate beyond the 5% gap-fraction floor) backing
the `material` verdict — the value is used to write a followup todo file
(`_write_gap_followup_todo`) that becomes a piece of the corpus record.

**Fix:** Either document explicitly in the docstring that this is a magnitude heuristic (not
a statistical test) so consumers of the generated todo file know its evidentiary weight is
low, or add a minimum-n / standard-error check before declaring `material`:
```python
def _gap_verdict(
    mean_gap: float, mean_nogap: float, gap_fraction: float,
    n_gap: int = 0, n_nogap: int = 0, tolerance: float = 0.01,
) -> str:
    if gap_fraction < 0.05 or min(n_gap, n_nogap) < 30:
        return "not_supported"
    ...
```

### WR-02: `_write_report` verdict thresholds in `ops_oos_holdout_eval.py` are unexplained magic numbers with no APR backing, despite the file's own docstring stressing rigor

**File:** `scripts/ops/corpus/ops_oos_holdout_eval.py:293-300`
**Issue:** `oos_qualifying < in_sample * 0.5` ("significant drop") is a bare literal with no
APR key, no citation, and no unit test coverage (the test file covers `_oos_mask` and
`_count_qualifying` but not `_write_report`'s verdict classification at all). CLAUDE.md's
"migrate-as-you-go" mandate calls out exactly this pattern: "Any numeric threshold... that is
not APR-backed MUST be migrated in the same session." This script is new in this phase, so
the mandate applies at introduction, not retroactively. Since this scorer is explicitly
diagnostic-only (never a gate), an argument could be made this constant is APR-exempt as a
"derived/computed value" — but 0.5 is a genuine tunable threshold, not a derived one, and the
project's own exempt list doesn't cover "diagnostic-only scripts."
**Fix:** Extract `0.5` to a named module constant at minimum (`_SIGNIFICANT_DROP_FRACTION =
0.5`), and add a unit test for the three verdict branches in `_write_report` (or extract the
verdict classification into a small pure function, matching the pattern already used for
`_oos_mask`/`_count_qualifying`, so it is independently testable).

### WR-03: `_read_oos_rows` / `_score_symbol_tf` in the OOS harness silently diverge from `ic_engine.py`'s degenerate-feature and min-reliable-n semantics without being tested against them

**File:** `scripts/ops/corpus/ops_oos_holdout_eval.py:194-229`
**Issue:** The module docstring (lines 12-16) claims the harness "composes existing
machinery rather than reimplementing it," listing `_vectorized_ic` / `_fisher_z_ci` /
`_p_values_from_ic` / `_nan_to_none`. That's true for those four functions. But the
degenerate-feature detection differs materially from `ic_engine.py`'s: `ic_engine.py` masks
out degenerate columns entirely before ranking (`X_regime_nd = X_regime[:,
non_degenerate_mask]`, `services/ic_engine.py:830-844`), while the OOS harness applies the
same `stds > 1e-8` mask (line 199) but then additionally **mean-imputes NaNs within the
surviving columns before ranking** (lines 205-207: `X_nd_filled = np.where(np.isnan(X_nd),
col_means, X_nd)`) — a step `ic_engine.py`'s per-symbol path does not perform (it relies on
`valid_mask` row-filtering, not column mean-imputation). Mean-imputing feature values before
a Spearman-rank IC computation is a real methodological choice that can bias the reported IC
(imputed values cluster at the mean and change the rank distribution), and it has no unit
test coverage — the "in-sample-vs-OOS comparison" framing of this tool implicitly assumes the
two computations are apples-to-apples, but they are not, since in-sample `feature_ic_scores`
rows come from `ic_engine.py`'s row-filtered pipeline, not this file's column-imputed one.
**Fix:** Either drop rows with any NaN feature value in the OOS window (matching
`ic_engine.py`'s approach — likely more defensible since NaN features should be rare post-
Feature-Factory) instead of imputing, or explicitly document in the report output that the
OOS-side IC uses mean-imputation and is therefore not a strict apples-to-apples comparison to
the in-sample baseline it's plotted against.

### WR-04: `ops_cost_hurdle_calibration.py` Step 2 threshold read/write race — `current_thresholds` is read once but the loop can write a new threshold for a TF and then never re-reads it, meaning a re-run in the same process would use stale data (not a bug today, but a footgun for future extension)

**File:** `scripts/ops/corpus/ops_cost_hurdle_calibration.py:485-508`
**Issue:** `current_thresholds` is fetched once via `config_service.get()` per TF (line
486-488) before the verdict loop, then used to compute `_threshold_verdict`. This is correct
for a single pass. However nothing in the code or a comment states this is intentionally a
single-pass snapshot; a future maintainer adding a second calibration pass in the same run
(e.g., re-checking Step 2 after Step 1's cost-hurdle write, since Step 1 can change
`alpha_ci_lower`-derived percentiles that Step 2's `over_filtering` verdict logically
depends on for consistency) could easily assume `current_thresholds` reflects the
just-written Step 1 values and get silently stale data — this is exactly the kind of ordering
assumption this phase's other fixes (weight-epoch, OOS clamp) exist to make explicit rather
than implicit.
**Fix:** Low-severity — add a one-line comment above the `current_thresholds` fetch stating
it is a pre-Step-1-write snapshot by design (Step 1 writes `cost_hurdle`, not `threshold`, so
there is no actual dependency today) to prevent a future edit from introducing a real bug
here.

### WR-05: `_render_report` in `ops_cost_hurdle_calibration.py` reports `write_count` inconsistently between the summary line and the per-row "written" columns when `--dry-run` is combined with a partial write scenario

**File:** `scripts/ops/corpus/ops_cost_hurdle_calibration.py:432-436`
**Issue:** The summary line prints `write_count if not args.dry_run else 0`, which is
correct (dry-run never writes). But the per-row `written_str` computation in the Step 1/Step
2 tables (lines 375, 392) is `"yes" if (tf in step1_writes and not args.dry_run) else "no"` —
this is consistent with the summary, so on inspection this is actually fine; there's no
divergence. Re-classifying: not a bug. Withdrawn from Warnings — see IN-03 for the residual
documentation nit.

### IN-03: `ops_cost_hurdle_calibration.py`'s dry-run write-count semantics rely on the caller reading two separate print statements to reconcile "would have written N" vs "wrote 0" — mildly confusing UX, not a defect

**File:** `scripts/ops/corpus/ops_cost_hurdle_calibration.py:560-561`
**Issue:** `print(f"APR writes: {write_count if not args.dry_run else 0}")` always prints `0`
under `--dry-run`, even though `step1_writes`/`step2_writes` (the "would write" values) are
fully computed and shown in the report tables. An operator running `--dry-run` to preview
writes has to cross-reference the markdown table's "written" column rather than getting a
"would write N" count on stdout.
**Fix:** Print `f"APR writes: {write_count} (dry-run — not persisted)"` when `args.dry_run`
instead of collapsing to `0`, for clearer preview UX. Cosmetic only.
