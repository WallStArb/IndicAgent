<objective>
Parameterize `CrossSectionalSpreadTracker` so one class produces both constructions, wire
`hysteresis_legs()` into the cost-gated path, give the operator an explicit write-pass upper bound
so two partitions can be aligned to the identical window, and prove the two `construction_name`
partitions cannot leak state into one another.

Purpose: D-02 locks "a second `construction_spreads.construction_name` value computed by the same
service class, parameterized by the new rebalance rule, not a duplicated file. The existing
validated baseline must keep running unmutated so the before/after comparison stays measurable
indefinitely." The single highest-risk mechanical surface here is RESEARCH Pitfall 2 — a
watermark or prior-leg query that still binds the module constant instead of the instance
attribute would seed the new partition's turnover from the old partition's rows and silently
fabricate the very number D-04's gate is measured on.

Output: a `--construction-variant` CLI flag, a `--until-ts` upper bound for write passes,
`self.construction_name` threaded through every `construction_spreads` query, and an integration
test that fails if isolation ever regresses.
</objective>

**(c) `--construction-variant` and its read-only-mode semantics.**

`--backfill`) with `choices=["baseline", "cost_gated"]` and `default=None`. The `None` default is
deliberate and load-bearing: it is the sentinel that distinguishes "operator did not pass the
flag" from "operator explicitly passed `baseline`", which is what makes the read-only-mode
rejection below possible. The write-path dispatch normalizes it:
`construction_variant=(args.construction_variant or "baseline")`.

DECISION (closing 168-REVIEWS.md's underspecification finding, Codex): `--construction-variant`
is **rejected**, not ignored and not accepted, in every read-only evaluation mode. Rationale to
state in a comment at the guard: the read-only modes never select a partition via this flag —
`--evaluate-gate` and `--evaluate-attribution` read the baseline partition by name, and Plan 04's
`--evaluate-delta-gate` reads BOTH partitions by name — so accepting the flag there would let an
operator believe they had scoped an evaluation that in fact ignored them entirely. Silently
ignoring an operator-supplied flag is a silent wrong answer (CLAUDE.md).

Implement the guard in the CLI entrypoint immediately after `args = parser.parse_args()` and
before any dispatch: if `args.construction_variant is not None` and any read-only mode flag is
set (`args.evaluate_gate` or `args.evaluate_attribution`), call
`parser.error("--construction-variant is not valid with read-only evaluation modes; those modes select construction partitions by name")`.
Apply the identical treatment to `--until-ts` in the same guard, with its own message
(`--until-ts bounds write passes only`). Plan 04 extends this guard to cover
`--evaluate-delta-gate`.
