# Phase 142B.1: Ensemble Weighting Methodology - Research

**Researched:** 2026-07-02
**Domain:** Statistical ensemble combination (empirical-Bayes shrinkage + mean-variance signal combination) for an in-house quant IC pipeline
**Confidence:** HIGH

## Summary

This phase replaces a working-but-structurally-weak ensemble weighting scheme with two statistically
principled upgrades, judged by machinery that already exists (`EnsembleICEngine`). The current v1
scheme (`quality_weight = ic_ci_lower * max(sharpe_floor, ic_sharpe_hac)`, capped + cluster-deflated)
is transparent and sign-safe but has two known defects, both already diagnosed in prior research
(`.planning/research/2026-07-01-v3-architecture-review.md` §2): (a) it consumes raw, winner's-curse-biased
IC estimates, and (b) it computes a Ledoit-Wolf covariance matrix every run but only ever uses it for a
binary clustering heuristic — the covariance information is never actually inverted to decorrelate
signals continuously.

E1 (empirical-Bayes shrinkage of IC estimates toward a peer-group prior) and E2 (Grinold-Kahn
mean-variance combination, `w ∝ Σ⁻¹·IC`) are both textbook-standard, well-published techniques with
zero exotic dependencies — the entire implementation is `numpy`/`scipy` array math plus two new
columns on an existing table. Every piece of infrastructure needed already exists in the codebase:
`compute_shrinkage_covariance` (LW covariance), `n_independent` (the natural `n_eff` input to the
shrinkage weight), `feature_registry.group_name` (the peer-group key), and the EIC-04/EIC-05 gate
pattern (template for the new A/B comparison script). No new PyPI packages are required for this
phase — no Package Legitimacy Audit is needed.

The one item requiring the most implementation care is the out-of-fold acceptance test for E1 (D-05):
it must compare "shrunk IC predicting next-window realized IC" against "raw IC predicting next-window
realized IC" using genuinely held-out windows, not an in-sample fit-and-check. This is the same
temporal-leakage discipline the codebase already applies everywhere else (walk-forward folds with
embargo in `ic_engine.py`/`ensemble_ic_engine.py`) — reuse that pattern rather than inventing a new one.

**Primary recommendation:** Build Wave 0 (pooled cross-sectional pass + v1 baseline) first, since every
later A/B comparison is meaningless without it. Then E1 (shrinkage) strictly before E2 (mean-variance),
because E2's optimum is only as good as the inputs it's handed — running Σ⁻¹·IC on raw, biased IC
estimates would bake winner's-curse bias into supposedly "optimal" weights. This ordering is already
locked in CONTEXT.md (D-04) and confirmed correct by the statistical literature (shrink inputs before
combining, not after).

### Pattern 1: Empirical-Bayes Shrinkage as a Pure Function

**What:** A pure function taking per-cell raw IC + n_independent + peer-group membership, returning
`ic_shrunk` and `shrinkage_weight`, with zero DB/Kafka imports — following the exact style of
`src/intelligence/ensemble/weights.py`'s module docstring convention ("Pure functions only — no DB
imports, no Kafka imports").

**When to use:** Called once per (feature, symbol, tf, regime, lookahead) cell, either as a
post-processing pass over freshly-written `feature_ic_scores` rows, or inline in `ic_engine.py`'s
write path before the `INSERT`.

**Example (standard James-Stein-style empirical-Bayes formulation):**
```python
# Source: standard empirical-Bayes / James-Stein shrinkage-to-group-mean formulation,
# structurally consistent with the general form documented at
# https://en.wikipedia.org/wiki/James%E2%80%93Stein_estimator and empirical-Bayes
# hierarchical-shrinkage treatments (search-verified structural match, see Sources).
def shrink_ic(
    ic_raw: float,
    n_eff: float,
    ic_prior: float,
    k: float,
) -> tuple[float, float]:
    """Shrink a single cell's raw IC toward its peer-group prior.

    w = n_eff / (n_eff + k): as n_eff -> infinity, w -> 1 (trust the raw estimate);
    as n_eff -> 0, w -> 0 (trust the prior). k calibrates how many "effective
    observations" of prior strength to inject -- exactly the classic empirical-Bayes
    "prior sample size" interpretation.
    """
    if n_eff <= 0:
        # Degenerate: zero effective observations -- return the prior untouched,
        # not a divide-by-zero or a spurious ic_raw pass-through.
        return ic_prior, 0.0
    w = n_eff / (n_eff + k)
    ic_shrunk = w * ic_raw + (1.0 - w) * ic_prior
    return ic_shrunk, w
```

### Pattern 2: Mean-Variance Combination with Condition-Number Gate

**What:** Replace binary cluster deflation with continuous decorrelation via `Σ⁻¹·IC`, gated on
numerical stability.

**When to use:** In `ensemble_trainer.py::_process_stratum`, after `compute_shrinkage_covariance(X)`,
as an alternative branch to `cluster_deflate_weights` (selected via `alpha.ensemble.weight_method` APR
key).

**Example:**
```python
# Source: Grinold & Kahn "Active Portfolio Management" signal-combination framework
# (textbook mean-variance optimal combination of correlated signals: w ∝ Σ⁻¹ μ).
# Numerical-stability guard is standard practice for any Σ⁻¹ computation on an
# estimated (not population) covariance matrix.
import numpy as np

def mean_variance_weights(
    cov_matrix: np.ndarray,
    ic_shrunk: np.ndarray,
    condition_max: float,
) -> tuple[np.ndarray | None, float]:
    """Compute w ∝ Sigma^-1 . ic_shrunk. Returns (None, cond) if ill-conditioned --
    caller must fall back (e.g. to cluster_deflate_weights) rather than proceed on
    an unstable inverse.
    """
    cond = float(np.linalg.cond(cov_matrix))
    if not np.isfinite(cond) or cond > condition_max:
        return None, cond
    # solve(), not explicit inv() -- standard numerical-linear-algebra practice,
    # avoids the extra rounding error of forming the inverse explicitly.
    raw = np.linalg.solve(cov_matrix, ic_shrunk)
    total = float(np.sum(np.abs(raw)))
    if total < 1e-10:
        return np.zeros_like(raw), cond
    return raw / total, cond
```

**Design note (matches D-08):** this returns *raw* (uncapped, unsigned) weights — the existing
`derive_weights`-style per-feature cap and `ic_sign` application still run afterward, unchanged, exactly
as CONTEXT.md D-08 requires. Do not fold cap/sign logic into this function.

### Anti-Patterns to Avoid

- **Fitting the out-of-fold acceptance test in-sample:** Computing "does shrunk IC predict the SAME
  window's realized return better" is not an out-of-fold test — it re-uses the data that produced
  `ic_raw` in the first place and will trivially "pass." The test must compare predictions of a
  **future, held-out** window's IC, using the same embargo/walk-forward discipline already used
  everywhere else in this codebase (`ic_engine.py`'s expanding-window walk-forward with scale-specific
  embargo).
- **Explicit matrix inversion (`np.linalg.inv`) instead of `np.linalg.solve`:** unnecessarily amplifies
  numerical error for an ill-conditioned-adjacent matrix; always solve the linear system directly.
- **Applying MV combination to raw (unshrunk) IC:** violates D-04's explicit sequencing rationale —
  optimizing weights over noisy, winner's-curse-biased inputs produces weights that are "optimal" for
  noise, not signal.
- **Merging sparse `feature_registry.group_name` groups (`cross_tf`, `macro` at n=3) to "fix" small-group
  instability:** explicitly rejected by D-06 — let the out-of-fold gate surface instability empirically
  rather than pre-emptively re-engineering the taxonomy.

## Common Pitfalls

### Pitfall 1: Degenerate `n_eff` in the Shrinkage Weight

**What goes wrong:** `w = n_eff / (n_eff + k)` divides by zero or produces a nonsensical weight if
`n_eff <= 0`. This can happen for a brand-new feature, a sparse regime cell, or a peer group with too
few members to form a prior.

**Why it happens:** `n_independent` (the natural n_eff source, already computed per cell by
`ic_engine.py`) can legitimately be very small or (in edge cases) absent for freshly-added features or
sparse (tf, regime) cells — `feature_ic_scores.reliable` already exists specifically to flag
`n_independent < min_reliable_n` cells.

**How to avoid:** Explicitly branch on `n_eff <= 0` and return the prior untouched with
`shrinkage_weight = 0.0` (full shrinkage to peer group), rather than raising, returning NaN, or
defaulting to full trust in a near-zero-N raw estimate. Gate the whole shrinkage pass on the same
`reliable = true` filter already used everywhere else in this pipeline — an unreliable cell should not
even be a shrinkage candidate.

**Warning signs:** `ic_shrunk` columns containing NaN/Inf after the migration ships; a spike in
zero-`n_independent` cells feeding the peer-group mean and silently corrupting the prior for the whole
group.

### Pitfall 2: Peer-Group Prior Contaminated by the Cell Being Shrunk

**What goes wrong:** If the "peer group mean" prior for a given cell includes that cell's own raw IC in
its average, the shrinkage is partially shrinking a value toward (a mean that includes) itself — this
understates the true amount of independent information the prior contributes and biases the acceptance
test's apparent improvement upward.

**Why it happens:** The naive `SELECT AVG(ic_value) FROM feature_ic_scores WHERE group_name = X` includes
every row in the group, including the row being shrunk.

**How to avoid:** Either (a) compute a leave-one-out group mean (`(sum(group) - ic_raw) / (n_group - 1)`),
which is the textbook-correct empirical-Bayes construction, or (b) if the group size is large enough that
leave-one-out is immaterial (some `group_name` groups have only 3 features — `cross_tf`, `macro` — where
it is NOT immaterial), explicitly document the choice. Given the smallest groups have n=3, leave-one-out
is the statistically correct choice here and should be implemented, not skipped as a simplification.

**Warning signs:** Out-of-fold acceptance test passing suspiciously easily on the sparsest peer groups
(`cross_tf`, `macro`) specifically — a sign of self-contamination inflating the apparent shrinkage
benefit exactly where D-06 already flagged instability risk.

### Pitfall 3: Ill-Conditioned Covariance Silently Producing Extreme Weights

**What goes wrong:** Near-duplicate or highly collinear features (e.g. `momentum_z_fast`,
`momentum_z_mid`, `momentum_z_slow`, already known to cluster at corr > 0.80 per the existing cluster
deflation logic) push the LW-shrunk covariance matrix's condition number very high. `Σ⁻¹·IC` on an
ill-conditioned matrix produces enormous offsetting long/short weights on nearly-identical features —
mathematically "solving" the optimization but practically nonsensical and unstable across reruns.

**Why it happens:** LW shrinkage regularizes the covariance toward the scaled identity but does not
guarantee a well-conditioned matrix for all inputs — condition number can still be large when many
features are genuinely collinear (which is exactly the population this pipeline already knows exists,
per the cluster-deflation precedent).

**How to avoid:** D-08's condition-number gate (new APR key `alpha.ensemble.mv_condition_max`) is
already locked as a requirement. Implement the gate as a hard fallback: if `cond(Sigma) > mv_condition_max`,
do NOT proceed with the raw `Σ⁻¹·IC` solve — fall back to the existing `cluster_deflate_weights` path for
that stratum and log the fallback (not a silent skip). A defensible default threshold: condition numbers
above roughly 1e10-1e12 indicate the matrix is at or beyond double-precision numerical reliability
(the ratio of largest to smallest singular value approaching the reciprocal of machine epsilon,
~2.2e16, is where solves become meaningless); a more conservative practical threshold in the
100-1000 range is typical for portfolio-construction contexts where even "technically invertible" but
poorly-conditioned matrices produce unstable, non-robust weights `[ASSUMED — no project-specific
precedent exists for this exact threshold; this is a new APR key with no prior codebase convention.
Recommend seeding at a conservative default (e.g. 1000) marked [initial_estimate] and letting the
weight-turnover diagnostic (already recommended in the architecture review) surface whether it needs
loosening/tightening]`.

**Warning signs:** `ensemble_weights.weight` values with large magnitude and alternating sign on
near-duplicate features; weight vectors that change dramatically between consecutive runs on nearly
identical input data (weight turnover, flagged as a diagnostic in the architecture review §2).

### Pitfall 4: Out-of-Fold Test Comparing the Wrong Quantities

**What goes wrong:** D-05's acceptance test says "shrunk estimates must predict next-window IC better
than raw estimates." A naive implementation might instead compare `ic_shrunk` vs `ic_raw` as if they
were forecasts of the *forward return itself*, or compare in-sample fit rather than genuinely
out-of-sample next-window IC.

**Why it happens:** The distinction between "does the estimate track its own realized value next
window" (correct test) versus "does the estimate correlate with returns" (a different, already-answered
question — that's what IC itself measures) is subtle and easy to conflate.

**How to avoid:** The test should be: split the corpus into training window T and a subsequent holdout
window T+1 (with embargo, mirroring the existing walk-forward fold construction). Compute `ic_raw` and
`ic_shrunk` from window T. Compute the *realized* IC in window T+1 (`ic_realized_T+1`). The acceptance
criterion is that `|ic_shrunk - ic_realized_T+1|` (or an analogous error/correlation metric) is smaller
on average than `|ic_raw - ic_realized_T+1|` across cells — i.e., shrinkage should be a better estimate
of what actually happens next, not what happened in the same window it was computed from.

**Warning signs:** An acceptance test that passes on every single cell with no exceptions is suspicious —
real out-of-fold shrinkage benefit should show heterogeneity (larger benefit in sparse/noisy cells,
smaller or even negative benefit in already-well-estimated cells with large n_eff, since `w -> 1` there
and `ic_shrunk ≈ ic_raw` by construction).

### Pitfall 5: Wave 0's Pooled Pass Double-Counting or Miscounting Symbols

**What goes wrong:** `EnsembleICEngine._execute_inner` currently derives `symbol_tf_pairs` from
`SELECT DISTINCT symbol, tf FROM alpha_events`, which never contains `symbol='POOLED'`. A naive fix that
simply aggregates `alpha_score` across all symbols per (tf, bar_ts) via a plain `AVG` risks silently
mixing symbols that don't share the same regime label at that bar_ts (since regime labels are joined
per-symbol via `market_regimes.ts = ae.bar_ts` — but `market_regimes` rows are `asset_class`-scoped,
not per-symbol, so this should be safe by construction) — but the aggregation logic needs to explicitly
group by (tf, regime, bar_ts) BEFORE averaging across symbols, not average first and label second.

**Why it happens:** The existing `ensemble_trainer.py` cross-sectional pattern (`symbol='POOLED'` in
`feature_ic_scores`) is the correct template to follow — todo 046 itself names this as approach 1
("matching the design `feature_ic_scores`/`ensemble_trainer.py` already use for `symbol='POOLED'`
rows"). Deviating from that exact pattern (e.g., building a new ad hoc aggregation) risks a subtly
different pooling grain than what `ensemble_trainer.py` already validates elsewhere.

**How to avoid:** Follow todo 046's suggested approach 1 literally: dispatch one additional
`symbol='POOLED'` worker task per (tf, regime) that aggregates `alpha_score` across all symbols
sharing that (tf, regime, bar_ts) cell — mirroring the exact SQL/grouping pattern
`ensemble_trainer.py` already uses when writing `symbol='POOLED'`-eligible IC.

**Warning signs:** `alpha_ensemble_ic_pooled_symbol_consistent` CHECK constraint violations at
insert time (would fail loudly — good); pooled IC values wildly inconsistent with the per-symbol median
in EIC-05 Section 2 (would now populate for the first time — watch it carefully on the first real run).

## Open Questions

1. **Exact value of `alpha.ic.shrinkage_k` (the effective-sample-size calibration constant in `w = n_eff/(n_eff+k)`)**
   - What we know: todo 029 already flags this as `[initial_estimate, ML learning target]` — it is
     explicitly NOT meant to be hand-picked once and left alone; it's designed to be tuned.
   - What's unclear: what a reasonable *initial* seed value is before any tuning happens. No
     project-specific precedent exists (this is the first shrinkage estimator in the codebase).
   - Recommendation: seed conservatively (e.g. `k` on the order of a typical cell's `min_reliable_n`,
     currently 100, so that a cell right at the reliability threshold gets ~50% shrinkage toward its
     prior) and let the out-of-fold acceptance test (D-05) — which is explicitly designed to validate
     or reject the whole mechanism — be the actual arbiter, not a priori theorizing about the "right" k.

2. **Whether the shrinkage pass runs inline inside `ic_engine.py`'s write path or as a separate
   post-processing batch step reading already-written `feature_ic_scores` rows**
   - What we know: CONTEXT.md D-07 confirms the schema footprint is exactly 2 new columns on the
     existing table — no new table. The architecture review (§2, E1 entry) says "ensemble side is a
     one-line query change" implying the shrinkage computation itself happens somewhere else (either in
     `ic_engine.py` or a small standalone step), not literally inline in `ensemble_trainer.py`.
   - What's unclear: whether inlining into `ic_engine.py`'s existing write path (touching a
     large, heavily-audited file) vs. a separate lightweight oneshot (reading `feature_ic_scores`,
     computing shrinkage, `UPDATE`-ing the 2 new columns) is preferable from a blast-radius perspective.
   - Recommendation: prefer a separate, small oneshot step (mirrors the `bulk_update_by_key` pattern
     already in `services/_batch_utils.py` for exactly this kind of "compute derived columns, bulk
     UPDATE by key" operation) run once after `ic_engine.py` completes and before `ensemble_trainer.py`
     starts — this keeps `ic_engine.py`'s already-large, already-correctness-critical write path
     untouched, and slots cleanly into the existing `ops_corpus_pipeline_run.sh` sequencing
     (`regime_writer → forward_return_writer → ic_engine → [NEW: shrinkage step] → ensemble_trainer →
     alpha_publisher`). This is a planner decision, not a locked one — CONTEXT.md leaves internal
     structure to Claude's discretion for anything not explicitly enumerated in D-01 through D-14.

3. **Whether the E2 mean-variance branch should still run `cluster_deflate_weights` afterward, or skip
   it entirely for that `weight_version`**
   - What we know: D-08 says "keep the per-feature cap and ic_sign logic unchanged" but does not
     explicitly say whether cluster deflation is kept, replaced, or skipped for the MV variant. The
     architecture review frames E2 as "replacing the binary cluster-deflation heuristic with continuous
     decorrelation" — implying cluster deflation is superseded, not stacked, for the MV path.
   - What's unclear: whether running both (MV combination, then cluster deflation on top) would
     double-penalize already-decorrelated weights, or whether it's harmless because cluster deflation
     only bites when a cluster's total weight exceeds `max_cluster_weight` (which MV combination should
     rarely trigger, since it's already spreading weight based on true covariance).
   - Recommendation: skip `cluster_deflate_weights` for the `mean_variance` weight method (Σ⁻¹·IC
     already performs continuous decorrelation, making the binary cluster cap redundant for that path)
     but keep `derive_weights`'s per-feature cap. This matches the architecture review's framing of E2 as
     a *replacement* for cluster deflation, not an addition to it. Confirm at plan/discuss time if this
     reading is correct.
