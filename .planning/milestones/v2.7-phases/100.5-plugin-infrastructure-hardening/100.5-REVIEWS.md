# Cross-AI Plan Review — Phase 100.5: Plugin Infrastructure Hardening

## Gemini Review

### 1. Summary
The plan is highly disciplined, adhering to the "Renaissance Framing" of statistical rigor and evolvable components. The use of a TDD-first approach with equivalence testing infrastructure is excellent for high-stakes quantitative code. The focus on replacing scattered telemetry with `PluginObserver` and enforcing contracts via `emit_signal` directly addresses the technical debt associated with silent failures. While the plan is robust, it faces operational risks regarding the extended duration of a "broken" CI state and potential regressions in stateful plugin migrations.

### 2. Strengths
- **Observability Consolidation:** Moving from scattered inline metrics to a centralized `PluginObserver` significantly reduces code rot and improves metric consistency.
- **Contract Enforcement:** Hard-enforcing `emit_signal()` via `validate_signal()` is a necessary evolution to ensure pipeline data integrity.
- **Regression Safeguards:** The use of equivalence testing against legacy snapshots (Tasks 8–14) provides a solid mathematical foundation for verifying the migration of stateful plugins.
- **Phased Migration:** Grouping migrations by complexity (1A–1C) allows for early detection of systemic issues in the migration pattern.

### 3. Concerns
- **[HIGH] CI Red-State Duration:** A hard-block test that is *intentionally* failing throughout Tasks 9–14 is dangerous. It masks legitimate test failures in other areas of the system, potentially delaying the discovery of unrelated regressions during the migration.
- **[MEDIUM] Tolerance Sensitivity:** 0.1% tolerance for stateful plugins like GARCH, Kalman, and BOCPD might be too tight due to floating-point drift over 2000 bars, or too loose for simpler indicators.
- **[MEDIUM] Dashboard/Alert Breakage:** Renaming `plugin_fallbacks_total` (Task 1) will break all historical Grafana dashboards and Prometheus alerts relying on this metric.
- **[MEDIUM] Pre-validation Risks:** Moving frame pre-validation into the executor (Task 5) might cause plugins that rely on specific (non-standard) lookback requirements to be silently dropped.

### 4. Suggestions
- **CI Strategy:** Instead of a single hard-block test, use a whitelist of migrated plugins that must be updated as migrations progress, keeping CI green. Alternatively use `pytest.mark.skipif` for unmigrated plugins.
- **Tolerance Calibration:** Define a per-plugin tolerance tier (e.g., `LOOSE` for probabilistic models like HMM/BOCPD, `STRICT` for simple technical indicators).
- **OTel Migration Path:** Emit both old and new metric names simultaneously for one release cycle before decommissioning `plugin_fallbacks_total`.
- **Executor Guardrails:** Ensure `PluginExecutor` supports `custom_lookback` for plugins with non-standard frame requirements.

### 5. Risk Assessment
**Risk Level: MEDIUM** — Technical plan is sound. Primary risks are operational (CI red-blocking and dashboard breakage). Both are manageable with iterative CI updates and graceful metric deprecation.

## Codex Review

### Summary
The plan is directionally strong: it attacks silent plugin failure at the executor boundary, centralizes observability, enforces signal validity before events enter the bus, and reduces incremental-plugin state drift through `IncrementalMixin`. The main risks are operational rather than conceptual: metric renames may break dashboards, frame pre-validation could incorrectly suppress plugin execution, the red-CI strategy may disrupt unrelated work, and equivalence testing for stateful migrations needs tighter definition than "500 bars / 0.1% tolerance." Treat this as a high-value hardening phase, but split it into safer mergeable slices with compatibility shims and explicit verification gates.

### Strengths
- Centralizing plugin telemetry behind `PluginObserver` is a good design move. It reduces scattered metric calls and makes executor behavior easier to test.
- `NoOpPluginObserver` keeps constructor injection simple without forcing telemetry into plugin singletons.
- Moving inline `plugin_validator.py` instruments into `metrics.py` improves ownership and avoids hidden OTel setup paths.
- `PluginCallResult` is a worthwhile structural improvement over tuple returns.
- Hard enforcement in `emit_signal()` is correct for canonical event quality.
- Migration pattern of legacy snapshot → equivalence test → migrate → verify is sound.
- Recognizing context plugins separately in Task 14 is important (BOCPD, HMM, GARCH, Kalman have very different state behavior).

### Concerns
- **[HIGH] Metric rename can break dashboards and alerts.** Renaming `plugin_fallbacks_total` without a compatibility window may break Prometheus queries, alerts, SLO dashboards, and runbooks.
- **[HIGH] Frame pre-validation may silently drop valid plugin work.** A generic `min_lookback` check could suppress plugins that emit partial outputs, fallback values, session-boundary outputs, or event-style signals with fewer rows than their full lookback. Moving 104 in-plugin guards into the executor risks accidentally suppressing legitimate outputs.
- **[HIGH] Red CI from Task 7 is disruptive.** Blocks unrelated merges, makes regressions harder to identify, can normalize broken CI.
- **[HIGH] Equivalence tests may be under-specified.** "500-bar / 0.1%" is insufficient for recursive indicators, session-aware plugins, volume profile structures, regime models, and probabilistic context plugins — each needs plugin-specific comparison rules.
- **[HIGH] Deleting legacy fixtures removes useful regression protection.** Future refactors lose an important baseline.
- **[MEDIUM] OTel instrument types need explicit specification.** Counters, histograms, gauges, and up-down counters are not interchangeable in Prometheus dashboards.
- **[MEDIUM] `PluginCallResult.state` ownership is unclear.** Whether this is a snapshot, reference, diagnostics-only, or persisted state object needs definition — passing mutable state could create aliasing risks.
- **[MEDIUM] `emit_signal()` failure needs pipeline-level observability.** Raising `ValueError` without recording plugin name, tier, instrument, and validation reason makes hard enforcement hard to debug.
- **[MEDIUM] Output key consistency test may miss dynamic keys.** 60-bar synthetic frames may not trigger all branches (volatility spikes, session transitions, regime change, error paths).
- **[LOW] Task 13 consolidated-but-numbered is confusing.** Better to remove from tracking entirely.

### Suggestions
- Add a metric compatibility period: keep publishing `plugin_fallbacks_total` alongside the new name for one release.
- Make frame pre-validation opt-in via explicit plugin metadata (`requires_full_lookback=True`, `allows_partial_output`, `session_boundary_sensitive`) rather than universal rule.
- When pre-validation skips, emit `record_warmup_skip` with reason, required bars, actual bars — prevents the new guard from being another silent failure mode.
- Replace hard-block with staged gate: `xfail(strict=True)` with an explicit allowlist that shrinks per migration, or run in a dedicated CI job allowed to fail until Task 16.
- Compare equivalence tests after warmup burn-in window — ignore initial unstable bars for recursive indicators.
- Use plugin-specific tolerances: RSI/MACD/EMA → relative + absolute; SessionLevels/VWAP → session-boundary exactness; MarketProfile → bucket key equality + volume; BOCPD/HMM → distribution shape, posterior normalization; GARCH/Kalman → seeded deterministic.
- Keep minimal golden regression fixtures after Task 16 — delete bulky legacy source but retain compact input/output snapshots for high-risk migrations.
- Add integration test for `PluginExecutor` proving observer calls fire for success, null output, warmup skip, validation error, plugin exception, and circuit breaker transition.
- Before restarting `indicagent-intelligence-pipeline`, include smoke test: one instrument, one full pipeline pass, confirm DB writes, OTel metrics, no unexpected fallback spike.

### Risk Assessment
**Overall risk: HIGH** — The architectural direction is good, but this phase touches executor, telemetry, signal construction, CI policy, and 24 stateful plugin migrations. Highest risks: accidental suppression from centralized frame pre-validation, operational breakage from metric renaming, long-running red CI. With metric compatibility, staged CI enforcement, explicit plugin warmup metadata, and retained golden fixtures, risk drops to **MEDIUM**.

## Consensus Summary

### Agreed Strengths
- `PluginObserver` centralization is well-designed — both reviewers endorsed it
- `NoOpPluginObserver` injection pattern is clean and testable
- Hard enforcement in `emit_signal()` is the correct design choice
- Migration pattern (legacy snapshot → equivalence test → migrate → verify) is sound
- Grouping migrations by complexity (1A→1C→Group2→Group3) is a good risk sequencing

### Agreed Concerns (both reviewers flagged — highest priority)

**1. Metric rename will break dashboards [HIGH]**
Both reviewers independently called out renaming `plugin_fallbacks_total` → `intelligence_pipeline_plugin_fallback_total` as an operational risk. Existing Grafana panels, Prometheus alerts, and runbooks that reference the old name will silently break.

**Decision needed:** Either (a) dual-emit both names for one release cycle, or (b) confirm no existing dashboards/alerts reference `plugin_fallbacks_total` before proceeding.

**2. CI red-state from Task 7 is risky [HIGH]**
A deliberately failing test for the duration of Tasks 9-14 masks real regressions and can normalize broken CI. Both reviewers flagged this.

**Decision needed:** Switch to `xfail(strict=True)` with a shrinking allowlist, OR run the adoption test in a separate CI job tagged `allow-failure` until Task 16 flips it mandatory.

**3. Frame pre-validation may silently suppress valid plugins [HIGH → MEDIUM after mitigation]**
A universal `min_lookback` check in the executor could skip plugins that legitimately produce outputs before their full lookback is satisfied (session boundaries, partial-bar output, fallback modes).

**Decision needed:** Either add opt-out metadata (`allows_partial_output=True`) on specific plugins, or ensure `record_warmup_skip` fires with enough context to diagnose suppressions post-execution.

**4. Equivalence test tolerance is under-specified [MEDIUM]**
"0.1% / 500 bars" is not appropriate for probabilistic models. BOCPD/HMM/GARCH/Kalman need regime-label equality, posterior normalization checks, and seeded determinism — not numeric tolerance.

**Decision needed:** Define per-plugin-group tolerance strategy before Tasks 9-14 begin.

### Divergent Views
- **Risk level:** Gemini = MEDIUM, Codex = HIGH. Codex's higher rating is driven by legacy fixture deletion and under-specified equivalence tests — both valid, but mitigable.
- **CI fix:** Gemini prefers a whitelist/skipif approach; Codex prefers `xfail(strict=True)`. Either works — `xfail(strict=True)` with shrinking allowlist is more explicit.
- **Legacy fixtures:** Codex says keep compact golden outputs permanently; Gemini didn't raise this. Worth keeping minimal snapshots for BOCPD/HMM/Kalman as they're high-risk.
