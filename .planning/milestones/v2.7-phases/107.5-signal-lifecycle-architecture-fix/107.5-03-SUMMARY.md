**Key finding:** `intelligence_features.trading_signals` JSONB is a point-in-time snapshot written at feature computation time. It does not contain all signal_ids that appear in `signal_ledger`. Only ~45% of signal_ledger entries (475k/1.05M) had their signal_id present in the JSONB, and all of those were successfully populated. The remaining 55% have no retrievable zone source from this path.

## Decisions Made

1. **Single-pass LATERAL JOIN UPDATE** instead of timestamp-ordered IN-subquery batch cursor. Initial approach of `signal_id IN (SELECT ... ORDER BY timestamp ASC LIMIT 10000)` exited after the first zero-hit batch because the oldest signals (1d timeframe from 2026-05-21) had no JSONB match. The LATERAL JOIN approach handles all matchable signals in one pass.

2. **Three-way reconciliation split** instead of binary pass/fail on zero NULLs. The plan assumed `in_retention_unmatched = 0` after backfill, but investigation revealed the JSONB contains different signal_ids than signal_ledger for the same (symbol, ts, tf). The reconciliation now distinguishes: real join bugs (must be 0), no JSONB source (data limitation), and out-of-retention (acceptable miss). Only real join bugs block Fix 3.

3. **No `asyncio.sleep` throttle in final version** — The single-pass approach runs one UPDATE statement, not a loop. The original throttle design was for the batch loop approach. Not applicable when doing a single-shot UPDATE.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Timestamp-ordered batch cursor exits early when first batches are all unmatched**

- **Found during:** Task 1 (initial script run)
- **Issue:** The plan specified batching via `signal_id IN (SELECT signal_id ... ORDER BY timestamp ASC LIMIT 10000)`. The first 10k signals (oldest by timestamp, all 1d timeframe) had no JSONB match. The loop saw 0 rows updated and exited, leaving 473k matchable signals untouched.
- **Fix:** Switched to a single-pass LATERAL JOIN UPDATE (`UPDATE signal_ledger ... FROM intelligence_features, jsonb_array_elements(f.trading_signals)`) which naturally restricts to only signals that have a JSONB match. No batch cursor needed.
- **Files modified:** `production/scripts/backfill_zone_fields.py`
- **Verification:** Subsequent runs show 0 real join bugs; 475k signals populated

**2. [Rule 2 - Missing] Reconciliation misidentifies data limitation as bug**

- **Found during:** Task 1 (reconciliation analysis)
- **Issue:** The plan's success criterion "In-retention unmatched = 0" cannot be met — 578k in-retention signals have no signal_id in any intelligence_features JSONB snapshot. These are not a bug; the JSONB is a point-in-time snapshot at feature compute time.
- **Fix:** Added `_NO_JSONB_SOURCE_SQL` diagnostic query that counts NULLs where the signal_id is absent from all JSONB snapshots vs those where the JSONB exists but the update failed (real join bug). Reconciliation gates on `real_join_bugs == 0`, not on `in_retention_unmatched == 0`.
- **Files modified:** `production/scripts/backfill_zone_fields.py`
