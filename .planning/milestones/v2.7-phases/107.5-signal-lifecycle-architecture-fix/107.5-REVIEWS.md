# Cross-AI Plan Review — Phase 107.5

## Gemini Review

### Review: Phase 107.5 Signal Lifecycle Architecture Fix

#### Summary
The plan is structurally sound and effectively addresses the identified defects. By moving from a bar-count-based TTL (which is inherently prone to drift across restarts/backfills) to an absolute `expires_at` timestamp, the architectural integrity of the signal lifecycle is significantly improved. The wave-based approach ensures that dependencies (DDL, then data migration, then logic switch) are respected. While the "atomic deploy" is a conceptual target rather than a strict technical guarantee in a distributed system, the graceful fallback and counter-based observability mitigate the risk of a "big bang" failure.

#### Strengths
- **Logical Dependency Chain:** The migration path (DDL -> Data Backfill -> Logic Update) is robust and prevents breaking changes.
- **Idempotency:** Including idempotent SQL/Python scripts for backfills minimizes the risk of partial failures during massive updates.
- **Observability-First:** Using counters (`_NULL_EXPIRES_AT_COUNTER`, `SIGNAL_REPLAY_NULL_ZONE_TOTAL`) to track failure states is an excellent practice for debugging distributed system state.
- **Simplicity:** Removing the `LATERAL JOIN` is the correct path forward. Moving signal zone fields into the ledger removes the dependency on the `intelligence_features` JSONB blobs, which is a major performance win for the replay auditor.

#### Concerns
- **[HIGH] "Atomic Deploy" Reality (Plan 107.5-05):** Updating two distinct agents (lifecycle tracker vs. signal tracker) via a sequential `systemctl` command is **not** atomic. There is an inevitable window where one service uses the old model and the other uses the new one. Given that these services communicate via Kafka, this inconsistency could lead to temporary "split-brain" TTL evaluations.
- **[MEDIUM] Backfill Duration/Locking (Plan 107.5-03):** Updating 958k rows in a TimescaleDB hypertable might trigger excessive table locks or WAL growth if not throttled correctly. Ensure the "batch loop" has a `sleep` or transaction-committing interval to keep the DB responsive.
- **[LOW] Timezone/UTC Risk (Plan 107.5-04):** Ensure `expires_at` calculations account for potential leap-second/daylight saving edge cases if `datetime.now(UTC)` deviates from the timestamp provided by the upstream producer.

#### Suggestions
- **Mitigate "Atomic" Window:** In Plan 05, ensure that both services are written to handle *both* `expires_at` and `bars_elapsed` logic as a **transitional state** for one full deployment cycle. If `expires_at` is NULL (in the window before backfill is complete), the system should fail over to the old logic *with a log warning*.
- **DDL Best Practices:** In Plans 02 and 04, ensure the migration scripts are added as numbered files (e.g., `096_...`) rather than random production files, to maintain project convention.
- **Backfill Throttling:** Explicitly add a `time.sleep(0.1)` inside the 10k-row batch loop in Plans 03 and 04 to prevent I/O saturation on the TimescaleDB instance.

#### Risk Assessment
**Overall Risk: MEDIUM**
The primary risk is the logic switchover between two services. If the new `expires_at` logic and the legacy bar-count logic diverge significantly during the brief window of an asymmetric deployment, signal state could become corrupted. However, the plan's inclusion of robust observability and idempotent fallbacks makes this a manageable risk.

## Codex Review

**Summary**

The plan targets the right structural defects and the wave ordering is mostly sensible, but it is not yet strong enough for the stated success criteria. The biggest gaps are Plan 05's evaluator switch, Plan 03's reconciliation threshold, and the assumption that `symbol + feature_ts + feature_tf` is enough to backfill zones. Also, changing `lifecycle_tracker.evaluate_signal()` to use `datetime.now(UTC)` would break deterministic replay semantics; it should compare against the evaluation bar timestamp, not wall-clock now.

**Strengths**

- Correctly identifies the live restart backlog at `services/signal_tracker_compute_agent.py:408`.
- Correctly identifies the zone field mismatch at `services/signal_writer_agent.py:207`.
- Moving TTL to a persisted `expires_at` is the right architectural direction.
- Removing the replay auditor's `LATERAL` join is correct once ledger zones are reliable.
- Putting replay batch size and interval into `Settings` is appropriate.

**Concerns**

- **[HIGH] Plan 05 uses `datetime.now(UTC)` in evaluate_signal:** Replay evaluates historical bars and must compare `bar_time >= expires_at`, not current wall time. Using now() breaks deterministic replay semantics.
- **[HIGH] Plan 05 fallback bar-count path for NULL expires_at violates D-17:** "Use expires_at exclusively" means no silent bar-count fallback. Prefer fail-loud skip/DLQ/counter.
- **[HIGH] Plan 03 reconciliation threshold conflicts with success criterion:** Plans allow `unmatched <= 10%` but the roadmap success criterion says "zero unmatched signal_ids." That mismatch needs resolution.
- **[HIGH] Plan 03 backfill join key must include signal_id:** `symbol + feature_ts + feature_tf` only locates the feature row, not the specific signal within the array. Must match `tf_sig.value->>'signal_id' = sl.signal_id::text` from the JSONB array.
- **[MEDIUM] Plan 05 omits repository read paths:** `expires_at` must be added to `LedgerEntry`, `_INSERT_SQL`, `_SELECT_ACTIVE_COLS`, `fetch_pending_signals()`, and the `signal_ledger_full` view.
- **[MEDIUM] "Atomic deploy" is operationally weak:** Two services plus shared library code, Kafka in-flight messages, writer changes, DB migration, and backfill are not atomic under a plain `systemctl stop/start`.
- **[MEDIUM] tf_to_seconds() defaulting unknown timeframes to 60 can silently corrupt expires_at:** Unknown timeframe should increment a metric and fail the row/script reconciliation.
- **[MEDIUM] Plan 06 candidate filter should use expires_at:** Change `timestamp < NOW() - INTERVAL '2 minutes'` to `sl.expires_at < NOW()` to correctly filter by true TTL, not a fixed 2-minute offset.
- **[LOW] Plan 02 migration 096 is mostly redundant:** Migration 095 already added the zone columns; the safety check is harmless but adds noise.
- **[LOW] Plan 01 metric name mismatch:** Counter remains "backfill fast path" even after removing the `is_backfill` guard; rename for clarity.

**Suggestions**

- In Plan 01, add unit tests proving non-backfill stale signals take the fast path.
- In Plan 03, build a staging table keyed by `signal_id` from `intelligence_features.trading_signals`, then update `signal_ledger` from that staging table to avoid repeated JSONB expansion.
- In Plan 03, require unmatched count to be zero for rows inside feature retention; separately report out-of-retention rows.
- In Plan 04, fail reconciliation on NULL `ttl_bars`, NULL timeframe, or unknown timeframe — don't silently default.
- In Plan 05, use `bar_time >= expires_at` in `evaluate_signal()` and pass the current bar timestamp from live and replay callers.
- In Plan 05, deploy in stages: schema + writer emits `expires_at` → backfill → verify zero NULLs → restart evaluators together.
- In Plan 06, filter candidates by `expires_at < NOW()` instead of the 2-minute offset.

**Risk Assessment**

Overall risk: **HIGH** as written. The architecture direction is sound, but Plan 05 can break replay determinism, Plan 03 conflicts with the stated reconciliation target, and the deploy is not truly atomic. With the evaluator changed to use `bar_time`, strict `expires_at` reconciliation, and replay candidate filtering moved to `expires_at`, the risk drops to **MEDIUM**.

## Consensus Summary

### Agreed Strengths
- **Architecture direction is correct:** Moving TTL to `expires_at` eliminates the dual-model problem and makes signal lifecycle deterministic.
- **Wave ordering (DDL → backfill → logic switch) is sound:** Both reviewers confirmed the dependency chain is robust.
- **Observability via counters is good practice:** NULL_EXPIRES_AT_COUNTER and NULL_ZONE_TOTAL are well-placed.
- **Removing LATERAL JOIN is the right fix** once zone fields are reliably populated in signal_ledger.
- **Idempotent backfill scripts** (WHERE col IS NULL) are the correct approach.

### Agreed Concerns (Priority Order)

1. **[HIGH — Both] "Atomic deploy" in Plan 05 is not truly atomic.** A sequential `systemctl stop/start` leaves a window where lifecycle_tracker and signal_tracker use different TTL models. Both reviewers flagged this.

2. **[HIGH — Codex] Plan 05 `evaluate_signal()` should use `bar_time >= expires_at`, not `datetime.now(UTC)`.** Replay processes historical bars; using wall-clock now() breaks determinism. The bar timestamp must be passed to the evaluator.

3. **[HIGH — Codex] Plan 03 JSONB join key is incomplete.** `symbol + feature_ts + feature_tf` locates the features row but not the specific signal within the `trading_signals` JSONB array. Must also match on `signal_id` from the array element.

4. **[HIGH — Codex] Plan 03 reconciliation threshold (10%) conflicts with roadmap success criterion ("zero unmatched signal_ids").** Resolve: define "zero" as zero for in-retention signals only; out-of-retention signals are acceptable misses.

5. **[MEDIUM — Both] Backfill throttling on 958k-row TimescaleDB hypertable.** Both plans (03 and 04) need explicit `sleep` or `asyncio.sleep` between batches to avoid lock contention and WAL growth.

### Divergent Views
- **Gemini** rated overall risk MEDIUM (observability mitigates the atomic deploy gap). **Codex** rated HIGH because the bar_time vs now() semantic break in evaluate_signal is a correctness bug, not just an operations risk. Codex's finding is more precise — the bar_time issue must be fixed before execution.
- **Gemini** suggested a transitional compatibility window for the evaluator switch (both old and new logic live temporarily). **Codex** suggested strict stage-gate deployment (zero NULLs verified before cutover). The stage-gate approach is more consistent with the project's "one change, one observable outcome" principle.

### Recommended Pre-Execution Fixes (via `/gsd-plan-phase 107.5 --reviews`)

1. Plan 03: Fix JSONB backfill join to include signal_id match; clarify reconciliation threshold (zero for in-retention, documented for out-of-retention).
2. Plan 05: Change `evaluate_signal(bar_time)` signature — pass bar timestamp; compare `bar_time >= expires_at` not `now() >= expires_at`. Remove bar-count fallback; replace with counter + skip.
3. Plan 05: Add `expires_at` to `_SELECT_ACTIVE_COLS` and `fetch_pending_signals()` in signal_ledger_repository.
4. Plan 06: Change candidate filter from `timestamp < NOW() - INTERVAL '2 minutes'` to `expires_at < NOW()`.
