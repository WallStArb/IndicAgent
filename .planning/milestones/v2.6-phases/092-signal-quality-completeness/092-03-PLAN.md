<objective>
Wire tail-risk metrics from Plan 02 into the shadow governance promotion gate. Block promotions when skewness or recovery_factor falls below configured thresholds, emit OTel observability counter on every block, fail-open on transient DB errors so the audit cycle never crashes, and add unit-test coverage for the None-safe boolean semantics and the DB-failure path.

Purpose: Close the measurement→action loop. Without this plan, Plans 01 and 02 are instrumentation theater — distribution shape exists in the DB but nothing acts on it. With this plan, a setup with Sharpe 1.5 and skewness -2.5 (left-tail blowup risk) cannot graduate from shadow to live, AND a DB hiccup during the 30-minute audit cycle cannot halt all promotions across the system.

Output: Pure `_tail_risk_blocks_promotion()` gate function consistent with `_should_promote()` pattern; integrated into `_check_promotion()` BEFORE the existing promotion check; new OTel counters; full unit test coverage including fail-open path.
</objective>

<threat_model>
ASVS L1 — security and integrity threats addressed by this plan:

- **Integrity - silent suppression from None comparisons (mitigated):** Naive `if skewness < threshold` raises TypeError on None. `_tail_risk_blocks_promotion()` explicitly guards `if skewness is not None and skewness < min_skewness`. NULL metrics (n below threshold) skip the gate, never block.
- **Integrity - reading wrong signal_metrics row (mitigated):** Tail gate query filters `symbol = '*' AND entry_type = '*' AND track = 'market'` — reads the global market-track aggregate. Without these filters, it could read per-symbol or per-entry_type rows with smaller n and wrong distribution shape.
- **Availability - DB failure crashes audit cycle (mitigated, Gemini Actionable Item 2):** The fetchrow is wrapped in `try/except Exception` so any DB-side issue (connection drop, transient timeout, query error) is caught. On exception: log a structured warning, increment `SHADOW_TAIL_GATE_DB_ERROR` OTel counter, and **fail-OPEN** (skip the tail gate, fall through to `_should_promote()`). Rationale: a 30-minute cycle should not block ALL promotions because one query failed; the existing `_should_promote()` gate (n >= min_n AND ci_lower > min_ev_r) is still authoritative. Tail gate is an additive safety net, not a hard prerequisite. Operator alerting on `SHADOW_TAIL_GATE_DB_ERROR > 0` ensures the failure is not invisible.
- **DoS via extra DB load (mitigated, Gemini MEDIUM concern):** Tail gate query is one `fetchrow` per plugin per 30-minute audit cycle. Plugin count ~22. Total: ~22 fetches per cycle (NOT per-tick, NOT per-symbol). REUSES existing pool.acquire() context in _check_promotion() — does NOT open a new connection. Reuse is asserted explicitly via the must_haves truth and acceptance criteria.
- **SQL injection (mitigated):** Query uses parameterized binding `$1` for plugin name. No string interpolation.
- **Governance bypass (out of scope):** Promotion still requires `n >= min_n AND ci_lower > min_ev_r`; tail gate is ADDITIVE — it can only block, never approve. A failing tail gate can never falsely promote.
</threat_model>
