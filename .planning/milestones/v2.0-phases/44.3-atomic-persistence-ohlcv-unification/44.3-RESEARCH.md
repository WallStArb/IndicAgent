## Summary

Phase 44.3 has three tightly-scoped tasks: simplify FeatureWriterService, add i8 UPSERT to LLMWriterService, and wire live OHLCV writes into FeaturePipelineService. All three are persistence-layer changes — no intelligence logic, no schema invention beyond the 10 columns added in the DB migration.

**FeatureWriterService** currently subscribes to three topics (`development.intelligence`, `development.intelligence.i7`, `development.intelligence.i8`) and performs a two-phase write: `_INSERT_FEATURE_SQL` (I1-I6 first) followed by separate `_UPSERT_I7_SQL` and `_UPSERT_I8_SQL` flushes. The code to remove is precisely: `_process_i7_message()`, `_process_i8_message()`, `_flush_i7_i8()`, `_UPSERT_I7_SQL`, `_UPSERT_I8_SQL`, `_i7_buffer`, `_i8_buffer`. After simplification, the service subscribes to `development.intelligence.record` only, parses `BarIntelligenceRecord`, and executes a single-buffer batch INSERT with all columns populated.

**LLMWriterService** currently has one consumer group (`llm_writer`) and two topics (`llm.calls`, `llm.outcomes`). Adding i8 UPSERT means: add `development.intelligence.i8` to the topic list, add `_i8_buffer` and `_UPSERT_I8_SQL` (mirroring the removed code from FeatureWriterService almost verbatim), and route in `_process_loop()`. This is the smallest of the three tasks.

**FeaturePipelineService OHLCV writes** are a Phase 44.1 deliverable that Phase 44.3 must ensure is actually wired and validated. The spec is explicit: same batch pattern as current FeatureWriterService, 1m bars only, `ON CONFLICT DO NOTHING`. Since `market_data_ohlcv` is confirmed empty (0 rows), there is no data migration concern.

**Primary recommendation:** Execute in plan order — DB migration first, FeatureWriterService simplification second, LLMWriterService i8 wiring third, OHLCV validation last.

### Pattern 1: Single-Buffer Atomic INSERT (FeatureWriterService)

**What:** Replace three-topic fan-out + two-phase write with single `development.intelligence.record` consumer and one INSERT.

**Current state (to be removed):**
```python
# Topics: intelligence, intelligence.i7, intelligence.i8
# Buffers: _buffer (I1-I6), _i7_buffer, _i8_buffer
# Write path: _INSERT_FEATURE_SQL (18 params) then _UPSERT_I7_SQL + _UPSERT_I8_SQL

_UPSERT_I7_SQL = "INSERT INTO intelligence_features (ts, symbol, tf, i7) ... ON CONFLICT ... DO UPDATE SET i7 = EXCLUDED.i7"
_UPSERT_I8_SQL = "INSERT INTO intelligence_features (ts, symbol, tf, i8) ... ON CONFLICT ... DO UPDATE SET i8 = EXCLUDED.i8"
```

**After (target state):**
```python
# Topic: development.intelligence.record ONLY
# Buffer: _buffer only
# Write path: single INSERT, all columns populated from BarIntelligenceRecord

_INSERT_FEATURE_SQL = """
INSERT INTO intelligence_features (
    ts, symbol, tf, platform, source, schema_version,
    bar, i1, i2, i3, i4, i5, smc, i6, i7,
    winner_plugin, winner_confidence, winner_direction,
    signals_evaluated, signals_after_quality, signals_after_regime,
    signals_after_tod, signals_after_calibration,
    ledger_written, pipeline_latency_ms,
    i7_computed_at, computed_at, session_type, days_to_expiry
)
VALUES ($1, $2, $3, ..., $29)
ON CONFLICT (ts, symbol, tf) DO NOTHING
"""
```

**Key insight:** `BarIntelligenceRecord.ranked_signals` contains the full I7 JSONB data. The `i7` column is populated from `ranked_signals` serialized to JSON — same data that was previously written via `_UPSERT_I7_SQL`. The `winner_plugin`, `winner_confidence`, `winner_direction` fields are denormalized from the winner in `BarIntelligenceRecord`.

### Pattern 2: LLMWriterService i8 UPSERT Wiring

**What:** Add third topic subscription to existing LLMWriterService consumer group; handle i8 messages with UPDATE (not INSERT) — the row already exists from FeatureWriterService atomic INSERT.

**Current:** `llm_writer` consumer group, 2 topics, `_calls_buffer` only.

**After:** Same consumer group, 3 topics, add `_i8_buffer` + `_UPSERT_I8_SQL`:
```python
_UPSERT_I8_SQL = """
UPDATE intelligence_features
SET i8 = $4::jsonb
WHERE ts = $1::timestamptz AND symbol = $2 AND tf = $3
"""
```

**Why UPDATE not INSERT ON CONFLICT:** The atomic INSERT from FeatureWriterService always writes the row first. LLMWriterService's i8 UPSERT only needs to patch the existing row. An INSERT ON CONFLICT UPDATE would create a phantom row with only i8 populated if the FeatureWriterService INSERT hasn't run yet — that violates the atomicity guarantee. A plain UPDATE that finds no row is safe (0 rows affected, no phantom).

**Timing:** AI narrative runs after I7 fires. By the time i8 arrives, the FeatureWriterService INSERT has already committed (FeatureWriterService has ~5s flush window; i8 can buffer the same way).

### Pattern 3: `_record_to_insert_params()` — New Function in FeatureWriterService

**What:** Replace `_event_to_insert_params()` with a new `_record_to_insert_params(record: BarIntelligenceRecord, expiry_map)` function.

**Why separate:** `_event_to_insert_params()` takes an `IntelligenceEvent` (18 params for I1-I6 only). The new function takes a `BarIntelligenceRecord` and produces ~29 params covering all columns including i7, winner fields, and funnel audit counts.

**Parameter extraction from BarIntelligenceRecord:**
- `intelligence` field → all I1-I6 JSONB columns (same as before)
- `ranked_signals` → serialized to JSON for `i7` column
- `winner_plugin`, `winner_confidence`, `winner_direction` → direct fields
- `signals_evaluated`, `signals_after_quality`, ..., `signals_after_calibration` → direct fields
- `ledger_written` → direct field
- `pipeline_latency_ms` → direct field from record (not recomputed)
- `i7_computed_at` → direct field
- `session_type` → direct field (denormalized from intelligence.session_type)
- `days_to_expiry` → direct field (already computed by SignalGeneratorService)

**Important:** `_parse_ts()` function in feature_writer_service is imported by llm_writer_service via `from services.feature_writer_service import _parse_ts`. This import must remain when `_event_to_insert_params` is replaced — or `_parse_ts` must be moved to a shared location. Keep it in feature_writer_service; the import is already established.

### Pattern 4: OHLCV Write in FeaturePipelineService

**What:** FeaturePipelineService queues 1m `BarMessage` to `market_data_ohlcv` via the same buffer/flush pattern used by the current FeatureWriterService.

**Spec-mandated design (from approved design spec):**
- Buffer size: 50 rows
- Flush interval: 5 seconds
- Only 1m bars written (`bar.tf == "1m"`)
- `ON CONFLICT DO NOTHING` — idempotent
- Column mapping: `(timestamp, symbol, timeframe, open, high, low, close, volume)`

**Existing table columns to verify:**
```sql
-- Check schema before writing INSERT SQL
SELECT column_name, data_type FROM information_schema.columns
WHERE table_name = 'market_data_ohlcv' ORDER BY ordinal_position;
```

**No systemd restart needed for this validation** — FeaturePipelineService is a Phase 44.1 deliverable. Phase 44.3 verifies it is wired correctly and validates live writes.

### Anti-Patterns to Avoid

- **INSERT ON CONFLICT for i8 in LLMWriterService:** Creates phantom rows with only i8 populated if FeatureWriterService hasn't flushed yet. Use plain UPDATE.
- **Reusing `_event_to_insert_params()` with a shim:** The function signature doesn't fit `BarIntelligenceRecord`. Write a clean replacement.
- **Flushing i7/i8 separately in FeatureWriterService shutdown:** These buffers no longer exist. The simplified shutdown only needs `_maybe_flush(force=True)` on the single `_buffer`.
- **Keeping `topic_intelligence_i7` and `topic_intelligence_i8` in the FeatureWriterService topic list:** These are removed. The service subscribes to `topic_intelligence_record()` only.
- **Writing HTF bars to `market_data_ohlcv`:** Spec is explicit — 1m only. Existing TimescaleDB continuous aggregate views derive HTF. Writing pre-aggregated HTF bars would interfere.

## Common Pitfalls

### Pitfall 1: asyncpg timestamptz requires Python datetime, not ISO string
**What goes wrong:** `execute_batch()` with `"2026-03-21T10:00:00+00:00"` (string) for a `timestamptz` column causes `asyncpg.InvalidTextRepresentationError`.
**Why it happens:** asyncpg does not auto-coerce strings for timestamptz in batch mode. Works for single-row inserts with `::timestamptz` cast but not batch.
**How to avoid:** Use `_parse_ts()` from feature_writer_service.py on every timestamp field before building the params tuple.
**Warning signs:** `type_mismatch` error in batch writes.

### Pitfall 2: ranked_signals JSON serialization
**What goes wrong:** `BarIntelligenceRecord.ranked_signals` is `list[RankedSignal]`. Passing it directly to asyncpg as the `i7` jsonb column fails — asyncpg needs a JSON string.
**Why it happens:** asyncpg does not auto-serialize Pydantic models.
**How to avoid:** `json.dumps([s.model_dump() for s in record.ranked_signals])` for the `i7` column.

### Pitfall 3: `session_type` column missing in current schema
**What goes wrong:** INSERT SQL includes `session_type` column; column doesn't exist yet; INSERT fails with `column "session_type" of relation "intelligence_features" does not exist`.
**Why it happens:** The design spec states "session_type already exists" but the live DB does not have it. The migration must add it.
**How to avoid:** Run migration first; verify with `SELECT column_name ...` before writing INSERT SQL.

### Pitfall 4: LLMWriterService i8 UPDATE before FeatureWriterService INSERT committed
**What goes wrong:** i8 UPDATE finds 0 rows because the FeatureWriterService batch hasn't flushed yet (up to 5s window). The UPDATE silently succeeds with 0 rows affected.
**Why it happens:** FeatureWriterService and LLMWriterService flush independently. AI narrative generation takes seconds — the timing window is real.
**How to avoid:** This is expected behavior — the UPDATE is idempotent and will succeed when retried. Do NOT convert to INSERT ON CONFLICT (that creates phantom rows). If needed, add a metric `llm_writer_i8_update_miss_total` that counts zero-rows-updated cases.
**Warning signs:** `intelligence_features.i8` columns staying as `{}` after LLM narrative fires.

### Pitfall 5: `_parse_ts` import in LLMWriterService after function rename
**What goes wrong:** LLMWriterService does `from services.feature_writer_service import _parse_ts`. If FeatureWriterService renames or removes `_parse_ts`, LLMWriterService breaks at startup.
**Why it happens:** Cross-service import on a private function.
**How to avoid:** Keep `_parse_ts` in feature_writer_service.py unchanged. If it needs to move, move it to `src/core/service_utils.py` and update both callers.

### Pitfall 6: `_buffer` retry semantics lost
**What goes wrong:** On batch write failure, current code leaves params in `self._buffer` for retry. If simplified code clears buffer on failure, events are silently dropped.
**Why it happens:** The retry-on-failure pattern is subtle — the `except` block must NOT call `self._buffer.clear()`.
**How to avoid:** Preserve the current `_maybe_flush` exception handling: on failure, log + inc error counter + leave buffer intact. Only clear on success.

### Pitfall 7: Cross-asset handler silently dropped
**What goes wrong:** Removing the `cross_asset_topic` routing from `_process_loop` kills cross-asset feature persistence.
**Why it happens:** Phase 44.3 spec says "remove i7/i8 topic subscriptions" — easy to over-apply.
**How to avoid:** Cross-asset persistence via `_process_cross_asset_message()` is in scope only if cross_asset_enabled is True; keep that routing intact. Only `intelligence`, `intelligence.i7`, `intelligence.i8` subscriptions are replaced.

### `_record_to_insert_params()` — Parameter Structure
```python
# Source: feature_writer_service.py pattern + BarIntelligenceRecord schema from design spec

def _record_to_insert_params(
    record: BarIntelligenceRecord,
    expiry_map: dict[str, date] | None = None,
) -> tuple:
    """Build INSERT params tuple from BarIntelligenceRecord.

    Column order must match _INSERT_FEATURE_SQL exactly.
    ranked_signals serialized to JSON string for i7 jsonb column.
    All timestamptz params must be Python datetime objects (asyncpg requirement).
    """
    event = record.intelligence
    days = _compute_days_to_expiry(event.symbol, event.ts, expiry_map or {})
    winner = next((s for s in record.ranked_signals if s.is_winner), None)

    return (
        event.ts,                                          # $1  ts
        event.symbol,                                      # $2  symbol
        event.tf,                                         # $3  tf
        event.platform,                                    # $4  platform
        event.source,                                      # $5  source
        event.schema_version,                             # $6  schema_version
        json.dumps(event.bar.model_dump()),               # $7  bar jsonb
        json.dumps(event.i1.model_dump()),                # $8  i1 jsonb
        json.dumps(event.i2.model_dump(exclude_none=True)),  # $9  i2
        json.dumps(event.i3.model_dump(exclude_none=True)),  # $10 i3
        json.dumps(event.i4.model_dump(exclude_none=True)),  # $11 i4
        json.dumps(event.i5.model_dump(exclude_none=True)),  # $12 i5
        json.dumps(event.smc.model_dump(exclude_none=True)), # $13 smc
        json.dumps(event.i6.model_dump(exclude_none=True)),  # $14 i6
        json.dumps([s.model_dump() for s in record.ranked_signals]),  # $15 i7
        record.winner_plugin,                              # $16 winner_plugin
        record.winner_confidence,                         # $17 winner_confidence
        record.winner_direction,                          # $18 winner_direction
        record.signals_evaluated,                         # $19
        record.signals_after_quality,                     # $20
        record.signals_after_regime,                      # $21
        record.signals_after_tod,                         # $22
        record.signals_after_calibration,                 # $23
        record.ledger_written,                            # $24
        record.pipeline_latency_ms,                       # $25
        record.i7_computed_at,                            # $26 timestamptz — must be datetime
        event.computed_at,                                # $27 computed_at
        record.session_type.value if record.session_type else None,  # $28 session_type
        days,                                             # $29 days_to_expiry
    )
```

## Open Questions

1. **`session_type` column in `intelligence_features`**
   - What we know: `days_to_expiry` exists; `session_type` does not (verified 2026-03-21)
   - What's unclear: Design spec says "session_type already exists" — this was likely a forward-looking spec statement
   - Recommendation: Add `session_type text` to the migration as the 11th new column; verify during plan 44.3-01 execution

2. **`bar_close_ts` column in new INSERT**
   - What we know: Current `_INSERT_FEATURE_SQL` includes `bar_close_ts` ($15). The new INSERT targets `BarIntelligenceRecord.intelligence.bar_close_ts`.
   - What's unclear: Whether `BarIntelligenceRecord` preserves `bar_close_ts` from `IntelligenceEvent` (the inner `intelligence` field does contain it)
   - Recommendation: Include `bar_close_ts` from `record.intelligence.bar_close_ts` in the new INSERT — same as current behavior; no regression

3. **`_decode_field()` utility in FeatureWriterService**
   - What we know: Used by `_process_i8_message()` which is being removed
   - What's unclear: Whether it's used anywhere else in the file
   - Recommendation: Check before deleting — if only used by i8 message handler, remove with it

4. **Cross-asset `_process_cross_asset_message()` long-term**
   - What we know: Phase 44.3 keeps it; it writes cross-asset features into `i7` JSONB via UPSERT merge
   - What's unclear: Once FeatureWriterService does atomic INSERT, the cross-asset UPSERT-merge into `i7` after the fact recreates the partial-write problem for cross-asset features
   - Recommendation: Flag for Phase 44.3 planner — cross-asset merging into `i7` post-insert is technically still a two-phase write, just for cross-asset only. Acceptable for Phase 44.3 (cross_asset_enabled=False by default); address in Phase 45+
