## Summary

Phase 44.2 is a clean extraction refactor with a well-specified target. The 6 `src/intelligence/stages/` service classes each follow an identical pattern: a `Stage` ABC base class provides all Kafka consumer/producer lifecycle, circuit breaker, attribution emit, and Prometheus metrics. The `process()` method on each subclass contains the actual logic — and it is already nearly pure. The logic in `process()` for all 6 stages has zero Kafka calls, zero DB calls, and no side effects beyond dict mutation. This makes extraction to pure functions straightforward.

The current `signal_generator_service.py` has already wired the DAG path: `_process_bar()` publishes each signal to `topic_quality_gated()` (Kafka hop 1 of 8), and a parallel `_consume_winner_signals()` task reads from `topic_winner()` (hop 8) to do the DB write and downstream publish. This architecture exists because the service was built before the consolidation decision. Phase 44.2 removes all of this indirection: in-process function calls replace hops 1-8, the `_dag_winner_consumer` is removed, `_consume_winner_signals()` is removed, and the 6 stage services are retired.

The primary new complexity is the `BarIntelligenceRecord` schema and the `RankedSignal` type that it contains. The design spec is complete for both. The `RankedSignal` Pydantic model must map from the current stringly-typed signal dicts that `_run_setup_plugins()` produces. The audit queue pattern is specified in the design doc and is straightforward asyncio.

**Primary recommendation:** Extract each `process()` method body directly into a pure function module; do not refactor the logic itself during this phase. Test the pure functions against the same inputs/outputs as the existing stage tests. Wire in `_process_event()` replacing `_process_bar()` for the DAG path. Delete `_dag_winner_consumer`, `_consume_winner_signals()`, and `_setup_kafka_clients()` DAG consumer wiring.

### Anti-Patterns to Avoid

- **Refactoring the logic during extraction.** The `process()` method bodies should be copied nearly verbatim into pure functions, with Kafka/service dependencies removed and state injected as arguments. Logic changes belong in a separate phase.
- **Injecting `self` into pipeline functions.** Pure functions must receive all state as arguments. Functions that close over `self` fields are not pure and cannot be independently unit-tested.
- **Moving `_select_winner_for_bar()` logic without preserving CIS scorer.** The `WinnerSelectorService._select_winner_for_bar()` method uses `CISScorer` — this must be preserved in `select_winner()`. The `CISScorer` instance is passed as an argument (or its result is pre-computed before `select_winner` is called).
- **Creating new Kafka topics for the audit.** The 6 `pipeline.*` topic functions already exist in `stream_keys.py`. Use them.
- **Removing the `_signal_gate` / `_setup_cooldown` logic.** This currently lives in `_process_bar()` and runs BEFORE the signals are published to the DAG. In the new architecture, it runs before the in-process pipeline calls. Do not conflate it with `select_winner()`.

## Common Pitfalls

### Pitfall 1: `_THRESHOLDS` argument to `apply_quality_gate()`

**What goes wrong:** `QualityGateService.process()` reads `hurst_trend_quality`, `entropy_quality`, and `drift_penalty` directly from `event.features`. In the pure function version, these fields come from the signal dicts (they were injected by `_process_bar()` via `_dag_meta`). The pure function signature needs to accept the relevant multipliers extracted from the event, NOT re-read from features.

**Root cause:** The current DAG path packages `drift_penalty` and `regime_data` into the Kafka message as extra fields in `_dag_meta`. In the in-process version, these values are passed as explicit arguments.

**How to avoid:** The thresholds argument to `apply_quality_gate()` should be a dict extracted from the IntelligenceEvent before calling the function. The function signature in the design doc is `apply_quality_gate(signals, thresholds)` where `thresholds` is `{"hurst_quality": float, "entropy_quality": float, "drift_penalty": float}` extracted from `event.i4` or `event.i1`.

**Check:** `QualityGateService.process()` reads `features.get("hurst_trend_quality")` — the `hurst_trend_quality` field lives in `I4Context` (field `hurst_trend_quality` present in `I4Context` model). Verify this before hardcoding the extraction path.

### Pitfall 2: `select_winner()` is not stateless — it requires CIS scorer

**What goes wrong:** `WinnerSelectorService` owns a `CISScorer` instance and a per-bar buffer `_bar_buffer`. The buffer was needed because the DAG receives signals one-at-a-time across Kafka. In the in-process version, all ranked signals for a bar are available at once.

**Root cause:** The `_bar_buffer` pattern was a Kafka workaround. In-process, `select_winner(ranked: list[RankedSignal])` receives all signals simultaneously.

**How to avoid:** `select_winner()` takes `ranked: list[RankedSignal]` and a `cis_scorer: CISScorer` argument. No buffer needed. The `CISScorer` instance is stored on `SignalGeneratorService` (already exists as `self._cis_scorer`).

### Pitfall 3: `regime_ctx` argument to `apply_regime_gate()` vs. slow-clock authority TF

**What goes wrong:** `signal_generator_service.py` uses `_REGIME_AUTHORITY_TF` to look up the higher-TF regime from `_regime_cache`. This means the regime context used for gating is NOT from `event.i3` directly — it is from a different timeframe's cached event.

**Root cause:** 1m signals gate on 5m HMM, 5m signals gate on 15m HMM. The `_regime_cache` stores all timeframes per symbol. This logic must be preserved in the pure function call, not lost.

**How to avoid:** The service extracts `regime_data = self._regime_cache.get(symbol, {}).get(authority_tf)` before calling `apply_regime_gate()`. The pure function receives this pre-extracted dict, not `event.i3` directly. The spec's `apply_regime_gate(signals, regime_ctx)` signature is correct — `regime_ctx` is the authority-TF regime data, not the bar's native TF regime.

**Verified in:** `signal_generator_service.py` lines 1086-1088.

### Pitfall 4: `RankedSignal` vs. existing signal dicts — field name mapping

**What goes wrong:** The current signal dicts use `setup_plugin` as the plugin name field. `RankedSignal` uses `plugin`. The `confidence` field in signal dicts is the post-all-stages confidence. `raw_confidence` in `RankedSignal` is the pre-quality-gate confidence.

**Root cause:** Schema evolution — the `RankedSignal` model is new and uses cleaner field names.

**How to avoid:** When constructing `RankedSignal` from the calibrated signal dict:
- `plugin = sig["setup_plugin"]`
- `raw_confidence = sig["confidence"]` (captured before quality gate runs)
- `calibrated_confidence = sig["confidence"]` (after all stages run)
- `quality_score` = computed from `min(hurst_quality, entropy_quality) * drift_penalty`
- `tod_multiplier` = from `sig.get("tod_multiplier", 1.0)` (already injected in TOD step)
- Capture `raw_confidence` from signals BEFORE the pipeline runs.

### Pitfall 5: Prometheus duplicate registration on `start_metrics_server` port reuse

**What goes wrong:** `signal_generator_service.py` calls `start_metrics_server(port=9112)`. Adding new counters that are already registered (e.g., if tests run multiple times or service restarts quickly) raises `ValueError: Duplicated timeseries`.

**Root cause:** `prometheus_client` raises on duplicate metric names. Stage services used `Counter(f"stage_{stage_name}_events_consumed_total", ...)` with label names registered once at class instantiation. When service restarts, these names collide.

**How to avoid:** Use `src/observability/metrics.py` `counter()` helper for unlabeled metrics. For labeled metrics (required by the spec's `{stage}` label), use raw `prometheus_client.Counter` but wrap in a try/except or use `REGISTRY.unregister()` in tests. The existing `SIGNAL_VALIDATION_FAILURES` counter in `signal_generator_service.py` is the correct pattern to follow — it uses raw `prometheus_client.Counter` with labels, declared at module level so it's created once.

**Verified in:** `signal_generator_service.py` lines 89-94 — `SIGNAL_VALIDATION_FAILURES` is a module-level labeled Counter. New pipeline stage counters must follow this pattern.

### Pitfall 6: `_consume_winner_signals()` removal leaves gate logic disconnected

**What goes wrong:** `_check_gate()` and `_update_gate()` currently run in `_consume_winner_signals()`. After removal, gate logic must move to `_process_event()` in the in-process path, or signals will fire without cooldown enforcement.

**Root cause:** Gate logic lives in the winner consumer (downstream of Kafka), not in `_process_bar()` (upstream). In the in-process architecture, there is no downstream consumer — the gate must move upstream.

**How to avoid:** In the new `_process_event()`:
1. Run I7 plugins
2. Run `_filter_setup_cooldown()` (already in `_process_bar()`)
3. Run in-process pipeline stages
4. Run `_check_gate()` on the winner's direction (moved from `_consume_winner_signals()`)
5. Write ledger + publish (moved from `_consume_winner_signals()`)
6. Run `_update_gate()` on success (moved from `_consume_winner_signals()`)

### Pitfall 7: `days_to_expiry` in `BarIntelligenceRecord` — not available without 44.1

**What goes wrong:** `BarIntelligenceRecord` spec includes `days_to_expiry: int | None` "computed by FeaturePipelineService from expiry map". FeaturePipelineService does not exist until Phase 44.1.

**Root cause:** Phase 44.2 publishes `BarIntelligenceRecord` but runs before Phase 44.1 ships FeaturePipelineService.

**How to avoid:** `days_to_expiry` defaults to `None` in Phase 44.2. The expiry map computation is Phase 44.1 scope. `BarIntelligenceRecord` field definition: `days_to_expiry: int | None = None`. `FeatureWriterService` (Phase 44.3) consumes this field — `None` is acceptable until Phase 44.1 populates it.

## Code Examples

### Pure Function: apply_quality_gate

Extracted from `QualityGateService.process()` — Kafka/attribution removed, state injected:

```python
# src/intelligence/pipeline/quality_gate.py

def apply_quality_gate(
    signals: list[dict],
    thresholds: dict,           # {"hurst_quality": float, "entropy_quality": float, "drift_penalty": float}
) -> list[dict]:
    """Apply Hurst*Entropy quality multiplier and KS drift penalty to signal confidence.

    Reads multipliers from thresholds dict (pre-extracted from IntelligenceEvent by caller).
    Mutates copies — never mutates input dicts.
    Returns all signals with updated confidence (does not drop signals).
    """
    hurst_quality = float(thresholds.get("hurst_quality", 1.0))
    entropy_quality = float(thresholds.get("entropy_quality", 1.0))
    drift_penalty = float(thresholds.get("drift_penalty", 1.0))
    quality_multiplier = min(hurst_quality, entropy_quality)

    result = []
    for sig in signals:
        s = dict(sig)
        before = float(s.get("confidence", 0.0))
        after = round(before * quality_multiplier * drift_penalty, 4)
        s["confidence"] = after
        s["quality_score"] = round(quality_multiplier * drift_penalty, 4)
        result.append(s)
    return result
```

### Pure Function: apply_regime_gate

```python
# src/intelligence/pipeline/regime_gate.py

_REGIME_MAP: dict[str, list[int]] = {
    "trend": [1, 2],
    "mean_reversion": [0],
    "any": [0, 1, 2],
}
_REGIME_PROB_MIN = 0.55
_REGIME_DUR_MIN = 3

def apply_regime_gate(
    signals: list[dict],
    regime_data: dict | None,   # pre-extracted from _regime_cache[symbol][authority_tf]
) -> list[dict]:
    """Mark signals as regime_eligible=True/False. Does not drop — all signals returned."""
    if regime_data is None:
        return [{**s, "regime_eligible": True} for s in signals]

    hmm_regime = regime_data.get("hmm_regime")
    hmm_prob = float(regime_data.get("hmm_regime_prob", 0.0))
    hmm_dur = int(regime_data.get("hmm_regime_duration", 0))

    result = []
    for sig in signals:
        plugin_regime = sig.get("regime_type", "any")
        allowed = _REGIME_MAP.get(plugin_regime, [0, 1, 2])

        eligible = True
        reason = None
        if hmm_prob < _REGIME_PROB_MIN:
            eligible, reason = False, "regime_prob"
        elif hmm_dur < _REGIME_DUR_MIN:
            eligible, reason = False, "regime_duration"
        elif hmm_regime is not None and int(hmm_regime) not in allowed:
            eligible, reason = False, "regime_type"

        s = dict(sig)
        s["regime_eligible"] = eligible
        s["suppression_reason"] = reason
        result.append(s)
    return result
```

### Audit Queue Pattern

```python
# In SignalGeneratorService.__init__:
self._audit_queue: asyncio.Queue = asyncio.Queue(maxsize=1000)
self._audit_drops_total = counter(
    "signal_generator_audit_queue_drops_total",
    "Audit queue overflow drops — non-zero indicates backpressure",
)
# NOTE: use module-level raw Counter for labeled metrics:
# _PIPELINE_STAGE_INPUT = Counter("signal_generator_pipeline_stage_input_total", ..., ["stage"])

async def _queue_stage_audits(self, payloads: list[dict]) -> None:
    for p in payloads:
        try:
            self._audit_queue.put_nowait(p)
        except asyncio.QueueFull:
            self._audit_drops_total.inc()   # never silent

async def _drain_audit_queue(self) -> None:
    while not self.shutdown_requested:
        try:
            payload = await asyncio.wait_for(
                self._audit_queue.get(), timeout=1.0
            )
            await self._kafka_producer.publish(payload["topic"], payload["data"])
        except TimeoutError:
            continue
        except asyncio.CancelledError:
            break
        except Exception as e:
            self.logger.warning("audit_drain_error", error=str(e))
```

## Stage Logic Inventory

A precise audit of what each `process()` method does — critical for the pure function extraction.

### QualityGateService.process() → apply_quality_gate()

**Logic:** `min(hurst_trend_quality, entropy_quality)` × `drift_penalty` applied to `confidence`.
**Inputs from event.features:** `hurst_trend_quality` (float, default 1.0), `entropy_quality` (float, default 1.0), `drift_penalty` (float, default 1.0).
**State:** None — fully stateless.
**Output fields added:** `confidence` (updated), `attribution_reason`, `attribution_inputs`.
**Notes:** `hurst_trend_quality` lives in `I4Context`; `entropy_quality` lives in `I4Context`; `drift_penalty` was injected by `signal_generator_service.py` into `_dag_meta`. In the in-process version, these are extracted from the IntelligenceEvent before calling the function.

### RegimeGateService.process() → apply_regime_gate()

**Logic:** Three-tier gate: `hmm_regime_prob < 0.55` → suppress; `hmm_regime_duration < 3` → suppress; `hmm_regime not in allowed_regimes` → suppress.
**State:** None — reads from `event.features["regime_data"]` (injected by `_dag_meta`). In-process: passed as `regime_data` argument from `self._regime_cache`.
**Output fields added:** `regime_eligible` (bool), `suppression_reason` (str | None).
**Notes:** Does not drop signals — sets `regime_eligible=False` but keeps signal in list.

### TODAdjusterService.process() → apply_tod_adjustment()

**Logic:** Lookup `(regime_type_at_fire, tf, hour_et)` in `self.tod_multipliers`. Fallback to `_TOD_SESSION_PRIORS`. Clamp to `[0.7, 1.3]`. Multiply `confidence`.
**State:** `self.tod_multipliers` dict (loaded from DB). In-process: passed as `tod_table` argument from `self._tod_multipliers`.
**Input:** `regime_type` from signal dict, `tf` from event, `hour_et` from `timestamp.astimezone(_ET).hour`.
**Output fields added:** `confidence` (updated), `tod_multiplier` (float), `attribution_reason`, `attribution_inputs`.
**Notes:** `_TOD_SESSION_PRIORS` constants are duplicated in both `tod_adjuster.py` and `signal_generator_service.py` — the in-process version already has them. The pipeline module should import from a single location.

### CalibratorService.process() → apply_calibration()

**Logic:** `np.interp(raw_confidence, breakpoints, values)` using isotonic curve for `(plugin_name, tf)`. Passthrough when no curve.
**State:** `self.calibration_curves` dict. In-process: passed as `cal_model` argument from `self._calibration_curves`.
**Input:** `raw_confidence` = current `confidence` from signal dict, `plugin_name` from `setup_plugin` field, `tf` from event.
**Output fields added:** `confidence` (updated to calibrated), `calibrated_confidence`.
**Notes:** `np.interp` expects `np.ndarray`; service stores `(list[float], list[float])` but `signal_generator_service.py` stores `(np.ndarray, np.ndarray)` (pre-converted in Phase 43 PERF-04). The in-process version uses the already-ndarray format.

### RankerService.process() → rank_signals()

**Logic:** `adjusted_rank = SETUP_PRIORITY.get(plugin_name, 999) * perf_multiplier`.
**State:** `self.perf_weights` dict. In-process: passed as argument from `self._perf_weights`.
**Output fields added:** `adjusted_rank`, `perf_multiplier`.
**Notes:** Imports `SETUP_PRIORITY` from `src/intelligence/trading/aggregator.py` — this import is preserved in the pipeline module.

### WinnerSelectorService._select_winner_for_bar() → select_winner()

**Logic:** CIS override path (matching direction, boost by `_CONFIDENCE_BOOST_PER_AGREE * extra_agreeing`) OR fallback (majority direction + `adjusted_rank` sort). Separates `regime_eligible=True` signals.
**State:** `self._cis_scorer` (CISScorer instance). In-process: `CISScorer` passed as argument or pre-scored.
**Input:** `signals: list[dict]` where all have `regime_eligible`, `adjusted_rank`, `direction`, `confidence`, `setup_plugin`.
**Output:** `(RankedSignal | None, list[RankedSignal])` — winner + all ranked.
**Notes:** The `_bar_buffer` pattern is eliminated — all signals for a bar arrive at once in the in-process version.

## State of the Art

| Old Approach | Current Approach | Impact |
|--------------|------------------|--------|
| 6 separate Kafka hops for pipeline stages | In-process pure function calls | Eliminates ~6 ms of serialization/deserialization latency per bar |
| Per-stage circuit breaker + bypass logic | Caller handles exception; pipeline continues | Simpler failure mode; less state to track |
| Attribution via Kafka side-channel | Audit queue → same Kafka side-channel | Observability preserved; hot path not blocked |
| `_bar_buffer` in WinnerSelector (Kafka timing workaround) | All signals available at once; no buffer needed | Eliminates a class of race condition |
