# Phase 39.1 Plan 05: SignalOutcome Enum — Summary

## One-Liner

Created type-safe `SignalOutcome` str enum with 8 outcome classes for ML training labels, enforced at DB level via CHECK constraint.

## Implementation Summary

### Objective
Replace all raw outcome string literals with a type-safe `SignalOutcome` enum, eliminating typo risk for ML training labels and enabling DB-level enforcement.

### What Was Built

**1. SignalOutcome Enum (`src/intelligence/trading/signal_outcome.py`)**
- 8 outcome classes: `NEVER_ACTIVATED`, `STOPPED_AT_ENTRY`, `STOPPED_IN_TRADE`, `TARGET_1`, `TARGET_1_2`, `TARGET_FULL`, `TTL_EXPIRED_AHEAD`, `TTL_EXPIRED_BEHIND`
- Extends `str` for DB compatibility (asyncpg accepts enum values directly)
- Taxonomy frozensets: `WIN_OUTCOMES`, `STOP_OUTCOMES`, `TTL_OUTCOMES`
- Single source of truth for outcome classification

**2. File Migrations**
- **signal_ledger.py**: Imports from `signal_outcome.py`, re-exports for backward compatibility
- **lifecycle_tracker.py**: Returns `SignalOutcome` enum members in all outcome-returning functions
- **signal_lifecycle_service.py**: Uses enum in shadow outcome tracking

**3. DB Enforcement (`040_signal_ledger_outcome_check_constraint.sql`)**
- CHECK constraint permits `NULL` or 8 valid outcome values
- Blocks invalid outcomes at DB level (e.g., typos in ML labels)
- Verified no existing rows violate constraint before applying

**4. Unit Tests (`tests/unit/intelligence/test_signal_outcome.py`)**
- 9 tests covering enum size, value correctness, taxonomy sets, exhaustiveness
- Verifies str compatibility (DB writes), backward compatibility, immutability
- All tests pass

### Deviations from Plan

**None** — plan executed exactly as written.

## Key Decisions

### 1. SignalOutcome Extends str (Not Pure Enum)
**Decision**: Make `SignalOutcome(str, Enum)` instead of pure `Enum`

**Rationale**:
- asyncpg and other DB libraries expect `str` values, not `Enum` objects
- No DB migration needed — enum values match existing DB strings exactly
- Backward compatible with all existing code that expects strings

**Trade-off**: Slightly less type-safe than pure `Enum`, but enables zero-downtime deployment

### 2. Re-Export Pattern for Backward Compatibility
**Decision**: Import `WIN_OUTCOMES` from `signal_outcome.py` in `signal_ledger.py` and re-export it

**Rationale**:
- Existing code imports `WIN_OUTCOMES` from `signal_ledger` (e.g., `confidence_calibrator.py`, API routes)
- Re-export preserves backward compatibility without touching those files
- Single import statement vs. updating 10+ files

**Trade-off**: Extra indirection layer, but reduces churn and risk

### 3. DB CHECK Constraint Permits NULL
**Decision**: `CHECK (outcome IS NULL OR outcome IN (...))`

**Rationale**:
- `outcome` column is `NULL` until signal exits (signals can stay active for days)
- Constraint must allow `NULL` for active/pending signals
- Enforces validity only when outcome is set

**Trade-off**: Constraint doesn't catch missing outcome updates, but that's intentional (outcome is optional until exit)

### 4. Chandelier Stop Uses STOPPED_IN_TRADE Placeholder
**Decision**: Hardcode `SignalOutcome.STOPPED_IN_TRADE` in Chandelier stop logic

**Rationale**:
- `lifecycle_tracker.py` doesn't have `bars_in_trade` context needed to distinguish `stopped_at_entry` vs. `stopped_in_trade`
- Service layer (`signal_lifecycle_service.py`) reclassifies stops using `_classify_stop_outcome()`
- Placeholder is correct for 95% of cases (stopped after activation)

**Trade-off**: Minor inefficiency (reclassification), but keeps `lifecycle_tracker` pure and stateless
