# Phase 39.1: Intelligence Layer Enforcement - Context

**Gathered:** 2026-03-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Code quality enforcement work only — no new features, no behavioral changes. Four enforcement areas:

1. **Protocol enforcement** — `PatternPlugin` Protocol requires `regime_type: ClassVar[str]` field; `validate_tier()` checks value is `"trend"`, `"mean_reversion"`, or `"any"`; service startup crashes on invalid values
2. **Enum migration** — Replace all raw signal status string literals (`"pending"`, `"active"`, `"regime_suppressed"`) with `SignalStatus` enum across 6 files
3. **Naming enforcement** — Shell-based pre-commit hooks validate plugin class names end in `Plugin` suffix and plugin files use `snake_case.py`
4. **Documentation** — Consolidate gotchas, conventions, enforcement gaps, and checklists into `docs/analysis/intelligence-workflow-audit.md`

</domain>

<decisions>
## Implementation Decisions

### Philosophy
- **Renaissance-grade enforcement** — Never drop data quality standards. Fail fast on violations. Catch cascading failures at the earliest gate.
- **Institutional grade** — Everything instrumented, observable, and tracked. Technical debt is measured, not ignored.
- **Strict blocking** — All checks block commits. No warn-only bypasses. If a check isn't worth blocking, it shouldn't exist.

### Pre-commit Hook Implementation
- **Tool**: Shell-based hooks in `.git/hooks/pre-commit` (not pre-commit.com framework — avoid external dependency, simpler infrastructure)
- **Blocking**: All hooks exit non-zero on violation; commit is blocked
- **Parallel execution**: Run independent checks in parallel for speed (plugin naming, file naming, imports can run simultaneously)
- **Error messages**: Human-readable, show exact violation + file:line + remediation command
- **Logging**: Hook runs log to `.git/hooks/pre-commit.log` with timestamp, check name, result, duration

### Pre-commit Checks (Phase 39.1 Scope)
1. **Plugin naming check** — Plugin class names must end with `Plugin` suffix (e.g., `MACDPlugin`, not `MACD` or `MACDIndicator`)
   - Scope: All files in `src/intelligence/indicators/`, `src/intelligence/patterns/`, `src/intelligence/context/`, `src/intelligence/trading/`
   - Enforcement: `grep` for `^class [A-Z].*(?!Plugin)\(`; fail if matches found

2. **File naming check** — Plugin files must use `snake_case.py` (e.g., `bollinger_bands.py`, not `BollingerBands.py`)
   - Scope: All files in `src/intelligence/` subdirectories
   - Enforcement: Check filename against regex `^[a-z][a-z0-9_]*\.py$`; fail if not matching

3. **regime_type check** — I7 plugins must declare `regime_type: ClassVar[str]` with valid value
   - Scope: All files in `src/intelligence/trading/` (I7 plugins)
   - Enforcement: Parse AST, check for `regime_type` ClassVar with value in `["trend", "mean_reversion", "any"]`

4. **Dead import check** — All imports must be used; no dead code allowed
   - Scope: All Python files in commit
   - Enforcement: `ruff check --select F401` (unused-import); fail if any violations

### Future Renaissance-Grade Checks (Phase 40+)
Not in Phase 39.1 scope, but documented for future enforcement:
- **Type safety** — `mypy --strict` or `pyright` (catches type drift before runtime)
- **Test coverage gate** — Require tests for new plugin code (minimum coverage threshold)
- **Secret scanning** — Block commits with API keys/credentials (bandit or truffleHog)
- **Documentation** — Require docstrings on public plugin APIs
- **Complexity limits** — Fail on cyclomatic complexity > threshold (prevents unmaintainable functions)

### Enforcement Style
- **Strict blocking** — All checks block commits. No exceptions, no warn-only mode.
- **No bypass mechanism** — If a check is wrong, fix the check before committing. Prevents "just this once" technical debt accumulation.
- **Fast feedback** — Hooks run in < 2 seconds total. Parallel execution + targeted grep/AST parsing.
- **Observable failures** — Every violation logs to `.git/hooks/pre-commit.log` with timestamp, file, line, remediation hint.

### SignalStatus Enum Migration
- **Co-located with LedgerEntry** — Define `SignalStatus` in `src/intelligence/trading/signal_ledger.py`
- **String-compatible values** — Enum extends `str` so `.value` matches existing DB values (no migration needed)
- **Exhaustiveness checking** — All `if/elif` chains on `SignalStatus` use `assert_never()` in else branch (Python type checker catches unhandled cases)
- **Migration scope** — 6 files: `signal_ledger.py`, `lifecycle_tracker.py`, `signal_generator_service.py`, `signal_lifecycle_service.py` (×2), `src/api/routes/signals.py` (×2)
- **Verification gate** — `grep -r '"pending"\|"active"\|"regime_suppressed"' services/ src/` returns zero results after migration

### Documentation: intelligence-workflow-audit.md
**Purpose**: Single source of truth for intelligence layer conventions, gotchas, and enforcement gaps. Everything that caused past failures is documented here.

**Structure**:
1. **Naming conventions** — Plugin class names (`PascalCasePlugin`), file names (`snake_case.py`), service names (`snake_case_service.py`), constants (`UPPER_SNAKE_CASE`), topics (`development.name` not `dev:name`), DB tables/columns (`snake_case`)
   - For each: pattern, why it matters, examples of correct usage, common violations

2. **Gotchas catalog** — All gotchas from `CLAUDE.md` §TimescaleDB Gotchas and §Key Rules:
   - `ts` vs `feature_ts` in `intelligence_features`
   - `dev.*` vs `development.*` topic prefixes
   - `market_data_ohlcv` is backfill-only (live data never touches it)
   - Hypertable parent `pg_class` size is near-zero (use `hypertable_size()`)
   - `pg_stat_user_indexes.idx_scan` always 0 on hypertables
   - Autovacuum on hypertables (chunk iteration required)
   - `docker exec ... -f /dev/stdin` does NOT work (use `docker cp` then execute)
   - `instruments.symbol` is base symbol; contract code is in JSONB `symbol` key
   - `instruments.contract_details` is stored as JSON string, not object
   - Boolean serialization (`"1"`/`"0"` vs `true`/`false`)
   - `service test __new__ pattern` for instance attributes
   - `signal_id` UUID threading through pipeline
   - `aggregator active` from `all_ranked` not raw `signals`
   - `Chandelier trailing stop` monotonic tightening
   - `regime_type` on I7 plugins (this phase adds Protocol enforcement)
   - Signal status strings (this phase replaces with enum)

3. **Enforcement gaps** — What's NOT validated today, where manual review is required:
   - No runtime check for `regime_type` values before Protocol enforcement (Phase 39.1 fixes)
   - No pre-commit hooks before Phase 39.1 (this phase adds them)
   - Signal status strings not type-checked before Phase 39.1
   - Plugin file naming not enforced before Phase 39.1
   - Dead imports not caught before Phase 39.1
   - Type safety (mypy/pyright) not enforced yet
   - Test coverage not gated yet

4. **Plugin checklist** — For new I7 plugins, required fields/registration/tests:
   - Class extends PatternPlugin Protocol
   - Declares `regime_type: ClassVar[str]` with value in `["trend", "mean_reversion", "any"]`
   - File uses `snake_case.py` naming
   - Class name uses `PascalCasePlugin` naming
   - Registered in `TIER_I7` in `register_plugins.py`
   - Added to appropriate setup list (`TREND_SETUPS`, `MEAN_REVERSION_SETUPS`, or both)
   - Unit tests cover: `compute_full` returns expected output, `regime_type` is correct
   - Integration test: plugin fires in replay over 1-week window on ES/NQ 1m
   - Documentation: class docstring explains setup logic, parameters, edge cases

5. **Compliance metrics** — Observability into enforcement effectiveness:
   - Pre-commit hook pass/fail rate per check type (last 7 days, last 30 days)
   - Most common violations by type (naming, imports, regime_type)
   - Hook execution time metrics (p50, p95, p99 latency per check)
   - Trend: violations decreasing over time = checks working

6. **Exception log** — When enforcement was bypassed, why, who approved, repayment plan:
   - (Initially empty — strict blocking means no exceptions. This section exists for future transparency if policy changes.)

7. **Technical debt ledger** — Track shortcuts as debt with interest:
   - (Initially empty — Renaissance-grade enforcement means no shortcuts. This section exists for future tracking if needed.)

8. **Check performance** — Hook timing and optimization:
   - Target: All hooks complete in < 2 seconds on typical commit (3-5 files changed)
   - Parallelization strategy: which checks can run simultaneously
   - Optimization opportunities if target exceeded (e.g., cache AST parse results)

9. **Feedback loop** — How checks evolve based on effectiveness:
   - Review cycle: Monthly — do checks catch real bugs? Are they too noisy?
   - False positive tracking: violations that were overridden (future, if override mechanism added)
   - Check retirement: Remove checks that never fail (not adding value)
   - Check addition: New checks based on recurring issues found in production
