# Phase 39.1 Plan 02: SignalStatus Enum Migration Summary

**One-liner:** Replaced all raw signal status string literals with a type-safe `SignalStatus(str, Enum)` across 4 files — zero DB migration required.

## What Was Built

### SignalStatus Enum (signal_ledger.py)

```python
class SignalStatus(str, Enum):
    """Signal lifecycle status — matches database values for zero-migration compatibility."""
    PENDING = "pending"
    ACTIVE = "active"
    REGIME_SUPPRESSED = "regime_suppressed"
```

Enum extends `str` so all DB comparisons and asyncpg writes continue working unchanged.

### LedgerEntry.status Type Change

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Pre-commit hook false positive on ruff "All checks passed!" message**
- **Found during:** Task 2 commit attempt
- **Issue:** The pre-commit hook ran `VIOLATIONS=$(ruff check ...)` and tested `[ -n "$VIOLATIONS" ]`. When ruff finds no issues it still prints "All checks passed!" to stdout — a non-empty string — triggering a false FAILED result. Every subsequent commit was blocked.
- **Fix:** Updated hook to use ruff exit code (`RUFF_EXIT=$?`) rather than stdout content to determine pass/fail; "All checks passed!" message is now filtered from display output
- **Files modified:** `.git/hooks/pre-commit`
- **Commit:** 0de89ab (included with Task 2 commit)

## Decisions Made

1. **SignalStatus extends str** — allows `SignalStatus.ACTIVE == "active"` to be True, which means DB-returned raw strings from asyncpg continue working in comparisons without any code changes to callers that receive raw strings.

2. **Use `.value` for dict/DB writes** — dict assignments like `{"status": SignalStatus.ACTIVE.value}` use `.value` to ensure clean string output when the callee expects a plain `str`. In-memory comparisons use the enum directly.

3. **No migration needed** — enum values are identical to the DB string values that already exist. The `signal_ledger` table continues to store "pending", "active", "regime_suppressed" as TEXT — no schema change.
