# Phase 49.1: Regime Gate Fix — Write All Signals to Signal Ledger - Research

**Researched:** 2026-03-23
**Domain:** signal_generator_service.py — decoupling DB persist from winner selection
**Confidence:** HIGH

## Summary

This phase fixes a data collection bug: the `signal_ledger` DB INSERT is gated inside
`if winner:` in `_process_event()`, which means every bar where all signals are
regime-suppressed produces zero rows in `signal_ledger`. The fix is surgical — move
the entries-building loop and DB INSERT to run unconditionally whenever `all_ranked`
is non-empty, and populate `regime_type_at_fire` from `regime_data.hmm_regime` using
a new module-level mapping constant.

The CONTEXT.md decisions are sound and have been verified against the actual code.
Only one discrepancy was found: the current entries loop does NOT populate several
calibration-related LedgerEntry fields (`raw_cis_score`, `filtered_cis_score`,
`calibrated_confidence`, `hmm_regime_at_fire`, `cis_score`, `regime_type_at_fire`).
These are all NULL in current rows even when a winner exists — they were never wired.
This phase should populate `regime_type_at_fire` and `hmm_regime_at_fire` from
`regime_data` since that data is available. The others (`raw_cis_score`,
`filtered_cis_score`, `calibrated_confidence`) require signal-level data from the
pipeline stages that is not currently threaded into the entries loop — those remain
NULL and are out of scope per CONTEXT.md D-04.

**Primary recommendation:** The code change is structurally straightforward. Extract
the entries-building loop from inside the `else:` branch of `if self._check_gate()`
(which is inside `if winner:`), move it to run whenever `all_ranked` is non-empty,
add `_HMM_REGIME_LABEL` mapping, populate `regime_type_at_fire` and
`hmm_regime_at_fire` per signal, keep Kafka publish + `_update_gate()` inside
`if winner:`, and update `ledger_written = True` whenever the DB INSERT succeeds.

### Three Scenarios That Cause Data Loss (VERIFIED)

1. **`winner is None` (all signals regime-suppressed):** `all_ranked` is populated
   (L1255), but `if winner:` is False so the entries loop never runs. Zero rows written.

2. **`self._check_gate()` returns True (cooldown/direction flip):** Winner exists but
   the gate suppresses it. `winner = None` is set (L1291). Entries loop never runs.
   Zero rows written.

3. **Kafka publish fails:** Entries ARE built and DB INSERT runs (since DB INSERT is
   after publish at L1413), but `_update_gate()` is skipped. This path already works
   correctly — NOT a data loss scenario.

### What `all_ranked` Contains (VERIFIED)

`select_winner()` at L1255 returns `(winner, signals, resolution_method)` where
`signals` is the full input — all signals post-ranking, including regime-suppressed
ones. Each signal dict has:
- `regime_eligible: bool` — set by `apply_regime_gate()`
- `suppression_reason: str | None` — "regime_prob" | "regime_duration" | "regime_type" | None
- `calibrated_confidence: float` — set by `apply_calibration()`
- `adjusted_rank: float` — set by `rank_signals()`
- `setup_plugin`, `signal_type`, `direction`, `entry_price`, `stop_loss`, `targets`,
  `confidence`, `confluence_score`, `regime_context`, `supporting_factors` — from I7 plugin

When `active = []` (all suppressed), `select_winner()` returns `(None, signals, "no_signal")`.
When `active != []` but gate fires, `select_winner()` has already returned a winner —
the gate check at L1283 happens AFTER `select_winner()`.

### `_check_gate()` Interaction (VERIFIED)

The gate check at L1283 is inside `if winner:`. When `winner is None` (all signals
suppressed), the gate is never consulted — the entries loop should still run.

When `winner is not None` but the gate fires (cooldown), `winner = None` is set at L1291.
The entries loop must still run in this case. This is scenario 2 above — currently causes
data loss when a gate fires.

The fix structure is:

```python
# Stage 6: Winner selection — unchanged
winner, all_ranked, resolution_method = select_winner(...)

# NEW: Stage 6a — Persist all ranked signals (unconditional)
# runs whenever all_ranked is non-empty, BEFORE gate check
entries = _build_entries(all_ranked, ..., regime_data)
if entries and self.db_manager:
    await insert_signals_with_features(...)
    ledger_written = True

# Stage 6b: Winner execution — unchanged logic
if winner:
    if self._check_gate(...):
        winner = None
    else:
        # Kafka publish
        # _update_gate()
```

Wait — there is a subtlety here. The current code sets `_winner_signal_id` on the winner
dict before building entries (L1294–1296), and uses `_winner_signal_id` to identify which
entry has `was_selected=True` (L1300–1304). After the refactor, `_winner_signal_id` must
still be assigned before building entries if `winner` is non-None, so entries can correctly
set `was_selected`.

**Correct order for refactored code:**

```python
# Assign winner signal_id BEFORE building entries (needed for was_selected)
_winner_signal_id = ""
if winner:
    _winner_direction = int(winner.get("direction", 0))
    if self._check_gate(...):
        winner = None  # gate suppresses — entries still build, winner=None
    else:
        _winner_signal_id = str(winner.get("signal_id", "") or uuid4())
        winner["signal_id"] = _winner_signal_id

# Stage 6a: Build + persist entries (unconditional on all_ranked)
if all_ranked:
    entries = _build_entries(all_ranked, _winner_signal_id, ...)
    if entries and self.db_manager:
        await insert_signals_with_features(...)
        ledger_written = True

# Stage 6b: Kafka publish (only if winner passed gate)
if winner:
    # ... publish to signals + signals.aggregated ...
    # ... _update_gate() ...
```

**`was_selected` for gate-suppressed winner:** When gate fires (`_check_gate=True`),
`winner = None` and `_winner_signal_id = ""`. The signal that would have been selected
has `was_selected=False` in the ledger. This is the correct behavior — the gate suppressed
this winner so it was not actually selected for execution.

## Architecture Patterns

### `_build_entries()` Helper: Extract vs Inline

The current entries loop spans ~50 lines (L1297–1344). It is currently inlined inside
two levels of `if` nesting. After the refactor it moves out one level. Whether to extract
to a helper (`_build_entries()`) depends on readability.

**Recommendation (Claude's discretion per CONTEXT.md):** Extract to a module-level
helper function. The entries loop is pure (no side effects, no `self.*` calls except
`registry.patterns.get()`). Extracting makes it independently testable and aligns with
the pattern of other pure pipeline stages (`apply_regime_gate`, `select_winner`). The
IS_SHADOW flag check (L1347–1352) should be included in the helper or applied immediately
after.

**Function signature:**
```python
def _build_entries(
    all_ranked: list[dict],
    winner_signal_id: str,
    *,
    timestamp: datetime,
    symbol: str,
    timeframe: str,
    signal_computed_at: datetime,
    resolution_method: str,
    regime_data: dict | None,

```

**`_HMM_REGIME_LABEL` constant placement:** Module-level constant next to `_REGIME_MAP`
import or at the top of the file with other module-level constants. Must be defined before
`_build_entries()`.

### Preserve: Shadow Mode Flag (IS_SHADOW)

Lines 1347–1352 apply `IS_SHADOW` per-plugin. This must still run after entries are built,
regardless of winner. The refactor must include this block either inside `_build_entries()`
or immediately after the helper call.

## Common Pitfalls

### Pitfall 1: Gate-suppressed winner with `was_selected=True`

**What goes wrong:** If `_winner_signal_id` is set before `_check_gate()` is evaluated,
and then gate fires (winner becomes None), entries are built with `was_selected=True` on
the gate-suppressed signal. This is wrong — the signal was NOT selected for execution.

**How to avoid:** Only set `_winner_signal_id` to a non-empty string when the gate check
passes. When gate fires, leave `_winner_signal_id = ""` so all entries get
`was_selected=False`.

**Code pattern (correct):**
```python
_winner_signal_id = ""
if winner:
    _winner_direction = int(winner.get("direction", 0))
    if self._check_gate(...):
        winner = None
    else:
        _winner_signal_id = str(winner.get("signal_id", "") or uuid4())
        winner["signal_id"] = _winner_signal_id
# Now build entries — _winner_signal_id="" when gate fired or winner was None
```

### Pitfall 2: `signals_generated_total` double-counting

**What goes wrong:** The existing `signals_generated_total` counter is incremented inside
the DB INSERT block. After refactor, it continues to increment for every bar with a
successful write. This is semantically correct since it counts "signals inserted to
signal_ledger" — no double-counting risk. The new `signals_written_total` metric for
suppressed-only bars is an additive counter, not a replacement.

**How to avoid:** Keep `signals_generated_total.inc(len(entries))` in the DB INSERT
success path. Add `signals_written_total` (new counter) that increments only when
`ledger_written=True and winner is None` — i.e., suppressed-only bars.

### Pitfall 3: `ledger_written=True` in `BarIntelligenceRecord` on suppressed-only bars

**What goes wrong:** Existing test `test_ledger_write_failure_still_publishes_record`
(L1077) asserts `ledger_written=False` when DB raises. This test passes `regime_data=None`,
which means `apply_regime_gate()` makes all signals `regime_eligible=True`. With a single
signal, `winner` is non-None, so the test still exercises the winner path. After refactor,
the test should still pass.

**A new test is needed** that asserts `ledger_written=True` on a suppressed-only bar
(all signals `regime_eligible=False`, `winner=None`, DB succeeds). This test does not
currently exist.

### Pitfall 4: `all_ranked` empty vs winner=None

**What goes wrong:** The entries loop runs `for rank_idx, ranked_sig in enumerate(all_ranked, start=1)`.
If `all_ranked = []`, the loop produces no entries, `insert_signals_with_features` is
a no-op, `ledger_written` stays False. This is correct behavior — no signals fired, nothing
to write. Guard is: `if all_ranked:` before building entries (or check `if entries and ...`
before DB call, as already done at L1414).

**How to avoid:** The existing guard `if entries and self.db_manager:` at L1414 covers this.
Keep it in the refactored code. No additional guard needed.

### Pitfall 5: `_make_svc_for_pipeline` test helper missing new attribute

**What goes wrong:** If a `signals_written_total` counter is added to `__init__`, the
`_make_svc_for_pipeline` helper must manually set it (per CLAUDE.md `__new__` test pattern).
Without it, new tests calling `_process_event()` will fail with `AttributeError`.

**How to avoid:** Add `svc.signals_written_total = MagicMock()` to `_make_svc_for_pipeline`
in `test_signal_generator_service.py`.
