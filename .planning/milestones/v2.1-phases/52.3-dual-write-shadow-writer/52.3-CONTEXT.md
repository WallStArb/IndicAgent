# Phase 52.3: Dual-Write Shadow Writer — Context

**Gathered:** 2026-03-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Deploy `FeatureSnapshotWriterAgent` as an independent shadow consumer of `intelligence.journal`. It writes a copy of every intelligence bar to `feature_snapshots_shadow`, enabling automated parity validation (Phase 52.5) before any primary-write cutover. No coupling to primary write path. No shared state. No coordinated writes.

**Out of scope:** parity comparison logic (Phase 52.5), primary-write cutover, stream_keys/topic wiring fixes (done in Phase 52.1).

</domain>

<decisions>
## Implementation Decisions

### Phase Dependency (BLOCKING)

- **D-01:** Phase 52.2 (BaseAgent infrastructure) MUST execute before Phase 52.3. `FeatureSnapshotWriterAgent` inherits `BaseAgent` — `src/core/agent/` does not exist yet. Implementing as a plain asyncio service now would create architectural debt requiring refactor in 52.4/52.5. Correct DAG ordering: 52.1 → 52.2 → 52.3.

### FeatureRepository Design

- **D-02:** `FeatureRepository` gets a configurable `table_name` parameter with an explicit allow-list validation (`{"intelligence_features", "feature_snapshots_shadow"}`). This is the DRY-correct approach — the concern is "write a feature vector batch," the target table is a configuration parameter. Duplicating INSERT SQL in a separate class creates schema-drift risk when columns evolve.
  - Rename `insertBatch()` → `write_batch()` (fix camelCase naming violation per CLAUDE.md snake_case convention)
  - Default remains `table_name="intelligence_features"` (backward-compatible)
  - Allow-list validation at `__init__` time — raises `ValueError` on unknown table name
  - SQL uses `self.table_name` (validated, never interpolated directly)

### Error Handling (Shadow Path)

- **D-03:** Log-and-skip with structured logging + `shadow_parse_errors_total` Prometheus counter. No DLQ for the shadow path.
  - Rationale: Shadow path failure = missing row in `feature_snapshots_shadow`. Phase 52.5 parity auditor detects this as a violation — the gap IS the error signal. A DLQ would duplicate what the parity audit already surfaces, adding a topic to monitor/retain/replay with no additional insight.
  - The "never drop data" principle applies to the primary write path. The shadow is the validation layer.
  - On parse error: log `{symbol, tf, error}` as structured fields, increment counter, continue consuming.

### Metrics + Config

- **D-04:** Port 9119 (next available after 9118). Config dict pattern matching `feature_writer_service.py` (config dict with `metrics_port` default in `__main__`). `PYTHONUNBUFFERED=1` required in systemd unit.
  - Full Golden Signal instrumentation (per AGENT_STANDARD.md): Traffic (`events_consumed_total`), Latency (`persistence_batch_latency`), Errors (`shadow_parse_errors_total`), Saturation (`persistence_consumer_lag`)
  - Log file: `logs/feature_snapshot_writer_agent.log` via `setup_service_logging()`
  - Consumer group: `feature_snapshot_writer_group` (idempotent on restart)

### What Phase 52.1 Already Fixed (Do NOT re-implement)

- `topic_feature_processed` removed from `stream_keys.py` — gone
- `feature_writer_service.py` correctly subscribes to `topic_intelligence_journal` — done
- `topic_audit` added to `stream_keys.py` — done
- Phase 52.3 scope is Tasks 2–4 from the design doc only (shadow table DDL, FeatureRepository, agent, systemd)

### Migration Numbering Note

- Two `050_*.sql` files exist: `050_drop_unused_tables.sql` and `050_intelligence_metrics.sql` (naming conflict from prior work). New migration is `051_feature_snapshots_shadow.sql`. Planner should note this but not fix the 050 conflict — that's out of scope.

### Claude's Discretion

- Batch size and flush interval for shadow writer — mirror `feature_writer_service.py` defaults (BATCH_SIZE=50, FLUSH_INTERVAL_SECS=5.0) unless BaseAgent provides different conventions
- SIGTERM drain behavior — inherit from BaseAgent (whatever 52.2 delivers)
- `feature_parity_violations` table DDL — include in migration 051 per existing PLAN.md (needed by Phase 52.5)

<specifics>
## Specific Design Notes

- **Renaissance framing (user-explicit):** This service must be designed to Jim Simons standard: modularity, reuse, separation of concerns, microservices DAG, automation. No manual steps anywhere. Every failure mode is instrumented and observable.
- **Shadow independence is a hard constraint:** Shadow writer failure must never affect primary path. Independent consumer groups guarantee this at the Kafka level — enforce it in design (no shared state, no shared connections, no coordinated flushes).
- **The parity auditor (Phase 52.5) is the correctness guarantee.** Shadow writer is not responsible for detecting its own gaps — only for writing faithfully and reporting errors via Prometheus.
- **The existing PLAN.md is a good foundation.** Use it as the base when replanning. Key corrections: (1) Task 1 wiring is already done, skip it; (2) FeatureRepository rename `insertBatch` → `write_batch`; (3) no DLQ in shadow agent; (4) note Phase 52.2 blocking dependency.

</specifics>
