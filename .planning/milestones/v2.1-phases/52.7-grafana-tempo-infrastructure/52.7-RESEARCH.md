## Summary

Grafana Tempo is already the ecosystem-standard trace backend for Grafana-native stacks. This project
already runs TimescaleDB, Redpanda, Ollama, Prometheus, and Grafana as Docker containers via a
`production/docker-compose.yml` file. All five use `restart: unless-stopped`. Tempo must be added as
a sixth service to that same Compose file — not as a standalone `docker run` command.

Grafana is running at port 3001 with provisioning mounted from
`production/grafana/provisioning/`. The Prometheus datasource is already provisioned as a YAML file
at `production/grafana/provisioning/datasources/datasources.yml`. The Tempo datasource must be added
to that same file (or a new `tempo.yaml` alongside it — Grafana loads all YAML files in the
datasources directory).

Phase 52.6 Plan 05 wires `init_tracing()` into the `__main__` blocks of four services:
`indicator_compute_agent.py`, `intelligence_compute_agent.py`, `signal_generator_service.py` (unit:
`indicagent-signal-generator`), and `feature_writer_service.py`. Phase 52.7 must add
`OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318` to the four corresponding systemd unit files in
`services/`. The unit files in `services/` are the canonical source; changes must be copied to
`/etc/systemd/system/` and `systemctl daemon-reload` run.

The OTel OTLP HTTP exporter is already in `requirements.txt` and installed (v1.39.1). `otel.py`
already reads `OTEL_EXPORTER_OTLP_ENDPOINT` from the environment and defaults to
`http://localhost:4318`. No Python code changes are needed.

**Primary recommendation:** Add Tempo as a `docker-compose.yml` service with a minimal local-storage
`tempo.yaml` config; add the Tempo datasource to Grafana provisioning YAML; add
`OTEL_EXPORTER_OTLP_ENDPOINT` to the four unit files that Phase 52.6 wires with `init_tracing()`.

## Architecture Patterns

### Docker Compose Integration

All production containers run in the `production_default` Docker bridge network, defined by
`production/docker-compose.yml`. Current containers on that network:

| Container | IP | Ports |
|-----------|-----|-------|
| ollama | 172.19.0.2 | 127.0.0.1:11434 |
| indicagent-grafana | 172.19.0.3 | 3001→3000 |
| redpanda | 172.19.0.4 | 19092, 18082, 18081, 9644 |
| timescaledb | 172.19.0.5 | 5432 |
| indicagent-prometheus | 172.19.0.6 | 9090 |

Tempo will join `production_default`. Grafana reaches Tempo by hostname `tempo` (Docker DNS
resolves service names within the same Compose network). The Prometheus datasource already uses
`http://prometheus:9090` — the same pattern.

**OTLP HTTP port 4318:** Tempo listens on 4318 inside the container. The systemd agents run on
the host. They must reach Tempo at `http://localhost:4318`. This requires publishing port 4318
from the Tempo container to the host with `ports: - "4318:4318"`.

### Recommended Project Structure

```
production/
├── docker-compose.yml          # ADD: tempo service
├── tempo.yaml                  # NEW: Tempo minimal config
└── grafana/
    └── provisioning/
        └── datasources/
            └── datasources.yml # MODIFY: add Tempo datasource entry
```

All Tempo config lives in `production/` alongside `prometheus.yml`. No new top-level directories.

### Pattern: Tempo docker-compose Service

```yaml
# In production/docker-compose.yml — add to services:
tempo:
  image: grafana/tempo:2.10.3
  container_name: tempo
  restart: unless-stopped
  command: ["-config.file=/etc/tempo/tempo.yaml"]
  ports:
    - "4318:4318"   # OTLP HTTP receiver — host agents send spans here
    - "3200:3200"   # Tempo HTTP API — Grafana queries traces here
  volumes:
    - ./tempo.yaml:/etc/tempo/tempo.yaml:ro
    - tempo-data:/var/tempo
  networks:
    - default        # joins production_default automatically via Compose

# In production/docker-compose.yml — add to volumes:
volumes:
  tempo-data:
```

### Pattern: Minimal Tempo Configuration

```yaml
# production/tempo.yaml
server:
  http_listen_port: 3200
  log_level: info

distributor:
  receivers:
    otlp:
      protocols:
        http:
          endpoint: 0.0.0.0:4318

ingester:
  lifecycler:
    ring:
      replication_factor: 1

storage:
  trace:
    backend: local
    local:
      path: /var/tempo/traces
    wal:
      path: /var/tempo/wal

compactor:
  compaction:
    block_retention: 168h   # 7 days — sufficient for post-mortems; bounded disk growth

usage_report:
  reporting_enabled: false
```

**Notes on this config:**
- `local` backend is only supported in single-binary (monolithic) mode — which is exactly how
  Tempo runs here. No distributed deployment.
- WAL path separate from traces path — both under `/var/tempo` which maps to `tempo-data` volume.
- `168h` retention: the CONTEXT.md gives Claude discretion between 72h and 7d. At O(1000)
  spans/minute and local filesystem, 7d is conservative in disk usage (estimated <2 GB) given the
  810 GB available. 7d is better for incident post-mortems. Recommended over 72h.
- `usage_report.reporting_enabled: false` — no telemetry sent to Grafana Labs.
- gRPC port 4317 deliberately omitted — only HTTP is needed; the Python OTLP exporter uses HTTP.

### Pattern: Grafana Datasource YAML

Add Tempo to the existing `production/grafana/provisioning/datasources/datasources.yml`:

```yaml
# Append to existing datasources list:
  - name: Tempo
    type: tempo
    uid: tempo
    access: proxy
    url: http://tempo:3200
    isDefault: false
    editable: false
```

**Why same file vs new file:** Grafana loads all `.yaml`/`.yml` files in the datasources directory.
Either approach works. Adding to the existing file keeps provisioning consolidated and follows the
existing project convention (one `datasources.yml` for all datasources).

### Pattern: systemd Unit Env Var Addition

For each of the four unit files that Phase 52.6 wires with `init_tracing()`, add one line:

```ini
Environment=OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
```

Placement: after existing `Environment=` lines in the `[Service]` section.

**The four units:**
1. `services/indicagent-indicator-compute.service` — runs `indicator_compute_agent.py`
2. `services/indicagent-signal-generator.service` — runs `signal_generator_service.py`
3. `services/indicagent-feature-writer.service` — runs `feature_writer_service.py`
4. `indicagent-intelligence-compute` — no unit file in `services/` (only in
   `/etc/systemd/system/`; must be added to `services/` in this phase, or edited in-place on disk)

**Deployment:** After editing the `services/*.service` files, the installer pattern is:
1. `sudo cp services/<unit>.service /etc/systemd/system/`
2. `sudo systemctl daemon-reload`
3. `sudo systemctl restart indicagent-<name>`

Services emit no-op spans until Tempo is running; startup order does not matter — the BatchSpanProcessor
silently drops spans when the endpoint is unreachable (no crash, no error log spam).

### Anti-Patterns to Avoid

- **Using `latest` tag for Tempo image:** Prevents reproducible deploys. Always pin a version.
- **Exposing gRPC port 4317 to host unnecessarily:** The Python SDK uses HTTP (4318). gRPC exposure
  adds attack surface for no benefit. Keep gRPC internal-only or omit entirely.
- **S3/MinIO storage at this scale:** Unnecessary complexity. Local filesystem handles O(1000)
  spans/minute for years within the available disk budget.
- **Standalone `docker run` for Tempo:** All other containers use Compose. A standalone `docker run`
  command is a manual runbook step that breaks the "config IS the runbook" principle. Use Compose.
- **Editing unit files only in `/etc/systemd/system/`:** The canonical sources are `services/*.service`.
  Always edit the source files and copy to `/etc/systemd/system/`. Editing only the installed copy
  is lost on the next `git pull` or deployment.

## Common Pitfalls

### Pitfall 1: Tempo Container Not Reachable from Host Agents
**What goes wrong:** `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318` reaches the host's port
4318, but if Tempo's port is not published (`ports: - "4318:4318"`), the connection is refused.
Spans are silently dropped by `BatchSpanProcessor` — no agent crash, no obvious error.
**Why it happens:** Docker containers are isolated; publishing the port explicitly is required for
host→container communication.
**How to avoid:** Verify `docker ps` shows `0.0.0.0:4318->4318/tcp` after `docker compose up tempo`.
**Warning signs:** Agent logs show no tracing errors (spans are no-ops or silently dropped); Tempo
receives no spans. Query `http://localhost:3200/ready` — returns `ready` if Tempo is up.

### Pitfall 2: Grafana Doesn't See Tempo Datasource After Provisioning
**What goes wrong:** Adding to `datasources.yml` has no effect until Grafana restarts (or the
provisioning watcher picks it up).
**Why it happens:** Grafana reads provisioning files on startup. The volume mount is `:ro` so
Grafana sees file changes, but datasource provisioning only applies on full restart.
**How to avoid:** `docker compose restart grafana` after updating `datasources.yml`. Verify via
Grafana UI → Configuration → Data Sources → "Tempo" appears.
**Warning signs:** Tempo datasource missing in Grafana UI after adding YAML.

### Pitfall 3: `indicagent-intelligence-compute` Unit Not in `services/`
**What goes wrong:** The unit file for `intelligence_compute_agent.py` is only in
`/etc/systemd/system/` — there is no `services/indicagent-intelligence-compute.service` file in
the repository. Editing only the installed copy is fragile.
**Why it happens:** The unit was installed directly without a committed source file. This pattern
breaks reproducibility.
**How to avoid:** Create `services/indicagent-intelligence-compute.service` from the installed copy
as part of this phase, add the env var, then copy back. This brings the unit under version control.
**Warning signs:** `ls services/*.service` does not include `indicagent-intelligence-compute.service`.

### Pitfall 4: WAL Path = Traces Path
**What goes wrong:** Setting `wal.path` and `local.path` to the same directory causes Tempo to
mix WAL entries with completed blocks — block enumeration errors and data corruption.
**Why it happens:** Misconfiguration in `tempo.yaml`.
**How to avoid:** Keep them separate: `wal.path: /var/tempo/wal` and `local.path: /var/tempo/traces`.
Both resolve to the same Docker volume (`tempo-data`) so no extra volume needed.

### Pitfall 5: Tempo Starts Before Volume is Initialized
**What goes wrong:** `tempo-data` volume is empty on first run; Tempo tries to open WAL from
`/var/tempo/wal` and fails if the directory doesn't exist.
**Why it happens:** Docker volumes start empty; Tempo needs its directories pre-created or
auto-creates them. Grafana Tempo does create its own directories on first run — this is not usually
a problem, but the paths must be writable.
**How to avoid:** Tempo creates its own directories by default when running as root inside the
container. The `tempo-data` named volume is owned by root. This is safe — no extra `chown` needed.
