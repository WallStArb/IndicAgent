# Phase 53.3: RollDetectionAgent + DataProviderAgent Rename — Context

**Gathered:** 2026-03-28
**Status:** Ready for planning

<domain>
## Phase Boundary

Extract `RollMonitor` from `tws_daemon.py` into a standalone `RollDetectionAgent`; rename `TwsDaemon` → `DataProviderAgent` (file, class, systemd unit). Two deliverables: one new agent, one service rename. No new detection logic — extraction and plumbing only.

This phase unblocks Phase 50 (ROLL_MONITOR_ENABLED graduation) and Phase 53.2 (BarAggregatorAgent, which needs a clean DataProviderAgent before extraction).

</domain>

<decisions>
## Implementation Decisions

### Consumer Migration

- **D-01:** `signal_generator_agent` migrates from `topic_system_events` to `topic_roll_events` in this phase (53.3), not deferred to Phase 50. `ROLL_MONITOR_ENABLED=false` means the roll detection code path is dead in production today — zero risk. Phase 50 inherits a clean, single-topic subscription.
- **D-02:** `parse_roll_event()` in `src/core/service_utils.py` is updated (or replaced) to parse the typed `RollEvent` schema. The old dict-key parsing (`event_type`, `base_symbol`, `old_symbol`, `new_symbol`, `roll_gap`, `roll_direction`) is retired.
- **D-03:** `RollDetectionAgent` publishes to `topic_roll_events` ONLY — no dual-publish to `topic_system_events`. The system.events topic carries system control events; roll detection is a domain event on its own topic.

### ROLL_MONITOR_ENABLED Flag

- **D-04:** `ROLL_MONITOR_ENABLED` env var is **removed entirely** from the codebase. `RollDetectionAgent` always detects rolls unconditionally when running — the systemd service enable/disable IS the feature flag. This mirrors the `CROSS_ASSET_ENABLED` removal in v2.0.
- **D-05:** `RollDetectionAgent` systemd unit is **installed but not enabled** in this phase. Phase 50 runs `systemctl enable --now indicagent-roll-detection` as part of its graduation sequence.
- **D-06:** Settings fields `roll_monitor_window_size`, `roll_monitor_threshold_default`, `roll_monitor_postroll_bars`, `roll_monitor_cooldown_min`, `roll_confirmation_bars`, `roll_time_of_day_gated` stay in `Settings` — these are tuning parameters, not a feature gate.

### tws_daemon.py Rename

- **D-07:** Hard rename in 53.3. `git mv services/tws_daemon.py services/data_provider_agent.py`. Class: `TwsDaemon` → `DataProviderAgent`. No backward-compatibility shims — CLAUDE.md explicitly prohibits re-export hacks.
- **D-08:** Systemd unit renamed: `indicagent-tws.service` → `indicagent-data-provider.service`. The deployed unit file on disk must be updated (stop old unit, install new, start new). This is handled in the test/deploy notes for this phase.
- **D-09:** All imports referencing `tws_daemon` or `TwsDaemon` across `services/`, `tests/`, `src/` are updated in the same commit as the rename.
- **D-10:** CLAUDE.md "Active Services" table updated: `TWS Daemon | indicagent-tws` → `Data Provider | indicagent-data-provider`.

### RollEvent Schema

- **D-11:** `RollEvent` pydantic schema created in `src/core/schemas/market_events.py` (new file) with fields per design doc:
  ```python
  class RollEvent(BaseModel):
      symbol: str            # base symbol (ES, CL)
      old_contract: str      # ESH6
      new_contract: str      # ESM6
      roll_gap_price: float
      roll_gap_pct: float    # signed: positive=contango, negative=backwardation
      detection_ts: datetime # UTC
      volume_zscore: float   # confirmation strength — ML feature
      confirmation_count: int
  ```
- **D-12:** `topic_roll_events(env_name: str)` added to `src/core/stream_keys.py`. Topic string: `{env}.market.events.roll`.
- **D-13:** `volume_zscore` and `confirmation_count` are new fields not present in the old dict payload. They must be populated from the existing `RollMonitor` state at detection time. `RollMonitor._confirmation_counts` already tracks confirmation count.

### RollDetectionAgent

- **D-14:** `RollDetectionAgent(BaseAgent)` in `services/roll_detection_agent.py`. Follows BaseAgent lifecycle (SIGTERM drain, structlog, init_tracing, metrics_port=9122).
- **D-15:** `topics_consumed = [topic_market_bars(env)]`, `topics_produced = [topic_roll_events(env)]` for ProcessManifest.
- **D-16:** `RollMonitor` class moves verbatim from `tws_daemon.py` to `roll_detection_agent.py` (or into `src/intelligence/` — see Claude's Discretion below). Detection logic is NOT refactored in this phase — extraction only.
- **D-17:** Golden Signals per design doc: `events_consumed_total`, `rolls_detected_total`, `detection_latency_seconds`, `detection_errors_total`, `consumer_lag`.
- **D-18:** Paper account handling (`PAPER_SKIP_CONTRACTS`, `PAPER_ACCOUNT_HOSTS`) moves with `RollMonitor` to `RollDetectionAgent`. The guard must survive extraction.

### DataProviderAgent

- **D-19:** `DataProviderAgent` removes `self._roll_monitor` entirely. It no longer instantiates or calls `RollMonitor`. The `_on_roll_confirmed` method and `check_roll` call in the bar processing loop are deleted.
- **D-20:** `DataProviderAgent` is otherwise functionally unchanged — same IBKR TWS logic, same topic publishing, same metrics port (:9100). This is a rename + subtraction, not a rewrite.

### Claude's Discretion

- Where to locate `RollMonitor` class after extraction: Either keep it private inside `roll_detection_agent.py` (simpler) or move to `src/intelligence/signals/` (more discoverable). Planner should choose based on testability — if unit tests import `RollMonitor` directly, a `src/` location is preferable.
- Whether `parse_roll_event` in `service_utils.py` becomes a method on `RollEvent` model (`.from_kafka_payload()`) or stays as a module-level function. Either is acceptable.

</decisions>
