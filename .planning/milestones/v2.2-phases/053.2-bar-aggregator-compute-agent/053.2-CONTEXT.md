# Phase 53.2: BarAggregatorComputeAgent — Context

**Gathered:** 2026-03-28
**Status:** Ready for planning

<domain>
## Phase Boundary

Extract `BarAccumulator` + `_publish_htf_bar()` from `feature_compute_agent` into a standalone `BarAggregatorComputeAgent`. After extraction, `feature_compute_agent` becomes a pure intelligence consumer: it subscribes to both `market.bars` (1m) and `market.bars.htf` (HTF bars from BarAggregatorComputeAgent) and runs the I1-I6 pipeline for each bar independently.

Two deliverables: one new agent (`bar_aggregator_agent.py`), one simplified service (`feature_compute_agent.py`).

**Out of scope for this phase:**
- `_ohlcv_buffer` / `_queue_ohlcv_write` removal from FCA — Phase 53.1 (BarWriterAgent)
- BarAuditorAgent gap-healing loop — Phase 53.1
- Phase 50 graduation (ROLL_MONITOR_ENABLED, DualDivergence)

</domain>

<decisions>
## Implementation Decisions

### FCA Subscription Topology (D-01)

- **D-01:** `feature_compute_agent` subscribes to **both** `topic_market_bars` (1m) AND `topic_market_bars_htf` (5m-1d) using a **single KafkaConsumerClient** subscribed to both topics in one consumer group. The same `_process_bar()` handler receives all bars regardless of TF. No second consumer group, no asyncio coordination mechanism.
- **D-02:** Each bar arriving on either topic triggers an **independent** I1-I6 pipeline run. The in-process synchronous ordering guarantee (where 1m and HTF bars were processed together in `[bar] + htf_bars`) is intentionally dropped. This is correct Renaissance design: each timeframe's intelligence pipeline uses only its own bar history. The timing gap (~1-5ms) between 1m and HTF IntelligenceEvents is acceptable.
- **D-03:** `feature_compute_agent._process_bar()` simplifies to: (1) gap detection, (2) `_queue_ohlcv_write(bar)` for 1m only, (3) `_bar_history.append(bar)`, (4) `_run_pipeline(bar, t0)` if warm. No BarAccumulator, no HTF publishing.
- **D-04:** `feature_compute_agent.topics_consumed` (for ProcessManifest) becomes `[topic_market_bars(env), topic_market_bars_htf(env)]`. `topics_produced` is unchanged: `[topic_intelligence(env)]`.
- **D-05:** Remove from `feature_compute_agent`: `from src.core.bar_accumulator import BarAccumulator`, `self._bar_accumulator = BarAccumulator()`, `_publish_htf_bar()` method, `topic_market_bars_htf` import, the BarAccumulator update + HTF publish block in `_process_bar()`.

### Flat Bar Responsibility (D-06 — D-07)

- **D-06:** `BarAggregatorComputeAgent` **trusts** the upstream canonical grid guarantee from `DataProviderAgent`. It does NOT actively enforce the 1m grid itself — that is DataProviderAgent's job (SoC). BarAuditorAgent (Phase 53.1) is the designated gap-healing mechanism.
- **D-07:** `DataProviderAgent` flat bar emission is **added in this phase (53.2)**. When no IBKR tick data arrives for a full minute, `DataProviderAgent` emits a flat bar: `open=high=low=close=prev_close, volume=0, is_flat_bar=True`. This was deferred from Phase 53.3 (D-20: rename + subtraction only) but is now added here alongside the schema field.

### is_flat_bar Schema + Propagation (D-08 — D-10)

- **D-08:** Add `is_flat_bar: bool = False` to `BarMessage` schema (`src/core/schemas/bar_message.py`) in this phase. Default `False` — all existing 1m bars are non-flat unless explicitly set by DataProviderAgent.
- **D-09:** `BarAggregatorComputeAgent` propagates the flag through HTF output: if **all** constituent 1m bars in a period have `is_flat_bar=True`, the emitted HTF bar also has `is_flat_bar=True`. If any 1m bar in the period has real volume (`is_flat_bar=False`), the HTF bar is `is_flat_bar=False`.
- **D-10:** `BarAccumulator.update()` is updated to track `is_flat_bar` across constituent bars and set it on the emitted `BarMessage`. The propagation rule is: `htf_bar.is_flat_bar = all(b.is_flat_bar for b in period_bars)`.

### BarAggregatorComputeAgent Specification (D-11 — D-17)

- **D-11:** `BarAggregatorComputeAgent(BaseAgent)` in `services/bar_aggregator_agent.py`. Follows BaseAgent lifecycle: SIGTERM drain, structlog, `init_tracing(name)`, metrics start.
- **D-12:** `topics_consumed = [topic_market_bars(env)]` (1m only). `topics_produced = [topic_market_bars_htf(env)]`.
- **D-13:** `BarAccumulator` class moves from `src/core/bar_accumulator.py` (existing standalone module) — no relocation needed. `BarAggregatorComputeAgent` imports it directly from its current location.
- **D-14:** **Cold start:** `auto.offset.reset=latest`. On restart mid-period, accumulated state is lost; the next complete period boundary triggers the first HTF bar emission. Partial bar on restart is acceptable — period closes cleanly on next 1m bar that crosses a boundary.
- **D-15:** Systemd unit: `indicagent-bar-aggregator.service`. Installed **and enabled** in this phase (unlike `indicagent-roll-compute.service` which is installed but not enabled until Phase 50). BarAggregatorComputeAgent must run before feature_compute_agent can receive HTF bars.
- **D-16:** Metrics port: `:9120`. Golden Signals per design doc:
  - Traffic: `events_consumed_total`, `htf_bars_produced_total{tf}`
  - Latency: `bar_aggregation_latency_seconds`
  - Errors: `aggregation_errors_total`
  - Saturation: `consumer_lag`
- **D-17:** CLAUDE.md "Active Services" table updated to add `Bar Aggregator | indicagent-bar-aggregator` row.

### Startup Ordering

- **D-18:** `indicagent-bar-aggregator.service` must start before `indicagent-feature-compute.service`. After 53.2 ships: stop both → start BarAggregatorComputeAgent → start FeatureComputeAgent. Without BarAggregatorComputeAgent running, FCA receives no HTF bars and produces no HTF IntelligenceEvents (graceful degradation — 1m intelligence still works).

### Claude's Discretion

- Whether `BarAccumulator` gets a new `reset_symbol(symbol)` method to handle roll events (currently FCA calls `self._bar_history.migrate_symbol()` on roll). Planner should check if BarAggregatorComputeAgent needs to handle roll events from `topic_roll_events` to reset accumulator state.
- Consumer group name for BarAggregatorComputeAgent: follow `<concept>_consumer` pattern → `bar_aggregator_consumer`.
- Test structure: use the same `__new__` pattern as other service tests in `tests/unit/service_tests/`.

</decisions>

<specifics>
## User Specifics

- **Renaissance framing is mandatory:** Every decision must pass the "Jim Simons test" — modularity, SoC, no manual tasks, prefer automation.
- **Service = feature gate** (consistent with CROSS_ASSET_ENABLED removal). BarAggregatorComputeAgent is installed AND enabled — it is essential infrastructure, not an optional feature.
- **Canonical OHLCV grid is a system invariant:** 1440 1m bars, 288 5m bars, 96 15m bars, 24 1h bars per day per active symbol. DataProviderAgent guarantees 1m; BarAggregatorComputeAgent guarantees HTF from that.
- **Single responsibility:** Each agent has exactly one job. FCA computes intelligence. BarAggregatorComputeAgent aggregates bars. DataProviderAgent provides raw bars. No job overlaps.

</specifics>
